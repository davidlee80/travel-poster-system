# 多模型故障转移、模型池与超时分层 实施计划

**目标**：给 AI 调用加候选模型故障转移；模型候选以**池**为单位存在数据库里，
按用户 `tier_level` 选池，供运营灵活配置；图像超时从硬编码 20 秒改为分层可配
（主路径 40 秒 / 预热 60 秒）；AI 时延控制从「按次数近似」改为「按实际累计耗时」。

**本轮确认的九项决策**

| #   | 决策                                                                          |
| --- | ----------------------------------------------------------------------------- |
| 1   | T2 目标与告警阈值同步调高                                                     |
| 2   | 严格顺序调度：满超时才发下一候选，但**不 abort 已发出的请求**，继续监听其返回 |
| 3   | 候选是同一 endpoint 的不同模型名                                              |
| 4   | 日预算按**实际发出的请求数**计，不按成功数                                    |
| 5   | 图像默认 1 候选 / 特殊 2；文本默认 3 候选 / 特殊遍历整个池                    |
| 6   | 图像主路径单候选超时 40 s，预热 60 s                                          |
| 7   | 用户分层用 `users.tier_level`（**整数等级**，非枚举）                         |
| 8   | 池与映射存**数据库表**，配管理 CLI                                            |
| 9   | `tier → 唯一池`，**不做池间回退**                                             |

文本侧**不做本地兜底**（候选全失败即 FAILED）。

**Spec**：设计稿 21.2 措施二、21.4；`apps/generation-worker/src/assets/ai-budget.ts`

## 0 为什么必须一起改时延控制

`ai-budget.ts` 的两个上限是**用次数近似时延**，注释写明了算术：

> 总张数（3）是**成本**上限；Hero 次数（2）是**时延**上限 —— T2 扣掉 T1
> 只剩 35 秒，而一次 Hero 生成最多 20 秒。

这个近似的前提是「一次生成最多 20 秒」这个常量。超时可配 + 候选池之后，
同样的「2 次」可以是 80 秒也可以是 400 秒，次数就不再约束时延。

因此新增**任务级 AI 累计耗时预算**：次数管成本、耗时管时延，先到先停。

## 1 时间预算（图像与文本两套）

### 图像（硬窗口：素材解析必须在 T2−T1 内完成）

| 项                   | 现状        | 本计划                    | 来源                              |
| -------------------- | ----------- | ------------------------- | --------------------------------- |
| 单候选超时（主路径） | 20 s 硬编码 | **40 s**                  | `IMAGE_TIMEOUT_MS`                |
| 单候选超时（预热）   | 20 s        | **60 s**                  | `IMAGE_PREHEAT_TIMEOUT_MS`        |
| 候选数               | 1           | 按 tier 从映射表取        | `tier_model_pools.max_candidates` |
| 任务级 AI 累计耗时   | —           | **80 s**                  | `IMAGE_JOB_AI_BUDGET_MS`          |
| Hero 实时次数        | ≤ 2         | ≤ 2（受累计耗时先到先停） | `QUOTA_*_AI_HERO`                 |
| 单任务 AI 总张数     | ≤ 3         | ≤ 3                       | —                                 |

### 文本（T1 是 P95 目标而非硬上限）

| 项         | 现状 | 本计划                         |
| ---------- | ---- | ------------------------------ |
| 单候选超时 | 30 s | 30 s（`LLM_TIMEOUT_MS`，不变） |
| 候选数     | 1    | 按 tier 取，默认 3             |

文本不需要独立链预算：`callModel` 已经把单次超时压到**任务剩余预算内**，
300 s 任务上限天然兜住最坏情况。3 候选最坏 90 s 超过 T1 的 75 s 是可接受的。

### 端到端里程碑

| 项                | 现状  | 本计划        |
| ----------------- | ----- | ------------- |
| T1 计划可读       | 75 s  | 75 s（不变）  |
| T2 页面可看       | 110 s | **155 s**     |
| 素材窗口（T2−T1） | 35 s  | **80 s**      |
| 任务总上限        | 300 s | 300 s（不变） |

**校验**：75 + 80 = 155 = T2 ✓；155 < 300 ✓；
`40 s × 2 候选 = 80 s` 恰好等于素材窗口，即最坏情况一个 Hero 槽位用满窗口，
而任务级累计耗时预算阻止第二个槽位再花时间 ✓

## 2 数据库配置的代价：启动即校验 → 运行时校验 + 自我保护

`loadQuotaConfig` 与 `loadImageConfig` 现在都是**启动即校验、违反即拒绝启动**。
配置搬进数据库后这条防线消失了：运营可以在系统运行时把 `max_candidates` 改成
10，而 `10 × 40 s = 400 s` 会突破 300 s 任务上限。

因此读取处必须能自我保护：

```text
读到 max_candidates = N
  ↓
safeN = min(N, floor(IMAGE_JOB_AI_BUDGET_MS / IMAGE_TIMEOUT_MS))
  ↓
safeN < N  →  按 safeN 执行 + 记 warn 日志 + 计入指标
```

**截断而不是拒绝**：拒绝会让一次配置失误变成用户拿不到计划，而截断只是
少试几个候选。但必须**可见** —— 静默截断会让运营以为配置生效了。
新增指标 `travel_ai_pool_clamped_total{kind}` 与一条 warning 告警。

这是「运营自助」换来的必然代价，写在这里是为了让下一个人知道这不是遗漏。

## 3 数据模型

### 迁移 0009

```sql
-- 用户分层。整数等级：运营可随时插入新档（如 15）而不改约束
ALTER TABLE users ADD COLUMN tier_level INTEGER NOT NULL DEFAULT 0;
ALTER TABLE users ADD CONSTRAINT users_tier_level_check CHECK (tier_level >= 0);

-- 模型池。(name, kind) 复合唯一：「付费池」在文本与图像下各有自己的模型序列
CREATE TABLE model_pools (
    pool_id     UUID PRIMARY KEY,
    name        VARCHAR(64)  NOT NULL,
    kind        VARCHAR(16)  NOT NULL CHECK (kind IN ('LLM', 'IMAGE')),
    -- 有序数组，顺序即 failover 顺序
    models      JSONB        NOT NULL,
    note        TEXT,
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    updated_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    CONSTRAINT model_pools_name_kind_key UNIQUE (name, kind),
    -- 空池等于「这一档不许用 AI」，与「没有配置」是两件事，用非空约束把它们分开
    CONSTRAINT model_pools_models_nonempty CHECK (jsonb_array_length(models) > 0)
);

-- tier_level → 池映射，按区间匹配
CREATE TABLE tier_model_pools (
    kind           VARCHAR(16) NOT NULL CHECK (kind IN ('LLM', 'IMAGE')),
    min_tier_level INTEGER     NOT NULL CHECK (min_tier_level >= 0),
    pool_name      VARCHAR(64) NOT NULL,
    -- NULL = 不限，用满整个池（第 5 项决策里「特殊用户遍历整个池」）
    max_candidates INTEGER     CHECK (max_candidates IS NULL OR max_candidates >= 1),
    PRIMARY KEY (kind, min_tier_level),
    FOREIGN KEY (pool_name, kind) REFERENCES model_pools (name, kind)
);
```

**区间匹配**：给定 `tier_level`，取 `min_tier_level <= level` 中最大的那条。
所以运营新增 `tier_level = 15` 的用户时**不需要**加映射 —— 它会自动落到 10 那一档。
这正是选整数等级而非枚举的收益。

**不插种子数据。** 两张表为空时回落到 env 的 `LLM_MODEL` / `IMAGE_MODEL`
单模型行为，即迁移后不配置任何池，系统行为与现在**完全一致**。
这让整个特性可以渐进启用，也让回滚不需要动代码。

### 查询

```sql
SELECT p.models, t.max_candidates, t.pool_name
FROM tier_model_pools t
JOIN model_pools p ON p.name = t.pool_name AND p.kind = t.kind
WHERE t.kind = $1 AND t.min_tier_level <= $2
ORDER BY t.min_tier_level DESC
LIMIT 1;
```

**缓存**：进程内 + TTL 60 s。运营改配置最多 60 秒生效。不做失效通知
（需要 pub/sub，而 60 秒的滞后对配置类数据无实质影响）。TTL 可配以便调试。

### tier_level 如何到达 worker

`generate-plan.ts:365` 的 `findJobContext(payload.jobId)` 已经查库拿 `userType`，
让它一并返回 `tierLevel`：不改 job payload（payload 里的值会在用户升级后过期），
拿到的是查询时的最新值。

## 4 failover 语义（严格顺序 + 不 abort）

```text
t=0s     发候选 1
t=40s    候选 1 未返回 → **不 abort**，发候选 2
t=40~80s 候选 1 此刻返回 → 立即采用，取消候选 2
t=80s    链预算耗尽 → 全部 abort → 图像降级占位图 / 文本 FAILED
```

快速失败（连接被拒、4xx、模型名不存在）不等满超时，立刻切下一个。

**关键实现点**：`Promise.race` 不能直接用 —— 已 reject 的候选会让 race 立刻
返回那个 reject，跳过仍在跑的候选，正好破坏「监听前面是否返回」。需要一个
「首个成功，或全部落定」的组合器，把每次尝试包成不 reject 的 settled 结果。

## 7 风险与回滚

| 风险                                | 处置                                                                                                                                            |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 配置进数据库 → 失去启动即校验       | 读取处截断 + warn + 指标 + 告警（见第 2 节）。这是运营自助的必然代价                                                                            |
| T2 从 110 调到 155                  | 本轮显式决定。告警阈值同步改，否则变噪音                                                                                                        |
| 日计数改按发出数 → 600 熔断更早触发 | 预期（它现在才真实反映成本）。过早就调 `AI_IMAGE_DAILY_BUDGET`，不要改回口径                                                                    |
| failover 掩盖主模型故障             | `position > 0` 占比告警；否则主模型挂了只表现为「慢一点」                                                                                       |
| 池里模型名配错                      | 快速失败会立刻切下一个，代价是每次多一个无效请求。**不在写入时校验模型名**（中转站没有可靠的模型列表接口），靠 `--dry-run` 与 failover 指标发现 |
| 缓存 60 s 滞后                      | 运营改完要等一分钟。可配 TTL 以便调试                                                                                                           |

**回滚**：清空 `tier_model_pools` 即回到 env 单模型行为（装饰器不包装）；
`IMAGE_TIMEOUT_MS=20000` 回到原超时；`tier_level` 列留着不用无副作用。
代码无需回退，两张表可以留空。

## 8 交付边界

- **没有管理后台 UI**，池与 tier 只能用两个 CLI 或直接改库
- 文本侧只做候选切换，**不做本地兜底**
- 候选是同一 endpoint 的不同模型名；跨供应商容灾（每个候选独立 base_url + key）不在本轮
- **不做池间回退**（第 9 项决策）：tier 选定唯一池，池内 failover 到底即降级
- 对冲式调度（触发延迟 ≪ 超时）不在本轮，`raceFirstSuccess` 预留了
  `hedgeDelayMs` 参数位
- 预热路径用 60 s 但**不做 failover**：预热失败下次再跑即可
- **不校验池里的模型名是否真实存在**：中转站没有可靠的模型列表接口
