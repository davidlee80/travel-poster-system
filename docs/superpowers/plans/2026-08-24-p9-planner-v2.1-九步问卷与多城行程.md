# P9 Planner V2.1 九步问卷与多城行程 实施计划

> **For agentic workers:** 逐期实施，每期跑完自己的 verify 才进下一期。步骤用 `- [ ]` 复选框跟踪。

**Goal:** 把首页采集界面从「8 步长滚动 + 13 个契约字段」换成《Planner V2.1 页面交互规范》定义的「9+1 步分页三栏工作台 + 76 个产品字段」，并让这 76 个字段全链路落到库、进 Prompt、被模型消费；同时让行程真正支持多城市与弹性日期。**配色沿用现有 `preview/planner.html` 的 `.planner` 色板，不采用用户版 HTML 的灰蓝色系。**

**Architecture:** 五层，自下而上：

1. **字段元数据层**（`@tps/schemas`）——76 条 `PlannerFieldSpec` 是前后端共用的唯一真相源：field_id / api_key / step / 层级 / 运行时类型 / 优先级 / 阻塞 / 触发条件 / 右侧摘要分组。规范 21.1 的硬门槛（「必须能识别 76 个唯一 Field ID」）与 21.2 的可追溯性（`source_field_id`）都指向它。
2. **契约层**（`TravelRequestUISchema`）——新增**单一顶层块 `planner_profile`**，内部 19 个子块与字段表 API Key 的第一段逐字对应。既有 `trip/travelers/budget/pace/conditions/custom_requirements` **一行不改**。整块 `optional`，因此 `travel_request_ui_v1` 不升版本、存量客户端一行不改。

   > **实现时修正了原计划（P9-1 完成后回写）。** 原计划写的是「就地扩展 4 块 + 加 11 个新块」，实际做的是「不动旧块 + 加 1 个新顶层块（内含 19 子块）」。原因：就地扩展会立刻撞上四对「同一概念两个路径」——`budget.travel_tier` 与 P8 的 `budget.tier`、`pace.level`（1–5 整数）与 P8 的 `pace.intensity`、`profile.additional_notes` 与 `custom_requirements.raw_text`、`budget.scope_and_priorities` 与 `budget.included_items`。要么改 P8 的字段名（破坏性变更），要么维护一张「api_key → 实际路径」别名表——而别名表是第二个真相源，漏一条的表现是「用户填了档次，生成时读到 undefined」。新块把它变成一条可被测试穷举的规则：**76 个字段的载荷路径 ≡ `planner_profile.` + api_key**，已由 `planner-profile.test.ts` 双向断言（缺字段 / 多余叶子键都报错）。
   >
   > 代价是三态标签在 `planner_profile` 与 `conditions[]` 里各出现一次。这是刻意的：`conditions[]` 的 code 白名单由配置中心的**发布版本**决定，而问卷答案必须在配置改版后仍可回放。两者角色明确——`planner_profile` 是逐字记录，`conditions[]` 是喂给既有 V-30/V-32 校验的投影。

3. **标准化层**（`@tps/planning`）——`NormalizedTravelRequest` 新增 `cities` / `date_flexibility` / `constraints`（带 `constraint_id` + `source_field_id` + `decision_weight` 的运行时约束清单）/ `verify_items`；同样全部可选，存量 `normalized_request` 行仍能被 worker 解析。
4. **生成层**（`@tps/llm` + `plan-rules`）——Prompt 按 `LOCKED > HARD > EXCLUDE > VERIFY > PREFER` 分段渲染；V-04 从「每日城市 == 目的地」改为「每日城市 ∈ 城市序列」。
5. **前端层**（`apps/web`）——新建 `lib/planner/` 承载 Field / Step / Trip 三层状态机、条件触发引擎、五类画像派生、跨字段冲突与草稿持久化；组件按 9 步分页重写，旧 8 步实现整体删除。

**Tech Stack:** Node 24 LTS、pnpm workspaces + Turborepo、TypeScript strict、Zod 4、React 19 + Next.js App Router、vitest、PostgreSQL 17。

**Spec:**

- 交互基线：`docs/design/Planner_V2.1_页面交互规范_最终版.docx`（24 章 + 附录 A/B/C）
- 字段基线：`docs/design/Planner_V2_产品字段表.xlsx`（76 个 Field ID / API Key）
- 参考实现：`docs/design/Planner_V2.1_最终用户版.html`（**只是参考，规范优先。**规范 0 章原文：「若 Demo 与本文件冲突，应修正 Demo」）
- 配色基线：`preview/planner.html` → 即 `apps/web/src/app/planner.css` 的 `.planner` 令牌块

## Global Constraints

以下是全仓库既有约束，每个任务隐含包含本节：

- **TypeScript strict** 且开启 `noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`、`verbatimModuleSyntax`。索引访问必须显式判空，可选属性不可传 `undefined`，类型导入必须带 `type`。
- **Linux 是唯一正确性基准**（22.3）。本机（Windows）跑通不算通过。
- **跨平台护栏**：路径字面量禁止含 `\`；新文件换行 LF。
- **`planner.css` 的作用域纪律不可放松。**该文件顶部的长注释说明了为什么令牌挂 `.planner` 而不是 `:root`、背景挂 `.planner` 而不是 `body`：`globals.css` 由根 layout 引入，而 `/render/**` 的信息图页面是它的后代，写到 `body` / `:root` 会让导出 PNG 底色变灰、字体绕过 `@tps/fonts` 自托管子集。**本轮重写布局，但不得新增任何 `body` / `:root` / 裸元素选择器规则。**
- **迁移**：前向单向、每迁移一事务、可重复执行幂等；文件名 `NNNN_<slug>.sql` 放 `infrastructure/migrations/`。
- **既有条件 code 一律不改名不删除**（`conditions.ts` 的命名约定 2）：它们已写入 `plan_json` 与 `constraint_report.satisfied`，改名会让存量计划的条件比对静默错位。只允许追加。
- **条件 code 的否定语义走 `value: false`**，不进 code 名（命名约定 1）。
- **契约版本递增规则**（`versions.ts`）：可选字段新增不递增；删除 / 重命名 / 类型变更 / 枚举值移除必须递增并保留旧读取路径。本轮全部是可选新增，因此**不递增任何版本号**。

## 三处必须显式处理的陷阱

这三处都是「不处理不会报错、只会静默错」的地方，先写在最前面。

### 陷阱 1：发布过 planner config 之后，内置条件码白名单会被整体替换

`apps/api/src/routes/travel-plans.ts:194-206` 从 `planner_config_options` 里取所有 `*.tags` 字段的 option key 组成 `allowedConditionCodes`，而 `packages/planning/src/conflicts.ts:221` 是：

```ts
const known = context.allowedConditionCodes?.has(code) ?? isKnownConditionCode(code);
```

`??` 意味着**一旦数据库有已发布配置，内置的 `CONDITION_CODE_VALUES` 白名单就完全不参与判断**。所以本轮新增的三态标签码如果只加进 `conditions.ts`，在装了配置中心的环境里会被 N-08 拒掉，错误是 `REQ_CONDITION_CODE_UNKNOWN` —— 而前端界面上那个标签看起来完全正常。

**处理：** P9-6 必须同时交付一条迁移，把新增 code 注册进 `planner_config_options` 并发布新版本号。

### 陷阱 2：给 `NormalizedTravelRequestSchema` 加必填字段会让存量任务解析失败

`apps/generation-worker/src/generate-plan.ts:405` 会把库里的 `normalized_request` 重新 `safeParse` 一遍。新增**必填**字段会让 P8 及之前落的行全部解析失败，而那条路径的注释（同文件 :491）说这只可能是「标准化规则改版」——也就是说它会被当成脏数据而不是版本问题。

**处理：** 新增字段全部可选。下游取值一律走 helper 而不是直接读字段：

```ts
// packages/planning/src/normalize.ts
export function planCities(n: NormalizedTravelRequest): readonly PlaceRef[] {
  return (
    n.cities ?? [
      {
        text: n.destination_name,
        ...(n.destination_place_id === undefined ? {} : { place_id: n.destination_place_id }),
      },
    ]
  );
}
```

存量单目的地行因此仍然得到一个单元素城市序列，V-04 的集合校验对它退化成原来的等值校验。

### 陷阱 3：`trip.destination` 是数据库的提取列来源，不能只发 `destinations`

`travel_requests` 表有 `destination_name VARCHAR(200) NOT NULL` 与 `destination_place_id`，而 `travel_requests_days_check` 等约束也依赖提取列。

**处理：** 前端**同时**发 `trip.destination`（= `destinations[0]`）与 `trip.destinations`。契约层用 Zod `superRefine` 断言两者一致（不一致时报 `REQ_SCHEMA_INVALID` + field，而不是静默取其一）。

**P9-1 期间新增的一处决定：币种从「仅 CNY」扩到 6 种。**
字段表把 `budget.currency` 列为 ISO 4217 且必填，而一个只能选人民币的币种下拉框没有意义。扩容牵动四处，已核实并处理：

1. `@tps/presentation` 的 `CURRENCY_SYMBOL` 是 `Record<Currency, string>` —— 少一个成员是编译错误，安全；顺手把 `build-full-plan.ts` 里那句 `currency === 'CNY' ? '¥' : currency` 改成查同一张表（否则完整页显示「JPY 12000」而单日页显示「JP¥12000」）；
2. 日元用 `JP¥`、港币用 `HK$`，不与 CNY/USD 共用符号 —— 差 20 倍与 8 倍的两个数字长得一样是最坏的一种错；CNY 保持裸 `¥`，12.1 的文案范例与视觉基线按它拍的；
3. **字体子集不需要改** —— 原以为 `€`/`£` 落在 GB 2312 之外，实测两者都已在覆盖范围内（`charset.test.ts` 有一条「不必列出已覆盖字符」的反向断言，加进去会红）；
4. **N-12 的「50 元/人/天」下限必须按币种查表** —— 50 日元/人/天是荒谬的下限。这一项留在 P9-6 与 conflicts 一起做，用**声明式的每币种阈值表**（与原来声明 50 CNY 同性质），不引入汇率依赖。

**P9-6 期间的四处实现决定**

1. **Prompt 文案表按 field_id 分层，不是一张扁平表。** 起初写成扁平表，`THREE_PLUS` 立刻撞车：换宿容忍度是「可以换三次以上住宿」，星级是「三星以上」。同类碰撞还有 `NONE`（自由时间 / 大件行李）与 `ECONOMY`（舱等 / 旅行档次）。扁平表的症状是 **Prompt 里出现一条语义被改写的硬约束**（「住宿星级：可以换三次以上住宿」），模型照着它生成而没有任何校验能发现 —— 比界面上显示错文案严重得多。这与 `apps/web` 的 `OPTION_LABEL` 按 api_key 分层是同一个理由。两份表**刻意不复用**：界面文案可以很短（旁边有上下文），Prompt 里每条必须自足（「≤ 3 km」读不出是步行还是骑行）；且 `apps/web` 不能被 `packages/planning` 引用。

4. **分隔符用 `·` 而不是 `→`，超过三城收尾成「等 N 城」。** 箭头已经被路线图与行程条用掉（`A → B → C`），同一符号在同一页表达两种层级的顺序会让人读错层级；五城的完整标签在信息图固定宽度的标题区会被 `toCompact` 从中间截断，而「东京 · 京都 · 大阪 · 奈…」比「东京 · 京都 · 大阪 等 5 城」信息量更少。
