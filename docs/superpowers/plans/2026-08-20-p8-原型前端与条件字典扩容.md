# P8 原型前端与条件字典扩容 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 让 `apps/web` 的需求采集界面在结构与视觉上贴合既有原型页，同时把「前端可整体替换」固化成一份带夹具与校验脚本的契约 —— 后端接口零改动即可换任意 HTML 模板。

**Architecture:** 三层分离。①`@tps/schemas` 的 `travel_request_ui_v1` 是唯一的前后端边界，本轮把 5.1 的条件字典从 24 码扩到 46 码，让原型的全部标签都有结构化落点；②`apps/web/src/lib/travel-request-form.ts` 是「表单状态 → 契约」的纯函数映射层，本轮补上「必须不要」这一态；③界面按原型的 7 步工作台重构，样式**全部作用域化**到 `.planner` 之下，不碰 `body`。

**Tech Stack:** Next.js 15 App Router、React 19、TypeScript strict、Zod、vitest。无新增运行时依赖。

**Spec:**

- 设计稿 5.1（条件字典、TravelRequestUI）、13.1/13.2（生成与轮询）、13.7（错误码与 field）
- 视觉真相源：用户提供的原型 HTML（`interface_example-0.html`，线上为 `https://www.doomet.cn/`）。本计划已把其中的设计令牌、7 步结构、全部标签文案逐项提取到下文，因此不依赖该文件也能实施。
- 前置决策（已确认）：无码标签走**扩白名单**；可替换性做到**契约文档 + 夹具 + 校验脚本**；V1 不支持的控件**保留但禁用并标注**。

**三处刻意的不对应，实施时不要「顺手补上」：**

1. **「混合交通」不建 code。** 一个表示「没有约束」的条件无法被验证 —— V-30 要求每条 `MUST` 都出现在 `constraint_report.satisfied` 里，而没有任何行程结构能「满足混合交通」。不选任何交通标签本身就是混合。

### 为什么这是缺陷而不是新功能

`travel-request-form.ts:135-139` 目前恒传 `value: true`，`mode` 由域推导。也就是说 5.1 契约里能表达的「必须不要 X」这一态，**前端根本发不出去**。原型界面把它做成了标签的第三次点击（红色删除线），因此这一态必须先在映射层打通。

三态到契约的映射：

| 界面态 | 颜色     | `mode`   | `value` |
| ------ | -------- | -------- | ------- |
| 偏好   | 蓝       | `SHOULD` | `true`  |
| 必须   | 绿       | `MUST`   | `true`  |
| 不要   | 红删除线 | `MUST`   | `false` |

「不要」用 `MUST` 而不是 `SHOULD`：用户明确排除某项时，那是硬约束 —— V-30 会校验它，而 `SHOULD` 只进命中率统计（`plan-rules.ts:748`）。「尽量不要」这一态原型里没有，本轮也不造。

```ts
/**
 * 标签的三态。不在映射里 = 未选。
 *
 * 用「三态」而不是两个布尔（selected / excluded）：两个布尔有四种组合，
 * 其中「既选中又排除」是无意义状态，而它一定会在某次重构里被构造出来。
 */
export type ConditionStance = 'PREFER' | 'REQUIRE' | 'EXCLUDE';

/** code → 态。用 Record 而不是 Map：它要进 React state 并被结构化克隆 */
export type ConditionSelection = Readonly<Partial<Record<ConditionCode, ConditionStance>>>;

export function conditionToContract(code: ConditionCode, stance: ConditionStance): TravelCondition {
  if (stance === 'EXCLUDE') {
    /*
     * 「不要」一律 MUST：用户明确排除时那是硬约束，V-30 会校验它。
     * 用 SHOULD 的话它只进命中率统计（plan-rules 的 should 分支），
     * 而一个「不要夜生活」却排了酒吧的计划会照常放行。
     */
    return { code, mode: 'MUST', value: false };
  }

  const domainIsHard = MUST_BY_DEFAULT_DOMAINS.includes(conditionDomain(code));
  return {
    code,
    mode: stance === 'REQUIRE' || domainIsHard ? 'MUST' : 'SHOULD',
    value: true,
  };
}
```

`TravelRequestFormState.conditions` 的类型从 `readonly ConditionCode[]` 改为 `ConditionSelection`，`INITIAL_FORM_STATE.conditions` 改为 `{}`，`buildTravelRequest` 里那段改为：

```ts
    conditions: Object.entries(state.conditions).flatMap(([code, stance]) =>
      stance === undefined ? [] : [conditionToContract(code as ConditionCode, stance)],
    ),
```

`flatMap` + 空数组而不是 `filter` + `map`：`Partial<Record<...>>` 在 `exactOptionalPropertyTypes` 下取值类型含 `undefined`，两步写法要么多一次类型断言，要么被 `noUncheckedIndexedAccess` 拦住。

## 本轮不做，及理由

- **Prompt 改为发中文文案而不是裸 code。** `llm/src/prompt.ts` 现在发 `condition.code`（`interest.hot_spring` 这样的英文标识）。扩到 46 码后，让模型读中文文案理论上更准。不做的原因是包依赖方向：`CONDITION_LABEL` 住在 `@tps/presentation`，而 `@tps/llm` 只依赖 `@tps/schemas` —— 加一条 llm → presentation 的边，等于让 Prompt 包依赖展示层。正确的解法是把「code → 文案」下沉到 `@tps/schemas`（它本来就是同一个事实的两半），但那是对既有文件的重构，不属于本轮范围。**留作 P9 的一个独立小任务。**
- **`transport.mixed`、以及「路线结构」的 8 种形态。** 前者表达「无约束」，无法被 V-30 验证；后者契约里没有任何字段承载，且强行塞进 conditions 会得到 8 个互斥的 code（选一个就排除其余七个，而 schema 层表达不了互斥）。原型的路线结构控件本轮**保留为纯前端展示**，选中值拼进 `custom_requirements.raw_text`。
- **原型的「✨ 解析为旅行条件」按钮的假解析。** 原型里是 7 条关键词 if。真实系统靠 LLM 读 `raw_text`，前端伪造出的 label 不在 46 码内，发出去会被 `REQ_CONDITION_CODE_UNKNOWN` 拒。本轮把该按钮改为「把这段话加入需求」（只做字数与剩余额度提示），不产生 conditions。
- **`plans/[planId]` 计划展示页的视觉。** 它不在原型里，本轮不动。
