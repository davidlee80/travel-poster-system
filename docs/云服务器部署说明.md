# 云服务器部署说明（Ubuntu 单机内测）

把仓库跑在一台 Ubuntu 云主机上，供内测使用。全程约 40～60 分钟，其中
镜像构建占一半以上。

## 0 这份文档的定位

**目标形态**：一台机器，Docker Compose 起 8 个容器（3 个基础设施 + 5 个应用），
Nginx 做反向代理与 TLS。**不是**高可用部署 —— 数据库、Redis、对象存储都在同一台
机器上，重启会中断服务，磁盘坏了数据就没了。

正式上线走 `deploy/helm/travel-poster`（Kubernetes），与本文档是两条路：
Helm 那条假设有托管数据库、独立对象存储与多副本，成本与复杂度都高一个量级，
不适合拿来验证产品。

**与本地开发的区别**：本地是「服务跑在宿主、用 localhost 互连」
（`env.example` + `pnpm infra:up`）。这里是「服务跑在容器、用服务名互连」，
因此环境变量、端口暴露、对外地址三件事都不一样，不能直接照搬 `.env`。

**验证状态**：见 [附录 C](#附录-c-本文档的验证状态)。命令、环境变量、端口、
契约全部取自当前代码；Ubuntu 侧的 apt 步骤与 Nginx 配置未在实机跑过。

## 1 机器与网络要求

### 1.1 规格

| 项目 | 最低             | 建议             | 为什么                                                                         |
| ---- | ---------------- | ---------------- | ------------------------------------------------------------------------------ |
| 架构 | x86_64 (amd64)   | 同               | 三个 Dockerfile 的构建说明都是 `--platform=linux/amd64`；arm64 未验证          |
| 系统 | Ubuntu 22.04 LTS | Ubuntu 24.04 LTS | 容器内是 bookworm/jammy，宿主版本只影响 Docker 与 Node 的安装方式              |
| vCPU | 2                | 4                | 导出是 Chromium 渲染，`values.yaml` 给 render-worker 的上限是 2 CPU            |
| 内存 | 8 GB             | 8～16 GB         | **4 GB 不够**，见下                                                            |
| 磁盘 | 40 GB            | 60 GB SSD        | render-worker 镜像约 1.2 GB + Playwright 基础镜像 + pnpm 构建缓存 + 两个数据卷 |

**内存为什么是 8 GB 起**：render-worker 单进程就要 2 GB（一个 Chromium browser +
3 个 page，`values.yaml` 的 requests 就是 2Gi），加上 postgres/redis/minio 约
0.5 GB、api + web + 另两个 worker 约 1 GB，稳态就到 3.5～4 GB。构建阶段
`next build` 与 5 个包的 tsc 还有一个更高的峰值。4 GB 机器的表现是构建时 OOM
或 render-worker 被 OOMKilled，而后者的报错是 `Target closed` ——
与共享内存不足的症状一样，会把人引到错的地方去查。

### 1.2 端口与安全组

**安全组只放 22 / 80 / 443。这一步不能省，也不能用 ufw 代替。**

`infrastructure/docker-compose.yml` 把 5432（Postgres）、6379（Redis）、
9000/9001（MinIO）发布在 `0.0.0.0` 上，且口令是仓库里硬编码的
`tps_local_dev_only`。而 Docker 发布端口时直接往 iptables 的 `DOCKER` 链插规则，
**绕过 ufw 的 filter 规则** —— `ufw deny 5432` 看起来生效了，实际端口仍然全网可达。
只有云厂商的安全组（在宿主之外）能可靠拦住它。

如果想彻底不发布，把 `infrastructure/docker-compose.yml` 里那四行 `ports` 加上
`127.0.0.1:` 前缀即可（例如 `'127.0.0.1:5432:5432'`）。这是部署侧调整，
本文档不改仓库文件。

五个应用端口（3000/3001/3011/3012/3013）由 `deploy/mvp-apps.yml` 只绑到
`127.0.0.1`，不需要额外防护。

### 1.3 域名：需要两个

| 域名              | 指向                         | 用途                                      |
| ----------------- | ---------------------------- | ----------------------------------------- |
| `tps.example.com` | Nginx → web:3000 与 api:3001 | 站点本身。api 挂在同一个域名的 `/api/` 下 |
| `s3.example.com`  | Nginx → minio:9000           | 导出下载与素材图片                        |

**为什么 api 必须与 web 同域**：api 没有装 CORS 插件（有意为之），而身份完全依赖
HttpOnly + SameSite=Lax 的 Cookie。跨站请求既过不了 CORS 也带不上 Cookie。
web 镜像里 `NEXT_PUBLIC_API_BASE` 已在构建期固化为空串，浏览器发的是相对路径
`/api/v1/...` —— 单域名 + 反代正是它期望的形态，不要试图用运行时变量去改它。

**为什么 S3 必须是独立子域名而不是 `/s3` 路径**：13.6 的导出下载是 SigV4 预签名
URL，签名覆盖 **Host 头与完整路径**。用路径前缀就必须让 Nginx 剥掉 `/s3`，
而剥掉之后 MinIO 收到的路径与签名里的对不上，一律 403；不剥掉则 MinIO 会把
`s3` 当成桶名，一律 404。两条路都不通，子域名是唯一干净的做法。

### 1.4 出网

构建与运行需要能访问：

- `registry-1.docker.io`、`ghcr.io`、`mcr.microsoft.com`（三个基础镜像）
- `registry.npmjs.org`（pnpm 安装依赖）
- 接真模型后：LLM / 图片 API 的域名

国内机器如果拉不到 Docker Hub，给 `/etc/docker/daemon.json` 配镜像加速器
（`mcr.microsoft.com` 通常直连可达，不走加速器）。

**不需要** `raw.githubusercontent.com`：字体子集产物
（`packages/fonts/assets/*.woff2`）已经入库，不必在服务器上跑 `pnpm fonts:build`。

## 2 前置软件

### 2.1 系统基础

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl gnupg git
sudo timedatectl set-timezone UTC        # 容器内统一 UTC，宿主保持一致便于对日志
```

### 2.2 Docker Engine + Compose 插件

**用 Docker 官方 apt 仓库，不要用 `apt install docker.io`，也不要用 snap。**
后两者的 Compose 插件版本旧或缺失，而本部署依赖 compose v2 的多文件合并与
`depends_on: condition: service_healthy`。

```bash
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg

echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] \
https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io \
  docker-buildx-plugin docker-compose-plugin

sudo systemctl enable --now docker
sudo usermod -aG docker "$USER"   # 之后需要重新登录一次才生效
```

验证（重新登录后）：

```bash
docker --version           # 期望 ≥ 24
docker compose version     # 期望 v2.x
docker buildx version      # 构建用到 BuildKit 的 cache mount
```

### 2.3 Node 24 + pnpm

**即使全部服务都在容器里，宿主也需要 Node 与 pnpm** —— 数据库迁移在宿主执行
（运维手册明确要求迁移不放进容器 hook：失败的迁移会让部署卡在中间态，
既不能回滚也不能重试）。装上之后还顺带能用 `pnpm content:find`、`pnpm gate`
这些运维 CLI。

```bash
curl -fsSL https://deb.nodesource.com/setup_24.x | sudo -E bash -
sudo apt-get install -y nodejs

node --version            # 必须是 v24.x：.npmrc 有 engine-strict=true，
                          # 不符合 engines(>=24 <25) 时 pnpm install 直接拒绝

sudo corepack enable pnpm
cd ~/travel-poster-system && pnpm --version   # 期望 10.34.5（由 packageManager 字段锁定）
```

corepack 拉不动时的替代：`sudo npm i -g pnpm@10.34.5`。

宿主的 `pnpm install` **不会**下载 Chromium：render-worker 依赖的是
`playwright-core`（不含浏览器下载脚本），浏览器只存在于渲染镜像里。sharp 会拉
linux-x64 预编译包，由根 `package.json` 的 `pnpm.supportedArchitectures` 保证。

### 2.4 Nginx 与证书

```bash
sudo apt-get install -y nginx certbot python3-certbot-nginx
sudo systemctl enable --now nginx
```

### 2.5 版本下限一览

| 组件           | 约束                | 来源                                                                                           |
| -------------- | ------------------- | ---------------------------------------------------------------------------------------------- |
| Node           | `>=24.0.0 <25`      | 根 `package.json` 的 `engines`，`engine-strict=true` 强制                                      |
| pnpm           | `10.34.5`           | 根 `package.json` 的 `packageManager`                                                          |
| Docker Engine  | ≥ 24（带 BuildKit） | Dockerfile 用了 `--mount=type=cache`                                                           |
| Docker Compose | v2                  | 多文件合并 + healthcheck 依赖条件                                                              |
| PostgreSQL     | 17 + pgvector       | 由 compose 固定为 `pgvector/pgvector:pg17`；官方 postgres 镜像无 vector 扩展，迁移 0001 会失败 |
| Redis          | 7                   | compose 固定                                                                                   |

## 3 取代码与生成配置

```bash
cd ~
git clone <仓库地址> travel-poster-system
cd travel-poster-system
git checkout p7            # 或 main
```

生成两个密钥并写配置：

```bash
cp deploy/mvp.env.example .env.deploy

# 两个密钥必须逐台生成，不要复用样例里的空值
echo "RENDER_SIGNING_KEY=$(openssl rand -hex 32)" >> .env.deploy
echo "INTERNAL_API_KEY=$(openssl rand -hex 32)"   >> .env.deploy
```

然后编辑 `.env.deploy`，把三处 `example.com` 换成真实域名：

```
S3_ENDPOINT=https://s3.你的域名
S3_PUBLIC_BASE_URL=https://s3.你的域名/tps-assets
```

`.env.deploy` 被 `.gitignore` 的 `.env.*` 规则挡住，不会入库。

> **`S3_PUBLIC_BASE_URL` 第一天就要填对。** 素材 URL 会被写进
> `plan_presentations.view_model` 并永久保存（19.3），事后改域名不会修正
> 已经存进去的那些。
>
> **还没配 TLS、想先用 `http://IP` 验一遍时**，额外加一行
> `COOKIE_SECURE=false`，并把上面两个地址改成 `http://IP:9000`。
> 不加的表现是「注册返回 201，但下一个请求又是未登录」——
> 浏览器静默丢弃了非 HTTPS 下的 Secure Cookie。配好证书后删掉这一行。

`.env.deploy` 里刻意**没有**列配额、保留期、超时那些项：它们在代码里有与
`env.example` 一致的默认值，重复一遍只会与默认值漂移。要改哪一项再加哪一项。

## 4 起基础设施

```bash
docker compose -f infrastructure/docker-compose.yml up -d
docker compose -f infrastructure/docker-compose.yml ps
```

期望 postgres / redis / minio 三个 `healthy`，`tps-minio-init` 是
`exited (0)` —— 它是一次性任务：建两个桶并导入 15.4 的生命周期规则后退出。

确认规则真的导进去了：

```bash
docker run --rm --network travel-poster-system_default \
  --entrypoint sh minio/mc:RELEASE.2025-04-16T18-13-26Z -c \
  "mc alias set local http://minio:9000 tps tps_local_dev_only >/dev/null && \
   mc ilm rule list local/tps-exports"
```

期望只有一条 `registered-exports-90d`，前缀 `users/`，90 天。**`anon/` 前缀
不应有任何规则** —— 那是 R-50 的硬约束（匿名导出由保留期清理按对象键删除，
不允许按路径前缀批量清）。

## 5 建库结构（迁移）

**顺序不能换：先迁移，再起应用。**

```bash
pnpm install --frozen-lockfile          # 约 1～2 分钟

DATABASE_URL=postgres://tps:tps_local_dev_only@localhost:5432/travel_poster \
  pnpm db:migrate

DATABASE_URL=postgres://tps:tps_local_dev_only@localhost:5432/travel_poster \
  pnpm db:status
```

注意这里用 `localhost`（宿主视角），而 `.env.deploy` 里用 `postgres`（容器视角）
—— 同一个数据库的两个地址，不是笔误。

期望 `已应用: 8`（0001～0008）、`待应用: 0`、`漂移: 0`。出现漂移说明某个已应用的
迁移文件被改过 —— 迁移是仅向前的，不要改历史文件，加一个新的。

## 6 构建镜像

```bash
docker compose -f infrastructure/docker-compose.yml -f deploy/mvp-apps.yml build
```

约 15～30 分钟（首次），render-worker 占大部分。它在构建期就会断言两件事，
失败即构建失败：

- 镜像内至少有一个 Noto 字体（L-04）—— 否则运行期表现是 PNG 里全是豆腐块，
  而任务成功、监控全绿，只有用户看得见
- `sharp` 的 linux-x64 二进制可加载（L-05）—— 否则第一次导出 PNG 时才报错

## 7 起五个应用服务

```bash
docker compose -f infrastructure/docker-compose.yml -f deploy/mvp-apps.yml up -d
docker compose -f infrastructure/docker-compose.yml -f deploy/mvp-apps.yml ps
```

**两个 `-f` 必须一起给，顺序不能换。** `deploy/mvp-apps.yml` 是叠加层不是独立栈：
项目名与网络来自第一个文件，应用容器靠 `postgres`/`redis`/`minio` 三个服务名
直连。只给第二个文件会因为找不到这些服务而失败。

期望 8 个容器全部 `Up`（minio-init 除外），5 个应用 `healthy`。

## 8 Nginx 反向代理

```bash
sudo tee /etc/nginx/sites-available/tps.conf > /dev/null <<'NGINX'
# ── 站点：web + api 同域 ───────────────────────────────────
server {
    listen 80;
    server_name tps.example.com;
    location / { return 301 https://$host$request_uri; }
}

server {
    listen 443 ssl;
    http2 on;
    server_name tps.example.com;

    # ssl_certificate / ssl_certificate_key 由 certbot 写入

    # api 的 bodyLimit 是 1MB，这里留一点余量
    client_max_body_size 2m;

    # 17.1 的内部渲染路由不对外。它返回用户私有计划内容，
    # 只应由 render-worker 从容器网络访问
    location /render/ { return 404; }

    location /api/ {
        proxy_pass http://127.0.0.1:3001;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        # 覆盖而不是追加（不用 $proxy_add_x_forwarded_for）：api 开了
        # trustProxy，会信任这个头的首段。追加模式下客户端能自带一个假 IP
        # 放在最前面，从而绕过 21.4 的 IP 维度防刷
        proxy_set_header X-Forwarded-For $remote_addr;
        # 13.1 提交是异步入队的，但生成状态轮询会长一些
        proxy_read_timeout 65s;
    }

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $remote_addr;
    }
}

# ── S3：导出下载与素材图片 ────────────────────────────────
server {
    listen 80;
    server_name s3.example.com;
    location / { return 301 https://$host$request_uri; }
}

server {
    listen 443 ssl;
    http2 on;
    server_name s3.example.com;

    # 导出文件可能几十 MB，不要让 Nginx 限制或整体缓冲
    client_max_body_size 0;
    proxy_buffering off;

    location / {
        proxy_pass http://127.0.0.1:9000;
        proxy_http_version 1.1;
        # SigV4 把 Host 签进了签名。改写这个头 = 所有预签名 URL 一律 403
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
    }
}
NGINX

sudo ln -sf /etc/nginx/sites-available/tps.conf /etc/nginx/sites-enabled/tps.conf
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx

sudo certbot --nginx -d tps.example.com -d s3.example.com
```

把两处 `tps.example.com` / `s3.example.com` 换成真实域名，且必须与
`.env.deploy` 里的 `S3_ENDPOINT` 完全一致（协议、主机名都算）。

## 9 冒烟验收

九步，逐条对期望。前四步在服务器上跑，第 5 步起可以从任意机器跑。

**1）探针**

```bash
for p in 3001 3011 3012 3013; do
  printf '%s -> ' "$p"; curl -s "http://127.0.0.1:$p/readyz"; echo
done
curl -s -o /dev/null -w 'web -> %{http_code}\n' http://127.0.0.1:3000/
```

期望四行都是 `{"status":"ready","detail":{...}}`，web 是 200。
出现 `"postgres":false` 或 `"redis":false` 就停在这里 —— 探针在如实报告，
往下走只会拿到更难懂的错误。

**2）迁移状态**（同第 5 节的 `pnpm db:status`）：已应用 8、待应用 0、漂移 0。

**3）生命周期规则**（同第 4 节）：只有 `registered-exports-90d`。

**4）站点可达**

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://tps.example.com/
curl -s -o /dev/null -w '%{http_code}\n' https://s3.example.com/minio/health/live
```

期望 200 和 200。第二条失败说明 S3 子域名没配通 —— 此时生成和导出都会成功，
只有下载打不开，而那个症状出现得很晚。

**5）P7：未注册请求被拒**

```bash
curl -s -i https://tps.example.com/api/v1/auth/session | head -20
```

期望：`HTTP/2 401`、错误码 `AUTH_IDENTITY_REQUIRED`、且响应头里**没有**
`set-cookie: tp_anon=`。若拿到 200 与 `user_type: ANONYMOUS`，说明
`FEATURE_ANONYMOUS_ENABLED` 被配成了 true。

**6）注册**

```bash
curl -s -c /tmp/tps.jar -X POST https://tps.example.com/api/v1/auth/register \
  -H 'content-type: application/json' \
  -d '{"email":"smoke@example.com","password":"a-sufficiently-long-passphrase-1","display_name":"冒烟"}'
```

期望 201，`"user_type":"REGISTERED"`，`quota.daily_remaining` 为 5。

**7）生成一份 3 天计划**

```bash
START=$(date -u -d 'tomorrow' +%F)
END=$(date -u -d 'tomorrow +2 days' +%F)

cat > /tmp/req.json <<JSON
{
  "schema_version": "travel_request_ui_v1",
  "client_request_id": "smoke-$(date +%s)",
  "locale": "zh-CN",
  "timezone": "Asia/Shanghai",
  "trip": {
    "origin": { "text": "上海" },
    "destination": { "mode": "FIXED", "text": "杭州", "place_id": "cn-hangzhou",
                     "allow_multiple_destinations": false },
    "dates": { "start_date": "$START", "end_date": "$END", "flexibility_days": 0 }
  },
  "travelers": { "adults": 2, "children": [], "seniors": [] },
  "budget": { "currency": "CNY", "basis": "PER_PERSON_PER_DAY", "min": 200, "max": 600,
              "included_items": ["ACCOMMODATION","MEALS","LOCAL_TRANSPORT","TICKETS"] },
  "pace": { "level": "BALANCED" },
  "conditions": [],
  "custom_requirements": { "raw_text": "想看运河和博物馆。" },
  "output_preferences": { "language": "zh-CN", "template_id": "travel_infographic_v1",
                          "generate_png": true, "generate_pdf": true }
}
JSON

curl -s -b /tmp/tps.jar -X POST https://tps.example.com/api/v1/travel-plans/generate \
  -H 'content-type: application/json' -d @/tmp/req.json
```

记下返回的 `plan_id` 与 `job_id`，然后轮询：

```bash
curl -s -b /tmp/tps.jar https://tps.example.com/api/v1/generation-jobs/<job_id>
```

期望在 30 秒内到 `"status":"COMPLETED","progress":100`。

fake 模式下会带 4 条降级 warning（`ASSET_AI_GENERATION_FAILED`、
`ASSET_AI_GENERATION_TIMEOUT`、`ASSET_LIBRARY_MISS`、
`ASSET_LICENSED_SOURCE_UNAVAILABLE`）—— **这是预期的**，素材库是空的、
图源是假的，降级链一路走到占位图。任务不该因此被阻断。

**8）导出 PNG 与 PDF**

```bash
PLAN=<plan_id>
for FMT in PNG PDF; do
  curl -s -b /tmp/tps.jar -X POST \
    "https://tps.example.com/api/v1/travel-plans/$PLAN/exports" \
    -H 'content-type: application/json' \
    -d "{\"format\":\"$FMT\",\"template_id\":\"travel_infographic_v1\",\"scope\":\"ALL_DAYS\",\"day_numbers\":null}"
  echo
done
```

`scope` 取 `ALL_DAYS` 时 `day_numbers` 必须为 null；只有 `SINGLE_DAY` 才填，
且长度必须恰好为 1（13.5 的 R-07：数组是为 V2 的多选天预留的）。

轮询 `GET /api/v1/exports/<export_id>` 到 `"status":"SUCCEEDED"`。参考量级
（fake 模式、3 天、Docker Desktop 实测）：PNG 约 3 秒出 3 个文件、每个约
220 KB、2400×5496；PDF 合并成 1 个约 260 KB 的文件。

**9）预签名下载**

```bash
curl -s -o /tmp/out.pdf -w '%{http_code} %{size_download}\n' '<files[0].url>'
head -c 4 /tmp/out.pdf   # 期望 %PDF
```

到这里九步全过，说明「注册 → 生成 → 渲染 → 上传 → 预签名 → 下载」整条链路通了。

## 10 日常运维

以下命令都需要那两个 `-f`。建一个别名会省很多事：

```bash
echo "alias tpsc='docker compose -f ~/travel-poster-system/infrastructure/docker-compose.yml -f ~/travel-poster-system/deploy/mvp-apps.yml'" >> ~/.bashrc
```

| 目的                 | 命令                                                      |
| -------------------- | --------------------------------------------------------- |
| 看状态               | `tpsc ps`                                                 |
| 跟日志               | `tpsc logs -f api render-worker`                          |
| 重启单个服务         | `tpsc restart api`                                        |
| 改了 `.env.deploy`   | `tpsc up -d`（compose 会重建受影响的容器）                |
| 全停（保留数据）     | `tpsc down`                                               |
| 全停并删数据         | `tpsc down -v` ← 会删掉数据库与所有导出，不可逆           |
| 查某份内容的存储位置 | `DATABASE_URL=... pnpm content:find -- --content-id <id>` |
| 跑验收门禁           | `pnpm gate`                                               |

**升级到新版本**（顺序不能换，先迁移再换镜像）：

```bash
cd ~/travel-poster-system
git fetch && git checkout <新标签>
pnpm install --frozen-lockfile
DATABASE_URL=postgres://tps:tps_local_dev_only@localhost:5432/travel_poster pnpm db:migrate
tpsc build && tpsc up -d
```

**紧急止血**（不动版本，只改开关，几秒生效）：

```bash
# 关生成、保留导出 —— 用户至少还能把已有计划导出带走
sed -i 's/^FEATURE_GENERATION_ENABLED=.*/FEATURE_GENERATION_ENABLED=false/' .env.deploy
tpsc up -d api
```

**回滚**：`git checkout <旧标签>` 后重新 build + up。
**不要回滚迁移** —— 0001～0008 全是加列/加表，旧代码在新 schema 上能跑；
反过来（先退迁移）会让还没换掉的新版本立刻开始报错。

**备份**（内测最低限度，每天一次）：

```bash
docker exec tps-postgres pg_dump -U tps travel_poster | gzip > ~/backup/db-$(date +%F).sql.gz
docker run --rm -v travel-poster-system_minio-data:/data:ro -v ~/backup:/out \
  busybox tar czf /out/minio-$(date +%F).tar.gz -C /data .
```

## 11 故障排查对照表

| 症状                                | 最可能的原因                                                                              | 怎么确认                                                                                                                          |
| ----------------------------------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 注册返回 201，下一个请求又是未登录  | HTTPS 未配好而 `COOKIE_SECURE` 默认 true，浏览器丢弃 Cookie                               | 看响应头有没有 `set-cookie`；有则是浏览器侧丢弃                                                                                   |
| 导出永久停在 `RENDERING 50%`        | 上传阻塞（MinIO 不可达），锁过期后任务被重投，第二次撞 `EXPORT_ALREADY_PROCESSING` 进死信 | `docker exec tps-render-worker node -e "require('http').get('http://minio:9000/minio/health/live',r=>console.log(r.statusCode))"` |
| 导出成功但下载 403                  | `S3_ENDPOINT` 与 Nginx 的 `server_name` 不一致，或反代改写了 Host                         | `curl -i '<预签名URL>'`，403 体里 MinIO 会说签名不匹配                                                                            |
| 导出成功但下载打不开/超时           | `S3_ENDPOINT` 填的是 `http://minio:9000`（容器地址，浏览器到不了）                        | 看返回的 `files[].url` 主机名                                                                                                     |
| PNG 里全是豆腐块                    | 渲染镜像缺 CJK 字体                                                                       | 不应发生 —— L-04 在构建期就会失败。若发生说明镜像不是本仓库 Dockerfile 构建的                                                     |
| 渲染报 `Target closed`              | `/dev/shm` 太小，或 render-worker 内存不足                                                | `docker exec tps-render-worker df -h /dev/shm`，期望 1G                                                                           |
| 导出一直停在排队                    | render-worker 没起来，或 `RENDER_SIGNING_KEY` 与 web 不一致（渲染页一律 404）             | `tpsc logs render-worker`；两边的密钥来自同一个 `.env.deploy`，不一致通常是只重启了一个                                           |
| 首页能开、接口全 404                | Nginx 的 `/api/` 没转发到 3001                                                            | `curl -i https://域名/api/v1/auth/session`                                                                                        |
| 全站只有前 10 份计划能生成          | Nginx 没传 `X-Forwarded-For`，所有用户共享一个 IP 配额桶（`QUOTA_IP_PLANS_PER_DAY=10`）   | 看 api 日志里的 `ip` 字段是不是恒为 `127.0.0.1`                                                                                   |
| 生成任务返回 `SYS_FEATURE_DISABLED` | 灰度开关被关                                                                              | `grep FEATURE_ .env.deploy`                                                                                                       |
| 未注册请求居然拿到 200              | `FEATURE_ANONYMOUS_ENABLED=true`                                                          | 同上；改回 false 后重启 api                                                                                                       |
| `pnpm install` 报 engine 不匹配     | 宿主 Node 不是 24.x（`engine-strict=true`）                                               | `node --version`                                                                                                                  |
| 迁移报 `vector` 扩展不存在          | Postgres 不是 pgvector 镜像                                                               | `docker inspect tps-postgres --format '{{.Config.Image}}'`                                                                        |
| 机器休眠/迁移后数据库突然连不上     | Docker 的宿主端口转发变僵（宿主 TCP 连得上但转不进容器，容器日志里看不到任何连接尝试）    | `docker restart tps-postgres`，再重启握着死连接的服务                                                                             |

## 附录 B 为什么不建议源码直跑

在宿主上 `pnpm build` 然后用 systemd 拉五个进程，看起来比构建镜像快得多。
不建议的原因集中在 render-worker：

1. 需要在宿主装 Chromium 与全套系统库
   （`pnpm --filter @tps/render-worker exec playwright-core install --with-deps chromium`）
2. 需要在宿主装 CJK 字体并建缓存
   （`apt install fonts-noto-cjk fonts-noto-cjk-extra && fc-cache -f`）——
   漏掉这步的表现是导出 PNG 里全是豆腐块，而任务成功、监控全绿
3. 需要保证 `/dev/shm` 足够（宿主上通常是内存的一半，这条一般自动满足）

而这三件事在 `deploy/images/render-worker.Dockerfile` 里都做了，
且第 2 条在**构建期就断言**（L-04：`fc-list | grep -c noto` 必须 ≥ 1），
让缺陷进不了镜像。手工装则没有任何东西替你检查。

另外四个服务源码直跑没有技术障碍，但混合形态（一个容器四个进程）会让日志、
重启、升级各有两套操作方式。内测阶段这个代价不值得。
