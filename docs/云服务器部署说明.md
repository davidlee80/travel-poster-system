# 云服务器部署说明（Ubuntu 单机内测）

把仓库跑在一台 Ubuntu 云主机上，供内测使用。全程约 40～60 分钟，其中
镜像构建占一半以上。

## 0 这份文档的定位

**目标形态**：一台机器，Docker Compose 起 8 个容器（3 个基础设施 + 5 个应用），
Nginx 做反向代理与 TLS。**不是**高可用部署 —— 数据库、Redis、对象存储都在同一台
机器上，重启会中断服务，磁盘坏了数据就没了。

正式上线走 `deploy/helm/travel-poster`（Kubernetes），与本文档是两条路：
Helm 那条假设有托管数据库、独立对象存储与多副本，成本与复杂度都高一个量级，
不适合拿来验证产品。

**与本地开发的区别**：本地是「服务跑在宿主、用 localhost 互连」
（`env.example` + `pnpm infra:up`）。这里是「服务跑在容器、用服务名互连」，
因此环境变量、端口暴露、对外地址三件事都不一样，不能直接照搬 `.env`。

**验证状态**：见 [附录 C](#附录-c-本文档的验证状态)。命令、环境变量、端口、
契约全部取自当前代码；Ubuntu 侧的 apt 步骤与 Nginx 配置未在实机跑过。

## 1 机器与网络要求

### 1.1 规格

| 项目 | 最低             | 建议             | 为什么                                                                |
| ---- | ---------------- | ---------------- | --------------------------------------------------------------------- |
| 架构 | x86_64 (amd64)   | 同               | 三个 Dockerfile 的构建说明都是 `--platform=linux/amd64`；arm64 未验证 |
| 系统 | Ubuntu 22.04 LTS | Ubuntu 24.04 LTS | 容器内是 bookworm/jammy，宿主版本只影响 Docker 与 Node 的安装方式     |
| vCPU | 2                | 4                | 导出是 Chromium 渲染，`values.yaml` 给 render-worker 的上限是 2 CPU   |
| 内存 | 8 GB             | 8～16 GB         | **4 GB 不够**，见下                                                   |
| 磁盘 | 40 GB            | 60 GB SSD        | 五个镜像**实测合计 5.9 GB**（见下）+ buildx 构建缓存 + 两个数据卷     |

**磁盘为什么把估算换成了实测**：本机整栈跑通后逐个量过，与原先的估算差得多：

| 镜像                          | 实测    |
| ----------------------------- | ------- |
| `tps/render-worker:local`     | 4.09 GB |
| `tps/generation-worker:local` | 503 MB  |
| `tps/api:local`               | 490 MB  |
| `tps/retention-worker:local`  | 451 MB  |
| `tps/web:local`               | 441 MB  |
| 合计                          | 5.9 GB  |

原先写的「render-worker 镜像约 1.2 GB」是按 `values.yaml` 推的，实际是 **4.09 GB**
（Chromium + 中文字体），差 3.4 倍。40 GB 仍然够用，但余量比这一行原本暗示的小得多 ——
再算上 buildx 缓存（首次构建后通常几 GB）与两个数据卷，40 GB 的机器要留意
`docker system df`；60 GB 是更安全的起点。

**内存为什么是 8 GB 起**：render-worker 单进程就要 2 GB（一个 Chromium browser +
3 个 page，`values.yaml` 的 requests 就是 2Gi），加上 postgres/redis/minio 约
0.5 GB、api + web + 另两个 worker 约 1 GB，稳态就到 3.5～4 GB。构建阶段
`next build` 与 5 个包的 tsc 还有一个更高的峰值。4 GB 机器的表现是构建时 OOM
或 render-worker 被 OOMKilled，而后者的报错是 `Target closed` ——
与共享内存不足的症状一样，会把人引到错的地方去查。

### 1.2 端口与安全组

**安全组只放 22 / 443（走 1.3.1 方案 B 再加 9443）。这一步不能省，也不能用
ufw 代替。**

80 端口在本机被阿里云按 ICP 备案拦截，放通它没有意义（见 1.3.1）。**这台机器上
9000/9001 尤其要挡住** —— MinIO 的控制台就在 9001，凭据是仓库里硬编码的那一对。

`infrastructure/docker-compose.yml` 把 5432（Postgres）、6379（Redis）、
9000/9001（MinIO）发布在 `0.0.0.0` 上，且口令是仓库里硬编码的
`tps_local_dev_only`。而 Docker 发布端口时直接往 iptables 的 `DOCKER` 链插规则，
**绕过 ufw 的 filter 规则** —— `ufw deny 5432` 看起来生效了，实际端口仍然全网可达。
只有云厂商的安全组（在宿主之外）能可靠拦住它。

如果想彻底不发布，把 `infrastructure/docker-compose.yml` 里那四行 `ports` 加上
`127.0.0.1:` 前缀即可（例如 `'127.0.0.1:5432:5432'`）。这是部署侧调整，
本文档不改仓库文件。

五个应用端口（3000/3001/3011/3012/3013）由 `deploy/mvp-apps.yml` 只绑到
`127.0.0.1`，不需要额外防护。

### 1.3 域名：需要两个

| 域名               | 指向                         | 用途                                                                     |
| ------------------ | ---------------------------- | ------------------------------------------------------------------------ |
| `www.doomet.cn`    | Nginx → web:3000 与 api:3001 | **站点入口**。api 挂在同一个域名的 `/api/` 下                            |
| `travel.doomet.cn` | Nginx → minio:9000           | **仅对象存储**：导出文件下载与素材图片。不是站点入口，用户不会直接访问它 |

> 名字容易读反：站点是 `www.`，对象存储是 `travel.`。后者只出现在预签名下载
> 链接与 `<img src>` 里 —— 有人把它当成应用地址去访问，只会看到 MinIO 的
> S3 接口响应。

上面两个是本项目实际使用的域名（本机取值与现有环境见 1.3.1）。**名字本身可以
任意换** —— 代码里没有任何硬编码的域名，也没有 CSP 或素材 URL 主机白名单。
约束只有下面这些，满足了就随便叫什么。

**站点域名：完全自由。** 裸域、二级域、任意子域都行。要一致的只有三处：DNS 记录、
Nginx 的 `server_name`、证书覆盖范围。web 侧不需要配 —— 它发的是相对路径，
自动跟着页面所在的域名走（见下一段）。

**为什么 api 必须与 web 同域**：api 没有装 CORS 插件（有意为之），而身份完全依赖
HttpOnly + SameSite=Lax 的 Cookie。跨站请求既过不了 CORS 也带不上 Cookie。
web 镜像里 `NEXT_PUBLIC_API_BASE` 已在构建期固化为空串，浏览器发的是相对路径
`/api/v1/...` —— 单域名 + 反代正是它期望的形态，不要试图用运行时变量去改它。

**S3 域名：名字自由，但有三条硬约束。**

1. **必须与 `S3_ENDPOINT` 逐字符一致**（协议、主机名、端口都算）。SigV4 把 Host 头
   签进签名，差一个字符就是所有预签名 URL 一律 403。
2. **`S3_PUBLIC_BASE_URL` 反而可以指向另一台主机。** 它的默认值是
   `S3_ENDPOINT + '/' + 桶名`（见 `packages/storage/src/storage.ts` 的 `base`），
   只用于拼素材的公开读地址，不参与签名 —— 将来挂 CDN 就是只改这一个变量，
   那正是它存在的理由。
3. **不能是主域名下的路径前缀**（`https://站点/s3`）：13.6 的导出下载是 SigV4
   预签名 URL，签名覆盖 **Host 头与完整路径**。用路径前缀就必须让 Nginx 剥掉
   `/s3`，而剥掉之后 MinIO 收到的路径与签名里的对不上，一律 403；不剥掉则
   MinIO 会把 `s3` 当成桶名，一律 404。两条路都不通。

可选的几种拓扑：

| 方案                                       |  可行  | 说明                                                                                       |
| ------------------------------------------ | :----: | ------------------------------------------------------------------------------------------ |
| 两个子域名                                 |   ✓    | 本文档采用的方案。子域名叫什么随意（本项目用 `travel.`，`s3.` / `files.` / `cdn.` 等价）   |
| 两个毫无关系的域名                         |   ✓    | 预签名 URL 靠查询参数鉴权、素材是公开读，**都不依赖 Cookie**，因此不需要与站点有同站关系   |
| 同域名 + 另一个端口（`https://站点:9443`） |   ✓    | Host 头带非默认端口，SDK 与 MinIO 两侧都把端口算进签名，能对上。代价是安全组要多开一个端口 |
| 只用一个域名一个端口                       |   ✗    | 没有可行做法（见上面第 3 条）                                                              |
| 改 `S3_FORCE_PATH_STYLE=false`             | 不建议 | 走 virtual-hosted 风格要给 MinIO 配 `MINIO_DOMAIN` 加通配证书，换来的只是 URL 长相不同     |

**改域名要同步的五处**：`.env.deploy` 的 `S3_ENDPOINT` 与 `S3_PUBLIC_BASE_URL`；
第 8 节两个 `server_name`；`certbot` 的 `-d` 参数（要带上原有的全部域名，
`certonly` 是整份替换而不是追加）；DNS 记录；第 9 节冒烟命令里的地址。

**域名要在灌数据之前定下来**：`S3_PUBLIC_BASE_URL` 会被写进
`plan_presentations.view_model` 并永久保存（19.3），事后换域名不会修正
已经存进去的那批 URL。

### 1.3.1 本机实际取值（doomet.cn）

现有环境（2026-08-20 实测）：

| 事实                      | 值                                                 | 影响                                                         |
| ------------------------- | -------------------------------------------------- | ------------------------------------------------------------ |
| `www.doomet.cn` A 记录    | `120.79.241.186`（阿里云杭州）                     | 部署目标机                                                   |
| `doomet.cn`（裸域）A 记录 | `59.82.113.122`（**另一台机器**）                  | 裸域不指向本机，因此本文档不为它配 server 块                 |
| `travel.doomet.cn`        | 无 A 记录                                          | 走方案 A 需要新增                                            |
| 443 现状                  | `nginx/1.18.0 (Ubuntu)`，在跑旧的静态需求采集原型  | Nginx 已装，**不要**删既有配置；新系统接管 `/` 会顶掉原型页  |
| 现有证书                  | Let's Encrypt，SAN = `doomet.cn` + `www.doomet.cn` | 覆盖站点域名；**不含** `travel.doomet.cn`                    |
| 80 端口                   | 被阿里云 **ICP 备案拦截**（403 跳 beian-block）    | `listen 80` 的跳转形同虚设，且 **certbot 的 HTTP-01 走不通** |

**站点固定为 `https://www.doomet.cn`**，接管根路径。旧的静态原型页会被顶掉 ——
它的文件仍在磁盘上，既有 server 块也还在，回退只是把软链换回去。想同时保留，
把原型页挪到 `/legacy/` 之类的 location 下（本文档不做）。

**S3 侧两个方案，配置都在第 8 节给全：**

| 方案                                     | 需要你在云控制台做的事                     | 代价                                                             |
| ---------------------------------------- | ------------------------------------------ | ---------------------------------------------------------------- |
| **A（目标形态）** `travel.doomet.cn`     | 加一条 A 记录 → `120.79.241.186`；扩展证书 | 扩证书**必须走 DNS-01**（80 被拦），手动签发的证书自动续期会失败 |
| **B（起步最省事）** `www.doomet.cn:9443` | 安全组放通 9443                            | 复用现有证书、不动 DNS；但 URL 带端口，部分企业网络会拦非标端口  |

**建议直接上方案 A。** 理由不是好看：素材 URL 会永久存进 `view_model`，
用 B 起步会在库里留下一批带 `:9443` 的地址。如果暂时拿不到证书而先用 B，
切到 A 时**把 9443 的监听保留着**，旧 URL 才继续可用 ——
这与「换 CDN 后旧 URL 仍要能访问」是同一件事。

## 2 前置软件

### 2.1 系统基础

先确认系统版本 —— 本机的 `nginx/1.18.0 (Ubuntu)` 对应 20.04 或 22.04，两者
在下一步有区别：

```bash
lsb_release -a
```

**如果是 20.04**：NodeSource 的 Node 24 包不一定提供该发行版，`apt-get install
nodejs` 会报找不到候选。此时用 fnm 或 nvm 装 Node 24（只是宿主上跑迁移用，
容器内的 Node 版本由镜像决定，不受影响）。22.04 / 24.04 走 2.3 的正常路径。

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl gnupg git
sudo timedatectl set-timezone UTC        # 容器内统一 UTC，宿主保持一致便于对日志
```

### 2.2 Docker Engine + Compose 插件

**用 Docker 官方 apt 仓库，不要用 `apt install docker.io`，也不要用 snap。**
后两者的 Compose 插件版本旧或缺失，而本部署依赖 compose v2 的多文件合并与
`depends_on: condition: service_healthy`。

```bash
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg

echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] \
https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io \
  docker-buildx-plugin docker-compose-plugin

sudo systemctl enable --now docker
sudo usermod -aG docker "$USER"   # 之后需要重新登录一次才生效
```

验证（重新登录后）：

```bash
docker --version           # 期望 ≥ 24
docker compose version     # 期望 v2.x
docker buildx version      # 构建用到 BuildKit 的 cache mount
```

### 2.3 Node 24 + pnpm

**即使全部服务都在容器里，宿主也需要 Node 与 pnpm** —— 数据库迁移在宿主执行
（运维手册明确要求迁移不放进容器 hook：失败的迁移会让部署卡在中间态，
既不能回滚也不能重试）。装上之后还顺带能用 `pnpm content:find`、`pnpm gate`
这些运维 CLI。

```bash
curl -fsSL https://deb.nodesource.com/setup_24.x | sudo -E bash -
sudo apt-get install -y nodejs

node --version            # 必须是 v24.x：.npmrc 有 engine-strict=true，
                          # 不符合 engines(>=24 <25) 时 pnpm install 直接拒绝

sudo corepack enable pnpm
cd ~/travel-poster-system && pnpm --version   # 期望 10.34.5（由 packageManager 字段锁定）
```

corepack 拉不动时的替代：`sudo npm i -g pnpm@10.34.5`。

宿主的 `pnpm install` **不会**下载 Chromium：render-worker 依赖的是
`playwright-core`（不含浏览器下载脚本），浏览器只存在于渲染镜像里。sharp 会拉
linux-x64 预编译包，由根 `package.json` 的 `pnpm.supportedArchitectures` 保证。

### 2.4 Nginx 与证书

**本机 Nginx 与 Let's Encrypt 证书都已就位**（1.18.0，证书覆盖 `doomet.cn` 与
`www.doomet.cn`），不要重装。只需确认 certbot 在：

```bash
nginx -v
certbot --version || sudo apt-get install -y certbot
```

**不需要** `python3-certbot-nginx`：这台机器的 80 端口被拦，签发只能走 DNS-01
（见 8.2），而那个插件是为 HTTP-01 + 自动改写 Nginx 配置准备的。

### 2.5 版本下限一览

| 组件           | 约束                | 来源                                                                                           |
| -------------- | ------------------- | ---------------------------------------------------------------------------------------------- |
| Node           | `>=24.0.0 <25`      | 根 `package.json` 的 `engines`，`engine-strict=true` 强制                                      |
| pnpm           | `10.34.5`           | 根 `package.json` 的 `packageManager`                                                          |
| Docker Engine  | ≥ 24（带 BuildKit） | Dockerfile 用了 `--mount=type=cache`                                                           |
| Docker Compose | v2                  | 多文件合并 + healthcheck 依赖条件                                                              |
| PostgreSQL     | 17 + pgvector       | 由 compose 固定为 `pgvector/pgvector:pg17`；官方 postgres 镜像无 vector 扩展，迁移 0001 会失败 |
| Redis          | 7                   | compose 固定                                                                                   |

## 3 取代码与生成配置

```bash
cd ~
git clone <仓库地址> travel-poster-system
cd travel-poster-system
git checkout p7            # 或 main
```

生成两个密钥并写配置：

```bash
cp deploy/mvp.env.example .env.deploy

# 两个密钥必须逐台生成，不要复用样例里的空值
echo "RENDER_SIGNING_KEY=$(openssl rand -hex 32)" >> .env.deploy
echo "INTERNAL_API_KEY=$(openssl rand -hex 32)"   >> .env.deploy
```

`deploy/mvp.env.example` 里的 S3 地址已经是本机的取值（方案 A），`cp` 之后
不需要再改：

```
S3_ENDPOINT=https://travel.doomet.cn
S3_PUBLIC_BASE_URL=https://travel.doomet.cn/tps-assets
```

若走 1.3.1 的**方案 B**（复用现有证书、不动 DNS），改成：

```bash
sed -i 's#^S3_ENDPOINT=.*#S3_ENDPOINT=https://www.doomet.cn:9443#' .env.deploy
sed -i 's#^S3_PUBLIC_BASE_URL=.*#S3_PUBLIC_BASE_URL=https://www.doomet.cn:9443/tps-assets#' .env.deploy
```

`.env.deploy` 被 `.gitignore` 的 `.env.*` 规则挡住，不会入库。

> **`S3_PUBLIC_BASE_URL` 第一天就要填对。** 素材 URL 会被写进
> `plan_presentations.view_model` 并永久保存（19.3），事后改域名不会修正
> 已经存进去的那些。
>
> **还没配 TLS、想先用 `http://IP` 验一遍时**，额外加一行
> `COOKIE_SECURE=false`，并把上面两个地址改成 `http://IP:9000`。
> 不加的表现是「注册返回 201，但下一个请求又是未登录」——
> 浏览器静默丢弃了非 HTTPS 下的 Secure Cookie。配好证书后删掉这一行。

`.env.deploy` 里刻意**没有**列配额、保留期、超时那些项：它们在代码里有与
`env.example` 一致的默认值，重复一遍只会与默认值漂移。要改哪一项再加哪一项。

### 3.1 模型服务凭据（ofox）

`deploy/mvp.env.example` 里 `LLM_MODE` 与 `IMAGE_MODE` 都是 `fake`，**这一步先别改**。

fake 三件套能走通整条链路（标准化 → 检索 → 生成 → 校验 → 编排 → 渲染 → 导出），
第 4～9 章的冒烟验收**全部不需要模型凭据**。产出的是固定的杭州 POI 加渐变占位图，
但它证明的恰恰是「除模型之外的一切都通了」—— 而那是接凭据前最该先排除的部分。
带着凭据一起首发，任何一处失败都要在「是模型的问题还是别的问题」之间猜。

**验收通过之后**再回到这一节。

#### 填 key：不要用 `echo`

```bash
cd ~/travel-poster-system
vi .env.deploy      # 或 nano
```

把这四行改成（`LLM_API_KEY` 手工粘贴）：

```
LLM_MODE=direct
LLM_MODEL=openai/gpt-5.5
LLM_BASE_URL=https://api.ofox.ai
LLM_API_KEY=sk-of-…
```

**用编辑器而不是 `echo "LLM_API_KEY=$KEY" >> .env.deploy`。** 后者把 key 完整留在
`~/.bash_history` 里，而那个文件的生命周期比任何人记得清理它的时间都长 ——
它会被备份、被打包、在换机时一起搬走。`sed -i "s|…|$KEY|"` 同样不行：展开后的
命令进 `argv`，同机其他用户 `ps` 一眼就能看到。

填完收紧权限并确认它没进 git：

```bash
chmod 600 .env.deploy
git check-ignore -v .env.deploy    # 应输出 .gitignore 的 .env.* 规则
git status --short | grep env       # 应无输出
```

#### 两个能让人卡半天的取值

| 项          | 正确                            | 错在哪                                                                                                          |
| ----------- | ------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `..._MODEL` | `openai/gpt-5.5`                | **必须带 provider 前缀**。写 `gpt-5.5` 是 4xx                                                                   |
| `..._URL`   | `https://api.ofox.ai`（无 /v1） | ofox 文档给的 `https://api.ofox.ai/v1` 是 **SDK 写法**（SDK 自己拼后半段）；本系统自己拼 `/v1/chat/completions` |

第二项照抄文档会打到 `/v1/v1/…`。**服务会启动即失败并明确报错**（`loadLlmConfig`
拒绝带 `/v1` 尾缀的取值）—— 这是有意设计的：让它启动的话，症状是一串归因不明的
`HTTP 404` 重试，而错误消息里没有任何线索（二十章禁止回显请求体）。

模型清单见 <https://ofox.ai/models>。**避开只支持 `responses` API 的那几个**
（`openai/gpt-5.4-pro` 一类）—— 本系统走 `chat/completions`。

#### 起服务之前先跑探针

生产代码为了不回显提示词只保留状态码，于是端点拼错、参数名过时、模型不支持
结构化输出、凭据无效这四种原因在日志里长得一模一样：`HTTP 400`。探针隔离变量
逐项探并回显完整错误体。

云上凭据在 `.env.deploy` 而探针默认读 `.env`，所以要先导进环境：

```bash
set -a; source .env.deploy; set +a
pnpm probe:llm
```

`set -a` 让 `source` 的变量自动导出，探针才读得到；用 `source` 而不是把 key 写进
命令行，同样是为了不留 history。

它会依次确认：端点拼法 → `max_tokens` 参数名 → 五档结构化输出。**第三项是重点** ——
本系统发 `json_schema` + `strict: true`，而那有三条硬性规则（见设计稿 16.10）。
探针的 S2 档就是生产实际发的那一份，S2 通过即可起服务。

只想看本地体检（不发请求、不花钱、不需要凭据）：`pnpm probe:llm -- --dry-run`。

#### 图像端后接，并先压低日预算

顺序建议是 **LLM 先、IMAGE 后**：文本接通后内容立刻变真实，而图片贵一个量级。
只开 LLM 时整条链路照常走完，图是渐变占位。

接图像时：

```
IMAGE_MODE=direct
IMAGE_MODEL=openai/gpt-image-2
IMAGE_BASE_URL=https://api.ofox.ai
IMAGE_API_KEY=sk-of-…      # 走 ofox 时与 LLM_API_KEY 同值，但仍要各填一遍
AI_IMAGE_DAILY_BUDGET=20   # 首次的护栏，见下
```

**`IMAGE_MODEL` 选 `openai/*` 而不是 `google/*-image-*`**：Gemini 系图片模型走
OpenAI images 端点时只接受最少参数，而本系统必须发 `response_format=b64_json`
（二十章要求图片转存自有存储、不引用第三方地址，那一项不能省）。

**`AI_IMAGE_DAILY_BUDGET` 首次压到 20**（稳态值 600 = Top 50 目的地 × 12 主题桶）。
理由是反馈延迟：一次重试风暴或一处配置笔误能在几分钟内烧掉日额度，而**账单要到
下个周期才看得见**。达到阈值只是全局降级为「素材库 + 占位图」，服务不中断。
成本形态确认之后再调回 600。

口径是「实际发出的请求数」而不是「成功的张数」—— 超时的候选供应商很可能已经
生成完并计了费，我们只是没等到。

两个 key 各填一遍而不是共用一个变量：文本与图片在多数供应商上是不同端点、甚至
不同供应商，共用的表现是「换文本供应商之后图片请求全部 404」，而排查方向会先
落到图片模型名上。

#### 生效

```bash

tpsc logs -f generation-worker | head -30
```

启动日志会打 `llm_mode` / `llm_model` / `image_mode` / `image_model`，**不会打
key 与 baseUrl**。看到 `llm_mode: direct` 且模型名正确即生效。

## 8 Nginx 反向代理

Nginx 已经装好（1.18.0），443 上有在跑的站点。因此这一步是**加一个 site 文件并
停用旧站点的那一个**，不是从零配置。

### 8.0 先备份并找到证书路径

```bash
sudo cp -a /etc/nginx/sites-available /root/nginx-sites-backup-$(date +%F)
ls -l /etc/nginx/sites-enabled/            # 记下现在启用的是哪个文件
sudo ls /etc/letsencrypt/live/             # 期望看到 doomet.cn（证书 CN 是它）
```

下面的配置按 `/etc/letsencrypt/live/doomet.cn/` 写。若 `ls` 出来的目录名不同
（例如 `doomet.cn-0001`），把两处路径一起改掉。

> **这一层不是可选的装饰。** `NEXT_PUBLIC_API_BASE` 在 web 镜像里固化为空串，
> 浏览器发的是同源 `/api/v1/...` —— 没有下面这个 `location /api/`，页面上每个
> 请求都会打到 web 并 404，右上角报「网络连接失败」，一步也走不下去。
>
> 本地开发用 `deploy/local-proxy.yml` 起一份等价的容器内 nginx
> （`pnpm mvp:up`，开 `http://localhost:8080`），配置逐条对着本节写，
> 因此本地就能验证这些指令是否成立 —— 而不是只在生产上第一次试。

### 8.1 站点：web + api 同域

```bash
sudo tee /etc/nginx/sites-available/tps.conf > /dev/null <<'NGINX'
# 旅行计划信息图系统（内测）。与旧的静态需求采集原型互斥：
# 两者都监听 www.doomet.cn:443，同时启用会让 nginx -t 报 duplicate server_name
server {
    listen 443 ssl;
    http2 on;
    server_name www.doomet.cn;

    ssl_certificate     /etc/letsencrypt/live/doomet.cn/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/doomet.cn/privkey.pem;

    # api 的 bodyLimit 是 1MB，这里留一点余量
    client_max_body_size 2m;

    # 17.1 的内部渲染路由不对外。它返回用户私有计划内容，
    # 只应由 render-worker 从容器网络访问
    location /render/ { return 404; }

    location /api/ {
        proxy_pass http://127.0.0.1:3001;
        proxy_http_version 1.1;
        proxy_set_header Host $http_host;
        proxy_set_header X-Forwarded-Proto $scheme;
        # 覆盖而不是追加（不用 $proxy_add_x_forwarded_for）：api 开了
        # trustProxy，会信任这个头的首段。追加模式下客户端能自带一个假 IP
        # 放在最前面，从而绕过 21.4 的 IP 维度防刷
        proxy_set_header X-Forwarded-For $remote_addr;
        # 13.1 提交是异步入队的，但生成状态轮询会长一些
        proxy_read_timeout 65s;
    }

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $http_host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $remote_addr;
    }
}
NGINX
```

**没有 `listen 80` 的跳转块**：这台机器的 80 端口被阿里云按 ICP 备案拦截
（返回 403 并跳 `aliyun.com/beian/beian-block`），流量到不了 Nginx。
写了不报错，但永远不生效 —— 内测入口只能是 `https://`。

### 8.2 S3 入口：二选一

**方案 A —— `travel.doomet.cn`（推荐）**

先在 DNS 加一条 A 记录 `travel.doomet.cn → 120.79.241.186`，然后扩展证书。
**必须走 DNS-01**，`--nginx`/`--webroot` 的 HTTP-01 会因为 80 被拦而失败，
报的是「Timeout during connect」，很容易被当成防火墙问题去查：

```bash
sudo certbot certonly --manual --preferred-challenges dns --cert-name doomet.cn \
  -d doomet.cn -d www.doomet.cn -d travel.doomet.cn
```

`-d` 要把**原有的两个也带上** —— certonly 是整份替换而不是追加，漏掉哪个
哪个就从证书里消失了。手动 DNS-01 的证书**不会自动续期**，到期前要么重跑一次，
要么装阿里云 DNS 插件改成自动。

这个 server 块承担两类完全不同的访问，它们的鉴权方式相反：

| 访问             | 桶            | 鉴权                               | 要求                 |
| ---------------- | ------------- | ---------------------------------- | -------------------- |
| 导出下载（13.6） | `tps-exports` | SigV4 预签名，URL 自带签名         | 桶**必须拒绝**匿名读 |
| 素材图片（19.3） | `tps-assets`  | 无 —— 就是普通 `<img src>`，无签名 | 桶**必须允许**匿名读 |

素材桶的匿名读由 `infrastructure/docker-compose.yml` 的 `minio-init` 建立
（`mc anonymous set download local/tps-assets`）。**这一步此前不存在**，
而本节原本就假定了「素材公开读」—— 也就是说那个前提在整个仓库里没有一处建立。
换成托管对象存储（OSS/S3）时要自己配等价的桶策略：素材桶公开读、导出桶私有。

漏掉它的表现极其隐蔽：素材图片一律 403，而 `RenderReadyProbe` 刻意让坏图不阻塞
就绪（十八章降级链），于是导出照样 `COMPLETED`、健康检查全绿，
**用户拿到的长图里每个图片位置都是空白**。部署后用
`travel_render_asset_image_failure_total` 确认它是 0，不要靠肉眼看页面。

```bash
sudo tee -a /etc/nginx/sites-available/tps.conf > /dev/null <<'NGINX'

# ── S3：导出预签名下载（私有桶）与素材图片（公开读桶）────────
server {
    listen 443 ssl;
    http2 on;
    server_name travel.doomet.cn;

    ssl_certificate     /etc/letsencrypt/live/doomet.cn/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/doomet.cn/privkey.pem;

    # 导出文件可能几十 MB，不要让 Nginx 限制或整体缓冲
    client_max_body_size 0;
    proxy_buffering off;

    location / {
        proxy_pass http://127.0.0.1:9000;
        proxy_http_version 1.1;
        # SigV4 把 Host 签进了签名。改写这个头 = 所有预签名 URL 一律 403。
        # 用 $http_host 而不是 $host：后者**不含端口**，在非默认端口下会对不上
        proxy_set_header Host $http_host;
        proxy_set_header X-Forwarded-For $remote_addr;
    }
}
NGINX
```

**方案 B —— `www.doomet.cn:9443`（复用现有证书，不动 DNS）**

先在安全组放通 9443，然后：

```bash
sudo tee -a /etc/nginx/sites-available/tps.conf > /dev/null <<'NGINX'

# ── S3：同域名另一个端口。Host 头会带 :9443，SigV4 两侧都算进签名 ──
server {
    listen 9443 ssl;
    http2 on;
    server_name www.doomet.cn;

    ssl_certificate     /etc/letsencrypt/live/doomet.cn/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/doomet.cn/privkey.pem;

    client_max_body_size 0;
    proxy_buffering off;

    location / {
        proxy_pass http://127.0.0.1:9000;
        proxy_http_version 1.1;
        # 这里**必须**是 $http_host。$host 会丢掉 `:9443`，而签名里带着它 ——
        # 表现是所有预签名 URL 一律 403，而 MinIO 日志里只说签名不匹配
        proxy_set_header Host $http_host;
        proxy_set_header X-Forwarded-For $remote_addr;
    }
}
NGINX
```

### 8.3 启用并切换


fake 模式下会带 4 条降级 warning（`ASSET_AI_GENERATION_FAILED`、
`ASSET_AI_GENERATION_TIMEOUT`、`ASSET_LIBRARY_MISS`、
`ASSET_LICENSED_SOURCE_UNAVAILABLE`）—— **这是预期的**，素材库是空的、
图源是假的，降级链一路走到占位图。任务不该因此被阻断。

**8）导出 PNG 与 PDF**

```bash
PLAN=<plan_id>
for FMT in PNG PDF; do
  curl -s -b /tmp/tps.jar -X POST \
    "https://www.doomet.cn/api/v1/travel-plans/$PLAN/exports" \
    -H 'content-type: application/json' \
    -d "{\"format\":\"$FMT\",\"template_id\":\"travel_infographic_v1\",\"scope\":\"ALL_DAYS\",\"day_numbers\":null}"
  echo
done
```

`scope` 取 `ALL_DAYS` 时 `day_numbers` 必须为 null；只有 `SINGLE_DAY` 才填，
且长度必须恰好为 1（13.5 的 R-07：数组是为 V2 的多选天预留的）。

轮询 `GET /api/v1/exports/<export_id>` 到 `"status":"SUCCEEDED"`。参考量级
（fake 模式、3 天、Docker Desktop 实测）：PNG 约 3 秒出 3 个文件、每个约
220 KB、2400×5496；PDF 合并成 1 个约 260 KB 的文件。

**9）预签名下载**

```bash
curl -s -o /tmp/out.pdf -w '%{http_code} %{size_download}\n' '<files[0].url>'
head -c 4 /tmp/out.pdf   # 期望 %PDF
```

到这里九步全过，说明「注册 → 生成 → 渲染 → 上传 → 预签名 → 下载」整条链路通了。

## 10 日常运维

以下命令都需要那两个 `-f`。建一个别名会省很多事：

```bash
echo "alias tpsc='docker compose -f ~/travel-poster-system/infrastructure/docker-compose.yml -f ~/travel-poster-system/deploy/mvp-apps.yml'" >> ~/.bashrc
```

| 目的                 | 命令                                                      |
| -------------------- | --------------------------------------------------------- |
| 看状态               | `tpsc ps`                                                 |
| 跟日志               | `tpsc logs -f api render-worker`                          |
| 重启单个服务         | `tpsc restart api`                                        |
| 改了 `.env.deploy`   | `tpsc up -d`（compose 会重建受影响的容器）                |
| 全停（保留数据）     | `tpsc down`                                               |
| 全停并删数据         | `tpsc down -v` ← 会删掉数据库与所有导出，不可逆           |
| 查某份内容的存储位置 | `DATABASE_URL=... pnpm content:find -- --content-id <id>` |
| 跑验收门禁           | `pnpm gate`                                               |

**升级到新版本**（顺序不能换，先迁移再换镜像）：

```bash
cd ~/travel-poster-system
git fetch && git checkout <新标签>
pnpm install --frozen-lockfile
DATABASE_URL=postgres://tps:tps_local_dev_only@localhost:5432/travel_poster pnpm db:migrate
tpsc build && tpsc up -d
```

**紧急止血**（不动版本，只改开关，几秒生效）：

```bash
# 关生成、保留导出 —— 用户至少还能把已有计划导出带走
sed -i 's/^FEATURE_GENERATION_ENABLED=.*/FEATURE_GENERATION_ENABLED=false/' .env.deploy
tpsc up -d api
```

**轮换模型 key**（计划内，例如定期轮换）—— **先切换，后吊销**：

```bash
cd ~/travel-poster-system
vi .env.deploy                    # 换成新 key（别用 echo/sed，见 3.1）
tpsc up -d generation-worker
tpsc logs --tail 30 generation-worker    # 确认 llm_mode=direct 且无 4xx
# 确认新 key 可用之后，才回 ofox 后台吊销旧 key
```

顺序不能换：先吊销会让在途任务立刻开始 401，而 `PLAN_LLM_UNAVAILABLE` 是可重试
错误 —— 它们会重试到耗尽次数才失败，用户看到的是「生成中」转很久然后失败。

**key 泄露应急**（意外提交、贴进聊天、打进日志）—— 顺序**相反**，**先吊销**：

```
1. 立刻去 ofox 后台吊销那个 key          ← 不要先改配置
2. 生成新 key，按上面的轮换流程切过去
3. 若已进 git 历史：git log -S 'sk-of' --oneline 定位；
   已 push 的话 rewrite history 也救不回来 —— 吊销才是唯一有效的动作
```

先改配置再吊销，等于让泄露的 key 在你操作的那几分钟里继续可用。而 key 一旦
离开可控范围，**吊销是唯一真正生效的措施** —— 删掉那行、改掉那个文件都只是
让它从你眼前消失。

生产环境的 key 不进日志由代码保证（`packages/shared/src/logger.ts` 的 redact
清单含 `apiKey` / `api_key`，客户端只把它放进 `Authorization` 头，HTTP 错误只留
状态码）。**但 `tools/probe-*.mjs` 会回显上游完整错误体** —— 少数网关会在里面
echo 请求头。那两个脚本是给人在终端用的，不要接进流水线或把输出贴到公开位置。

**回滚**：`git checkout <旧标签>` 后重新 build + up。
**不要回滚迁移** —— 0001～0009 全是加列/加表，旧代码在新 schema 上能跑；
反过来（先退迁移）会让还没换掉的新版本立刻开始报错。

**备份**（内测最低限度，每天一次）：

```bash
docker exec tps-postgres pg_dump -U tps travel_poster | gzip > ~/backup/db-$(date +%F).sql.gz
docker run --rm -v travel-poster-system_minio-data:/data:ro -v ~/backup:/out \
  busybox tar czf /out/minio-$(date +%F).tar.gz -C /data .
```

## 附录 B 为什么不建议源码直跑

在宿主上 `pnpm build` 然后用 systemd 拉五个进程，看起来比构建镜像快得多。
不建议的原因集中在 render-worker：

1. 需要在宿主装 Chromium 与全套系统库
   （`pnpm --filter @tps/render-worker exec playwright-core install --with-deps chromium`）
2. 需要在宿主装 CJK 字体并建缓存
   （`apt install fonts-noto-cjk fonts-noto-cjk-extra && fc-cache -f`）——
   漏掉这步的表现是导出 PNG 里全是豆腐块，而任务成功、监控全绿
3. 需要保证 `/dev/shm` 足够（宿主上通常是内存的一半，这条一般自动满足）

而这三件事在 `deploy/images/render-worker.Dockerfile` 里都做了，
且第 2 条在**构建期就断言**（L-04：`fc-list | grep -c noto` 必须 ≥ 1），
让缺陷进不了镜像。手工装则没有任何东西替你检查。

另外四个服务源码直跑没有技术障碍，但混合形态（一个容器四个进程）会让日志、
重启、升级各有两套操作方式。内测阶段这个代价不值得。
