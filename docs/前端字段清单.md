# 前端字段清单与必填/附加判定（已决策）

原型页（`https://www.doomet.cn/`）的**全部 70 个输入节点**，逐项标注它在契约里的地位。

**决策日期**：2026-08-20。**结论**：7 项必填、56 项附加、6 项纯前端、1 项移除（第二轮细化后，见下）。

## 三个类别的含义

| 类别       | 契约表现                              | 缺失时的行为                                                   |
| ---------- | ------------------------------------- | -------------------------------------------------------------- |
| **必填**   | schema 要求存在且非空                 | 服务端拒绝，返回带 `field` 的 `REQ_*` 错误码，前端高亮该表单项 |
| **附加**   | schema 可选，**由 schema 填入默认值** | 系统按默认值处理，不影响生成                                   |
| **纯前端** | 不进契约                              | 后端不知道它存在                                               |

**判定原则**：必填集越小，替换前端越容易。一个字段进必填集，只有当
「缺了它生成的计划一定是错的或无法生成」—— 而不是「有它计划会更好」。后者是附加。

**「附加」不等于「不结构化」。** 一个附加字段仍然可以有自己的 condition code 并受
V-30 硬约束校验；区别只在「缺了会不会拒绝请求」。附加项里哪些值得建结构化 code、
哪些进自由文本就够了，由第二轮决策处理（见本文末两节）。

## 决策结论

**必填（7 项用户输入）**

| #   | 名称     | 契约字段                |
| --- | -------- | ----------------------- |
| 01  | 出发地   | `trip.origin.text`      |
| 02  | 目的地   | `trip.destination.text` |
| 05  | 出发日期 | `trip.dates.start_date` |
| 06  | 返回日期 | `trip.dates.end_date`   |
| 09  | 成人数   | `travelers.adults`      |
| 20  | 最低预算 | `budget.min`            |
| 21  | 最高预算 | `budget.max`            |

**纯前端（6 项）**：37 路线结构、43 混合交通、55 兴趣搜索框、69「我没有其他特殊需求」、
70「解析为旅行条件」按钮，以及第二轮细化后归入的 03 目的地尚未确定。

**移除（1 项）**：30「侧重：美食」与 59「当地美食」重复，界面上只保留 59。

**附加（其余 56 项）**，全部由 schema 填默认值。其中 08 / 19 / 33 需要新增契约字段
（见本文末「六项处置」一节），13 拆解到既有的两个 `accessibility` 码。

### 附一的 8 项机器填充字段按同一原则判定

这 8 项不在 70 个用户输入里（界面上没有控件），因此不在上面的决策范围内。
按同一条原则逐项判定的结果：

| 字段                                                            | 判定     | 理由                                                                                                                         |
| --------------------------------------------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `schema_version`                                                | **必填** | 它是契约的版本判别式。给它默认值意味着一个 v2 客户端漏传时会被**静默当作 v1 解析** —— 那正是版本号要防的事                   |
| `client_request_id`                                             | **必填** | 13.8 的幂等键。服务端代生成等于每次请求都唯一，幂等保护消失：用户双击提交会得到两份计划                                      |
| `timezone`                                                      | **必填** | N-01 用它判断「今天」。默认成 `Asia/Shanghai` 而用户在别的时区时，出发日期的合法性判断会**错一天**，且没有任何报错           |
| `budget.basis`                                                  | **必填** | 决定 min/max 是「人均每天」还是「全程总额」。猜错让预算偏差约（人数 × 天数）≈ 20 倍，且 N-12 的 50 元/人/天 下限也是按它算的 |
| `locale`                                                        | 附加     | 只有一个合法值 `zh-CN`，默认即正确                                                                                           |
| `budget.currency`                                               | 附加     | 只有 `CNY`                                                                                                                   |
| `output_preferences.template_id`                                | 附加     | 默认 `travel_infographic_v1`；N-11 仍校验取值合法                                                                            |
| `output_preferences.language` / `generate_png` / `generate_pdf` | 附加     | 默认 `zh-CN` / `true` / `true`                                                                                               |

### 于是契约的必填集是 11 个字段

`schema_version`、`client_request_id`、`timezone`、`trip.origin.text`、
`trip.destination.text`、`trip.dates.start_date`、`trip.dates.end_date`、
`travelers.adults`、`budget.basis`、`budget.min`、`budget.max`。

一份只带这 11 个字段的请求必须能生成出计划 —— 这是「前端可任意替换」的最低门槛，
也是契约夹具要覆盖的第一个用例。

## 与今天契约的差异

今天真正强制的是 8 项用户输入（多一个「预算包含项至少 1 项」），且另有 12 处
**字段本身必填但值可为空**的写法（`conditions: []`、`raw_text: ''`、`children: []` 等）——
它们让客户端不得不显式传空值，而那与「附加」的语义不符。

**改动方向是放宽而不是收紧，因此向后兼容**：今天照旧发全量字段的客户端一行都不用改，
`travel_request_ui_v1` 不需要升版本号。

需要改的 12 处（详见实施计划的增量 0）：

| 字段                                           | 今天                     | 改为                                                              |
| ---------------------------------------------- | ------------------------ | ----------------------------------------------------------------- |
| `budget.included_items`                        | 必填且 `.min(1)`         | `.default(['ACCOMMODATION','MEALS','LOCAL_TRANSPORT','TICKETS'])` |
| `budget.currency`                              | 必填                     | `.default('CNY')`                                                 |
| `travelers.children` / `travelers.seniors`     | 必填数组                 | `.default([])`                                                    |
| `trip.destination.mode`                        | 必填                     | `.default('FIXED')`                                               |
| `trip.destination.allow_multiple_destinations` | 必填                     | `.default(false)`（N-10 仍拒 `true`）                             |
| `trip.dates.flexibility_days`                  | 必填                     | `.default(0)`（N-09 仍拒非 0）                                    |
| `pace`                                         | 必填对象（内部已全可选） | `.default({})`                                                    |
| `conditions`                                   | 必填数组                 | `.default([])`                                                    |
| `custom_requirements`                          | 必填对象                 | `.default({ raw_text: '' })`                                      |
| `output_preferences`                           | 必填对象（4 个必填字段） | 整体 `.default({...})`，内部四项各自带默认值                      |
| `locale`                                       | 必填                     | `.default('zh-CN')`                                               |

**用 `.default()` 而不是 `.optional()`**：前者在 parse 时就把值填好，下游拿到的
`NormalizedTravelRequest` 与今天完全一样（`normalize.ts:181` 直接读
`ui.travelers.children.length`，改成 optional 会让那一行需要处理 undefined）。
代价是 Zod 的输入类型与输出类型不再相同 —— 前端构造请求时要用
`z.input<typeof TravelRequestUISchema>`，而下游消费仍用 `z.infer`。

## 六项「无落点」的附加项处置（第二轮决策，2026-08-20）

标成附加之后仍有 6 项在契约里没有落点。它们与「V1 不支持所以禁用」的那三个
（03/04/07）不同：那三个有字段、只是被 N 规则拒；这些是无处可去。

| #      | 名称                         | 处置                                                                                                                                    | 理由                                                                                                                   |
| ------ | ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 08     | 已有订单                     | **新增字段** `trip.existing_bookings`（枚举数组，默认 `[]`）                                                                            | 它实际改变行程结构：已订酒店意味着住宿位置固定、每日路线要围绕它排。丢掉它等于让模型在错误前提下规划                   |
| 19     | 预算档位名                   | **新增字段** `budget.tier`（枚举，可缺省）                                                                                              | 数值已进 min/max，但「经济穷游」与「品质度假」在同一区间下的选点取向不同 —— 这是给模型的语境，丢了就只剩两个数字       |
| 33     | 节奏 1–5 档                  | **新增字段** `pace.intensity`（1–5 整数，可缺省），与 `level` 并存                                                                      | `level` 只有 3 档，5→3 把「躺平」和「慢游」压成同一个 `RELAXED`。5.1 已规定「数值字段与 level 冲突时以数值为准」，同构 |
| 13     | 老人行动能力 4 档            | **拆解**：「需轮椅」→ `accessibility.wheelchair`；「减少步行台阶」→ `accessibility.low_walking`；「频繁休息」→ 自由文本；「正常」→ 不发 | 两档能落到既有硬约束码并受 V-30 保护，比新造一个四值枚举更有用 —— 后者下游还得再翻译一次                               |
| 03     | 目的地尚未确定               | **纯前端**（控件禁用 + V2 角标）                                                                                                        | `DestinationMode` 只有 `FIXED`，V1 生成链路要求确定目的地才能检索素材与算路线。加一个立刻被拒的字段没有价值            |
| 30, 59 | 「侧重：美食」与「当地美食」 | **合并**：只在兴趣区保留 59「当地美食」，预算侧重区去掉 30                                                                              | 同一个 `interest.food` 出现在两处，用户可能一处标「必须」另一处标「不要」，而契约里只有一条记录 —— 结果取决于遍历顺序  |

新增的三个字段全部**可缺省**，因此仍属「附加」，也仍然向后兼容。

### 三个新字段的取值

```ts
/** 08：已有订单。空数组 = 尚无预订（不需要 NONE 成员） */
export const EXISTING_BOOKING_VALUES = [
  'INTERCITY_TRANSPORT', // 已有往返交通
  'LODGING', // 已有酒店
  'TICKETS', // 已有门票或演出
] as const;

/** 19：预算档位。CUSTOM 表示用户拖了滑块，min/max 才是权威 */
export const BUDGET_TIER_VALUES = [
  'ECONOMY', // 经济穷游
  'STANDARD', // 舒适标准
  'QUALITY', // 品质度假
  'LUXURY', // 豪华旅行
  'CUSTOM', // 自定义
] as const;
```

`pace.intensity` 是 `z.number().int().min(1).max(5).optional()`。

## 附二 · 契约里有、但原型界面上**没有入口**的 9 个条件（缺口）

这 9 个码今天已经在字典里、服务端会当硬约束校验，但原型没有采集控件 ——
用户只能靠第 68 项的自由文本表达，而自由文本不受 V-30 硬约束校验保护。

| 现有 code                  | 中文     | 性质               |
| -------------------------- | -------- | ------------------ |
| `diet.vegetarian`          | 素食     | **饮食硬约束**     |
| `diet.halal`               | 清真     | **饮食硬约束**     |
| `diet.no_spicy`            | 忌辛辣   | 饮食               |
| `diet.allergy_seafood`     | 海鲜过敏 | **安全相关硬约束** |
| `accessibility.wheelchair` | 轮椅通行 | **无障碍硬约束**   |
| `accessibility.stroller`   | 婴儿推车 | 无障碍             |
| `transport.avoid_transfer` | 避免换乘 | 交通偏好           |
| `interest.nightlife`       | 夜生活   | 兴趣               |
| `schedule.no_late_night`   | 不要太晚 | 作息               |

**整个「饮食」域在原型里一个入口都没有。** 海鲜过敏与清真是安全/信仰级的硬约束，
落在自由文本里意味着它们的满足与否不会被 V-30 校验 —— 生成的计划看起来完全正常，
用户要到餐桌上才发现。这一条与「必填/附加」的决定直接相关。
