# 规划器配置中心

九步问卷里每一个可点的选项 —— 单选卡片、多选标签、三态标签、排序项、
Repeater 行内的下拉 —— 都保存在 PostgreSQL，而不是散落在 React 组件里。
浏览器读 `GET /api/v1/planner/config` 的当前发布版本；读取失败时才用代码内置值兜底。

版本 3 共 331 行：62 个界面选项列表的 313 个选项（其中 43 个是条件机器码），
加上 18 个界面上没有标签、只由投影产生的条件码 —— 合起来是白名单里的全部 61 个码。

## 能力边界

「可配置」在这里有精确的含义，两类字段不一样：

| 动作 | 条件码列表（6 个） | 枚举列表（56 个） |
| --- | --- | --- |
| 停用（等于删除） | 纯配置 | 纯配置 |
| 改文案 | 纯配置 | 纯配置 |
| 改排序 | 纯配置 | 纯配置 |
| 重新启用已停用项 | 纯配置 | 纯配置 |
| 新增一个全新值 | 配置 + 改代码（见下） | **做不到** |

**枚举列表新增做不到**，因为契约里那些字段是 Zod 枚举。配置里给
`budget.mode` 加一个 `MAYBE`，只会得到一个「点了提交被拒」的按钮，
而错误指向 `planner_profile.budget.mode` —— 运营看不懂。因此前端对枚举列表取
**配置 ∩ 内置**：多出来的值被丢弃，浏览器控制台留一条说明。想真的加一个枚举
成员，要改 `packages/schemas/src/planner-profile.ts` 的枚举与
`apps/web/src/lib/planner/field-spec.ts` 的文案表，跟一次发布。

**条件码新增要改两处代码**。契约里 `code` 是域前缀正则（不是字面量联合），
所以配置发布一个新码，前端能渲染、提交也能过 schema 与 N-08。但它还必须进：

- `packages/schemas/src/conditions.ts` 的 `CONDITION_CODE_VALUES` —— 否则
  Prompt 的分域遍历认不出它，条件**静默失效**；
- `packages/presentation/src/condition-labels.ts` 的 `CONDITION_LABEL` ——
  那是 `Record<ConditionCode, string>`，漏配是编译错误。

`apps/api/src/routes/planner-config-coverage.test.ts` 双向断言「内置字典 ⇄ 迁移
注册的码」，因此少了任何一步 CI 会红。

## 数据表

- `planner_config_versions`：版本状态（`DRAFT`、`PUBLISHED`、`ARCHIVED`）。
  数据库约束保证同时只有一个发布版本。
- `planner_config_options`：选项明细。
- `planner_config_current`：当前发布版本的只读视图。**它不过滤 `enabled`** ——
  停用的行照样在里面（`enabled` 是它的一列）。手写查询时要自己加
  `WHERE enabled`，否则会把已下线的选项一起算进去。API 侧的
  `createPlannerConfigRepository` 显式过滤了。

`planner_config_options` 的四列需要解释：

**`field_key` = 选项所在的载荷路径。** 与 `planner_profile` 里那个值的实际位置
一字不差：

```text
trip.date_flexibility                     单部件字段 = api_key
transport.flight_comfort.cabin            多部件 = api_key + 部件键
trip.locked_orders.type                   对象数组行内的键
food.allergy_details.allergens.severity   数组套数组，再深一层
conditions.projected                      界面上没有标签的投影产物（见下）
```

不用 field_id 当键，是因为一个字段可以有多个选项列表 —— `PV2-05-003`
（飞行舒适度）有「舱等」与「座位」两份，挤在一个键下会让改「舱等」的文案
连带改到「座位」。

**`option_key` 是提交给后端的稳定值**：枚举列表里是枚举成员（`CONFIRMED`），
条件码列表里是机器码（`interest.food`）。**永远不要改它** —— 它已经写进
`plan_json` 与 `constraint_report.satisfied`，改名会让存量计划的条件比对静默错位。

**`metadata.value_kind` 决定这一行是什么**：

- `CONDITION_CODE` —— 进 N-08 白名单，不论 `field_key` 叫什么
- `ENUM` —— 只供界面渲染

这一列取代了 0011 之前「`field_key` 以 tags 结尾就算条件码」那条命名约定。
换掉的理由不只是新口径下装条件码的路径（`transport.intercity_modes`、
`lodging.amenities`）一个都不以 tags 结尾，更要紧的是**旧约定从来不够用**：
61 个条件码里有 18 个界面上没有标签，它们由前端 `request.ts` 从枚举答案投影
出来（饮食要求 → `diet.*`、行动能力 → `accessibility.*`），必须进白名单却挂不到
任何界面路径下。这 18 个放在 `conditions.projected` 下 —— 那个键与任何载荷路径
都不相等，因此永远不会被渲染成标签。

**`label` 与 `sort_order` 是运营的真相源。** 配置里有值就以配置为准，
代码里的内置文案只是兜底。

## 停用一个选项

不要物理删除，把 `enabled` 改为 `FALSE`。这样历史版本可追溯，回滚也不丢配置。

```sql
SELECT clone_planner_config(3, 4, '下线夜间活动标签');

UPDATE planner_config_options o
SET enabled = FALSE
FROM planner_config_versions v
WHERE o.version_id = v.id
  AND v.version = 4
  AND o.field_key = 'interests.tags'
  AND o.option_key = 'interest.nightlife';

SELECT publish_planner_config(4);
```

发布是单事务操作：原发布版自动归档，目标草稿变为发布版。API 最多缓存 60 秒，
无需重启服务。回滚是 `SELECT publish_planner_config(3)`，不需要 down 迁移。

**停用条件码时注意存量草稿。** 问卷答案存在浏览器 localStorage，可能是几天前
填的，里面还带着那个码。白名单收缩之后直接提交会被 N-08 拒
（`REQ_CONDITION_CODE_UNKNOWN`）。界面会在该字段下方给出
「有 N 项你选过的偏好已经下线」和一个移除按钮 —— **不自动清掉**，因为
`mode: 'MUST'` 的条件是硬约束，静默丢弃一个轮椅需求会让生成出的计划看起来
完全正常，而用户要到出行当天才发现。停用枚举值不存在这个问题：契约照旧接受
那个值，提交不受影响。

## 改文案与排序

```sql
SELECT clone_planner_config(3, 4, '调整兴趣标签文案');

UPDATE planner_config_options o
SET label = '博物馆与艺术展', sort_order = 15
FROM planner_config_versions v
WHERE o.version_id = v.id
  AND v.version = 4
  AND o.field_key = 'interests.tags'
  AND o.option_key = 'interest.art_museum';

SELECT publish_planner_config(4);
```

`sort_order` 升序即界面顺序。同值时按 `option_key` 兜底排序。

## 新增一个条件码

三步，缺一不可（第 2、3 步是代码，要跟一次发布）：

```sql
-- 1. 注册进配置并发布
SELECT clone_planner_config(3, 4, '新增屋顶酒吧标签');

INSERT INTO planner_config_options (version_id, field_key, option_key, label, sort_order, metadata)
SELECT v.id, 'lodging.amenities', 'accommodation.rooftop_bar', '有屋顶酒吧', 130,
       '{"value_kind":"CONDITION_CODE"}'::jsonb
FROM planner_config_versions v WHERE v.version = 4;

SELECT publish_planner_config(4);
```

2. 往 `CONDITION_CODE_VALUES` 追加 `'accommodation.rooftop_bar'`，并把
   `CONDITION_CODE_COUNT` 加一。**既有码一律不改名不删除**，只追加。
3. 往 `CONDITION_LABEL` 加中文标签。

命名用 `<域>.<英文小写名称>`，域必须是 `interest`、`transport`、
`accommodation`、`budget`、`accessibility`、`diet`、`schedule` 之一。
否定语义走 `value: false`，不进码名 —— 「不要多人间」是
`accommodation.shared_dorm` + `value: false`，建一个 `no_shared_dorm` 会让
「不要它」变成读不懂的双重否定。

## 前端怎么读

`apps/web/src/components/planner/PlannerConfigProvider.tsx`：

- `usePlannerOptionResolver()` 返回一个纯函数，控件树里按需解析
  `(field_key, 内置值, kind) → {values, labelOf}`。返回函数而不是选项，是因为
  Repeater 的行摘要要为若干个行内部件各解析一次，而那发生在一个普通函数里。
- `useSummaryLabel()` 给右栏摘要用，按 `field_key` 前缀匹配取文案 ——
  让同一个标签在主栏与右栏显示同一份文案。

`apps/web/src/lib/planner/config-binding.ts` 从描述符表**派生**那 62 个
`field_key` 与各自的 `kind`（`kind` 由「值是否全部是已知条件码」判定）。
派生而不是手写映射表：手写的那份与描述符漂移无法被发现 —— 描述符里新加一个
带选项的部件、忘了补映射，那个列表就静默退回硬编码，运营改了没生效而界面
看起来完全正常。

配置在**浏览器里**拉，因此服务端渲染的那一帧走内置值，配置到位后再换。
代价是停用过的选项会闪一下；换成服务端取需要给 web 容器一份内部 API 地址与
一次阻塞请求，而首页是入口 —— 让它等一个可以回退的依赖不值得。

## 迁移与守卫

| 迁移 | 做了什么 |
| --- | --- |
| `0010` | 建表、克隆/发布函数、版本 1（P8 八步问卷的 16 个选项分类） |
| `0011` | 版本 2：P9 新增的 15 个条件码 + 11 个按 api_key 命名的枚举列表 |
| `0012` | 版本 3：62 个列表全部按载荷路径注册、标注 `value_kind`、停用 0010 那 16 个遗留键 |

0010 的 16 个 `field_key` 是八步问卷时代的命名（`traveler.tags`、`budget.tiers`、
`pace.intensity`……），V2 里没有任何字段叫这些名字，代码里也已零消费方，
因此 0012 把它们 `enabled = FALSE`。它们承载的条件码在新口径下重新注册过。

0011 的 11 个键与 0012 有交集，冲突时**只补 `metadata` 与 `enabled`，
不动 `label` 与 `sort_order`** —— 后两列是运营的真相源，用内置文案覆盖会把
运营改过的文案改回去。代价是这 11 个键的文案沿用 0011（例如步行上限显示
「3 公里以内」而不是内置的「≤ 3 km」），而那正是「配置优先」应有的表现。

四组自动化守卫：

- `apps/web/src/lib/planner/config-binding.test.ts` —— 派生的 62 个键 ⇄ 0012
  注册的行，双向且含顺序；`kind` 与 `value_kind` 一致；投影专用键下恰好是
  界面上没有标签的那些码。
- `apps/web/src/components/planner/config-driven.test.tsx` —— 停用 / 改文案 /
  改排序 / 新增在渲染产物里逐个验证，含「枚举新增被丢弃」与「下线码提示」。
- `apps/api/src/routes/planner-config-coverage.test.ts` —— 内置条件码字典 ⇄
  迁移注册的码，双向。
- `apps/api/src/routes/planner-config-whitelist.test.ts` —— 装了配置中心时
  N-08 的实际行为（停用生效、投影码通过、新码通过、ENUM 不混进白名单）。

这些断言比的都是**仓库里的迁移**与**仓库里的代码**，与生产库的当前内容无关 ——
运营在生产库里增删改是运行期行为，不碰迁移文件。
