## 1.3 与现有网关的关系

`travel-poster-system` 通过 HTTP 调用 `enterprise-ai-platform` 的 `POST /v1/chat/completions` 获取 LLM 能力，**不共享数据库、不共享代码、不共享用户体系**。

```text
travel-poster-system/generation-worker
        │ HTTP + Bearer
        ▼
enterprise-ai-platform/gateway  →  POST /v1/chat/completions
```

两侧的「用户」概念完全无关：网关侧是 `tenant_id`（调用方租户），本系统侧是 `user_id`（终端旅行者）。本系统作为**单一租户**接入网关，终端用户身份不透传。

**风险**：该网关的认证（`TASK-M2-002`）与 Provider 适配（`TASK-M2-005`）目前是**接口契约而非可用实现**（`UnavailableGatewayAdapters.cs`），实际调用会返回 `503`。

**应对**：`packages/shared` 中定义 `LlmClient` 接口，提供两个实现 —— `GatewayLlmClient`（走网关）与 `DirectLlmClient`（直连 Anthropic SDK）。第一至三阶段用 `DirectLlmClient` 推进，网关就绪后切换配置即可，不改业务代码。

### R-13 的两个关键设计判断

**统一 `users` 表而非独立匿名表**（3.6.2）：匿名升级只需翻转 `user_type`，`user_id` 不变，历史自动继承，**零业务行迁移**。独立匿名表方案要跨 4 张表搬归属列并处理中途失败的部分继承状态。代价是匿名行累积，用保留期清理解决 —— 运维成本远低于正确性风险。

**脱敏投影独立成列 + 列级 GRANT**（3.2.4、15.2）：全局检索按需求跨用户进行，但直接读 `plan_json` 会把 A 用户的预算、日期、人员构成、自由文本诉求带进 B 用户的生成上下文。因此新增 `retrieval_projection` 列，`plan_embedding` 也必须由该列计算（否则敏感字段以向量形式残留），并用只读角色的**列级 `GRANT` 排除 `plan_json`** —— 即使应用代码写错，数据库也会拒绝。安全由数据布局保证，不靠调用方自觉。

### R-13 的一个副产物：匿名数据清理不损失行程知识

匿名行到期删除会级联删掉 `travel_plan_versions`，让全局检索持续失血（匿名流量占比可能很高）。因此清理前把脱敏投影转存到 `plan_knowledge` 表（无 `user_id`、无日期、无金额、无人员构成）。**被清理的是「谁何时去哪花多少」，保留的是「杭州运河主题 5 天可以这样安排」** —— 后者不是个人数据。此区分必须同步写进用户协议（设计稿二十章）。

# 三、实施策略

## 3.1 五条原则

**原则一：渲染链路优先。** 十六章阻断判定表中，`RENDER_TEMPLATE_FAILED` 与 `RENDER_CORE_ASSET_MISSING` 是唯一无法通过降级绕过的失败。先用静态数据打通「模板 → HTML → PNG/PDF」，在引入 LLM 之前拿到确定性产物。

**原则二：契约先行，Zod 为单一真相源。** `packages/schemas` 是第一个交付物。API、Worker、React 模板全部从它导入类型；JSON Schema 由 Zod 导出后交给 LLM 结构化输出，一份定义两处使用。这是 R-04 类不一致不再复发的机制保障。

**原则三：降级路径与主路径同批交付。** 不允许「先做主路径，兜底以后补」。设计稿十八章的每条降级链在对应阶段就要有测试覆盖 —— 验收标准 6/7/8 全部是降级行为，事后补会导致大范围返工。

**原则四（R-14）：Linux 是唯一的正确性基准。** 开发在 Windows，但「本地跑通」不算通过 —— 只有 Linux CI 上的 L-01～L-10 全绿才算。跨平台护栏（大小写、换行、路径、执行位）在 P0 就由工具强制，不留到发现故障时再补。

**原则五（R-13）：归属列先行。** `users` 表是第一张业务表，任何业务表在建表时就带 `user_id NOT NULL`。事后加归属列意味着加列 + 回填 + 改造全部查询 + 补一次跨表归并事务。

## 3.4 身份体系为什么进一步前移到 P1（V1.1 计划为 P2）

V1.1 计划把用户体系放在 P2，理由是「表在 P2 建立，此时不带 `user_id` 会导致 P5 返工」。R-13 引入双模式后，这个理由**变得更强**，需要再前移一个阶段：

| 依赖                               | 说明                                                                                                                                              |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `users` 表是全部业务表的外键目标   | `travel_requests` / `travel_plans` / `generation_jobs` / `exports` 的 `user_id NOT NULL` + `ON DELETE CASCADE` 都指向它。它必须是**第一张业务表** |
| 幂等键含 `user_id`（13.8）         | P2 要实现幂等，而幂等键的输入之一是身份。身份未就位则幂等键定义无法冻结                                                                           |
| 配额是生成端点的前置校验（21.4）   | P2 的生成端点必须先过配额检查，而配额按 `user_type` 分档                                                                                          |
| 匿名自动建号改变了端点契约（13.0） | 「生成端点永不因缺身份返回 401」是端点级行为，不能后加                                                                                            |
| 归并与升级涉及全部业务表           | 13.9.4 的改挂逻辑要覆盖 4 张表；表建完再补归并，等于补一次跨表事务                                                                                |

**P1 只做身份，不做业务归属** —— P1 阶段还没有业务表，因此 P1 交付的是 `users` 表 + 身份解析中间件 + 注册/登录/匿名令牌 + 配额框架。业务表的 `user_id` 列与归并逻辑在 P2 随表一起落地。这样切分让 P1 的渲染链路验证不被身份阻塞（渲染路由本来就不认身份 Cookie）。

   但**未对真实端点发起过调用** —— 那需要凭据。接入时只改环境变量。

   连带影响：向量化用本地哈希向量器（词汇重合度），因此**请求驱动的历史检索
   在本地/CI 下多半报「无历史参考」** —— 请求文本与投影文本的共同词很少，

   （门禁 #26、#28）。接上语义向量模型后同一段代码即可命中，接口不变，

# 六、回滚策略

| 层级        | 手段                                                                                                     |
| ----------- | -------------------------------------------------------------------------------------------------------- |
| 代码        | 独立新仓库 `travel-poster-system`，P0～P5 每阶段一个 tag；回滚 = revert + 重部署                         |
| 数据库      | 前向单向迁移，破坏性变更走 expand-backfill-contract 三步；每阶段迁移前快照                               |
| Schema 契约 | `packages/schemas` 语义化版本；`schema_version` 字段在数据行内，旧版 ViewModel 可继续渲染                |
| 缓存键      | 19.2 的 `v1` 版本号递增而非清空，旧产物保留可回滚对比                                                    |
| 素材        | 不物理删除，`assets` 加下架标记，绑定关系保留                                                            |
| 功能开关    | TP-5-10 支持一键关闭新链路，回退到上一版本                                                               |
| 灰度        | 百分比放量，指标异常自动停止放量                                                                         |
| 身份数据    | 匿名行删除前先转存 `plan_knowledge`（TP-4-22），删除顺序不可逆但知识不丢；归并为幂等事务，失败可原样重放 |

**关键约束**：`plan_presentations` 与 `travel_plan_versions` 按版本隔离、不覆盖，因此任何编排或模板变更都可以通过「重新编排为新版本」回滚，不需要修改历史数据。

**不可回滚的一处**：15.1 的匿名数据物理删除。缓解是删除前的知识转存（TP-4-22）与删除前 30 天宽限期，但已删除的个人数据无法恢复 —— 这是保留承诺的必然结果，需在上线前确认清理任务的批量与阈值配置无误。
