## 1.3 与现有网关的关系

`travel-poster-system` 通过 HTTP 调用 `enterprise-ai-platform` 的 `POST /v1/chat/completions` 获取 LLM 能力，**不共享数据库、不共享代码、不共享用户体系**。

```text
travel-poster-system/generation-worker
        │ HTTP + Bearer
        ▼
enterprise-ai-platform/gateway  →  POST /v1/chat/completions
```

两侧的「用户」概念完全无关：网关侧是 `tenant_id`（调用方租户），本系统侧是 `user_id`（终端旅行者）。本系统作为**单一租户**接入网关，终端用户身份不透传。

**风险**：该网关的认证（`TASK-M2-002`）与 Provider 适配（`TASK-M2-005`）目前是**接口契约而非可用实现**（`UnavailableGatewayAdapters.cs`），实际调用会返回 `503`。

**应对**：`packages/shared` 中定义 `LlmClient` 接口，提供两个实现 —— `GatewayLlmClient`（走网关）与 `DirectLlmClient`（直连 Anthropic SDK）。第一至三阶段用 `DirectLlmClient` 推进，网关就绪后切换配置即可，不改业务代码。

### R-13 的两个关键设计判断

**统一 `users` 表而非独立匿名表**（3.6.2）：匿名升级只需翻转 `user_type`，`user_id` 不变，历史自动继承，**零业务行迁移**。独立匿名表方案要跨 4 张表搬归属列并处理中途失败的部分继承状态。代价是匿名行累积，用保留期清理解决 —— 运维成本远低于正确性风险。

**脱敏投影独立成列 + 列级 GRANT**（3.2.4、15.2）：全局检索按需求跨用户进行，但直接读 `plan_json` 会把 A 用户的预算、日期、人员构成、自由文本诉求带进 B 用户的生成上下文。因此新增 `retrieval_projection` 列，`plan_embedding` 也必须由该列计算（否则敏感字段以向量形式残留），并用只读角色的**列级 `GRANT` 排除 `plan_json`** —— 即使应用代码写错，数据库也会拒绝。安全由数据布局保证，不靠调用方自觉。

### R-13 的一个副产物：匿名数据清理不损失行程知识

匿名行到期删除会级联删掉 `travel_plan_versions`，让全局检索持续失血（匿名流量占比可能很高）。因此清理前把脱敏投影转存到 `plan_knowledge` 表（无 `user_id`、无日期、无金额、无人员构成）。**被清理的是「谁何时去哪花多少」，保留的是「杭州运河主题 5 天可以这样安排」** —— 后者不是个人数据。此区分必须同步写进用户协议（设计稿二十章）。

# 三、实施策略

## 3.1 五条原则

**原则一：渲染链路优先。** 十六章阻断判定表中，`RENDER_TEMPLATE_FAILED` 与 `RENDER_CORE_ASSET_MISSING` 是唯一无法通过降级绕过的失败。先用静态数据打通「模板 → HTML → PNG/PDF」，在引入 LLM 之前拿到确定性产物。

**原则二：契约先行，Zod 为单一真相源。** `packages/schemas` 是第一个交付物。API、Worker、React 模板全部从它导入类型；JSON Schema 由 Zod 导出后交给 LLM 结构化输出，一份定义两处使用。这是 R-04 类不一致不再复发的机制保障。

**原则三：降级路径与主路径同批交付。** 不允许「先做主路径，兜底以后补」。设计稿十八章的每条降级链在对应阶段就要有测试覆盖 —— 验收标准 6/7/8 全部是降级行为，事后补会导致大范围返工。

**原则四（R-14）：Linux 是唯一的正确性基准。** 开发在 Windows，但「本地跑通」不算通过 —— 只有 Linux CI 上的 L-01～L-10 全绿才算。跨平台护栏（大小写、换行、路径、执行位）在 P0 就由工具强制，不留到发现故障时再补。

**原则五（R-13）：归属列先行。** `users` 表是第一张业务表，任何业务表在建表时就带 `user_id NOT NULL`。事后加归属列意味着加列 + 回填 + 改造全部查询 + 补一次跨表归并事务。

## 3.4 身份体系为什么进一步前移到 P1（V1.1 计划为 P2）

V1.1 计划把用户体系放在 P2，理由是「表在 P2 建立，此时不带 `user_id` 会导致 P5 返工」。R-13 引入双模式后，这个理由**变得更强**，需要再前移一个阶段：

| 依赖                               | 说明                                                                                                                                              |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `users` 表是全部业务表的外键目标   | `travel_requests` / `travel_plans` / `generation_jobs` / `exports` 的 `user_id NOT NULL` + `ON DELETE CASCADE` 都指向它。它必须是**第一张业务表** |
| 幂等键含 `user_id`（13.8）         | P2 要实现幂等，而幂等键的输入之一是身份。身份未就位则幂等键定义无法冻结                                                                           |
| 配额是生成端点的前置校验（21.4）   | P2 的生成端点必须先过配额检查，而配额按 `user_type` 分档                                                                                          |
| 匿名自动建号改变了端点契约（13.0） | 「生成端点永不因缺身份返回 401」是端点级行为，不能后加                                                                                            |
| 归并与升级涉及全部业务表           | 13.9.4 的改挂逻辑要覆盖 4 张表；表建完再补归并，等于补一次跨表事务                                                                                |

**P1 只做身份，不做业务归属** —— P1 阶段还没有业务表，因此 P1 交付的是 `users` 表 + 身份解析中间件 + 注册/登录/匿名令牌 + 配额框架。业务表的 `user_id` 列与归并逻辑在 P2 随表一起落地。这样切分让 P1 的渲染链路验证不被身份阻塞（渲染路由本来就不认身份 Cookie）。

#### 与计划的偏离

| 项           | 计划               | 实际                                                         | 理由                                                                                                           |
| ------------ | ------------------ | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| 字体格式     | woff2 + ttf        | 只发 woff2                                                   | Chromium 从 woff2 加载的字体一样会嵌入 PDF；ttf 会给仓库增加约 15MB 二进制而无功能收益（R-15 D-1）             |

存量数据照常 30 天保留期清理（不改隐私政策）、8 项门禁反转断言而非删除。

**零改动的三处**：`packages/db`、`apps/retention-worker`、
`docs/用户协议与隐私政策.md`。没有新增迁移 —— 这是「开关」而非「移除」的定义。

**一处必须先解决的依赖**

20 个验收用例的注册身份原先是靠匿名自举的（`GET /auth/session` 拿 `tp_anon`
→ 带着它 `POST /auth/register` 走原地升级分支）。因此关闭匿名会让**全部 21 个
用例**一起红，而不只是其中 10 个匿名的。这一项排在最前并在开关**还不存在**时
完成，因此它必须在两种开关状态下都通过 —— 那正是「不再依赖匿名自举」的证明。

顺带修掉的结构问题：20 个验收用例要验的是生成链路，把它们的前置条件挂在另一个
功能上，等于让一个功能的关闭连带 21 个用例一起红，而红的原因与它们要验的东西无关。

**拦截点的选择**

开关拦在 `IdentityService.resolve()` 内部而不是各业务路由：
`allowAnonymousCreation` 有 15 个调用点，而 `/auth/session` 根本不走
`resolveIdentity`（它直接调 `resolve`）—— 路由层的拦截会漏掉会话端点，
而那是匿名号的唯一签发入口。

**默认值的刻意不对称**

`FEATURE_ANONYMOUS_ENABLED` 默认 `false`，与 `generationEnabled` /
`exportEnabled` 的默认 `true` 相反。那两个是「正常开着、紧急时关」，
忘记配等于「和引入灰度之前一样」；这一个是产品已决定关闭的功能，
默认 `true` 会让任何漏配的部署静默重新开放匿名注册 —— 那是产品行为的回退，
不是可观测的故障：没有告警会响，只有转化数据在几周后变得可疑。
`ALL_FEATURES_ON` 里这一项同样是 `false`（两个「默认」不一致是最难查的一类
配置问题）。

**实施中发现并修正的两处自身问题**

| 问题                                                                      | 说明                                                                                                                                                                                                    |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 用正则批量补 `anonymousEnabled` 时打到了不该打的地方（路由 deps、重复键） | 编译期立刻拦住。回滚正则的全部插入后逐处精确补 —— 6 处全是 `IdentityService` 构造                                                                                                                       |

**四处交付边界**

   `travel_identity_total{event="anonymous_rejected"}` 归零之后才可以考虑真正

### P8 实现说明与偏差

**已完成**：TP-8-01～TP-8-06、TP-8-08。`pnpm gate` 报 **40 项**（P8 加 #39/#40），
本机 14 项自动通过、4 项仅 CI、2 项人工、20 项跳过（缺 `DATABASE_URL`）、**0 项失败**。

**TP-8-07 未开始** —— 见下方交付边界。

**契约改动是放宽而非收紧，因此向后兼容**：照旧发全量字段的客户端一行不改，
`travel_request_ui_v1` 不升版本号。没有新增迁移 —— 条件码存在 `plan_json`（JSONB）
里，没有任何 CHECK 约束依赖它。

**实施中撞到的两个 Zod 4 陷阱**

① **`.default()` 能造出不满足自身推断类型的值。** Zod 4 改了语义：输入为
`undefined` 时**直接返回默认值，不走内部 schema 解析**。因此
`OutputPreferencesSchema.default({})` 产出 `{}`，而 `z.infer` 声称那里有四个必填
字段 —— TypeScript 完全看不见这个洞。测试先红才发现。修法是**对象级默认值一律用
`.prefault()`**，标量与数组用 `.default()`；这条规则写进了 `travel-request.ts`。

② **`.default()` 不复制引用。** 给常量会让每次解析拿到同一个数组，下游任何就地
修改都会污染模块级常量。数组默认值改成函数形式 `.default(() => [...X])`。

**一处比原计划更准的处理**：`included_items` 的 `.min(1)` **保留**而不是删掉。
`.default()` 只在键缺省时生效，于是「可以不传」与「传了就不能为空」两个语义同时
成立 —— 而既有那条「空数组被拒」的测试一行都不用改。

**核实掉一条设计稿条款**：5.1 写着「新增域必须同时更新 Prompt 模板」。逐行核对
`describeConditions` 后确认它是对 code 的泛型遍历、分域靠前缀而非硬编码小节，
因此新增 `budget` 域**确实不需要改 Prompt**。这句话同时写进代码与测试注释 ——
下一个加域的人会先看条款，而「条款说要改但找不到要改的地方」会让他去改一个
不该改的地方。

**三处交付边界**

1. **TP-8-07（界面重构）未开始。** 它是本阶段最大的一块，且一动
   `apps/web/src/app/globals.css` 就有视觉基线风险：根 layout 是 `/render/**`
   信息图页面的祖先，原型的 `body { background: #f5f7fb; font-family: Inter… }`
   直接落进去会让导出 PNG 的底色从白变灰、字体不再走自托管子集，
   `apps/render-worker/__visual__` 的基线整片失配。因此样式必须全部作用域化到
   `.planner` 之下，且 `globals.css` 的 `:root` 与 `html/body` 段不得修改。
   实施步骤见 `docs/superpowers/plans/2026-08-20-p8-原型前端与条件字典扩容.md`
   的增量 5。
2. **`PlanRequestForm` 目前是过渡形态**：三态已打通，但呈现的是三态循环按钮而不是
   原型的三色标签。它会在 TP-8-07 被 `components/planner/` 下的一组组件整体取代。
3. **`budget.included_items` 至今是惰性数据**（P8 之前就存在的缺口，未修）：
   `normalize.ts` 只透传它，Prompt 没渲染，没有任何 V-xx / N-xx 规则读它 ——
   模型并不知道预算覆盖了哪些开支，而 `min`/`max` 的含义恰恰取决于此。
   记在 R-56 末尾。
