# 开发改动指南

## 开始前的定位方法

先判断改动属于哪一层：

```text
请求/响应形状       → packages/schemas
问卷字段/元数据      → schemas/planner-fields + planner-profile + web/lib/planner
纯业务规则           → packages/planning / presentation / assets
HTTP 与身份语义      → apps/api
有 IO 的生成编排     → apps/generation-worker
浏览器导出           → apps/render-worker
页面与模板           → apps/web
数据库/查询          → infrastructure/migrations + packages/db
队列/存储/运维       → packages/queue/storage + deploy/tools
```

不要在应用中复制共享纯逻辑，也不要让共享包反向依赖某个应用。

## 修改旅行请求字段

检查清单：

1. 判断是兼容核心字段还是 Planner V2.1 问卷字段；后者先修改 `planner-fields.ts` 与 `planner-profile.ts`，并保持 `planner_profile.{api_key}` 规则；
2. 修改 `packages/schemas/src/travel-request.ts`，明确输入是否必填、默认值与输出类型；
3. 若是枚举，修改 `schemas/enums.ts`；若是条件，修改 `schemas/conditions.ts`；
4. 更新 `web/lib/planner/descriptors.ts`、配置绑定、选项文案、触发/校验和 `buildPlannerRequest`；
5. 更新 `planning/constraints.ts`、`normalize.ts` 和 `prepare-request.ts`，决定逐字保留、运行时约束与兼容投影；
6. 检查 N-xx 冲突规则和错误字段路径；
7. 检查 `llm/prompt.ts` 是否真正把字段告诉模型；
8. 检查 V-xx 是否验证模型遵守它；
9. 更新 planner config 新版本迁移、最小/全量 fixture、前端接入契约和字段清单；
10. 跑 contract、planner field/profile/config/request、planning 与 typecheck 测试。

对象默认使用 `.prefault()`，数组默认用函数返回新数组。不要用 `as` 掩盖 Zod input/output 差异。

## 新增或修改条件码

```text
conditions.ts 的机器码
→ planner-fields/profile 的字段与枚举
→ descriptors/config-binding/内置文案
→ planner config 草稿并发布新版本
→ 通用三态控件/对应步骤
→ buildPlannerRequest 与 describeConditions/Prompt
→ 需要时新增 V 规则
→ ConditionSummary/计划解释
```

API 在存在发布配置时用配置白名单替换内置白名单，所以只改 `conditions.ts` 会在真实部署被 N-08 拒绝。迁移后运行 planner-config coverage/whitelist 测试。新增全新域时，确认 Prompt 是泛型前缀遍历还是硬编码分区；当前实现按 code 泛型遍历，通常不需要复制 Prompt 小节。

## 新增业务校验规则

1. 在 `packages/planning/src/plan-rules.ts` 增加稳定规则 ID、severity、path 与 detail；
2. 判断是 `BLOCKING`、`REPAIRABLE` 还是 `ADVISORY`；
3. 若可程序修复，在 `repair-plan.ts` 实现确定性、幂等修复；
4. 若需要定向重生成，确保 repair prompt 能表达具体违规；
5. 每条规则至少一条违规、一条通过，并补边界/组合用例；
6. 确认 `travel_validation_violations_total{rule_id}` 可观测；
7. 跑 `pnpm test:validation`，关注随机违规计划是否在上限内收敛。

规则必须读取正确的请求锚点，不要让模型输出自己证明自己。例如日期范围应与 `NormalizedTravelRequest` 对照，不能只检查计划内部首尾一致。

## 新增 API 端点

1. 先决定是公网 `/api/v1` 还是内部 `/internal/v1`；
2. 请求/响应若跨应用，先建 `@tps/schemas` 契约；
3. 在 route 层只处理 HTTP、身份、错误映射，把业务放 service/package；
4. 仓储接口必须从方法签名携带 `userId`，SQL 同时过滤 ID 与归属；
5. 不存在与越权都返回 404；
6. 写 fake 仓储和 route 测试，覆盖 2xx、Schema、越权、依赖失败；
7. 在 `server.ts` 注册并在 `main.ts` 注入真实依赖；
8. 更新本 Wiki、前端契约与代理/内部鉴权规则。

内部端点不要因为“外网代理暂时没配”就省略鉴权；共享密钥是第二道边界。

## 修改任务状态机

状态机有四个必须同步的真相面：

- `packages/schemas/src/job-status.ts`：枚举、合法边、进度和文案；
- `infrastructure/migrations/0003_travel_plans.sql` 或新的前向迁移：DB CHECK；
- `apps/generation-worker/src/generate-plan.ts`：实际推进与阶段计时；
- API/前端轮询：状态读取和用户呈现。

新增状态时还要更新 stage timing、指标 label 白名单/目录、超时与取消测试。终态不能有出边；回边必须有明确迭代上限；进度不能回退。

## 修改展示字段或模板

### ViewModel 字段

```text
schemas/view-model.ts
→ presentation/derive|compact|build-view-model|build-full-plan
→ plan_presentations 持久化/读取
→ web 两套模板
→ render page checks/视觉基线
```

模板只读取 ViewModel，不应从 `TravelPlan` 临时推导第二套逻辑。需要新派生值时把纯函数放 `@tps/presentation`，让 Worker 与 Web fixture 共用。

### CSS/布局

- 规划器样式必须以 `.planner` 作用域开头，不能污染 `/render/**`；
- 根 `globals.css` 的 `html/body/:root` 变化会影响所有导出；
- 保留 `data-overflow-guard` 等页面检查标记；
- 修改后先 `pnpm fixture:render`，再 `pnpm test:visual`；
- 同时检查 7 天和 14 天、中文长文、图片缺失、relaxed 变体。

## 新增素材来源或角色

1. 在 schemas 枚举、`ROLE_ASSET_TYPE` 和 requirement/resolved 契约定义角色；
2. 在 `@tps/presentation/requirements.ts` 产生稳定槽位；
3. 在 `resolve-assets.ts` 增加角色路由；
4. 实现 resolver，并定义超时、预算、授权、source metadata；
5. 必须提供到底 fallback，决定 warning 和 `validation_status`；
6. 若入库，复用 `processors/image.ts` 和 `search-ingest.ts`，不要另写后处理；
7. 在 binding 中记录 strategy、score、fallback level；
8. 注册素材解析/搜索/成本指标；
9. 增加故障注入：超时、无授权、低质量、上传失败、额度耗尽时任务仍符合阻断表。

AI 不能生成带文字、价格、Logo 或地图文字的素材；AI 景点图必须 `ILLUSTRATIVE` 并在页面显示“示意图”。

## 接入新的 LLM/图片模型

优先通过模型池配置而不是硬编码：

1. 用 `pnpm probe:llm` 或 `pnpm probe:image` 验证 base URL、端点拼法、参数名、结构化输出与真实像素；
2. 在 `model_pools` 添加候选，并用 `tier_model_pools` 映射用户档位；
3. 文本/图片分别使用 `wrapLlmFailover`/`wrapImageFailover`；
4. 给每个候选明确单次 timeout 和整体预算，图像候选可能因总时延预算被截断；
5. 观察 `travel_model_candidate_total` 一类候选位置/结果指标；
6. 小 tier 灰度，确认成本、T1/T2、错误率后放量。

`model:pool --list` 看的是实际生效候选数，比只查表更可靠；Worker 最多缓存 60 秒。

## 新增数据库迁移

1. 在 `infrastructure/migrations` 追加下一个编号；
2. 使用幂等 DDL 只在确实需要时，不修改旧迁移；
3. 写清 FK `ON DELETE`、NULL 语义、CHECK 和索引用途；
4. 更新 `packages/db` row/interface/repository；
5. 为约束写正向和反向集成测试；
6. 空库迁移、重复迁移、`db:status` 漂移检查；
7. 在 pgvector Linux CI 验证扩展/索引；
8. 更新 [数据、检索与存储](05-数据检索与存储.md)。

## 新增指标或告警

1. 在拥有该事件的应用/包注册 metric；
2. label 只能使用 `ALLOWED_LABELS`，不得用用户/内容 ID；
3. 在 `observability/catalog.ts` 登记 owner、kind、labels 和来源；
4. 若新增告警，修改 `deploy/prometheus/rules`；
5. 在运维手册增加可执行 runbook 锚点；
6. 跑 `pnpm test:alerts`、`pnpm test:docs` 和相关 metrics-catalog 测试。

指标缺失会表现成“永远健康”，因此目录和告警必须双向测试。

## 修改 CR 计费

计费涉及真实余额，先阅读 [用户货币与计费](../用户货币与计费.md)。联动面：

```text
packages/billing 的单位/SKU/估算/计价
→ credit_price_versions/items 迁移或新发布版本
→ db/credit-wallet 的事务与幂等
→ api CreditsService/credits routes/生成与导出闸门
→ generation-worker UsageMeter + settle/release
→ render-worker 导出失败退款
→ web CreditHint/Session/CreditLedger
→ 指标、告警、CLI 与运维文档
```

硬规则：CR 只用整数；充值向下取整、计费向上取整；不能改已发布价目行，应 clone→修改草稿→publish；结算按 hold 锁定的版本；不得直接 UPDATE 钱包而不写 ledger；开关必须 API、generation-worker、render-worker 三侧一起开启。

## 提交前建议验证

普通业务改动：

```bash
pnpm format:check
pnpm lint
pnpm typecheck
pnpm test
```

按改动范围追加：

- 请求/前端：`pnpm test:contract`；
- 规则：`pnpm test:validation`；
- 身份/归属：`pnpm test:identity && pnpm test:isolation`；
- 素材：`pnpm test:scoring && pnpm test:asset-ingest`；
- 数据：`pnpm test:integration`；
- 模板：`pnpm fixture:render && pnpm test:visual`；
- 运维/指标：`pnpm test:alerts && pnpm test:docs && pnpm test:logs`；
- 发布候选：`pnpm gate`，并单独确认 CI-only 与人工项。
