> **文档类型**：专项说明 / 可执行方案 + 交付规范。
> **核实方式**：全部格式、尺寸、阈值、公式与色值均从代码读出并标行号（流程部分核实于 2026-08-28，制作规范部分核实于 2026-09-03，设计稿 V1.14）。
> **前置阅读**：[图片与素材全链路](图片与素材全链路.md) 的第二、三、四节。
>
> 第一至五节是**怎么跑灌库流程**（清单、命令、验收）；
> 第六至九节是**图片本身在制作时要满足什么**（尺寸、画质、版面、禁止内容）。

## 零、先分清两条轨道

「预热库」在代码里是**两个不同的东西**，用途、命令、命中层都不同。混为一谈是这件事
最常见的失败方式。

|             | 轨道 A：Hero 预热      | 轨道 B：种子素材库                       |
| ----------- | ---------------------- | ---------------------------------------- |
| 命令        | `pnpm assets:preheat`  | `pnpm assets:ingest --manifest`          |
| 图从哪来    | **AI 生成**            | 联网搜索 + 人工审核后的本地文件          |
| `cache_key` | 有（`hero:v1:…`）      | **null**                                 |
| 命中层      | ① `CACHE_HIT`          | ② `LOCAL_LIBRARY_MATCH`（需评分 ≥ 0.65） |
| 耗时        | < 50 毫秒              | < 500 毫秒                               |
| 规模        | 目的地数 × 13 桶       | 按需，无固定规模                         |
| 角色        | 只有 `HERO_BACKGROUND` | Hero / 景点 / 美食 三种                  |

`ingest-cli.ts` L185-187 把轨道 B 的取舍写得很直接：

> 种子素材不带缓存键：它们不是「按某个键生成的产物」，而是可被多个键命中的库存
> （19.5 的复用发生在检索层）。

**§21.2 措施二依赖的是轨道 A。** 「命中预热库（预期 ≥ 80% 请求）→ < 50 毫秒」这条
只有精确键命中做得到；轨道 B 落在下一层，是给「预热没覆盖到的组合」兜底的。

### 两条轨道之外还有三类预制图形

上面那张表只盖了**入库素材**。完整到「一个不少」的清单是五类，后三类不进
`assets` 表、不参与评分、也不靠上面两个命令制作：

| #   | 类别            | 数量        | 怎么来                   | 规格在哪 |
| --- | --------------- | ----------- | ------------------------ | -------- |
| 1   | Hero 背景（AI） | 目的地 × 13 | 轨道 A，`assets:preheat` | 六、七   |
| 2   | 景点图 / 美食图 | 按需        | 轨道 B，`assets:ingest`  | 六、八   |
| 3   | 默认占位图      | 固定 **3**  | 程序生成，不要手工出图   | 九、一   |
| 4   | 图标            | 固定 **19** | 编译期内联的 SVG         | 九、二   |
| 5   | 模板预览图      | 每模板 1 张 | 从视觉基线生成           | 九、三   |

把后三类也写进这篇是因为它们同样是「上线前必须已经存在的图」。遗漏的表现各不相同：
占位图缺失会让降级链的最后一步无处可取；图标缺失让 `travel_icon_load_failure_total`
非 0（验收标准 5 要求恒为 0）；预览图缺失则模板选择器上是一个破图。

### 三类入库素材共用同一道硬门禁

轨道 A 的 AI 产物与轨道 B 的人工素材**走的是同一个 `processImage`**（第六节）。
因此第六节的尺寸与画质规格对两条轨道同时生效 —— 包括「叫供应商重新生成一批
更好的 Hero」这种情形。

## 一、开工前必须定的一件事：键用 place_id 还是名称

这一条决定后面所有工作是否有意义。

`cache-keys.ts` L43-52 的目的地段：**优先 `place_id`，缺失时退化为归一化名称**。
而 `travel-request.ts` L44-45 写明 `place_id` 是**可选**的 ——「用户输入的地名不一定
有对应 place_id，缺时用 19.1 的归一化文本」。

于是同一个「杭州」会产出两种键：

```text
前端送了 place_id   →  hero:v1:cn_hangzhou:canal_culture:chinese_travel_editorial:16x6
前端没送 place_id   →  hero:v1:杭州:canal_culture:chinese_travel_editorial:16x6
```

**两者永远不会互相命中。** `preheat.ts` 的文件头把后果说得很清楚：

> 预热时用一套自己编的 ID，产出的键与真实请求的键**永远不会相同**：600 张图全部躺在
> 库里没人命中，而缓存命中率指标会如实地显示 0，却看不出原因。

### 动手前先做这个验证

用生产前端真实提交一次请求，然后查库：

```sql
SELECT r.normalized_request -> 'destination' AS destination
FROM travel_requests r
ORDER BY r.created_at DESC
LIMIT 5;
```

看 `place_id` 这个键**在不在**。

- **在** → 预热清单的 `place_id` 必须用同一个命名空间的值（从前端用的地理编码服务导出）
- **不在** → 清单的 `place_id` 填**归一化后的目的地名**本身，让两侧退化到同一条路径

> 示例清单 `infrastructure/seed/preheat-destinations.example.jsonl` 里的
> `cn_hangzhou` **只与本仓库的 fixture 对得上**，用于本地打通链路。
> 上线用的那份是数据工作，不能照抄。

## 二、13 个主题桶（不是 12 个）

设计稿 §19.5 写的是 12 个桶，而 `preheat.ts` L20-25 论证了必须预热 **13** 个：

> `general` 恰恰是**未命中关键词时的落点**，也就是最容易被真实请求击中的那一个。
> 漏掉它等于漏掉「主题短语没有出现任何已知关键词」的全部情况。

因此 50 个目的地 = **650** 个键。

### 桶名、关键词与预热用的代表短语

关键词表在 `theme-buckets.ts` L34-67，代表短语在 `preheat.ts` L62-76：

| `canal_culture`   | 运河 水乡 河埠 漕运 水巷 拱宸 桥西 临水             | 运河人文   |
| `lake_scenery`    | 西湖 湖光 湖畔 湖山 湖景 湖滨 太湖 洱海 断桥        | 湖光山色   |
| `old_town`        | 古城 古镇 老街 街区 巷弄 老城 直街 骑楼             | 古城老街   |
| `museum_art`      | 博物 美术 展览 艺术 文博 展馆 画院                  | 博物与艺术 |

| `general`         | —（兜底）                                           | 城市印象   |

### 归桶算法：按命中字数打分，不是首个命中

`themeBucket()`（L81-105）：

1. 主题短语过 `normalizeName`（去空白、全角转半角、去括号、小写、拼接）
2. 对 12 个具体桶各算一次分：**每个命中的关键词累加它的字数**
3. 取最高分；`score` 全为 0 落 `general`
4. **同分时按 `THEME_BUCKET_VALUES` 的枚举顺序取第一个**

第 2 步用字数而非计数是有理由的：长词更具指示性（「钱塘江畔」比「山」更能确定主题）。
`temple_heritage` 里同时收「寺」「禅」与「问禅」「礼佛」也是为此 —— 只有单字时
「灵隐问禅·山径听泉」会与 `mountain_nature` 同分，结果取决于枚举顺序，
那不是判断，是巧合。

**预热时不需要跑这个算法** —— 你直接按桶枚举。它在这里是为了让你能预测
「真实请求的某个主题会落到哪个桶」，从而判断预热覆盖得对不对。

## 三、cache_key 的精确格式

```text
hero:v1:{destination}:{theme_bucket}:{visual_style}:{aspect_ratio}
```

五个段的取值规则（`cache-keys.ts` L65-75）：

| 段             | 取值                                   | 来源              |
| -------------- | -------------------------------------- | ----------------- |
| `v1`           | `KEY_VERSION`，固定                    | L30               |
| `destination`  | `place_id` 或归一化名称                | L43-52            |
| `theme_bucket` | 13 个桶名之一，**原样**                | —                 |
| `visual_style` | `chinese_travel_editorial`（**小写**） | `enumSegment` L38 |
| `aspect_ratio` | `16x6`（冒号换 `x`）                   | L33               |

Hero 的风格与画幅是固定的，不用猜：`requirements.ts` L44 建 Hero 需求时写死
`CHINESE_TRAVEL_EDITORIAL`，`resolve-assets.ts` L382 也默认它；`preheat.ts` L45-46
给出 `16:6` 与最小宽度 1600。全仓只有两种风格，另一种 `REALISTIC_FOOD_PHOTOGRAPHY`
是美食图用的。

### 归一化的六步与两处刻意偏离

`normalizeKeySegment`（`normalize.ts` L63-69）：去首尾空白 → 全角转半角 →
去括号及内容 → 小写化拉丁字符 → 非字母数字/CJK 替换为 `_` 并合并。

**两处按 R-26 刻意不做**，写清单时要知道：

- **不做繁简转换** ——「靈隱寺」与「灵隐寺」是两个键。清单一律用简体。
- **不做拼音转写** —— CJK 原样保留在键里。`food:v1:葱包桧与小馄饨:杭州:…` 是正常的。
  转拼音会让「拱宸桥」与「拱辰桥」碰撞，而缓存键碰撞的表现是「A 的图出现在 B 的位置」。

### 什么时候必须递增 KEY_VERSION

§19.2：任何影响**产物外观**的变更 —— AI 提示词模板改版、SVG 渲染器升级、
比例定义变化、归一化规则变化。**递增而不是清空缓存**：递增保留旧产物用于回滚与对比，
清空是不可逆的，而那些 Hero 是花钱生成的。

## 四、轨道 A：Hero 预热的执行步骤

### 步骤 1 · 备清单

JSONL，一行一个目的地，`#` 开头是注释（`preheat.ts` L133-171）：

```jsonl
{ "place_id": "<与前端同命名空间>", "name": "杭州" }
{ "place_id": "<...>", "name": "苏州" }
```

两个字段都必填非空。解析器**收集全部错行后整体拒绝**，不跳过 ——
跳过等于「预热了 638 个，12 个静默缺失」，而缺失的那些会在线上以实时生成
（10～40 秒）的形式暴露。`place_id` 重复也算错行，因为它会让「预热了多少」这个数字失真。

### 步骤 2 · 干跑，看键

```bash
pnpm assets:preheat -- --manifest ./infrastructure/seed/preheat-destinations.jsonl --dry-run
```

不花钱，逐行打印 `目的地 / 桶 → 缓存键`。**这一步是键正确性的唯一检查点** ——
把打印出的键与线上真实请求产生的键对一次（见第一节的 SQL）。

### 步骤 3 · 小批量验画质

```bash
pnpm assets:preheat -- --manifest <清单> --limit 13
```

`--limit` 只跑前 N 个（一个目的地的 13 个桶），先看画面质量再全量跑。

**必须确认 `IMAGE_MODE=direct|gateway`。** fake 模式下会打这条警告：

> `IMAGE_MODE=fake`：产物是渐变占位图而不是插画，仅用于打通链路，不可作为上线预热

代码选择警告而不是拒绝，因为 fake 预热对验证键与复用链路仍有用。但**不看这行日志
就全量跑，线上会以「Hero 全是灰蓝渐变」的形式暴露，而缓存命中率指标一切正常。**

### 步骤 4 · 全量

```bash
pnpm assets:preheat -- --manifest <清单>
```

- 并发固定 **4**（`PREHEAT_CONCURRENCY`）。理由：预热与在线请求争的是同一个供应商
  速率配额，开到 20 会让正在等页面的用户排在几百张预热图后面。650 张 × 20 秒 ÷ 4
  ≈ 55 分钟，属于可接受的上线前准备时间。
- **一张都没成功且连续失败 5 个就中止整批**（`PREHEAT_ABORT_AFTER_FAILURES`）——
  那是配置错误（S3 地址、图片凭据）的形状，不该打印 650 行同样的错误。
- 单个目标失败**不中断**，失败清单在末尾一次列出，可缩小清单重跑。
- **有失败即非零退出**：「预热通过」必须意味着全部键就位。

需要的环境变量：`DATABASE_URL`、S3 四项、`IMAGE_*`。

### 步骤 5 · 验收

```sql
-- 键数是否等于 目的地数 × 13
SELECT count(*) FROM assets WHERE cache_key LIKE 'hero:v1:%';

-- 有没有哪个桶漏了
SELECT split_part(cache_key, ':', 4) AS bucket, count(*)
FROM assets WHERE cache_key LIKE 'hero:v1:%'
GROUP BY 1 ORDER BY 2;

-- 是不是假图（fake 模式的产物 source_type 是 AI_GENERATED 但画面是渐变，
-- 无法从库里分辨 —— 只能靠抽样打开 storage_url 看）
SELECT storage_url FROM assets WHERE cache_key LIKE 'hero:v1:%' LIMIT 5;
```

真正的验收是**上线后看 `travel_asset_cache_hit_ratio{role="HERO_BACKGROUND"}`**，
目标 ≥ 0.8（告警线 0.7）。低于预期时先查第一节那个 `place_id` 口径。

## 五、轨道 B：联网搜索 + 人工审核 + 灌库

### 设计明确拒绝「给个 URL 让程序去抓」

`seed-manifest.ts` L21-26：

> 二十章要求外部图片**下载、审核、转存**。审核是人的工作 —— 版权是否允许商用、
> 画面里有没有可识别的人脸、是不是拍的正确地点。让程序按 URL 自动抓取会把这一步
> 跳过去，而跳过的后果是法务问题。因此入口是「已经审核过并落到本地的文件 +
> 人工填写的授权信息」。

所以轨道 B 的联网搜索是**人做的**。运行时的 ③ 授权图源层会自动入库，那是因为它在
在线路径上等不起人工审核 —— 两种姿态的差别是有意的，不是遗漏。

### 搜索词怎么构造：必须与检索侧同口径

这是轨道 B 最容易做错的地方。`search-ingest.ts` L107 的注释：

> 不复用 `semanticQueryText` 会导致检索侧的查询词与入库侧不同，
> 用不同的词会让「搜到并入库的图，下次靠检索居然找不到」。

`semanticQueryText` 的构造是四段拼接（空段丢弃，空格连接）：

```text
entity_name + destination + ROLE_QUERY_LABEL[role] + style_tags.join(' ')
```

**人工搜索时用同一组词。** 例如为「杭州 / 拱宸桥 / 景点图」找图，
搜索词就该是 `拱宸桥 杭州 <景点角色标签> bridge canal daylight` 这个量级的组合，
而不是「杭州旅游高清大图」。用后者搜到的图入库后，`entity_match`（权重 0.35）
拿不到分，检索时命中不了 —— 图在库里，钱花了，没人用得上。

### 图源选择

- 白名单落配置 `IMAGE_SEARCH_PROVIDERS`，**不接受运行时添加**
- 授权必须允许商用；`license_type` 取 `PLATFORM_OWNED` / `LICENSED` / `CC0` / `AI_GENERATED`
- 需要署名的授权（CC BY 等）**必须**填 `attribution_text`，否则清单层就被拒
  （`SeedManifestEntrySchema` 的第一条 `refine`）—— 这一条在清单层拦而不是入库后拦，
  因为入库后的修正要回填几千行

### 清单格式

图片文件与清单放在**同一目录**，`file` 是相对文件名：

```jsonl
{
  "file": "gongchen-bridge-01.jpg",
  "role": "DESTINATION_PHOTO",
  "entity_name": "拱宸桥",
  "destination_name": "杭州",
  "destination_place_id": "cn_hangzhou",
  "license_type": "CC0",
  "style_tags": [
    "bridge",
    "canal",
    "daylight"
  ]
}
```

字段规则（`seed-manifest.ts` L45-82）：

| 字段                         | 必填 | 说明                                                                                                                      |
| ---------------------------- | ---- | ------------------------------------------------------------------------------------------------------------------------- |
| `file`                       | ✓    | 相对清单目录的文件名                                                                                                      |
| `role`                       | ✓    | 只能是 `HERO_BACKGROUND` / `FOOD_IMAGE` / `DESTINATION_PHOTO`。`ROUTE_MAP` 是程序生成的 SVG，用独立枚举而不是 refine 拦住 |
| `license_type`               | ✓    | 四个取值                                                                                                                  |
| `entity_name`                | —    | 缺省 null。**但它是评分权重最大的一项（0.35）**，能填就填                                                                 |
| `destination_name`           | —    | 权重 0.20                                                                                                                 |
| `destination_place_id`       | —    | 与轨道 A 同一个口径问题                                                                                                   |
| `title`                      | —    | 进 `search_text`                                                                                                          |
| `style_tags`                 | —    | 缺省 `[]`，进 `search_text` 与语义查询                                                                                    |
| `attribution_text`           | 条件 | `license_type = LICENSED` 且 `source_type ≠ PLATFORM_LIBRARY` 时必填                                                      |
| `license_expires_at`         | —    | ISO 日期，无到期日留空                                                                                                    |
| `source_type`                | —    | 缺省 `PLATFORM_LIBRARY`                                                                                                   |
| `representation_type`        | —    | 缺省 `PHOTOGRAPHIC`。`source_type = AI_GENERATED` 时**必须**是 `ILLUSTRATIVE`（9.4，数据库另有 CHECK 兜底）               |
| `aspect_ratio` / `min_width` | —    | 覆盖角色默认值                                                                                                            |

### 各角色的画幅与最小宽度

`ROLE_INGEST_DEFAULTS`（`seed-manifest.ts` L92-99）。两处不一致的表现是「灌进来的素材在解析时被
`aspect_ratio_score` 判低分，命中率莫名偏低，而两边单独看都是按规格做的」：

| 角色                | 画幅 | 最小宽度 |
| ------------------- | ---- | -------- |
| `HERO_BACKGROUND`   | 16:6 | 1600     |
| `DESTINATION_PHOTO` | 16:9 | 800      |
| `FOOD_IMAGE`        | 4:3  | 600      |

> 这两列是**入库不被拒的下限**，不是交付目标。按最小宽度交稿的图能入库，但
> `resolution_score` 只拿到 0.6 —— 推荐值与完整推导见第六节。

### 执行

```bash
# 干跑
pnpm assets:ingest -- --manifest ./path/to/manifest.jsonl --dry-run

# 灌入
pnpm assets:ingest -- --manifest ./path/to/manifest.jsonl

# 顺带灌三张默认占位图（它们有 cache_key，走精确命中）
pnpm assets:ingest -- --placeholders
```

同样是**错行整体拒绝**：清单人工维护，错行通常是同一类错误（比如整批漏填授权），
一次报全比修一条跑一次快得多。

## 六、尺寸与画质规格（三类入库素材共用）

本节对**两条轨道同时生效**：AI 产物与人工素材走的是同一个 `processImage`
（`processors/image.ts` L95-206）。

### 6.1 四道硬门禁：不达标直接拒收，不修正

| #   | 检查     | 拒收码                  | 判据                                  | 代码     |
| --- | -------- | ----------------------- | ------------------------------------- | -------- |
| 1   | 文件有效 | `INVALID_IMAGE`         | sharp 解不开，或缺宽高元数据          | L99-117  |
| 2   | 分辨率   | `RESOLUTION_TOO_LOW`    | 宽度 < 角色的 `min_width`             | L119-125 |
| 3   | 长宽比   | `ASPECT_RATIO_MISMATCH` | \|log2(实际/需求)\| > 0.5（半个八度） | L127-141 |
| 4   | 质量分   | `QUALITY_TOO_LOW`       | 仅当调用方传了下限时判定（见 6.4）    | L169-175 |

**为何拒而不修**（L20-27）：比例不符可以裁剪、分辨率不足可以放大，但两者都会
**降低质量却让分数变高** —— 裁剪后比例完美匹配（`aspect_ratio_score` 满分），
而画面主体可能被切掉一半。唯一例外是**缩小**（不改变构图）。

因此交稿时尺寸与比例必须已经对，没有「灌库时系统帮我裁一下」这回事。

### 6.2 推荐交付尺寸：三个角色的高都是 **900**

`resolutionScore`（`scoring.ts` L255-264）不是线性的：

```text
宽 < min_width          → 0      （硬性不达标，且第 2 道门禁已经拒了它）
宽 ≥ 2 × min_width      → 1.0
两者之间                 → 0.6 + 0.4 × (宽 − min) / min
```

注意它算的是**落库宽度**（`ingest.ts` L180 写入 `image.width`，即转码后的宽），
而 `MAX_STORED_WIDTH = 2400`（`image.ts` L35）会把更宽的图缩下去。于是：

| 角色      | 画幅 | 入库下限 | 满分需 2×min | 推荐交付像素   | 实际可达 `resolution_score` |
| --------- | ---- | -------- | ------------ | -------------- | --------------------------- |
| Hero 背景 | 16:6 | 1600     | 3200         | **2400 × 900** | **0.80（封顶）**            |
| 景点图    | 16:9 | 800      | 1600         | **1600 × 900** | 1.00                        |
| 美食图    | 4:3  | 600      | 1200         | **1200 × 900** | 1.00                        |

两个结论值得写下来：

**一、Hero 的 `resolution_score` 永远到不了 1.0。** 它的 `min_width` 是 1600，
满分需要落库 3200，而落库上限是 2400 —— 上限处恰好算得
`0.6 + 0.4 × (2400−1600)/1600 = 0.80`。影响是 `(1−0.8) × 0.05 = 0.01`（百分位一点），
因此**不是缺陷、不要去“修”它**，写在这里只为了省掉一次调查：
看到 Hero 的分项永远是 0.8 时不用找原因。

**二、交比 2400 更宽的图没有任何收益。** `MAX_STORED_WIDTH` 的注释就是这么写的 ——
「超过只是浪费带宽，导出用不到 4K 素材」。交 4K 稿只会拖慢灌库。

> 三个角色的推荐高都是 900 不是巧合：16:6×900=2400、16:9×900=1600、4:3×900=1200，
> 恰好全部落在【满分所需、≤ 2400】区间里。排稿时统一按高 900 导出最简单。

### 6.3 比例容差：两个档位

`aspectRatioScore`（`scoring.ts` L243-252）用比值的对数：
`d = |log2(实际 / 需求)|`，`score = max(0, 1 − d / 0.5)`。
用对数而不是差值是为了让 16:9 与 9:16 的惩罚对称。

| 目标          | d 上限 | 宽/高偏差   | 对 2400×900 的高容差 |
| ------------- | ------ | ----------- | -------------------- |
| 不被拒收      | 0.5    | ×1.414 以内 | 636 到 1273          |
| `score ≥ 0.9` | 0.05   | **±3.5%**   | **870 到 931**       |
| `score = 1.0` | 0      | 精确相等    | 900                  |

容差看似宽松（×1.414 才拒），但中间档惩罚很快：偏 10% 就只剩 0.72 分。
比例权重 0.10，是四项客观指标里最重的一项 —— **寘尺比画质更值得计较**。

### 6.4 画质：`quality_score` 的三项

`qualityScoreOf`（`processors/quality.ts` L150-162）：
`0.4 × 清晰度 + 0.3 × 曝光 + 0.3 × 主体占比`。
三项都在**原图**上算（而不是压缩后的 WebP，L143-147），先转灰度并缩到宽 512
（L148-153，否则大图天然得高分）。

**清晰度**（权重 0.4）：拉普拉斯方差 ÷ 500，封顶 1.0（L81-85，
`SHARPNESS_VARIANCE_CEILING = 500` 在 L31）。注释给了量级：**100 以下通常肉眼可见模糊**
（L10-11）。因此柔焦、动模糊、强降噪过度的稿子在这一项上直接塔下来。

**曝光**（权重 0.3）：`亮度居中度 × (1 − min(1, 截断比例 × 2))`（L87-109）。

- 像素 ≤ 5 或 ≥ 250 计为**截断**（`CLIP_LOW/HIGH`，L33-34）；
- 截断的惩罚系数是 **2**：10% 的像素被截断就扣 20% 分。比 1 更降是有意的 ——
  截断是**不可恢复**的细节丢失，而亮度偏移在展示时还能被版式与遮罩补偿（L103-107）；
- 亮度居中度 = `1 − |均值 − 128| / 128`。

实操上：**平一点、不要压死黑与熬白高光**。深夜景与雪景在这一项上天然吃亏，
而它只占 final 的 `0.05 × 0.3 = 1.5%` —— 不要为了它把夜景提亮成黄昏。

**主体占比**（权重 0.3）：中心 50% 面积内的边缘能量 ÷ 全图边缘能量（L111-148）。
四边各缩进 `(1 − 1/√2)/2 ≈ 14.6%`。它是**近似而不是等价**（真正的主体分割需要模型）：

```text
能量全在中心   → 1.0   主体明确
能量均匀分布   → 0.5   没有主体（一整片纹理墙）
能量全在边缘   → 0.0   主体被切在画面外
```

> **这一项与 Hero 的版面要求相矛盾，以版面为准。** Hero 的
> `subject_area` 是 `RIGHT_AND_BOTTOM`（第七节），主体偏右下必然拉低这一项。
> 而它只占 final 的 1.5%，且代码自己就声明了「误差影响有界」（L24-27）。
> 为了这 1.5% 把 Hero 主体摆到中间，换来的是标题压在建筑上不可读。

### 6.5 两条轨道都没有机器质量门禁 —— 审核的人就是那道门禁

第 4 道门禁（`QUALITY_TOO_LOW`）**只在调用方显式传了下限时才判定**（`image.ts` L169-175）。
全仓只有一处传了它：运行时的搜索入库，值是 `SEARCH_QUALITY_FLOOR = 0.3`
（`search-ingest.ts` L58，传入处 L298）。

也就是说：

| 来源               | 质量下限 | 把关的是谁           |
| ------------------ | -------- | -------------------- |
| 轨道 A（AI 预热）  | **无**   | 按需求定制，抽样目检 |
| 轨道 B（种子清单） | **无**   | **审核的人**         |
| 运行时搜索入库     | 0.3      | 机器                 |

`image.ts` L80-83 把理由写得很直：平台自有素材是人挑的、AI 生成物是按需求定制的，
只有搜索结果需要一道机器可判定的把关（因为它在在线路径上等不起人工审核）。

**后果是：你灌什么进去，就是什么。** 一批模糊的种子素材不会被任何程序拦住，
它们会以 `quality_score` 偏低的形式影响排序（权重 0.05），但仍然可能在没有更好
候选时被采用 —— 然后出现在用户的 PDF 里。

### 6.6 交付格式

- 交稿格式：**JPEG / PNG / WebP** 三种位图（`ALLOWED_SEARCH_MIME`，
  `search-ingest.ts` L67）。这个白名单名义上只约束搜索入库，但人工交稿没理由走得更宽。
- **SVG 不在其中且不要交** —— 外部 SVG 可以含 `<script>` 与外链资源，
  而素材 URL 会被直接嵌进导出页面并由 Chromium 渲染（同处 L63-64）。
- 落库统一转 **WebP，quality = 82**（`image.ts` L37），并额外生一张
  **宽 640** 的缩略图（`THUMBNAIL_WIDTH`，L31）。因此不要自己先转 WebP 再交：
  两次有损压缩叠加，而清晰度评分是在你交的那份上算的。
- 不要带 EXIF 旋转依赖：宽高取自 sharp 元数据，靠 EXIF Orientation 竖起来的横图
  会按横图的比例参与第 3 道门禁。

## 七、Hero 的版面规格（唯一有文字压图的角色）

### 7.1 `reserved_text_area` 是契约字段，不是建议

`BriefLayoutSchema`（`packages/schemas/src/ai-asset.ts` L45-49）：

| 字段                 | Hero               | 景点图 / 美食图 |
| -------------------- | ------------------ | --------------- |
| `reserved_text_area` | `LEFT_TOP`         | `NONE`          |
| `subject_area`       | `RIGHT_AND_BOTTOM` | `CENTER`        |
| `aspect_ratio`       | `16:6`             | `16:9` / `4:3`  |

取值由 `buildVisualBrief`（`packages/assets/src/visual-brief.ts` L159-164）按角色写定，
并有测试钉住（`preheat.test.ts` L60）。同处 L41-43 的注释说明了为何只有 Hero 需要：
模板在左上角压标题与日期，那块区域必须留白；景点图与美食图是卡片内配图，模板
不在图上压字。

提示词层面，「留白」必须说成**正向要求**（`visual-brief.ts` L215-221）：写成负向
提示词（`no subject in top left`）在多数供应商上会被理解为「不要左上角」而整体重构图。

### 7.2 两套模板对 Hero 的处理**完全相反**，而图只有一张

这是 Hero 制作最容易遗漏的约束。同一张 Hero 会在两种完全不同的版式里出现：

|          | `ink_paper_v1`                            | `blueprint_v1`                           |
| -------- | ----------------------------------------- | ---------------------------------------- |
| 是否满幅 | 满幅背景，`object-fit: cover`             | **不满幅**，框内图                       |
| 遮罩     | 有，100deg 渐变压暗                       | **无**                                   |
| 文字压图 | 是，左上，`max-width: 760px`              | **不压**，标题在纯色底上                 |
| 显示尺寸 | 整个 Hero 区（`padding: 48px 56px 40px`） | 宽 100%、**高 155px**                    |
| 代码     | `ink-paper-v1/daily/styles.css` L63-95    | `blueprint-v1/daily/styles.css` L112-126 |

`ink_paper_v1` 的遮罩确切值（同文件 L81-90）：

```css
linear-gradient(
  100deg,
  rgba(0, 0, 0, 0.62) 0%,
  rgba(0, 0, 0, 0.24) 58%,
  rgba(0, 0, 0, 0.05) 100%
)
```

**于是一张合格的 Hero 必须同时满足两件事：**

1. 左侧被压暗 62% 并盖上白字后，那块区域**不能有需要看清的细节**（否则白花钱）；
2. 在 `blueprint_v1` 里它是一张**高 155px、无遮罩、无文字的小图** —— 主体必须在
   这个尺寸下仍能认出来，且画面不能指望遮罩来压住杂乱。

具体作画指引：

- 主体（建筑、桥、山形）放**右侧与下方**，左上约三分之一宽度留作天空、墙面、水面这类
  低频区域；
- 左上不要放高对比的亮色块（压暗后变脏），也不要放大面积纯白（白字不可读）；
- 横向构图、不要居中对称：16:6 是很扬的画幅，居中主体在 155px 高的框里会只剩一条；
- 不要把主体顶到画面最下沿：`object-fit: cover` 在两套模板里裁切量不同。

### 7.3 景点图与美食图：主体居中

`subject_area: CENTER` + `reserved_text_area: NONE`。模板不在图上压字，因此不用留空，
且这两个角色的 `subject_score`（中心 50% 面积）与版面要求方向一致 —— 主体填满中心
既得分也好看。

## 八、画面禁止内容与配色

### 8.1 十二条禁止项

`NEGATIVE_REQUIREMENTS`（`packages/assets/src/visual-brief.ts` L52-71），按 11.3 分类：

| 类别            | 负向提示词                                                    |
| --------------- | ------------------------------------------------------------- |
| 不画标题        | `no text` `no title` `no captions` `no lettering`             |
| 不画门票价格    | `no price tags` `no numbers`                                  |
| 不画地图文字    | `no map labels` `no street signs`                             |
| 不画品牌 Logo   | `no logo` `no brand marks`                                    |
| 11.1 的其余三条 | `no watermark` `no malformed buildings` `no excessive people` |

用英文而不是中文是**技术选择而非审美选择**（L43-45）：图片模型的负向提示词在英文
语料上训练得最充分，而「`no text` 失效的表现是图上出现乱码假文字」—— 那正是
11.3 要防的东西。

> **这张表对人工选图同样适用。** 它字面上是给模型的负向词，但内容就是轨道 B 审核
> 时的筛选标准：带招牌文字、价格牌、品牌 Logo、水印的照片一样不能灌。
> 尤其是**水印**：带水印的图多半意味着授权没拿到。

**11.3 的第五条（不把 AI 景点图标记成真实照片）不在这张表里**（L47-50）—— 它不是
对模型的要求，而是对我们自己的要求，由 `representation_type = 'ILLUSTRATIVE'` 与
迁移 0005 的 `assets_ai_must_be_illustrative` 强制。灌库时就体现为一条规则：
`source_type = AI_GENERATED` 时 `representation_type` **必须**是 `ILLUSTRATIVE`（第五节清单表）。

### 8.2 配色按主题桶，不按目的地

`PALETTE_BY_BUCKET`（`visual-brief.ts` L101-115）给 13 个桶各三个色词：

| 桶                | 配色                                          |
| ----------------- | --------------------------------------------- |
| `canal_culture`   | fresh green / warm gold / soft blue           |
| `lake_scenery`    | misty blue / willow green / pale rose         |
| `old_town`        | warm grey / brick red / ink black             |
| `museum_art`      | off white / deep indigo / brass               |
| `food_street`     | warm amber / chili red / cream                |
| `mountain_nature` | pine green / stone grey / sky blue            |
| `temple_heritage` | ochre / vermilion / moss green                |
| `modern_city`     | steel blue / glass cyan / silver              |
| `night_view`      | deep navy / lantern gold / violet             |
| `garden_classic`  | jade green / white wall grey / dark tile blue |
| `coastal`         | turquoise / sand beige / coral                |
| `family_park`     | grass green / sunny yellow / sky blue         |

## 九、程序生成与编译期内联的三类

这三类不进 `assets` 表、不参与评分，也**不靠设计交付**。写在这里是为了回答两个问题：
它们的规格是什么，以及**为什么不要手工替掉它们**。

### 9.1 默认占位图（固定 3 张）

`PLACEHOLDER_SPECS`（`apps/generation-worker/src/assets/placeholders.ts` L43-77）：

| 角色                | 像素       | 画幅 | 渐变                | 文字       | cache_key                               |
| ------------------- | ---------- | ---- | ------------------- | ---------- | --------------------------------------- |
| `HERO_BACKGROUND`   | 1600 × 600 | 16:6 | `#2f6b52`→`#8fc0a9` | 主题背景   | `placeholder:v1:hero_background:16x6`   |
| `DESTINATION_PHOTO` | 1200 × 675 | 16:9 | `#3f5e78`→`#a9c3d6` | 暂无实景图 | `placeholder:v1:destination_photo:16x9` |
| `FOOD_IMAGE`        | 900 × 675  | 4:3  | `#8a5a2b`→`#e0c9a6` | 暂无美食图 | `placeholder:v1:food_image:4x3`         |

生成方式：sharp 渲染一段 SVG（L102-119）—— 45° 线性渐变矩形 + 居中白字
（`fill-opacity: 0.82`，字号 = 高/10）。文字用 SVG 叠加而不是 sharp 的文字 API：
后者依赖 pango/fontconfig，在 Alpine 与部分 Linux 镜像上缺失（L82-85）。

灌入命令在第五节：`pnpm assets:ingest -- --placeholders`。

**为何不要换成设计稿出图**（L13-18）：占位图的要求是「不假装是照片、能填住版位、
中文可读」。程序生成的产物在任何环境都一致，**视觉基线测试因此稳定**；
设计出图反而引入一个二进制夹具与「谁负责更新」的问题。

**为何它们不会被当成库素材误命中**（L87-100）—— 这一条值得读：不是靠 `quality_score`
压低（实测渐变图仍能拿到 0.6 左右 —— 清晰度接近 0，但曝光居中、边缘能量集中在
中间的文字上），而是靠**没有实体与目的地**：`entity_name` 为 null → `entity_match` = 0
→ 权重 0.35 直接归零，final 上限约 0.5～0.6，低于 0.65 阈值。

> 因此**不要给占位图补 `entity_name` 或 `destination_name`**。那会让它们从
> `STATIC_DEFAULT` 降级层爬到 `LOCAL_LIBRARY_MATCH` 层，于是渐变图以「库素材命中」
> 的身份出现在页面上，而指标一切正常。

### 9.2 图标（固定 19 个，编译期内联）

清单在 `packages/icon-library/scripts/generate.mjs` L31-42，注释写明「数量与名称都是契约，
不是约定」：

| 组   | 数量 | 键                                                                                                        |
| ---- | ---- | --------------------------------------------------------------------------------------------------------- |
| 模块 | 8    | `calendar` `food` `map` `route` `camera` `ticket` `budget` `tips`                                         |
| 时段 | 5    | `period-morning` `period-noon` `period-afternoon` `period-evening` `period-night`                         |
| 交通 | 6    | `transport-walk` `transport-transit` `transport-taxi` `transport-boat` `transport-bike` `transport-drive` |

**两类要求要分开看：一类校验你的源文件，一类渲染时直接盖掉你的值。**

第一类 —— `validate()` 对**源 SVG** 的硬校验（`generate.mjs` L62-68），不满足则
生成脚本直接失败：

| 项        | 要求                                | 行号   |
| --------- | ----------------------------------- | ------ |
| `viewBox` | 必须是 `0 0 24 24`                  | L63-64 |
| `stroke`  | 必须是 `currentColor`（继承文字色） | L66-67 |

第二类 —— `iconMarkup()` 在渲染时把这几项写在**外层 `<svg>`** 上
（`packages/icon-library/src/index.ts` L98-110），内部路径继承它们：

| 项                            | 值             | 行号     |
| ----------------------------- | -------------- | -------- |
| `fill`                        | `none`         | L103     |
| `stroke`                      | `currentColor` | L104     |
| `stroke-width`                | `1.6`          | L105     |
| `stroke-linecap` / `linejoin` | `round`        | L106-107 |

> 因此**源文件里自己写的 `stroke-width` 与 `fill` 会被盖掉**，不要指望靠它们调细粗；
> 反过来，按 1.6 描绘才能看到最终效果。渲染时只取 SVG 的**内部内容**
> （`innerContent()`，`generate.mjs` L102），外层标签整个丢弃。

**五类禁止写法**（`FORBIDDEN_PATTERNS`，L47-54）：`<image>` 引用外部位图、
`xlink:href` 或 `href="http..."` 外部引用、`<script>`、`font-family`（图标不该依赖字体）、
`<text>`（图标内不放文字，11.3）、`url()` 引用。
违反任一条就不再是「自包含」的图标，**PDF 导出或离线渲染时会失效**（L46）。

新增图标不是「丢个 SVG 进目录」：要同时改 `EXPECTED` 清单与消费端的映射表，
否则单测会报**孤儿图标**（`index.test.ts` 断言 19 个图标全部被三张映射表覆盖）。

运行期守卫：清单外的图标引用会让 `Icon` 组件渲染一个带 `data-icon-missing` 的占位方框，
被 `travel_icon_load_failure_total` 计数 —— 验收标准 5 要求它**恒为 0**，且有
`TravelIconLoadFailure` 告警（任意一次即告警，critical）。

### 9.3 模板预览图（每模板 1 张）

`apps/render-worker/tools/make-template-previews.mjs`，入口
`pnpm --filter @tps/render-worker previews`（L5）。

| 项   | 值                                                                    | 行号        |
| ---- | --------------------------------------------------------------------- | ----------- |
| 宽度 | **400px**（`PREVIEW_WIDTH`），高度按原图比例                          | L45         |
| 格式 | PNG，`palette: true` + `compressionLevel: 9`                          | L96         |
| 源   | 视觉基线的第 1 天（`BASELINE_DAY = 'day-01.png'`）                    | L53         |
| 输出 | `apps/web/public/images/templates/{templateId}.png`（下划线转连字符） | L59, L62-64 |

取第 1 天而不是随便一天是有理由的：第 1 天已覆盖全部区块与两种字体。
缺基线时脚本**明确报错而不跳过**（L81-86）。

预览图不入库，是静态资源；地址登记在模板目录的 `metadata.preview_image`（迁移
`0017_template_catalog.sql`），前端由模板选择器消费。

**因此改了模板样式后要重跑这个命令**，否则选择器上展示的是上一版的模样 ——
而那不会让任何测试变红。

### 9.4 明确不预制的：`ROUTE_MAP`

路线示意图是**程序生成的 SVG**，既不入种子清单（`seed-manifest.ts` 用独立枚举
`IngestableRole` 拦住，而不是靠 refine），也**不允许 AI 生成**（`AI_ASSET_TYPE_BY_ROLE`
的类型就排除了它，`visual-brief.ts` L73-79）。理由是 11.3：不让 AI 绘制地图文字。

## 十二、已知边界

**「≥ 80% 命中率」从未在生产规模验证过。** 门禁 #17 标的是 `manual`，需要真实流量。
650 这个数字来自 §19.5 的 50 × 12（代码修正为 13），不是测出来的。

**目的地清单本身是数据工作。** 仓库里只有一份 6 行的 example，与 fixture 对齐用于
本地打通链路。上线用的 50 个目的地要从真实地理编码源导出，与 TP-3-06 的种子素材同性质。

**轨道 B 没有规模建议。** 设计没说要灌多少张，因为它取决于轨道 A 的覆盖缺口 ——
而那个缺口只有上线后看 `travel_asset_resolution_total{strategy}` 的分布才知道。

**两条轨道都没有机器质量门禁（见 6.5）。** 没有任何自动化能拦住一批模糊的种子素材：
它们会以 `quality_score` 偏低的形式影响排序（权重仅 0.05），但在没有更好候选时
仍会被采用。审核的人就是那道门禁，这是设计选择而不是遗漏。

**`subject_score` 是近似，且与 Hero 的版面要求方向相反。** 它用「中心 50% 面积的边缘
能量占比」代替真正的主体分割（需要模型），而 Hero 的 `subject_area` 是
`RIGHT_AND_BOTTOM`。当前以版面为准（影响仅 final 的 1.5%），引入分割模型后
重算这一列即可，不影响其他列。

**遵照了版面规格不等于真的可读。** `ink_paper_v1` 把白字压在 Hero 左上，而
「遮罩后这行字到底看不看得清」没有任何自动化判定 —— 视觉基线用的是固定夹具图，
换成真实 Hero 后不会重跑。批量入库前抽几张真实图渲一次页面目检是目前唯一的手段。
