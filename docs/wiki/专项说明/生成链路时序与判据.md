## 1. API 同步路径：4 处不可交换的顺序

入口 [`travel-plans.ts:215`](../../../apps/api/src/routes/travel-plans.ts#L215)，前端调用点 [`api-client.ts:349`](../../../apps/web/src/lib/api-client.ts#L349)。

这一段**全程同步**，返回 201 之前不做任何昂贵工作。源码在 L202-213 用伪代码写出了整个幂等流程。

### 1.1 「先查既有幂等，再扣配额」

|        | 位置                                                               |
| ------ | ------------------------------------------------------------------ |
| 查既有 | [L302-310](../../../apps/api/src/routes/travel-plans.ts#L302-L310) |
| 扣配额 | [L339-350](../../../apps/api/src/routes/travel-plans.ts#L339-L350) |

**反过来会怎样**：用户刷新页面重试，命中幂等拿到原任务，但配额已经被再扣一次。
设计稿 21.4 明确「幂等命中不计入配额」。

### 1.2 「CR 预检在配额之后」

预检位置 [L371-386](../../../apps/api/src/routes/travel-plans.ts#L371-L386)。

**反过来会怎样**：余额为 0 的账号可以无限次触发「解析 + 校验 + 读价目 + 读余额」——
拦住它的每分钟 3 次与每 IP 每日限额都在配额层里。

代价是一次 402 会消耗一格日配额。这是有意接受的：CR 才是产品意义上的限额，次数配额已被提到兜底值。

### 1.3 「CR 预留在入队之前」

原子预留 [L430-449](../../../apps/api/src/routes/travel-plans.ts#L430-L449)，入队 [L451-470](../../../apps/api/src/routes/travel-plans.ts#L451-L470)。

**反过来会怎样**：Worker 可能在预留落库前就跑完并结算，而 `settle` 找不到 hold 会直接返回 ——
那次生成免费。

### 1.4 「预检只是省垃圾，预留才是闸门」

- 预检（L371）是普通读，**不防并发**；
- 预留是 `UPDATE ... WHERE balance_cr >= $n`（`packages/db/src/credit-wallet.ts`），查与扣之间无窗口，因此并发不会超发。

预检存在的唯一理由是**不留垃圾行**：建了任务行之后再拒，会留下一条 QUEUED 任务和一个被占用的幂等键，
用户充值后拿同一份表单重试会命中那个幂等键，拿到一个**永远不会跑的任务**。

走到预留才发现不足时（并发争抢），代码会 `cancelJob` 回滚刚建的任务行（L439）。

### 1.5 同步校验必须在入队之前

[`prepareTravelRequest`](../../../packages/planning/src/prepare-request.ts#L40) 三步：Zod 解析 → 标准化（纯计算，不会失败）→ N-01～N-12 冲突检查。

**判据**：一次 LLM 调用几分钱，而「出发日期在过去」这类错误在入队前就能拦住（源码 L286-290 的注释）。
校验失败直接 4xx，**不占用幂等键、不计配额、不入队**。

## 2. 三层幂等，最终真相在唯一索引

| 层                     | 位置                                                                       | 失效时的行为                             |
| ---------------------- | -------------------------------------------------------------------------- | ---------------------------------------- |
| Redis SETNX            | [L318-323](../../../apps/api/src/routes/travel-plans.ts#L318-L323)         | **fail open**：异常一律当成「抢到了」    |
| DB 唯一索引            | [L403-414](../../../apps/api/src/routes/travel-plans.ts#L403-L414)         | 捕获 `UniqueViolationError` → 回到查既有 |
| BullMQ jobId 去重      | [`plan-queue.ts:96`](../../../packages/queue/src/plan-queue.ts#L96)        | 同 jobId 在队列里只存一份                |
| Worker 侧 RedisJobLock | [`main.ts:214-217`](../../../apps/generation-worker/src/main.ts#L214-L217) | 抢不到直接返回，不等待                   |

锁 TTL = **300 秒**（[`idempotency.ts:140`](../../../packages/shared/src/idempotency.ts#L140)）。

**为什么 Redis 层必须 fail open**：13.8 规定唯一索引才是最终真相。若 fail closed，Redis 一挂全站无法生成计划。
反向的代价只是「重复提交时多走一次 INSERT 再回滚」。

**抢不到锁时返回 409 而不是等待**（L325-337）：等待会把 HTTP 请求挂住，并发一高就耗尽连接池。
客户端拿 409 + `x-tps-job-id` 后改为轮询。

**Worker 侧抢不到锁不等待**（`main.ts:214`）：等待会占住 BullMQ 的并发槽位。

## 3. 三层超时

定义在 [`job-deadline.ts`](../../../apps/generation-worker/src/job-deadline.ts)。

| 层            | 值                                     | 出处                                                                                | 越界表现                                             |
| ------------- | -------------------------------------- | ----------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 队列等待      | **600 秒**                             | [L29](../../../apps/generation-worker/src/job-deadline.ts#L29)                      | `FAILED` + `JOB_QUEUE_TIMEOUT`，判定是消费的第一件事 |
| 整个任务      | **300 秒**                             | [L26](../../../apps/generation-worker/src/job-deadline.ts#L26)                      | `FAILED` + `JOB_TIMEOUT`，在阶段边界判定             |
| 单次 LLM 调用 | env `LLM_TIMEOUT_MS`，且被压进剩余预算 | [`generate-plan.ts:284`](../../../apps/generation-worker/src/generate-plan.ts#L284) | 剩余为 0 时直接抛 `LlmTimeoutError`，不发请求        |
| 单素材槽位    | **800 毫秒**                           | [`selection.ts:38`](../../../packages/assets/src/selection.ts#L38)                  | 降级到下一层，不阻断                                 |

### 3.1 为什么是协作式而不是 `Promise.race`

`race` 只能让**等待**结束，不能让正在跑的工作停下：模型调用还在飞、数据库事务还在写。
一个「已经超时并置为 FAILED」的任务随后仍会写入 `travel_plan_versions` 与 `plan_presentations` ——
**那些行属于一个失败的任务，没有任何东西引用它们，也没人知道它们是怎么来的**（源码 L10-19）。

代价：最坏情况会超出 300 秒（正好卡在一次 LLM 调用上）。
压制手段是 `remainingFor()` 收紧下一次外部调用的超时 —— 剩 8 秒时不会再发一个 30 秒超时的请求。

### 3.2 排队时长必须由数据库算

`generation_jobs.created_at` 是数据库时钟的值，Worker 只有自己的 `Date.now()`。
两者相减是跨时钟比较，**实测中让总耗时算出了负数**（[L67-74](../../../apps/generation-worker/src/job-deadline.ts#L67-L74)）。

因此 `findJobQueueTiming` 返回已排队毫秒数，Worker 只做加法：
`sinceQueued() = queuedForMs + (now() - consumeStartedMs)`（[`generate-plan.ts:492-495`](../../../apps/generation-worker/src/generate-plan.ts#L492-L495)）。

### 3.3 `SAVING_PLAN` 刻意不检查超时

[L671-678](../../../apps/generation-worker/src/generate-plan.ts#L671-L678)：计划已生成并通过校验，落库只差一次 INSERT。

此刻因为超了 300 秒而丢弃它，等于把已花掉的模型成本连同用户的全部等待一起扔掉，而重试要从零再花一遍。
**超时的意义是「别再启动新的昂贵工作」，不是「把做好的东西扔掉」。**

## 4. 四层重试

完整定义在 [`retry-policy.ts:3-13`](../../../apps/generation-worker/src/retry-policy.ts#L3-L13)。

| 层          | 参数                                                        | 出处                                                                       |
| ----------- | ----------------------------------------------------------- | -------------------------------------------------------------------------- |
| 客户端      | 仅 `retryable: true`，指数退避基数 2 秒，上限 3 次          | `retry-policy.ts` 头注释                                                   |
| Worker 内部 | LLM / AI 图片 / 上传：指数退避 + 抖动，基数 1 秒，最多 3 次 | 同上                                                                       |
| 队列级      | `attempts: 3`，`exponential delay 5000`                     | [`plan-queue.ts:71-80`](../../../packages/queue/src/plan-queue.ts#L71-L80) |
| 不可重试    | `PLAN_HARD_CONSTRAINT_UNSATISFIABLE` 与全部 `REQ_*`         | [`main.ts:308-310`](../../../apps/generation-worker/src/main.ts#L308-L310) |

### 4.1 第四层为什么必须存在

队列层的 3 次会与任务内部的 LLM 重生成次数**相乘**。第四层把「重试也不会改变结论」的错误
用 BullMQ 的 `UnrecoverableError` 结束消费，**不占用 `attempts`**。
于是真正消耗 3 次重试的只剩瞬时失败（模型抖动、数据库连接被回收）。

### 4.2 失败必须抛错，不能静默返回

[`main.ts:300-319`](../../../apps/generation-worker/src/main.ts#L300-L319)：BullMQ 只按「消费函数是否抛错」判定成败。
静默返回会让一个失败的任务在队列里显示为成功 —— 排查时「任务失败了但队列说成功」是最难定位的一类不一致。

### 4.3 死信必须挂在 `failed` 事件上

[`main.ts:344-391`](../../../apps/generation-worker/src/main.ts#L344-L391)：消费函数内部不知道自己是不是最后一次尝试
（`attemptsMade` 在函数内还没自增）。
**漏掉最后一次的表现是「死信队列永远是空的」—— 看起来一切正常。**

重试耗尽时同时释放 CR 预留，坏账按 0 记（读不到那次消费的用量累加器）。

## 5. 协作式取消：零额外查询

`updateJobState` 的 SQL 带 `AND status <> ALL(terminal)`，因此任务被取消后，
**任何一次状态推进都会改 0 行并返回 false**（[`generate-plan.ts:196-208`](../../../apps/generation-worker/src/generate-plan.ts#L196-L208)）。

每个阶段边界本来就要写一次状态，那次写入的成败**同时回答了「这个任务还该继续吗」**。

**若改成轮询 `SELECT status`**：每阶段多一次往返，且查询与写入之间仍有窗口 ——
取消恰好落在窗口里就会被漏掉。

### 关键位置

取消检查放在**发出模型调用之前**（[L593-598](../../../apps/generation-worker/src/generate-plan.ts#L593-L598)）：
这是整条链路上唯一一次「不检查就会白花钱」的边界。用户点取消的动机多数是「我填错了」。

取消端点对已终态任务返回 **200 而不是 409**（[L541-545](../../../apps/api/src/routes/travel-plans.ts#L541-L545)）：
用户点取消的那一刻任务可能刚好完成，而他想要的结果（任务不再继续）**已经达成**。
响应带 `cancelled` 布尔告诉前端「本次调用是否真的改变了状态」。

## 6. 状态机的两条不变量

真相源 [`job-status.ts`](../../../packages/schemas/src/job-status.ts)，17 个状态。

### 6.1 只有两条回边

[`JOB_TRANSITIONS`](../../../packages/schemas/src/job-status.ts#L94-L119)：
`REPAIRING_PLAN → VALIDATING_PLAN`、`GENERATING_ASSETS → RESOLVING_ASSETS`。

**多一条回边就可能成环，而成环的表现是任务永远跑不完 —— 既不成功也不失败。**
`job-status.test.ts:163-183` 用 progress 值定序穷举全部边来守这条。

### 6.2 progress 单调不减

唯一实现点是 [`nextProgress`](../../../packages/schemas/src/job-status.ts#L138-L142) 的 `Math.max`。
回边 `REPAIRING_PLAN(54) → VALIDATING_PLAN(48)` 停在 54。

读路径也必须取库里的值而不是查表重算（[`travel-plans.ts:496-502`](../../../apps/api/src/routes/travel-plans.ts#L496-L502)）——
重算会在回边处把 54 显示成 48，进度条倒退会让用户以为任务重新开始。

`FAILED` / `CANCELLED` 的表值为 `null`，含义是**保持进入时的值**。

## 7. 生成阶段的内部阈值

### 7.1 历史检索（3.2.4）

[`retrieval.ts`](../../../apps/generation-worker/src/retrieval.ts) 的四个常量：

| 项                | 值                  | 出处                                                        |
| ----------------- | ------------------- | ----------------------------------------------------------- |
| 候选数            | Top 5（跨来源总数） | [L23](../../../apps/generation-worker/src/retrieval.ts#L23) |
| 余弦相似度下限    | 0.75                | [L25](../../../apps/generation-worker/src/retrieval.ts#L25) |
| `total_days` 容差 | ±3 天               | [L27](../../../apps/generation-worker/src/retrieval.ts#L27) |
| 超时              | 1500 毫秒           | [L29](../../../apps/generation-worker/src/retrieval.ts#L29) |

**三种情形都继续生成**并写入 `NO_HISTORICAL_REFERENCE` assumption：无 `place_id`、无命中、超时。
检索是**提高质量的输入，不是生成的前提** —— 空库时的首次生成必须成功，否则系统上线第一天就不可用。

**无 `place_id` 时不退化成按名称匹配**（[L88-100](../../../apps/generation-worker/src/retrieval.ts#L88-L100)）：
「杭州」与「杭州市」会被判为不同城市，而不同省的同名地点（朝阳）会被判为同一个 ——
后者意味着把辽宁朝阳的行程当作北京朝阳的参考塞进上下文。**宁可无参考。**

非超时异常**往上抛**（L125-130）：列权限被拒绝是隔离配置事故，被当成「无参考」吞掉会让它表现为「检索效果不好」。

### 7.2 分段生成（6.3）

| 项              | 值                                        | 出处                                                             |
| --------------- | ----------------------------------------- | ---------------------------------------------------------------- |
| 每段上限        | 7 天                                      | [`prompt.ts:45`](../../../packages/llm/src/prompt.ts#L45)        |
| max_tokens 分档 | ≤5 天 16384 / ≤10 天 32768 / ≤14 天 49152 | [`prompt.ts:26-30`](../../../packages/llm/src/prompt.ts#L26-L30) |

**分段串行而不是并发**（[`generate-plan.ts:381-386`](../../../apps/generation-worker/src/generate-plan.ts#L381-L386)）：
多段共享 21.4 的单任务成本上限，并发发出去时第一段超预算时第二段已在路上 —— 钱已经花掉。
段间还会再查一次 deadline（L408）。

14 天切成 7+7，**不留 0 天空段**（`prompt.ts:56-58`）：空段会让模型自己补一天，合并后天数比请求多，V-01 报 BLOCKING。

### 7.3 两级修复（3.2.2）

[`resolve-plan.ts`](../../../packages/planning/src/resolve-plan.ts)：

| 级             | 上限                             | 出处                                                      |
| -------------- | -------------------------------- | --------------------------------------------------------- |
| 程序化修复     | 3 轮／每次进入，纯函数无模型调用 | [L34](../../../packages/planning/src/resolve-plan.ts#L34) |
| LLM 定向重生成 | 2 次，**全任务累计**             | [L36](../../../packages/planning/src/resolve-plan.ts#L36) |

有**不动点提前退出**（[L151](../../../packages/planning/src/resolve-plan.ts#L151)）：`repairPlan` 返回 `changed: false` 时立即 break，跑满 3 轮只是浪费时间。

终态判定（[L186-206](../../../packages/planning/src/resolve-plan.ts#L186-L206)）：

- 仍有 BLOCKING 且含 V-30/V-31 → `PLAN_HARD_CONSTRAINT_UNSATISFIABLE`（**不可重试**）
- 仍有 BLOCKING 其余 → `PLAN_REPAIR_EXHAUSTED`
- 首轮零违规 → `READY`
- 其余 → `REPAIRED`，修不掉的 REPAIRABLE 降级为 assumptions 后放行

`REJECTED` 版本**先落库再置 FAILED**（[`generate-plan.ts:743-753`](../../../apps/generation-worker/src/generate-plan.ts#L743-L753)）：
顺序反了排查时拿不到那份草稿，而它是唯一能说明「模型到底写了什么」的证据。

### 7.4 素材解析并发

| 项             | 值  | 出处                                                                                         |
| -------------- | --- | -------------------------------------------------------------------------------------------- |
| 天级并发       | 8   | [`resolve-assets.ts:120`](../../../apps/generation-worker/src/assets/resolve-assets.ts#L120) |
| 单天内槽位并发 | 6   | [L121](../../../apps/generation-worker/src/assets/resolve-assets.ts#L121)                    |

单槽位异常一律被兜住转成 `FALLBACK`/`SKIPPED`（[L244-257](../../../apps/generation-worker/src/assets/resolve-assets.ts#L244-L257)）——

## 8. 计费在时序上的三个挂载点

| 挂载点          | 位置                                                                                | 记什么                                |
| --------------- | ----------------------------------------------------------------------------------- | ------------------------------------- |
| 每次模型调用后  | [`generate-plan.ts:351`](../../../apps/generation-worker/src/generate-plan.ts#L351) | `meter.addLlm(result.model, in, out)` |
| 编排结束 / 异常 | [L822-826](../../../apps/generation-worker/src/generate-plan.ts#L822-L826)          | AI 图张数、搜索次数、渲染页数         |
| 任务终态        | [`settleBilling`](../../../apps/generation-worker/src/generate-plan.ts#L1005-L1052) | 单一出口                              |

三处细节：

1. **token 在 schema 校验之前记**（L330-334）：那次调用的钱已经花了。只在解析成功后计数会让
   「模型一直输出不合规内容」这类最烧钱的故障在成本报表上完全不可见。
2. **用 `result.model` 而不是 `llm.model`**（L348-350）：故障转移下前者是真正出活的候选。
   拿主候选的名字计费会让「主候选挂了、更贵的备选顶上」被按主候选的价收。
3. **预算实例提到 `try` 之外**（L806-812）：编排抛异常时 AI 图已生成、钱已花，
   catch 分支里读不到它们的话「编排崩了」会变成「这次生成的图不要钱」。

`settleBilling` 的四条口径（源码 L987-997 有完整表格）：

```text
saved              settle    用户拿到了计划（13.3 可读即算拿到）
rejected           release   队列不重试它 → 已是终态
failed 不可重试    release   重试也是同样的结论
failed 可重试      保留      预留留给重试
cancelled          release   用户主动放弃
not_found          不动      用户已被清理，钱包随 FK 级联删除
already_terminal   不动      另一个消费者已结过
```

**结算失败不改变任务结果**（L999-1003）：整段包在 try 里。
此刻因为一次数据库抖动把任务判成失败，是拿一份做好的产物去换一条账目 ——
而账目还能靠预留过期与对账补，产物补不回来。

## 9. 已知边界

### 9.1 `GENERATING_ASSETS(82)` 在运行时不可达

状态机定义了它和它到 `RESOLVING_ASSETS` 的回边（`job-status.ts:105-107`），
但当前编排是 `RESOLVING_ASSETS` 直接到 `RENDERING_HTML`
（[`generate-plan.ts:838`](../../../apps/generation-worker/src/generate-plan.ts#L838) → [L947](../../../apps/generation-worker/src/generate-plan.ts#L947)）。
AI 出图发生在 `RESOLVING_ASSETS` 内部的降级链里。

保留该状态的代价是 `job-status.test.ts` 的「从 QUEUED 能到达每个状态」断言仍然通过，
但线上永远不会观测到 progress=82。

### 9.2 `RENDERING_HTML` 不产出任何东西

设计稿 16.1 把它描述为「渲染服务出 HTML 快照」，但 17.1 的渲染路由是按 `plan_version_id`
**实时**从库取 ViewModel 渲染的。源码 L902-932（R-35）记录了这个偏离：

生成快照反而有害 —— ViewModel 与快照会各自演化，「页面显示的内容」从此有两个真相源；
模板改版后旧快照还在，用户看到的是一个月前的排版。

因此这一阶段的实质工作是**确认可渲染**：`validationStatus === 'INVALID'` 才判失败。
17.3 的溢出检查需要真开浏览器，那发生在导出链路上。

### 9.3 `EXPORTING_PNG/PDF` 不属于生成任务

V1 的导出是用户主动发起的独立任务（13.5，`exports` 表 + render-worker）。
生成任务从 `RENDERING_HTML` 直达 `COMPLETED` —— 这条边在 16.1 的转移表里本来就存在。

### 9.4 展示编排失败不阻断，但用户会拿到「没有图的成品」

[L970-978](../../../apps/generation-worker/src/generate-plan.ts#L970-L978)：编排异常只记 error 日志，
返回 `saved` 并把任务留在 `SAVING_PLAN`。用户手里有完整文字行程（13.3 可读），
但 13.4 会一直 404 —— 而 13.4 的 404 同时覆盖「计划不存在」与「编排还没跑完」五种情况，
前端只能靠 13.2 的 `milestones.page_viewable` 区分。

### 9.5 未装配依赖时的静默降级

- `deps.presentation === undefined` → 任务停在 `SAVING_PLAN`，只 warn（[L800-804](../../../apps/generation-worker/src/generate-plan.ts#L800-L804)）；
- `deps.credits === undefined`（API）/ `billing === undefined`（Worker）→ **完全不计费**；
  两侧必须一起开，只开一侧的表现见 `main.ts:122-131`；
- `deps.plannerConfig === undefined` → 条件机器码回落到内置字典，
  而库里一旦有已发布配置，内置字典就**完全不参与判断**（`travel-plans.ts:70-105`）。

### 9.6 未实测项

`concurrency: 2`（[`main.ts:333`](../../../apps/generation-worker/src/main.ts#L333)）的依据是注释里的估算
（「一次主生成 + 最多 2 次重生成」的成本峰值），没有压测数据支撑。
调高它会同时放大数据库连接占用与 LLM 额度峰值。
