## 一、单位与配置

| 配置                         | 默认                   | 约束（`assertCreditConfig`，启动即校验，违者拒绝启动） |
| ---------------------------- | ---------------------- | ------------------------------------------------------ |
| `CREDIT_CR_PER_CNY`          | 1000（1 元 = 1000 CR） | 必须 > 0                                               |
| `CREDIT_SIGNUP_GRANT_CR`     | 9900（注册赠送）       | 必须 ≥ 0（0 = 不赠送）                                 |
| `CREDIT_HOLD_BUFFER_PERCENT` | 120                    | 必须 ≥ 100（低于 100 = 故意让结算超出预留）            |

- **CR 是唯一结算单位**。人民币只在两个地方出现：
  - 充值入口（`cnyToCredits`，**向下取整** —— 非整数余额会让后续整数运算失去前提）
  - 展示（`creditsToCnyText`，**返回字符串** —— 禁止调用方拿浮点做算术）
- `holdAmount(estimated) = ceil(estimated × holdBufferPercent / 100)`。
  放大是因为估算依赖若干「运营可改」的量（模型池候选数、`QUOTA_*_AI_HERO`），
  配置漂移时预留不足会让结算把余额扣成负数 —— 余额有 `>= 0` 的 CHECK，
  那会让结算事务失败、任务卡在终态之前。

## 二、价目表（PriceBook）

- **三类 SKU**：
  - 固定 SKU：`plan.base_fee`、`render.page`、`export.png`、`export.pdf`、`image.ai_generate`、`image.search`
  - 模型 SKU：`llm.in:{model}`、`llm.out:{model}`、`embedding.in:{model}`
- **版本化**：版本 1 = 占位版（seed），算「还没配价」→ 不计费；
  发布 2 以上立即生效（不改代码、不重启）。
- **缓存 60 秒**（`PRICE_BOOK_CACHE_MS`，API 与 Worker 各一份，按版本缓存 ——
  同一进程在跑的任务可能锁着调价前后的不同版本）。
- **未登记模型** → 兜底价（`SKU_FALLBACK_MODEL`）+ 记 `unpriced`；
  固定 SKU 没有兜底（它没有「变体」概念）。
- **价目缺失** → 不收费 + 记 `unpriced`。理由是：结算发生在任务终态，
  抛错会让任务卡在「已生成好却永远看不到」—— **少收一笔远好于弄丢一份产物**。

## 三、生成计费：报价 → 预留 → 计量 → 结算/释放

### ① 报价（`CreditsService.quote`，只收 `totalDays`）

| 量       | 公式                                                        |
| -------- | ----------------------------------------------------------- |
| LLM 输入 | `⌈天数/7⌉ × (1+重生成) × 天数 × estInputTokensPerDay(3000)` |
| LLM 输出 | `⌈天数/7⌉ × (1+重生成) × maxTokensForDays`                  |
| 嵌入     | 固定 1000                                                   |
| AI 图    | ≤ `MAX_AI_IMAGES_PER_JOB`（3）                              |
| 图搜     | ≤ `MAX_IMAGE_SEARCHES_PER_JOB`（8）                         |
| 渲染页   | **1 + 天数**（N+1 固定，与模板无关）                        |

产出两个数：**typical**（0 次重生成，用于预留）与 **ceiling**（含最多
2 次重生成，只展示与提前警告）。**预留取典型值** —— 拿上界当预留额会让
9.9 元买不了一次 14 天行程（实测上界是典型值的 2～2.7 倍）。

估算默认值与 Worker 侧常量**必须相等**（由 generation-worker 的测试断言）——
估得比实际上限低会预留不足，结算把余额扣成负数，事务失败，任务卡住。

### ② 预检 + 预留（生成路由内，顺序严格）

```text
配额 → 预检(checkJob) → 建任务行 → 原子预留(reserve) → 入队
```

- **预检不是闸门**。它只是把「余额不够」这个绝大多数情形挡在建行之前
  （避免留下一行 QUEUED 死任务和一个被占用的幂等键）。真正的闸门是
  `reserve` 里 `UPDATE … WHERE balance_cr >= $n` —— 查扣之间没有窗口，
  并发不超发。
- **预留不写流水**（钱还在账上，只是从可用挪到冻结）。写一条 SPEND 会让
  「求和 = 余额」这条自校验失效，也让用户在流水里看到一笔尚未发生的消费。
- 预检通过但并发抢走余额 → `cancelJob` + 402（不留永远不会跑的任务）。

### ③ 计量（`UsageMeter`，每任务一个实例）

六维：LLM 输入/输出（按模型聚合）、嵌入、AI 图、图搜、渲染页。
**失败的调用不计费**（打点挂在 `outcome === 'succeeded'` 之后）——
假设错了只是少收，反过来（把失败也收）会让一次上游故障变成用户账单上
的一笔莫名支出。按模型聚合而不逐次留一条：结算只需要「每个模型各用了
多少」，逐次留存的价值在排查，而排查已有指标与结构化日志。

### ④ 结算（`JobBilling.settle`，任务成功时）

- **按预留锁定的价目版本计价** —— 「已提交的任务不受调价影响」。
- 三种情形（同一事务，`credit-wallet.settle`）：
  1. `actual ≤ hold`：从冻结扣，**差额退回可用**
  2. `actual > hold`：冻结全扣，超出从可用继续扣
  3. **可用也不够**：扣到 0，剩下的记 `WRITE_OFF` **平台承担**
     （把余额扣成负会撞 CHECK，事务失败，任务卡在终态之前）
- **服务费（`plan.base_fee`）只在成功时收** —— 用户没拿到东西不该付服务费。
- 无预留 → 不扣费（`replayed`，0013 之前的存量任务）。
- 价目版本查不到 → **按 0 结算但预留照常释放**。这两个 `null` 刻意分开
  （`priceJob` 返回 null = 没有预留；`priced: null` = 有预留但算不出钱）——
  混成一个的后果是价目数据一出问题，用户的预留就再也不释放，钱冻到过期。

### ⑤ 释放（`JobBilling.release`，不可重试失败 / 用户取消）

预留全额退（`refunded`），烧掉的供应商成本记 `WRITE_OFF`。
**坏账口径不含服务费** —— 那是我们的收入项，不是烧掉的成本，
含进去会让「上游故障烧了多少钱」这个告警依据虚高。

### ⑥ 可重试的失败：什么都不做

释放了的话，BullMQ 重试成功时 `settle` 找不到 ACTIVE 预留 → 按 C-2
**不扣费** —— 于是「失败一次然后成功」的任务全都免费（持续漏钱且不可见）。
因此预留跨重试保留；重试耗尽由队列 `failed` 事件释放；进程 SIGKILL 由
`expires_at` 兜住。代价是失败那次烧掉的成本只进日志不进 WRITE_OFF 流水
（那一笔必须与释放同事务，否则重试成功后出现「既结算又坏账」的矛盾记录）。

## 四、导出计费

- **固定 SKU**（`export.png` / `export.pdf`），与内容、页数、模板完全无关 ——
  因此**不做预留/结算往返**，请求时一次原子扣减（`chargeExport`）。
- 幂等键 `export:{key}`（复用导出自己的幂等键）—— 重复请求、并发请求只扣一次。
- **在建行之前扣**：反过来余额不足时会留下一行永远不会渲染的导出任务
  占着幂等键，用户充值后重试会拿到那一行。
- 余额不足 → 402 且不动钱；缺价目 → `free` + warn 日志。

**退款有三条路径，各管一段**：

| 路径                     | 时机                          | 实现                                                                                                                                                                                   |
| ------------------------ | ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API 侧 `refundExport`    | 建行失败（非并发冲突）        | 用户看到的是 500，不会想到查流水；并发撞唯一索引不退款（胜出者真的产出了任务）                                                                                                         |
| Worker 侧 `refundFailed` | 渲染彻底失败（`FAILED`）      | **回查当时那条 SPEND 的金额，不现算** —— 调价窗口内现算会退错数（少退是赖账，多退是可反复触发的漏洞）；幂等，`markRendering` 只从 QUEUED 转 RENDERING，FAILED 是终态，重投直接 skipped |
| 不退                     | `PARTIAL`（至少一页渲染成功） | 用户手上有文件，那一笔钱对应的服务确实交付了，只是少了几页                                                                                                                             |

## 五、边界情况清单

| #   | 情形                          | 处理                                                                                                                                                                                         |
| --- | ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 匿名用户                      | 三个计费端点 403（返回「余额 0」会让前端画一个永远不够用的钱包，用户无从知道该注册）；生产上匿名入口默认关闭（`FEATURE_ANONYMOUS_ENABLED`）；测试环境匿名生成照常（与模板正交，见第六节 B4） |
| 2   | 无价目表 / 全零价             | `free` 放行 —— 降级方向必须是免费而不是 503（那等于「运营还没配价格，全站不能生成」）                                                                                                        |
| 3   | 占位版（版本 1）              | 视为未配价，生成与导出都不收费                                                                                                                                                               |
| 4   | 未登记模型                    | 兜底价 + `unpriced` 告警指标（按 SKU 域基数封顶）                                                                                                                                            |
| 5   | 余额恰好等于预留              | 通过（边界是 `>=` 不是 `>`）                                                                                                                                                                 |
| 6   | 结算超支                      | WRITE_OFF 平台承担；恶意用户拿最低余额反复触发高成本任务由次数配额挡住（那两层配额不删的价值）                                                                                               |
| 7   | 并发结算（重投 + 原任务）     | `FOR UPDATE` 串行，第二个看到 SETTLED 状态走重放分支，从流水读回原金额                                                                                                                       |
| 8   | 结算流水已存在但预留仍 ACTIVE | 抛错回滚 —— 两步在同一事务，走到这里说明有人绕过方法写流水                                                                                                                                   |
| 9   | 匿名归并                      | 赠送幂等键 `signup:{user_id}`，匿名原地升级不重复拿赠送                                                                                                                                      |
| 10  | 发放失败                      | 不抛错 —— 注册已成功，抛错会让用户重复注册撞「该账号已注册」                                                                                                                                 |
| 11  | 预留过期                      | `expires_at` 兜底（进程 SIGKILL 时队列事件也没走到）                                                                                                                                         |
| 12  | 导出渲染失败                  | `FAILED` → 退款（回查当时扣的金额，幂等）；`PARTIAL` → 不退（用户手上有文件）                                                                                                                |

## 六、模板与计费的解耦（B1-B4，2026-08-29 钉住）

产品决策：模板只在生成前选一次，结果页不提供换模板（见
[多样式模板方案](多样式模板方案.md) 第五节）。计费侧的结论是
**模板不参与定价** —— 这是机制事实，不是待开发的需求：

- 两个计费点（`quote` / `checkJob`、`chargeExport`）的入参都不含
  `template_id`
- `renderPages = 1 + 天数` 固定，模板只改版式不改页数
- 平台侧成本差异（`blueprint_v1` 日页矮 38%、14 天 PDF 从 28 页降到 14 页）
  由平台吸收，不进用户定价

四条守卫把这个事实钉住，防将来有人为「按模板差异化定价」改函数签名
而没有任何编译期或运行期信号（报价端点照常工作，只有账单悄悄变了）：

| #   | 守卫                                                                                 | 文件                                                      |
| --- | ------------------------------------------------------------------------------------ | --------------------------------------------------------- |
| B1  | `quote`/`checkJob` 签名不含模板参数（`.length`）+ 同一入参报价确定                   | `apps/api/src/credits/credits.test.ts`                    |
| B2  | `chargeExport` 签名不含模板参数 + 同一格式重复导出扣费相同                           | 同上                                                      |
| B3  | `renderPages = 1 + totalDays`（1/3/7/14 天遍历）+ 估算函数签名不含模板               | `packages/billing/src/billing.test.ts`                    |
| B4  | 匿名 × 非默认模板的正交（并入 pipeline 的 blueprint 端到端用例，它本来就是匿名提交） | `apps/generation-worker/src/pipeline.integration.test.ts` |

**`.length` 的局限**：对对象参数函数，往对象里加一个键不会改变 `.length` ——
因此每条签名守卫旁都配了行为断言（同一入参结果确定）互补。
B1 的反证做过：给 `quote` 加 `templateId` 参数 → 守卫红。

## 七、运营配置指南

前六节讲的是「钱是怎么算出来的」，这一节讲「那些数从哪里来」：上线前要配什么、
改一个数会波及到哪里、改完怎么确认真的生效。**告警响了之后的处置不在这里**，
在[运维手册](../../运维手册.md)的「坏账速率异常」「有SKU没配价」「余额不足占比升高」三节。

### 三处配置面，生效方式完全不同

| 面         | 载体                                                    | 改它的人   | 生效                         |
| ---------- | ------------------------------------------------------- | ---------- | ---------------------------- |
| 开关与旋钮 | env（`CREDIT_*`）                                       | 部署       | **重启进程**，且三侧要一起改 |
| 价目表     | Postgres `credit_price_versions` / `credit_price_items` | 运营跑 SQL | ≤ 60 秒，**不改代码不重启**  |
| 单用户余额 | `pnpm user:credit -- --grant`                           | 值班       | 立即                         |

价目表是唯一能热改的计费面 —— 这正是它在数据库而不在 env 的理由（另一半理由是可回放：
`credit_ledger.price_version` 能回答「那一单是按哪一版价格结算的」）。

### env 清单：谁读它、改它波及什么

| 变量                              | 默认    | 读它的进程                            | 改它的波及面                                                                                        |
| --------------------------------- | ------- | ------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `CREDIT_BILLING_ENABLED`          | `false` | api、generation-worker、render-worker | 三侧必须一致，见下「打开计费的顺序」                                                                |
| `CREDIT_CR_PER_CNY`               | 1000    | api、`user:credit`                    | **等于给存量余额重新标价**：库里存的是 CR，比率变了同一个余额就是另一个金额。代码刻意不提供折算函数 |
| `CREDIT_SIGNUP_GRANT_CR`          | 9900    | api                                   | **只影响此后注册的人**。存量用户要 `pnpm user:credit` 逐个补                                        |
| `CREDIT_HOLD_BUFFER_PERCENT`      | 120     | api                                   | 只放大**预留**，不改结算金额；调高 = 多冻多退，代价是余额利用率                                     |
| `CREDIT_EST_INPUT_TOKENS_PER_DAY` | 3000    | api                                   | 报价与预留的输入 token 经验值                                                                       |
| `CREDIT_EST_MAX_AI_IMAGES`        | 3       | api                                   | 同上                                                                                                |
| `CREDIT_EST_MAX_IMAGE_SEARCHES`   | 8       | api                                   | 同上                                                                                                |
| `CREDIT_EST_MAX_REGENERATIONS`    | 2       | api                                   | 同上                                                                                                |

两件从代码里才看得出来的事：

- **除了总开关，其余七个只在 api 的运行路径上生效**（`loadCreditConfig` / `loadJobLimits`
  只在 `apps/api/src/main.ts` 被调；CLI 另读其中两个，只为把 CR 折成元打印出来）。
  worker 侧的结算不看这些值 —— 它按预留锁定的价目版本算。
  因此调旋钮只重启 api 就够，**但改总开关必须三侧一起**。
- **`CREDIT_EST_*` 四个只能往上调。** 它们只进估算，worker 的真实上限是代码常量
  （`MAX_AI_IMAGES_PER_JOB` / `MAX_IMAGE_SEARCHES_PER_JOB` / `regeneration_count` 的 CHECK）。
  `billing-limits.test.ts` 守的是 `DEFAULT_JOB_LIMITS` 这组**默认值**，**env 覆盖不在它的覆盖面内**，
  `assertCreditConfig` 也不看它们。把 `CREDIT_EST_MAX_AI_IMAGES` 配成 1 不会有任何信号，
  只会让每个任务少预留两张图的钱，差额进坏账。

两组**不是**计费参数但常被认错的旋钮：

- `AI_IMAGE_DAILY_BUDGET`（600）与 `IMAGE_SEARCH_DAILY_BUDGET` 是**平台侧日预算熔断**，
  熔断后用户少用→少收→多退，方向安全，不需要与 `CREDIT_EST_*` 联动；
- `QUOTA_*`（每分钟 / 日 / 月 / IP / 每计划导出）是**次数**闸门，与 CR 并存。
  价目表被配成 0 或停在占位版时货币闸门完全失效，**次数闸门是那时候唯一还站着的**。

### 上线前必须一起定的四个数

1. **`llm.out:*`** —— 输出 token 占报价 60~75%，它单独决定产品的价格带，比其余八项加起来都重要；
2. 其余八项 SKU（包含具体模型的 `llm.in:<model>` / `llm.out:<model>`）；
3. **兜底价 `:*` 必须高于所有已登记模型**。报价走的就是兜底 SKU（`SKU_FALLBACK_MODEL`，
   因为 API 不知道 worker 的模型池会选中谁）—— 兜底比真实模型便宜就是**系统性预留不足**，
   而不是偶发偏差；
4. **`CREDIT_SIGNUP_GRANT_CR` 与最长行程的上界的关系**。判据与迁移 0014 同一条：
   **14 天的上界（含 2 次重生成）要落在赠送额之内**。只保证典型值不超不够 ——
   那会让「重生成两次」变成一个只在特定条件下出现的 402，而它恰恰最难复现。

第 4 条已经被违反过一次，而那次违反就是现在这三个版本语义的来历：

| 版本 | 来源                | 行为                                                             | 判定                     |
| ---- | ------------------- | ---------------------------------------------------------------- | ------------------------ |
| 1    | 迁移 0013（占位）   | **完全不计费** —— 占位价下 14 天要冻 10578 CR > 9900 CR 的赠送额 | `isSeedPriceBook`        |
| 2    | 迁移 0014（开发期） | 计费，但启动打一条 warn（只一条，不重复）                        | `isProvisionalPriceBook` |
| ≥ 3  | 运营 clone 改价     | 计费，无 warn                                                    | 两个判定都 false         |

**改价必须 clone 到新版本号，不要原地改版本 2** —— 版本号就是判据，
在版本 2 上改价等于「改完了系统仍然认为这是开发期定价」，那条 warn 会一直响。

### 改价的标准动作

```sql
SELECT clone_credit_prices(2, 3, '按 2026Q3 供应商报价重定');

UPDATE credit_price_items i SET price_cr = 15000
FROM credit_price_versions v
WHERE i.version_id = v.id AND v.version = 3 AND i.sku = 'llm.out:*';
-- 登记具体模型（模型池里有一个就要有一行，否则它按兜底价收）
INSERT INTO credit_price_items (version_id, sku, unit, price_cr)
SELECT v.id, 'llm.out:<model>', 'PER_MILLION_TOKENS', 12000
FROM credit_price_versions v WHERE v.version = 3;

-- 发布前最后一眼：逐项看一遍草稿，没改到的项会原样留着上一版的数
SELECT sku, unit, price_cr FROM credit_price_items i
JOIN credit_price_versions v ON v.id = i.version_id WHERE v.version = 3 ORDER BY sku;

SELECT publish_credit_prices(3);
```

- 发布是单事务：原发布版自动归档，目标草稿变发布版（`credit_price_one_published_uk` 保证同时只有一个）；
- **最多 60 秒生效**（`PRICE_BOOK_CACHE_MS`，api 与 worker 各缓存一份）；
- **已提交的任务不受影响**：`credit_holds.price_version` 锁住了结算用的版本；
- 回滚**不是一句 publish**：刚被顶下来的版本已是 `ARCHIVED`，而 `publish_credit_prices`
  只接受 `DRAFT`。完整两句见[用户货币与计费](../../用户货币与计费.md)第八节「回滚不是一句 publish」。

### 打开计费的顺序

顺序不能换 —— 每一步都在拿掉上一步的一种全站故障：

```bash
pnpm db:migrate                                    # 到 0014
psql -c "SELECT version, count(*) FROM credit_prices_current GROUP BY version;"
                                                   # 期望：一个版本，≥ 9 行
pnpm user:credit -- --phone 138... --grant 9900     # 存量用户先授额
# 三个进程同时 CREDIT_BILLING_ENABLED=true 并重启，核对三份启动日志的 credit_billing_enabled
```

跳过步骤的后果：未迁移就开 → 每个生成请求与会话查询都撞「`credit_wallets` 不存在」（全站不可用）；
未授额就开 → 存量用户全部立即无法生成；三侧不一致的三种后果见
[用户货币与计费](../../用户货币与计费.md)第十节「三侧开关必须一起开」。

### 单用户处置

```bash
pnpm user:credit -- --email a@b.com                            # 查余额、冻结额与最近 10 条流水
pnpm user:credit -- --phone 13800000000 --grant 9900 --note "工单 123"
```

四条约束：只收 CR 不收元（`--grant 9.9` 与 `--grant 9900` 长得同样合理而差 1000 倍）；
超过 1000 元（`MAX_GRANT_CR` = 1000000 CR）需 `--force`；幂等键是随机 UUID，因此
**重跑会再授一次**（命令末尾打印余额，人能当场看出）；多授出去的 CR **没有撤销入口**。

不要为个别用户改 env 或价目表 —— 那两层是全局的。

### 会静默漏钱的五种配置错误

启动校验只拦得住四条：`optionalInt` / `optionalBool` 的类型非法值，与 `assertCreditConfig`
的三条（`CR_PER_CNY > 0`、`SIGNUP_GRANT_CR ≥ 0`、`HOLD_BUFFER_PERCENT ≥ 100`）。
下面这五种**一条都拦不住**，而它们的共同点是：出问题时没有任何东西会失败。

| 配置错误                                   | 症状                                                     | 唯一的可见信号                                      |
| ------------------------------------------ | -------------------------------------------------------- | --------------------------------------------------- |
| 价目表停在版本 1                           | 全站不收费                                               | `travel_credit_gate_total{outcome="free"}` 那条曲线 |
| 价目表停在版本 2                           | 按开发期价收（偏低）                                     | 启动日志那**一条** warn，之后不再打                 |
| 加了模型没配价                             | 按兜底价收，连兜底都没则完全免费                         | `travel_credit_unpriced_total{domain}`              |
| `CREDIT_EST_*` 被下调 / 兜底价低于真实模型 | 预留系统性不足，差额进坏账                               | `TravelCreditWriteOffHigh`（滞后一小时）            |
| 三侧开关不一致                             | 只开 api：钱冻到 2 小时后过期；只开 worker：一次都不收费 | 三份启动日志的 `credit_billing_enabled`             |

这也是为什么改完配置要主动看一眼，而不是等告警：上面五条里只有两条有告警，
而那两条都滞后至少 15 分钟。

### 改完之后的验证

1. `SELECT version, count(*) FROM credit_prices_current GROUP BY version;` —— 版本号与项数对上；
2. 等 60 秒后请一次 `POST /api/v1/credits/quote`（`{ total_days: 14 }`）—— 看 `typical` / `ceiling` /
   `hold` 三个数，并确认 `hold ≤ CREDIT_SIGNUP_GRANT_CR`；这个端点就是结算用的同一套估算，
   因此它是唯一权威口径（不要拿手算的数对）；
3. 跑一次真实生成，确认流水出现一条 `SPEND`、`held_cr` 归零；
4. 看 `travel_credit_gate_total` 的 `outcome` 分布：`free` 消失 = 计费真的开始生效了。

### 症状 → 先查哪个配置

| 症状                   | 先看                                                                 | 然后                         |
| ---------------------- | -------------------------------------------------------------------- | ---------------------------- |
| 全站不收费             | `credit_prices_current` 的 `version`（1 = 占位，被归一成「未配价」） | 上面「改价的标准动作」       |
| 改了价没生效           | 是否真的 `publish` 了（`DRAFT` 不生效）；不足 60 秒就是缓存          | 同上                         |
| 新用户点 14 天直接 402 | 14 天的预留额 vs `CREDIT_SIGNUP_GRANT_CR`                            | 上面第 4 条判据              |
| 坏账升高               | `CREDIT_HOLD_BUFFER_PERCENT`、`CREDIT_EST_*`、兜底价是否偏低         | 运维手册「坏账速率异常」     |
| 某模型免费或偏贵       | 该模型的 `llm.in/out:<model>` 有没有登记                             | 运维手册「有SKU没配价」      |
| 402 占比 > 20%         | `llm.out:*`、赠送额                                                  | 运维手册「余额不足占比升高」 |

最后一条，它不在任何旋钮里：**不要用 `plan.base_fee` 去「补回」坏账**。
坏账的根因是估算不准，而那么改是向所有正常用户收一笔本该我们承担的钱。
