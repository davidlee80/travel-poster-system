# 专项说明

Wiki 正文（`01`～`08`）负责**广度**：一次请求怎么穿过系统、哪个文件干什么、改动要联动哪些地方。
每篇都刻意压在 100 行上下，为的是能一口气读完。

这个目录负责**深度**：单个子系统的判据、阈值、以及每个取舍背后的理由。

## 分工规则

|          | Wiki 正文 `01`～`08`         | 本目录                           |
| -------- | ---------------------------- | -------------------------------- |
| 回答     | 「在哪、有什么、改了要动谁」 | 「为什么是这个值、不满足会怎样」 |
| 长度     | 约 100 行，可通读            | 不限，按需跳读                   |
| 索引方式 | 编号 + 阅读顺序              | 按主题，无顺序                   |
| 更新时机 | 结构变化时                   | 阈值、判据、降级语义变化时       |

**两边不重复清单。** 正文里的表格给「文件路径」，本目录给「那个文件里的数字与判据」。
一份专项说明如果开始复制正文的文件清单，说明边界画错了。

## 写作要求

1. **每个数字标出处** —— 文件 + 行号。没有出处的数字会在下一次重构后变成谣言，
   而谣言比缺失更贵：缺失会让人去查代码，错的数字会让人直接照它做决定。
2. **写「不满足会怎样」** —— 一条阈值的价值不在它是多少，而在越过它之后的表现。
   这也是判断该不该改它的唯一依据。
3. **标注核实日期与设计稿版本** —— 读者据此判断可信度。
4. **已知边界单独成节** —— 未实测项、假实现默认值、缺失的告警。
   一份只写「系统如何工作」的文档会让人以为没有边界。
5. **冲突时以代码为准**，并回来订正本文。
