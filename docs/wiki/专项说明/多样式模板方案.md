## 零、先纠正一个概念错位

「模板」这个词在代码里与在产品语义里指的不是同一样东西，这是本方案要处理的
第一件事。

**产品语义**（本方案采用）：

```text
样式模板 ink_paper_v1
├── 全览页布局   page_type = FULL_PLAN
└── 每日页布局   page_type = DAILY_POSTER
```

**代码现状**（[enums.ts L376](../../../packages/schemas/src/enums.ts)）：

```ts
export const TEMPLATE_ID_VALUES = ['travel_infographic_v1', 'travel_full_plan_v1'] as const;
```

这两个值是**页型**而不是样式：`travel_infographic_v1` 是每日页，
`travel_full_plan_v1` 是全览页。页型被编码进了模板 ID。

后果是今天**同一份计划的展示数据带两个不同的 `template_id`**
（[presentation-plan.ts L54-55、L65](../../../packages/presentation/src/presentation-plan.ts)）：

```ts
const daily: PresentationPlan[] = days.map((day) => ({
  template_id: dailyTemplateId,     // 'travel_infographic_v1'
  page_type: 'DAILY_POSTER',
  ...
{
  template_id: fullTemplateId,      // 'travel_full_plan_v1'
  page_type: 'FULL_PLAN',
```

按产品语义这是错的：一份计划的所有页应当共享同一个 `template_id`，靠
`page_type` 区分页型。

### 好消息：schema 早就是按产品语义建的

[0005_assets.sql L220-221](../../../infrastructure/migrations/0005_assets.sql)：

```sql
CREATE UNIQUE INDEX plan_presentations_uk
  ON plan_presentations (plan_version_id, template_id, page_type, COALESCE(day_number, -1));
```

`template_id` 与 `page_type` 是**两个独立的列**。schema 表达的正是
「一个模板 × 多种页型」，只是枚举值把页型塞进了模板 ID，浪费了这个设计。

**因此不需要改表结构，只需要纠正枚举值的语义**（第六节的存量迁移）。

## 二、三个潜伏缺陷（P0，与模板选型无关）

**今天不出问题只因为「每个页型恰好一行」。** 第二个同页型模板一存在，
这三处立刻出错。它们必须在加模板之前修 —— 否则后面所有问题都会被归因错。

### 缺陷一：渲染读路径是不确定行为

[presentations.ts L237-246](../../../packages/db/src/presentations.ts)，
`findPresentationByVersion` 正是渲染路径用的那个：

```sql
WHERE pr.plan_version_id = $1
  AND pr.page_type = $2
  AND ($3::int IS NULL OR pr.day_number = $3::int)
  AND v.status IN ('READY', 'REPAIRED')
LIMIT 1          -- 没有 ORDER BY，也不按 template_id 过滤
```

**不满足会怎样**：两个同页型模板并存时 PostgreSQL 不保证返回哪一行。
同一次导出的 PNG 与 PDF 都可能取到不同模板 —— 而两者都会被判为「成功」。

### 缺陷二：`listDayNumbers` 返回重复天数

[presentations.ts L265-267](../../../packages/db/src/presentations.ts)：

```sql
SELECT day_number FROM plan_presentations
 WHERE plan_version_id = $1 AND page_type = 'DAILY_POSTER' AND day_number IS NOT NULL
 ORDER BY day_number
```

**不满足会怎样**：两个模板 → 14 天变 28 行 →
[run-export.ts L119-121](../../../apps/render-worker/src/run-export.ts) 的
`pagesFor` 渲染 28 页。导出时长翻倍、按页计费翻倍，而任务状态是 COMPLETED。

### 缺陷三：指标会说谎

[render-metrics.ts L176](../../../apps/render-worker/src/render-metrics.ts)：

```ts
template_id: TEMPLATE_BY_PAGE_TYPE[input.pageType]
```

从硬编码映射表算，**不读实际值**。用户选了模板 B，指标仍报 A。

`listBindings`（[presentations.ts L333](../../../packages/db/src/presentations.ts)
`WHERE b.plan_version_id = $1`）同样不过滤 template。它当前的使用边界已在
[图片与素材全链路](图片与素材全链路.md) 里写明「不得用于渲染」，因此不构成
渲染缺陷，但多模板后它的返回值会含多套绑定，调用方必须自己过滤。

## 三、两项已定决策

### 决策一：`template_id` 正名为「样式套件 ID」

一个 `template_id` 覆盖全览页与每日页，靠 `page_type` 区分。

不采用「每页型一个 ID」的扁平扩展（如
`travel_infographic_kraft_v1` + `travel_full_plan_kraft_v1`）：那样每加
一种样式要加两个枚举值，而「这两个值属于同一套样式」这件事没有任何地方表达
—— 靠命名约定维持的关系会在第三种样式时失效。

代价是存量数据要迁移（第六节）。

### 决策二：多模板共享同一套 `visual_constraints`

新模板可以改配色、字体、排版、留白、卡片形状；**不能改画幅与最小宽度**。

**不满足会怎样**：缓存键含画幅
（`hero:v1:{destination}:{theme_bucket}:{visual_style}:{aspect_ratio}`，
见 [图片与素材全链路](图片与素材全链路.md)）。若新模板把 Hero 改成 4:3，
则换一次样式 = 全部素材未命中 = 重新生成一遍图。
「让用户选样式」就变成「让用户每次选样式都花一次 AI 钱」。

因此这一条要有测试守卫，否则第一个新模板就把素材复用打穿。

当前约束值（[requirements.ts L41-58](../../../packages/presentation/src/requirements.ts)）：

| 角色 | 画幅 | 最小宽度 |
| --- | --- | --- |
| `HERO_BACKGROUND` | 16:6 | 1600 |
| `FOOD_IMAGE` | 4:3 | 600 |
| `DESTINATION_PHOTO` | 16:9 | 800 |
| `ROUTE_MAP` | 见 `ROUTE_MAP_CONSTRAINTS` | 同 |

**副作用**：`plan_asset_bindings.template_id` 在本阶段是**冗余的**
（所有模板绑同一批素材）。保留它是对的 —— 将来真要放开画幅时不用迁移。

## 四、目标形态

```text
请求  output_preferences.template_id = 'kraft_v1'
  ↓  （现在这里断了：校验完就丢）
编排  buildPresentationPlans({ plan, templateId })
  ↓      日页与全览页共享同一个 template_id
落库  plan_presentations (version, 'kraft_v1', DAILY_POSTER, 3)
                         (version, 'kraft_v1', FULL_PLAN,   NULL)
  ↓
渲染  /render/plans/{v}/days/3?template=kraft_v1
  ↓      读库时按 template_id 过滤（现在不过滤）
web   TEMPLATE_REGISTRY[templateId][pageType] → 组件
```

### 渲染 URL 用查询参数而非路径段

**结论：查询参数 `?template=xxx`。**

理由是鉴权面。HMAC 载荷是
（[render-token-edge.ts L15](../../../apps/web/src/lib/render-token-edge.ts)）：

```text
payload = plan_version_id | page_key | expires_at | jti
```

而 `parseRenderPath`（同文件 L115-116）用严格正则匹配路径：

```ts
/^\/render\/plans\/([^/]+)\/days\/(\d+)\/?$/
```

加路径段要同时改这个正则、`page_key` 的推导、以及令牌授权的语义。
而 `variantToQuery`（[render-page.ts L113](../../../apps/render-worker/src/render-page.ts)）
已经确立了「不签名的呈现类查询参数」这个先例 —— 渲染轮次就是这么传的。

**模板不是安全边界**：同一份数据、不同排版，令牌授权的仍是「这个版本的这一页」。

#### 做的时候才发现的：`created_at` 必然打平

`ORDER BY pr.created_at DESC, pr.template_id` 里的**第二个字段不是点缀，
它是唯一起作用的那个**：

- `plan_presentations.created_at` 默认 `NOW()`
  （[0005_assets.sql L197](../../../infrastructure/migrations/0005_assets.sql)）
- PostgreSQL 的 `NOW()` 是**事务级**的，而 `savePresentations` 是单事务批量写入

于是同一批落库的多套模板 `created_at` **完全相同**，只按它排序等于没排，
`LIMIT 1` 退回物理顺序。

这也改变了测试的写法：测试里故意把 `magazine_v1` 插在 `classic_v1` 前面，
让物理顺序与排序顺序**相反** —— 否则那条用例无论 `ORDER BY` 在不在都会绿
（已实测：最初的写法在整条 `ORDER BY` 被删后仍然 13 passed）。

#### 反证结果

| 撕掉哪一处 | 失败用例与症状 |
| --- | --- |
| `findPresentationByVersion` 的 template 过滤 | `expected 'classic_v1' to be 'magazine_v1'` |
| `listDayNumbers` 的 template 过滤 | `expected [ 1, 1, 2, 2 ] to deeply equal [ 1, 2 ]` |
| `ORDER BY` 里的 `pr.template_id` | `expected 'magazine_v1' to be 'classic_v1'` |

`[1, 1, 2, 2]` 就是 14 天变 28 页的缩影。

> 上面这些是测试实际输出。其中的 `classic_v1` / `magazine_v1` 是测试里的
> **占位 ID**（只需字典序可比），不是正式模板名 —— 见第七节。

#### 客户端不传时的默认值：两条路径不同

**生成请求走 Zod 默认值。**
[travel-request.ts](../../../packages/schemas/src/travel-request.ts) 里
`template_id: TemplateIdSchema.default(TEMPLATE_ID_VALUES[0])`，而
`output_preferences: OutputPreferencesSchema.prefault({})` 让**整个对象**缺省也能填。
客户端什么都不传就用第一套。

**导出请求不能用全局默认值。** 导出必须用**生成时那一套** —— 如果在 schema 里
填 `TEMPLATE_ID_VALUES[0]`，而计划实际用了别的套件，那个默认值会指向一份
不存在的展示数据，然后被 `EXPORT_TEMPLATE_UNAVAILABLE` 拒掉 —— 而客户端
根本没提过模板。

因此改成 `.optional()`，缺省时在路由里解析：校验用的那次
`findPresentationByVersion` **不带 template 过滤**，拿回来的行就是这份计划
自己的套件。一次查询同时完成校验与解析。

**下游一律用解析后的值**，幂等键尤其如此。反证：把幂等键改回
`body.template_id` 后「缺省与显式传同一值」那条用例报
`expected 201 to be 200` —— 第二次没命中幂等，起了两个内容完全相同的
导出任务，扣两次配额、渲两遍。

> 前端仍然**显式传**（`ExportPanel` 从 ViewModel 取）—— 它手上有确切的值，
> 传比不传精确。可缺省是给其他客户端（脚本、第三方）的便利。

#### 一处设计判断：组件按 ViewModel 选，不按 URL 参数选

两个渲染路由里：

```ts
const requested = firstValue(query, 'template') ?? TEMPLATE_ID_VALUES[0];
const viewModel = await loadViewModel(planVersionId, day, requested);
const Template = templateComponent(viewModel.template_id, 'DAILY_POSTER');
```

URL 参数决定**取哪份数据**，取回的 ViewModel 决定**用哪个组件**。
正常下两者相同，但这么写排除了一种死角：取了 A 的数据却用 B 的组件渲 ——
那不会报错，只会产出一张排版错乱的图，而任务仍然 COMPLETED。

注册表用 `Record<string, Record<PageType, Component>>`：新增套件时 TypeScript
**强制**它同时提供两个页型 —— 这是「任何模板都应包含全览页和每日页」这条
产品约束在类型层面的落地方式。

#### 做的时候才发现的四处

**一、`export-request.ts` 有三处硬编码，本文先前的调查漏了。**
它按导出种类选模板（全览 PDF 用 `travel_full_plan_v1`、日页用
`travel_infographic_v1`）—— 同一个「页型当模板」的错误。现在三种导出都用
这份计划的套件，从 ViewModel 取。

漏掉的原因值得记下：那次 grep 的结果被 25 条上限**截断**了，而我没注意到截断。

**二、`export-plan.ts` 是第二个渲染入口** —— 本地预览与视觉基线工具。
给了可选 `templateId`，因为 P2 的基线是按套件拍的。

**三、template 不能拼进 path。** `variantToQuery` 的返回值恒以 `?` 开头，
path 里再带一个会拼出 `...?template=x?compact=1`。因此让 `variantToQuery`
统一拼查询串（多收一个参数）。同时确认 `parseRenderVariant` 只读
`compact`/`hide`/`layout`、忽略未知参数，因此加 `template` 安全。

#### 第 13 项：配色被声明了两遍

建 token 层之前的真实状态是同一套配色**写了两份**：

- `daily/styles.css` 的 `.poster { --tps-ink: … }`（7 个）
- `full/styles.css` 的 `.full-plan { --fp-ink: … }`（6 个，值逐一相同）

原因是 `.full-plan` 是根、`.poster` 嵌在它里面 —— 全览页看不到 `.poster` 的 token，
只能自己再抄一份。**新套件改一处漏另一处 → 一份产物两种配色，而那不会报错。**

作用域选 `[data-template='<套件>']` 而不是新加类：两个页型的根元素**本来就带这属性**。

度量 token（`--tps-gap` 等 8 个）留在 `.poster`：17.3 第 4 轮的 `[data-variant='relaxed']`
要覆盖它们，放到套件层会让那个覆盖跨两个文件去理解。

#### 字体属于套件，但不重抄字体栈

字体由样式自己决定（本轮确立）。但直接把字体栈写进 `tokens.css` 会造出
`FontFaces.tsx` 明确避开的那份手抄副本。因此分两层：

```css
/* tokens.css —— 套件只说「标题用哪一家」 */
[data-template='blueprint_v1'] {
  --tps-title-font:   var(--tps-font-sans);   /* 黑体 */
  --tps-body-font:    var(--tps-font-sans);
  --tps-numeric-font: var(--tps-font-numeric);
}
```

页型的 `styles.css` 只用角色 token。已入库 **3 家族 × 3 档字重**
（Noto Sans SC / Noto Serif SC / Inter，`FONT_WEIGHTS = [400, 500, 700]`），
套件在这三家里自由组合**零成本**；引新家族要进子集化流程。

**覆盖为何必然生效**：`FontFaces` 注入 `:root`（即 `<html>`），套件声明在
`.poster` / `.full-plan` **自身**。CSS 自定义属性会继承，而**元素自身的声明总是
胜过继承来的值** —— 与特异性无关（层叠只在同一元素的声明之间比特异性）。
因此不需要提特异性，也不依赖 `<style>` 与样式表在 `<head>` 里的先后顺序。

附带补了一处真缺口：正文原先**继承 `globals.css` 的 `body`**，所以套件其实换不了
正文字体。两个页型的根元素现在显式 `font-family: var(--tps-body-font)`。

#### 两处结构问题是做的时候才发现的

**一、`overflow-guards.ts` 必须共用（已上移）。** 它的槽位名与优先级是
**17.3 的契约**，不是样式选择。每套复制一份的后果是两套在优先级上漂移 ——
比如一套 `foodCard: 60` 另一套 `70`，于是「先隐藏哪个」变成套件相关的，

**二、类名冲突无编译期保护。** 模板 `styles.css` **不是 CSS Module**（是全局 CSS），

只是渲出一张排版错乱的图，而任务仍然 COMPLETED。

没改 ink_paper 的 69 个类名（会动 800+ 行且可能打破视觉基线），而是：
blueprint 全部用 `bp-` 前缀 + 一条守卫**禁止套件间类名相交**。
那条守卫不规定用什么前缀，只规定不能相交。

### P3 · 用户可见

**实施记录与设计决策见第八节**（原计划表在这里，已随进展迁走）。
其中计费口径的结论如下：

**换模板不重新计费生成，按导出计费。** 理由：素材不变（决策二保证画幅一致，
缓存全命中），成本结构与「重新导出一次」相同 —— 只有渲染与存储，没有 AI 调用。
把它按生成计费会让用户为同一批素材付两次钱。

**换模板不影响导出计费（产品决策，2026-08-29 确立）。** 用户换模板导出的费用
与常规导出同价 —— 模板不参与定价。即使内部成本有差异也由平台吸收：
把差异转嫁给用户会让「选样式」变成「选价格」，便宜的那套被选得更勤、
贵的那套没人敢选，而模板是样式选择不是成本选择。

> P2 的实测给了这条决策的内部成本背景：**不同套件的导出成本不相等**。
> `blueprint_v1` 的日页矮 38%，14 天的合并 PDF 从 28 页降到 14 页 ——
> 存储与带宽差一倍。这个差异是平台侧的（若计费实现按页数或字节算成本，
> 要在成本核算里考虑），但**不进入用户侧的定价**。

### 四条 UPDATE 与后置断言

迁移改三张表的 `template_id` 列，**加 `view_model` 里的那一份**。

1. 用 `pg_dump | psql` 把工作库克隆到 `tpl_rehearsal`，**先在克隆上演练**

3. 演练库 DROP，在工作库执行 → 同样 `36 / 189 / 0 / 36`

> `pnpm db:migrate` 同时应用了 0015 与 0016，说明这个开发库之前的
> `schema_migration` 记录不完整。0016 重跑是安全的（幂等，见下）。

### 反证：第一次是假的

也就是说迁移对那两个旧值是**自愈的**，这是好事，但让那次反证什么都没验到。

### 为什么是 `ink_paper`

现有套件的 CSS 变量名自己给了答案
（[ink-paper-v1/daily/styles.css](../../../apps/web/src/templates/ink-paper-v1/daily/styles.css)）：

```css
--tps-ink:    #1b1b1b   /* 墨 */
--tps-paper:  #fdfcf9   /* 纸，不是纯白 */
--tps-line:   #e4e0d8   /* 暖灰 */
--tps-accent: #2f6b4f   /* 深绿，接近石绿 */
--tps-warm:   #b8763a   /* 赭石 */
```

取名与 CSS token 同词汇，开发者读 `styles.css` 立刻能对上；且颜色微调后
这个名字仍然成立（依旧是墨色落在纸色上）。

### 两个被排除的名字，理由值得记下

**`classic_v1`（本方案先前的占位名）** —— `classic` 在本仓已经有两个含义：

```text
ROUTE_TYPE_VALUES = ['RELAXED', 'CLASSIC', 'DEEP', 'FAMILY']   行程节奏「经典路线」
THEME_BUCKET_VALUES 里的 'garden_classic'                       主题桶「古典园林」
```

再加一个模板 ID 就是第三个含义，以后 grep `classic` 会同时命中三处无关的东西。

**`editorial_v1`** —— `CHINESE_TRAVEL_EDITORIAL` 是**图片**风格，而按决策二
所有模板共享它（它在缓存键里）。也就是说 「editorial」描述的是每一套模板的
图片，不能用来区分其中任何一套。**禁止用图片风格词命名模板**。

### ID 不是用户可见文案

**展示名层已在 P3 落地**：模板目录行带 `label`（`planner_config_options`，
见迁移 0017），前端选择器从配置中心取它显示。ID 为**开发者**的清晰度服务，
展示名才为产品服务 —— 这也是描述性的名字比好听的名字更值的原因。

**当前不完整**：只有生成前的选择器显示展示名；计划页与导出面板不显示
用户所选样式的名字（已知边界，见第九节）。

`presentations.integration.test.ts` 的 R-85 那组需要两个可比较的值，原先用的是
`classic_v1` / `magazine_v1` —— 前者是已被排除的名字，留在测试里会看起来像正式的。
现已改为 `ink_paper_v1` / `kraft_v1`。

**示例图是占位**：`make-template-previews.mjs` 从视觉基线缩放而来
（Linux 容器渲的真实产物，与用户实际拿到的逐像素同源）。真图由设计提供，
**覆盖同名文件即可**，不动代码。加新套件重跑脚本；基线缺失时它明确报错
而不是跳过（跳过的后果是配置里登记了一张不存在的图，门禁会红）。

**本地编排的素材加载修复**（2026-08-29 验证时发现）：写入侧的素材 URL 是
`localhost:9000`（浏览器可解析），渲染容器里的 Chromium 解析 localhost 得它
自己 —— 素材全部失败而导出仍 COMPLETED。修法是 `CHROMIUM_HOST_RESOLVER_RULES
=MAP localhost minio`（`browser.ts` 的 `chromiumArgs` 读它，本地编排注入），
只影响 Chromium 的 DNS。生产不设：MinIO 在独立子域，无此分裂。

> 注意：`render-worker` 的 `S3_PUBLIC_BASE_URL` **不能**覆盖成 `minio:9000` ——
> 那个值还会写进**导出文件 URL**（给浏览器下载），且 SigV4 签名绑定 host。
> 曾试过该方案并回退。

## 九、已知边界

**P0 / P1 / P2 已完成，P3 进行中。** 已落地：模板目录（0017）、前端选择器
（第 9 步）、双套件端到端验证。未落地：结果页换模板导出（计费口径已定，
见第五节）。

**端到端已验过真实库。** 2026-08-29 在本地整栈（8080）上走完：生成（fake 模式
blueprint_v1）→ 落库 4 行 → 内部端点按 template 取数 → 导出 PNG/PDF →
像素级确认 blueprint 标志色（纸面 #f2f6fa / 墨蓝 #10243a，ink_paper 标志色 0%）。

**多模板的素材复用仍是推算而非实测。** 决策二保证画幅一致因此键一致（有测试守着），
但「换模板后缓存命中率不变」需要真实流量验证。

**本地编排的素材加载需要 host 重写（已修）。** 写入侧的素材 URL 是
`localhost:9000`（浏览器可解析），渲染容器里的 Chromium 解析 localhost 得
它自己 —— 素材全部失败而导出仍 COMPLETED。修法是 `CHROMIUM_HOST_RESOLVER_RULES
=MAP localhost minio`（`browser.ts` 的 `chromiumArgs` 读它，本地编排注入）。
生产不设：MinIO 在独立子域，无此分裂。

**展示名层只覆盖了生成前。** 选择器显示配置中心的 `label`；计划页与导出面板
不显示样式名，用户看不到自己的计划用了哪套。

**选择器静默消失。** 配置中心 503 / 未发布时 `useTemplateOptions` 返回空，
整个选择器不渲染 —— 用户拿默认样式但不知道原因。这是设计取舍（宁可拿默认），
代价是没有任何提示。

**套件能改什么与不能改什么（本轮确立）：**

| 能改 | 不能改 | 为何 |
| --- | --- | --- |
| 配色（7 个 token） | 素材 `aspect_ratio` × 4 | 进缓存键 |
| 字体角色（3 个，三家族自由组合） | 素材 `min_width` × 4 | 同上 |
| 日页版式度量（8 个） | Hero 的 `style` 与 `avoid_*` | 进缓存键 / 11.3 |
| 两个页型各自的布局结构 | `--tps-canvas-width: 1200px` | 绑 17.4 viewport |

「画幅」指的是**素材图片**的比例，与页面尺寸无关：
Hero 16:6、Food 4:3、Photo 16:9、RouteMap 3:2（`requirements.ts` L41-58）。

**新字体家族要进子集化流程。** 套件在已入库的三家族里组合零成本；
引新家族需要：`FONT_FAMILIES` 加项、生成子集化 woff2、字重落在
`[400, 500, 700]` 内（字重门禁会拦）、若用于正文还要考虑 `PRELOADED_WEIGHTS`
—— `font-display: block` 下不预载会多一个往返，而单次渲染预算只有 5 秒（17.3）。

**类名隔离靠守卫而不靠机制。** 模板 CSS 是全局的，因此第三套套件仍然
可能误用 ink_paper 的通用名。那条守卫会拦住它，但报错时才拦 ——
若将来套件多了，应该考虑改成 CSS Module 或给 ink_paper 也加前缀。

**换模板重新导出没有入口（计费口径已定）。** 那是 P3 的 19 项后半。
当前 `ExportPanel` 固定用生成时那一套（`viewModel.template_id`），
用户不能为已生成的计划换一套样式重新导出。13.4 用户端点的
`PresentationQuerySchema` 也没有 `template` 查询参数 —— 那是换模板导出的前置缺口。
计费口径（第 20 项）已定：按导出计费、模板不参与定价，实现未动工。

**未考虑模板改版。** `ink_paper_v1` → `ink_paper_v2` 时存量计划怎么办
（保持旧版还是重建）不在本方案范围内。`template_id` 带版本号是为它留的口子。

**未考虑按页型给不同模板。** 产品语义要求一套模板覆盖两个页型，因此
「日页用 A、全览页用 B」不被支持，且在类型层面已不可表达
（`buildPresentationPlans` 只收一个 `templateId`）。若将来要支持，需要回到两维模型。
