# 旅行规划必填项与条件交互设计

> 状态：字段分类评审已确认，前后端实施中  
> 文档版本：1.1  
> 更新日期：2026-09-03  
> 适用范围：Planner V2.1 首次旅行攻略生成、确认旅程页、生成前校验与行前准备中心

## 1. 设计目标

本设计解决以下问题：

1. 明确哪些信息是基础必填、场景必填、选填或生成后补充。
2. 避免把“硬约束”“高优先级”“系统待核验”误判成用户必填。
3. 用户做出上游选择后，前端立即说明为什么出现新问题、需要补充什么以及是否阻止生成。
4. 前端只校验本地能够确定的事实；签证、保险、供应商能力等交给后台或官方来源核验。
5. 缺少信息时给出可执行出口，不能只显示“还有 N 项”或让按钮无响应。
6. 尽量使用选择、加减、日期选择、滑杆和结构化卡片，只有“其他”或确需补充时允许自由输入。

## 2. 依据与决策优先级

字段定义的上游来源是：

1. `docs/design/Planner_V2_产品字段表.xlsx`；
2. `docs/design/Planner_V2.1_页面交互规范_最终版.docx`；
3. 已确认的后续产品决策，例如“至少选择一个具体目的地”；
4. `packages/schemas/src/planner-fields.ts` 中可执行的字段元数据。

发生冲突时，按“最新已确认产品决策 → 本文档 → 产品字段表 → 旧原型”的顺序执行。本文档通过评审后，应成为必填分类和交互行为的产品基线；代码、数据库配置和测试不得各自维护另一套口径。

## 3. 术语与判定准则

### 3.1 四类字段

| 类型 | 定义 | 未完成时是否阻止首次生成 | 前端表现 |
|---|---|---:|---|
| 基础必填 `BASE_REQUIRED` | 对当前产品支持的绝大多数旅行都适用，缺失后无法生成基本可执行方案，且不能由系统安全推导 | 是 | 始终展示“必填项”徽标 |
| 场景必填 `CONDITIONAL_REQUIRED` | 仅在明确场景或用户主动开启某项要求后适用 | 仅在触发后阻止 | 展开时展示触发原因和“当前必填” |
| 选填 `OPTIONAL` | 只增强个性化，或系统可采用安全默认值、研究后补充 | 否 | 默认不显示徽标，可显示“可跳过”帮助文本 |
| 生成后补充 `POST_PLAN` | 不影响首版攻略，属于行前准备或深度服务 | 否 | 首次问卷不展示，攻略生成后进入准备中心 |

`PV2-09-002` 是系统生成的“待补充问题容器”，不是独立的用户字段，不归入上述必填或选填统计。

### 3.2 基础必填的五项判定

一个字段只有同时满足以下条件，才能设为基础必填：

1. 对当前旅行场景普遍适用；
2. 用户是该信息的主要或唯一可靠来源；
3. 缺失后不能形成基本可执行的日期、地点、人员、安全边界或合法授权；
4. 无法使用保守默认值代替；
5. 必须在首次攻略生成前获得，而不是生成后再完善。

只要任意一项不满足，就不能设为基础必填。

### 3.3 场景必填的五项判定

场景必填必须同时具备：

1. 有明确、可执行、可测试的触发条件；
2. 触发条件来自已经完成的上游选择，不靠模型猜测；
3. 条件不成立时字段隐藏或保持非激活，不计完成度；
4. 条件成立后，缺失会导致该旅行分支不可执行、不安全或无法合法处理；
5. 用户可以通过“补充信息”或“修改/取消上游选择”解除阻塞。

### 3.4 选填判定

满足任意一项即可设为选填：

- 只影响推荐排序、风格或舒适度；
- 系统能够采用清晰说明的默认值；
- 可以在首版攻略生成后继续补充；
- 属于后台研究、官方或供应商核验责任；
- 不回答不会让方案失真、不安全或不可执行。

选填字段一旦填写，仍必须通过格式与跨字段校验；用户可以选择“修正”或“清空并跳过”。

### 3.5 以下信息不能直接决定必填

- `P0/P1/P2` 只表示产品优先级，不表示用户是否必填。
- `HARD/PREFER/EXCLUDE` 只表示答案进入方案后的约束强度，不表示问题本身必填。
- `VERIFY_BLOCKING` 只表示核验风险等级。用户完成必要回答后，系统待核验状态不阻止首版攻略生成。
- 页面始终显示不等于基础必填；条件显示也不等于场景必填。

### 3.6 阻塞范围

| 范围 | 使用条件 | 示例 |
|---|---|---|
| 全局阻塞 `PLAN` | 缺失后任何合理首版方案都无法生成 | 目的地、日期、旅行人数、本次服务授权 |
| 分支阻塞 `BRANCH` | 只影响某个用户主动选择的分支 | 自驾资格信息、硬预算上限、不可退订单详情 |
| 不阻塞 `NONE` | 只影响排序或需要系统继续研究 | 兴趣偏好、签证官方核验结果、品牌偏好 |

分支阻塞不应默认升级成全局阻塞：如果用户把自驾设为“偏好”，可以取消自驾偏好继续生成；如果设为“必须”，自驾分支无法取消时才升级成全局阻塞。

## 4. 前端视觉与文案规则

### 4.1 字段必填状态

| 状态 | 展示方式 | 禁止做法 |
|---|---|---|
| 基础必填 | 字段标题右侧显示中性徽标“必填项” | 不使用星形，避免和“必须满足”约束混淆 |
| 场景必填未触发 | 不展示字段 | 不预先显示红色错误 |
| 场景必填刚触发 | 字段上方蓝色说明：“因为你选择了自驾，需要补充驾驶条件。”；字段显示“当前必填” | 不直接报错，不制造用户做错了的感觉 |
| 场景必填已完成 | 保留一行简短触发说明，可折叠 | 不持续显示警告色 |
| 选填 | 不显示徽标；需要时显示“可跳过” | 不使用“未完成”或红色状态 |
| 系统待核验 | 时钟/盾牌图标加“已填写，系统待核验，不影响生成” | 不与“还需用户补充”混在同一个数量中 |

### 4.2 多状态偏好按钮

用户已明确要求不显示“偏好、必须、不要”三个状态文字，因此按钮使用以下视觉语言：

| 状态 | 图标位置 | 颜色 | 文字表现 | 无障碍名称示例 |
|---|---|---|---|---|
| 默认未选择 | 无图标 | 中性灰 | 正常 | “酒店，未选择” |
| 优先考虑 | 选项文字前的实心爱心 | 旅行蓝 `#3478F6` | 正常 | “酒店，优先考虑” |
| 必须满足 | 选项文字前的实心五角星 | 自然绿 `#159A72` | 正常 | “酒店，必须满足” |
| 明确不要 | 选项文字前的叉号 | 珊瑚红 `#E65D65` | 选项文字带删除线 | “酒店，明确不要” |

状态顺序为：默认 → 优先考虑 → 必须满足 → 明确不要 → 默认。图标必须位于选项文字前。视觉上不显示状态名称，但按钮必须通过 `aria-label`、`aria-pressed` 或隐藏说明向读屏软件表达完整状态。

事实、是否类、安全类、授权类和非此即彼的单选按钮不使用四态循环。

### 4.3 提示等级

| 等级 | 用途 | 出现时机 | 用户可执行操作 |
|---|---|---|---|
| 帮助 | 解释字段、默认值或口径 | 字段首次展示 | 继续选择、查看说明 |
| 分支说明 | 解释为什么出现条件字段 | 上游选择触发后立即出现 | 填写、修改上游选择、取消相关要求 |
| 行内校验 | 本地可确定的缺失或格式错误 | 值变更后或离开字段时 | 就地修正、清空选填内容 |
| 页面校验 | 当前页仍有用户必填项 | 点击“下一步”时 | 定位第一项、逐项补充、返回修改选择 |
| 全局校验 | 多页冲突或生成前缺失 | 进入确认页、点击生成时 | 就地补答、跳到来源字段、取消冲突条件 |
| 系统核验 | 用户已完成，等待后台/官方信息 | 回答后及确认页 | 继续生成、查看核验说明、稍后查看结果 |

暖橙只用于价格、预算和费用提醒；红色只用于明确排除和真实错误；系统待核验使用中性蓝灰，不使用阻塞红色。

### 5.11 分类评审结论

本章分类已按第 3 章的判定准则逐项复核，结论如下：

1. 76 个 Field ID 均有且只有一个主分类；统计为 16 个基础必填、19 个场景必填、34 个选填、6 个生成后补充和 1 个系统容器。
2. “必填”只描述生成前是否必须获得用户回答，不再由 `P0`、`HARD`、字段是否常显或是否需要后台核验推导。
3. `PV2-02-002` 与 `PV2-02-001` 是同一组人员加减器产生的两个数据落点，前端必须原子更新人数总数和年龄分类汇总；除第一位“本人”外，不得据年龄或数量猜测伴侣、朋友、父母等关系。目标契约应允许非本人关系省略或使用 `UNSPECIFIED`；`OTHER` 只表示用户明确选择了“其他关系”，不能由系统自动写入代替未知。
4. `PV2-02-005` 儿童安排在存在婴幼儿或儿童时为场景必填，并提供“无特殊安排”；`PV2-02-006` 多人分组只影响舒适度与组织方式，保持选填。
5. 住宿类型和房间数均允许交给系统推荐。只有用户明确设置房间数后，`PV2-06-003` 才成为场景必填；这避免把“没有填写住宿偏好”错误解释成“无需住宿”。
6. 高风险活动只要求用户回答当前保险状态，不要求前端判断保单是否承保；用户完成回答后转为系统待核验，不继续阻塞首版攻略。
7. `PV2-09-002` 只承载动态问题清单，不是用户答案，不得加入自身阻塞计算或完成度分母。

评审同时确认以下实现前提：基础必填必须提供可完成的结构化选项；场景必填必须有触发器、原因、补充路径和取消/修改上游选择的解除路径；选填字段为空时不报错，形成无效半成品时必须允许用户修正或清空。

| 有用户待补充项 | 标题“还需要你补充”；逐项显示具体问题、原因和来源步骤，不显示笼统数量 | 只列已触发的基础/场景必填和真实冲突 | 就地回答、跳到原字段、修改上游选择、取消分支 |
| 只有系统待核验 | 标题“可以生成”；单独卡片“系统将在生成后继续核验 N 项” | 不作为 blocker | 生成、查看核验项目 |
| 没有阻塞也没有核验 | “信息已足够，可以生成旅行攻略。” | 全局校验通过 | 生成、返回修改 |
| 未同意本次服务授权 | “需要你的同意才能使用这些信息生成攻略。” | 授权必须显式为同意 | 阅读说明并同意、退出不生成 |
| 点击生成时仍有缺失 | 不发送请求；滚动并聚焦第一项，同时保留完整清单 | 再执行一次全局校验 | 就地补答、跳转来源、取消分支 |
| 后端返回字段错误 | 使用后端 `field_id` 定位并显示可理解文案 | 后端为最终权威 | 修正后重试、保留草稿 |

## 7. 前端自校验边界

### 7.1 前端必须立即校验

- 必填值是否存在；
- 数量、金额、日期和时间的格式及上下限；
- 开始/结束顺序；
- 人员分类之和、房间容量等确定性算术；
- “无”和其他选项互斥；
- 同一选项不能同时为必须和排除；
- 必去日期、工作安排日期是否在旅行窗口内；
- 订单卡、过敏条目等动态记录是否完整；
- 已触发条件字段是否完成；
- 用户填写的选填字段是否为半成品。

### 7.2 前端不得自行下结论

- 签证、ETA、过境和护照有效期是否满足具体国家规则；
- 驾照、IDP或翻译件能否合法租车；
- 保险是否覆盖特定高风险活动；
- 餐厅能否安全处理严重过敏；
- 酒店是否保证连通房、提前入住或无障碍设施；
- 航班、票价、营业时间和实时可用性。

这些项目只能显示“系统待核验/供应商待确认”，不能显示为“用户还没完成”，也不能因后台尚未完成核验而阻止首版攻略生成。

## 8. 提示时机和焦点行为

### 8.1 选择发生时

- 上游选择触发新字段后，在原位置下方展开，不跳页。
- 首次展开显示完整原因；之后缩成一行帮助文本。
- 展开后不要立刻把字段染红，只有用户离开字段或尝试继续时才进入错误状态。

### 8.2 编辑过程中

- 可确定的范围错误实时提示，但输入尚未完成时避免过早报错。
- 数字输入必须把当前值同步显示在输入框、滑杆气泡或摘要中。
- 日期、时间和选择结果必须在选择后保持可见。
- 自动派生值要说明来源，例如“根据3位旅行者建议2间房”，且不能静默覆盖用户值。

### 8.3 点击下一步

- 只检查当前页已经触发的基础必填、场景必填和已填写的无效选填。
- 页面顶部显示“本页还有 N 项需要处理”，同时滚动聚焦第一项。
- 非阻塞选填不使用红色，也不把步骤状态标成失败。

### 8.4 进入确认页

确认页分成三个区域，不能混合计数：

1. **还需要你补充**：真正阻止生成的用户问题；
2. **信息冲突**：必须由用户选择取舍的问题；
3. **系统将继续核验**：不阻止生成的签证、保险、供应商事项。

每一项至少显示：问题名称、出现原因、当前状态、影响范围、来源步骤和一个主操作。点击后必须定位到具体字段或在确认页直接渲染对应控件。

### 8.5 点击生成

- `还需要你补充 > 0`：不发请求，定位第一项。
- `信息冲突 > 0`：不发请求，要求选择取舍。
- 只有系统待核验：允许生成，按钮文案为“生成旅行攻略 · 系统将继续核验 N 项”。
- 全部完成：按钮文案为“生成旅行攻略”。
- 请求失败：保留全部输入，并显示后端提供的字段级错误和重试入口。

## 9. 后端配置设计

前端不得根据 `runtime_type`、优先级或颜色猜测必填项。后台发布配置应直接下发结构化要求：

```json
{
  "field_id": "PV2-05-006",
  "requirement_mode": "CONDITIONAL_REQUIRED",
  "trigger_code": "SELF_DRIVE_SELECTED",
  "blocking_scope": "BRANCH",
  "reason_code": "LEGAL_FEASIBILITY",
  "allow_clear": true,
  "allow_change_source": true
}
```

### 9.1 必要字段

| 配置项 | 用途 |
|---|---|
| `field_id` | 稳定字段标识 |
| `requirement_mode` | 基础必填、场景必填、选填、生成后补充、系统容器 |
| `trigger_code` | 可执行触发器；基础必填和选填可为空 |
| `blocking_scope` | 全局、分支、不阻塞 |
| `reason_code` | 为什么需要：骨架、安全、合规、授权、锁定订单等 |
| `allow_clear` | 是否允许清空并跳过 |
| `allow_change_source` | 是否允许通过修改上游选择解除条件 |

触发器必须使用代码枚举和参数，不能只下发“国际旅行时显示”这样的自然语言。自然语言只能用于帮助文案。

`requirement_mode` 的完整枚举为 `BASE_REQUIRED`、`CONDITIONAL_REQUIRED`、`OPTIONAL`、`POST_PLAN`、`SYSTEM`。`SYSTEM` 当前只允许用于 `PV2-09-002`。

### 9.2 前后端职责

| 责任 | 前端 | 后端 |
|---|---:|---:|
| 展示必填徽标和触发原因 | 是 | 下发配置 |
| 条件分支即时显隐 | 是 | 提供触发定义 |
| 本地格式和确定性跨字段校验 | 是 | 必须重复校验关键规则 |
| 生成前最终必填判定 | 预检 | 权威判定 |
| 系统/官方核验 | 展示状态 | 执行并保存结论 |
| 运营调整必填清单 | 不允许硬编码 | 版本化发布、可回滚 |

### 9.3 配置发布校验

后台只有在以下条件全部通过时才能发布配置版本：

| 校验 | 失败处理 |
|---|---|
| 数组正好覆盖 76 个唯一 Field ID | 拒绝发布并列出缺失、重复和未知 ID |
| `BASE_REQUIRED` 没有触发器，且阻塞范围为 `PLAN` | 拒绝发布 |
| `CONDITIONAL_REQUIRED` 有已注册触发器、原因和解除路径 | 拒绝发布 |
| `OPTIONAL`、`POST_PLAN`、`SYSTEM` 的阻塞范围为 `NONE` | 拒绝发布 |
| `PV2-09-002` 为 `SYSTEM` 且不允许清空或修改上游来源 | 拒绝发布 |
| 每个 `trigger_code` 都被前端和后端同版本代码识别 | 拒绝发布；不能把未知触发器当作“不触发” |

运行时读取到损坏配置时，应记录包含配置版本和校验问题的告警，并整体回退到共享基线。禁止只采用其中一部分，因为这会使同一页面上的必填语义不一致。

### 9.4 生成请求的一致版本流程

1. 配置接口返回 `version`、`field_requirements` 和缓存标识；前端保存当前配置版本。
2. 用户修改上游选择时，前端用该版本配置重新计算显隐、必填徽标和 blocker。
3. 生成请求携带 `planner_config_version`；兼容期允许旧客户端省略，由后端使用当前发布版本并记录来源。
4. 后端加载请求指定的同一配置版本，重复计算基础必填、已触发场景必填和无效半成品。
5. 缺失时返回稳定错误码、具体 `field_id`、原因和可执行解除方式；不创建生成任务。
6. 校验通过后，把 `planner_config_version` 与原始请求一起保存，保证问题追踪和结果解释可复现。
7. 指定版本不可用时返回“配置已更新，请刷新校验”，前端拉取新配置、保留用户答案并重新展示受影响项目。

## 10. 状态与统计口径

右侧摘要和确认页必须分别统计：

| 计数 | 包含内容 | 是否阻止生成 |
|---|---|---:|
| `user_required_count` | 已触发但未完成的基础/场景必填 | 是 |
| `conflict_count` | 必须与排除、日期、预算、订单等硬冲突 | 是 |
| `system_verification_count` | 用户已回答但系统/供应商未核验 | 否 |
| `optional_completion` | 选填信息覆盖度 | 否，只用于说明个性化程度 |

不得再使用一个“待确认 N 项”同时表示用户缺失和系统核验。

## 11. 与实现的差异、结论和落点

本章中的“评审前实现”指 2026-09-03 本轮修改开始前的基线，“实施状态”用于约束本轮开发和验收。状态定义如下：

- **已落地**：代码和定向自动化测试已完成；
- **部分落地**：主链路已实现，但仍有明确的交互或后端权威校验缺口；
- **待实施**：尚不能按本设计验收，不得以文档完成代替实现完成。

### 11.1 差异评审结论

| 项目 | 评审前实现 | 确认后的设计 | 评审结论 |
|---|---|---|---|
| 必填来源 | API 下发平面 ID 清单，清单由编译期常量计算 | 发布配置维护每个字段的分类、触发器、阻塞范围和解除能力 | 必须改；平面清单只能暂时保留为兼容字段 |
| 预算 | 没有生成必填项 | 预算表达方式基础必填；金额、档次、硬上限按模式成为场景必填 | 确认；“暂时没概念”是合法答案，不强迫输入金额 |
| 旅行节奏 | 整体节奏不阻止生成 | 整体节奏基础必填，其他节奏细节选填 | 确认；基础节奏是每日排程的必要输入 |
| 步行能力 | 选填 | 基础必填，并提供“不确定” | 确认；缺失可能造成不安全路线，不能静默按“行动自如”处理 |
| 儿童需求 | 触发后不阻止 | 有婴幼儿或儿童时场景必填，提供“无特殊安排” | 确认；必须获得明确答案，不能把未回答当成没有需求 |
| 多人分组 | 与儿童需求合并讨论，容易被误归为必填 | 三人及以上时展示，但保持选填，未选采用“大部分时间一起”的可见建议 | 确认选填；它影响舒适度，不影响首版方案基本可执行性 |
| 住宿入口 | 房间数和房型直接进入必填清单 | 住宿类型、房间数选填；明确设置房间数后，房型配置场景必填 | 确认；系统可根据人数与路线提出安全默认建议 |
| 旅行人员关系 | 按年龄数量猜测伴侣、朋友、父母关系 | 只记录用户选择的年龄分类；除“本人”外关系可省略或为 `UNSPECIFIED` | 必须改；`OTHER` 也不能被当作“未知”的静默替代 |
| 保险 | 文案称高风险时必填，实际不阻塞 | 高风险活动时必须回答保险状态；回答后转系统核验且不阻止生成 | 确认；“没有/不确定”也是完成回答，不等于已承保 |
| 系统待核验 | 已不阻塞，但可能与用户缺失共用展示和计数 | 单独分组、单独计数、明确允许生成 | 确认；不得再使用笼统“待确认 N 项” |
| 自驾 | 优先和必须使用同一全局门槛 | 先形成自驾分支阻塞；用户可补充或取消自驾，只有坚持为必须时才升级约束 | 确认；界面必须提供解除路径 |
| 多状态按钮 | 图标与可见状态文字并存 | 只显示图标，图标位于选项文字前；完整语义保留在无障碍名称中 | 确认；爱心必须为实心且状态色保持统一体系 |

### 11.2 前后端实施映射

| 能力 | 前端落点 | 后端/契约落点 | 实施状态 | 剩余验收项 |
|---|---|---|---|---|
| 76 字段结构化分类 | `PlannerConfigProvider` 读取 `field_requirements`；配置不完整时整体回退 | `PlannerFieldRequirementSchema` 校验；配置版本保存 `field_requirements`；API 返回完整分类 | 已落地 | 在迁移后的数据库验证发布、克隆和回滚 |
| 必填徽标 | 基础必填显示“必填项”，已触发的场景必填显示“当前必填” | 分类和触发器由配置下发 | 已落地 | 浏览器检查九步所有徽标和响应式布局 |
| 条件必填计算 | `isRequirementActive` 按触发器计算，未触发项不计入 blocker | 后端仍需在接收生成请求时重复权威判定 | 部分落地 | 补后端必填判定器及 `field_id` 错误响应 |
| 预算分支 | 金额、档次、硬上限分别触发对应字段 | 请求 Schema 已校验结构，尚未按发布分类判定缺失 | 部分落地 | 覆盖四种预算模式的前后端契约测试 |
| 人员年龄分类 | 加减器原子更新总人数和年龄段；不再猜测具体关系 | `planner_profile.travelers` 当前仍要求关系枚举 | 部分落地 | 契约增加可省略关系或 `UNSPECIFIED`；迁移旧草稿；禁止用 `OTHER` 代替未知 |
| 儿童安排 | 有儿童时显示“当前必填”，可选“无特殊安排” | 条件触发器为 `CHILD_PRESENT` | 已落地 | 浏览器验证“无特殊安排”和其他项互斥 |
| 步行能力 | 字段改为基础必填 | 分类已下发 | 部分落地 | 增加“不确定”选项并完成请求投影语义 |
| 住宿自定义 | 房间配置仅在用户设置房间数后展开并阻塞该分支 | 触发器为 `ROOM_COUNT_SET` | 已落地 | 提供“清空房间数，改回系统安排”的直接操作 |
| 保险与核验 | 高风险活动触发保险必填；回答后不再列为缺失 | 系统核验状态与用户回答状态分离 | 部分落地 | 确认页分别显示用户缺失数与系统核验数 |
| 下一步校验 | 当前页有 blocker 时留在本页并聚焦第一项 | 无 | 部分落地 | 增加页首“本页还有 N 项需要处理”和可执行操作 |
| 选填半成品 | 空值不阻塞；已填写但无效时进入“修正或清空”路径 | 后端仍执行结构和关键跨字段校验 | 部分落地 | 每个复合选填控件补清空入口和错误码映射 |
| 多状态按钮 | 视觉只显示爱心、星形、叉号；图标在文字前，读屏名称完整 | `stance` 枚举保持不变 | 已落地 | 键盘、焦点和高对比度浏览器验收 |
| 生成前最终判定 | 前端继续执行预检并定位第一问题 | 后端必须使用与配置版本一致的判定器作为最终权威 | 待实施 | 前端通过而后端因同一字段规则失败的契约测试必须为零 |

### 11.3 兼容与失败策略

1. 旧客户端仍可读取 `generation_required_field_ids`，但新前端只以 `field_requirements` 为主；删除兼容字段必须另行版本化。
2. API 读取到缺失、重复、未知 Field ID 或不足 76 项的分类时，不得部分采用；应记录配置告警并整体回退到随版本发布的共享基线。
3. 前端收到不完整分类时同样整体回退，不允许把损坏配置解释成“没有必填项”。
4. 发布配置的缓存标识必须随配置版本和分类契约版本变化，防止浏览器沿用旧语义。
5. 后端生成前校验失败时，响应必须包含稳定错误码、`field_id` 和用户可理解文案；不得只返回“请求格式不正确”。

## 12. 验收标准

### 12.1 配置与字段覆盖

- 76个 Field ID 全部有且只有一个目标分类。
- `PV2-09-002` 明确标为系统容器，不进入必填统计。
- 所有场景必填都有触发器、触发原因、解除路径和自动化测试。
- 前端必填徽标、页面状态、确认页清单和生成门槛读取同一后台版本配置。

### 12.2 交互

- 每个上游选择触发或关闭分支后，页面在同一交互内更新。
- 每个条件字段首次出现都解释“为什么问”。
- 所有错误提示都包含具体问题和至少一个可执行动作。
- 点击确认页条目能定位具体字段；不能只跳转到步骤顶部。
- 所有数字、日期、时间和滑杆选择完成后都有持续可见的值。
- 必填项未完成时生成按钮仍可点击，但只定位问题、不发送请求。
- 只有系统待核验时必须允许生成。

### 12.3 状态与无障碍

- 多状态按钮按“默认→爱心→星形→叉号→默认”循环，图标在文字前。
- 状态文字“偏好/必须/不要”不直接显示，但读屏名称完整。
- 不依赖颜色表达状态；键盘可操作，焦点定位可见。
- 红色不用于普通选填缺失；系统待核验不使用阻塞色。

### 12.4 前后端一致性

- 前端预检通过的请求不能再因相同字段规则被后端判为格式错误。
- 后端返回的字段错误必须包含 `field_id`、错误码和用户可理解文案。
- 配置版本支持发布、回滚和缓存失效；同一版本在不同环境语义一致。
- 基础必填、每个条件分支、清空/恢复草稿、跨字段冲突和系统待核验均有自动化测试。

## 13. 实施顺序与发布门槛

### 13.1 实施顺序

| 顺序 | 工作项 | 完成定义 |
|---:|---|---|

### 13.2 不允许带缺口发布的门槛

以下任一项失败时不得发布到主干生产版本：

- 76 字段覆盖数量、唯一性或分类统计不一致；
- 前端显示“可以生成”，后端却因同一必填规则拒绝；
- 只有系统待核验时生成按钮被禁用或请求未发送；
- 场景必填出现后没有说明原因，或没有补充/修改上游选择的解除路径；
- 选填字段留空被标红，或无效半成品无法清空；
- 后端只返回“请求格式不正确”，没有可定位的 `field_id`；
- 配置版本变化后仍命中旧 ETag，或生成记录无法追溯所用配置版本；
- 多状态按钮视觉展示“偏好/必须/不要”文字，或只靠颜色表达状态；
- 人员加减后总人数与年龄分类不一致，或系统再次猜测具体同行关系。

### 13.3 最小自动化场景

| 场景 | 必须断言 |
|---|---|
| 国内双人、预算未知 | 基础必填完成即可生成；跨境、儿童、自驾字段不触发 |
| 带儿童家庭 | 监护和儿童安排触发；选择“无特殊安排”可完成；系统核验不阻塞 |
| 国际旅行 | 国籍、护照、签证、药品状态触发；回答后只计系统核验 |
| 金额预算 | 币种、金额范围、包含项目触发；切换到未知预算后解除金额分支阻塞 |
| 自驾偏好 | 驾驶详情触发；补充或取消自驾均可解除；不得静默丢弃偏好 |
| 自定义房间 | 设置房间数后房型配置触发；容量不足报具体差额；清空后恢复系统安排 |
| 高风险活动 | 保险状态触发；选择“没有/不确定”后允许生成但保留风险核验 |
| 旧草稿恢复 | 新分类重新计算，不丢答案；失效分支不计 blocker，重新触发时恢复原值 |
| 配置损坏 | 前后端均整体回退，不出现部分字段失去必填约束 |
| 配置版本竞争 | 提交旧版本时明确要求刷新，保留答案并按新版本重新校验 |
