## 通用起点

任何工单先做这三件事，顺序不要换：

1. **拿到 `request_id` 或 `trace_id`。** 用户能从错误提示里读到 `request_id`
   （api 把它回写到 `x-request-id` 响应头与错误体）。有它就能在日志里精确定位；
   没有它只能靠「大概几点、什么目的地」去猜。
2. **查那条任务的状态与 `stage_timings`。**

   ```sql
   SELECT status, error_code, progress, warnings, t1_at, t2_at, stage_timings
     FROM generation_jobs WHERE id = $1;
   ```

   `stage_timings` 直接回答「时间花在哪一段」（十五章），`warnings` 回答
   「哪些降级发生过」（13.7）。

3. **判断是阻断还是降级。** 16.3 的判定表决定了任务该不该失败。
   `status = 'COMPLETED'` 而用户抱怨「图不对」，那是降级而不是故障 ——
   处置方向完全不同。

**不要做的事**：不要直接改 `generation_jobs.status`。状态机的每条边都带谓词
（16.1），手工改会绕过它们 —— 而绕过的后果是那条任务此后既不会被消费也不是终态。
要终止一个任务用 13.10 的取消端点。

## T1 SLA 违约

**告警**：`TravelJobT1SlaBreach` —— T1（计划可读）P95 超过 75 秒，持续 15 分钟。

**这个告警说的是**：用户从点下按钮到能读到文字版计划，第 95 百分位超过了
21.2 的目标。它**不**说明系统坏了 —— 更常见的原因是排队或模型变慢。

**按顺序排除**

1. **是不是在排队？**

   ```promql
   histogram_quantile(0.95, sum by (le) (rate(travel_job_duration_seconds_bucket{stage="QUEUED"}[15m])))
   ```

   T1 的计时起点是**入队时刻**（21.2），因此队列积压会直接顶高它。
   排队占大头 → 扩 generation-worker 副本数（Helm 的
   `services.generationWorker.replicas`）。

2. **是不是模型变慢？**

   ```promql
   histogram_quantile(0.95, sum by (le, model) (rate(travel_llm_duration_seconds_bucket{outcome="succeeded"}[15m])))
   ```

   同时看 `travel_llm_duration_seconds{outcome="timeout"}` 的比率。
   超时占比升高说明供应商有问题，此时**不要**扩副本 —— 那只会让更多任务
   同时等在超时上，并且成本照花。

3. **是不是校验在反复重跑？** 见下面的[修复轮次异常](#修复轮次异常)。

4. **分档看。** 告警只看 ≤7 天那一档；如果 8～14 天档同时恶化，
   多半是共因（模型或数据库）。只有长档恶化则是分段生成那条路径的问题（6.3）。

**不要做的事**：不要提高 `JOB_TIMEOUT_MS`。300 秒的上限是成本约束（16.3），
放宽它只会让超时的任务花更多钱之后再失败。

## T2 SLA 违约

**告警**：`TravelJobT2SlaBreach` —— T2（页面可看）P95 超过 155 秒，持续 15 分钟。

**这个告警说的是**：用户能读到文字版计划之后，又等了太久才看到带图的完整页面。

**155 秒是怎么来的**：`T1(75) + 素材解析窗口(80)`。这三个数字必须一起改 ——
只改一个的后果是告警变噪音（阈值偏紧）或永不触发（偏松）。素材窗口 80 秒
= `IMAGE_TIMEOUT_MS(40) × 2 个候选`，也等于 `IMAGE_JOB_AI_BUDGET_MS`。

**按顺序排除**

1. **是不是主模型在拖？**

   ```promql
   sum by (kind) (rate(travel_ai_failover_total{position!="0"}[30m]))
     / sum by (kind) (rate(travel_ai_failover_total[30m]))
   ```

   占比高说明每次生成都先等满主模型的 40 秒才切候选。
   处置见[主模型胜出率下降](#主模型胜出率下降)。

2. **是不是缓存没命中？**

   ```promql
   travel_asset_cache_hit_ratio{role="HERO_BACKGROUND"}
   ```

   命中率掉了意味着大量请求要现场等 AI —— 那条路径本来就不该在首屏上。
   处置见[Hero 缓存命中率下降](#hero-缓存命中率下降)。

3. **是不是任务预算被吃满了？** 在 generation-worker 日志里找
   `JOB_AI_TIME_EXHAUSTED`。它出现说明单个任务的 AI 累计耗时到了
   `IMAGE_JOB_AI_BUDGET_MS`，后续槽位直接走占位图 —— 这是**设计行为**
   （时延闸生效），但频繁出现意味着候选或超时配得太宽。

**不要做的事**：不要单独调高 `IMAGE_JOB_AI_BUDGET_MS` 来「让它别再截断」。
那一项超过 80 秒时启动日志会打 `IMAGE_SLA_BUDGET_EXCEEDED`，并且这条告警的
155 秒阈值必须同步改 —— 否则你只是把违约从「被告警」变成「不被告警」。

## 队列积压

**告警**：`TravelQueueBacklogHigh` —— `max by (queue) (travel_queue_depth) > 8`，持续 5 分钟。

**这条告警存在的理由**：它是唯一一条**先行**指标。

T1 SLA 从提交算起，包含排队时长，所以看上去已经能发现积压 —— 但直方图
只在任务**完成时**落样本。队列积压到 200 条时，T1 的 P95 反映的是三分钟前
完成的那批，而正在受苦的这 200 个用户还一个都没进过直方图。等它们进去时
人已经走了。这条告警是在第一个用户超时**之前**介入的唯一窗口。

**先分清两种完全不同的原因**

```promql
# 消费还在进行吗？
sum(rate(travel_job_total[5m]))
```

| 现象                                  | 含义                           | 处置                               |
| ------------------------------------- | ------------------------------ | ---------------------------------- |
| 深度涨，`travel_job_total` **也在涨** | 提交速率超过消费能力（真积压） | 加 Worker 副本                     |
| 深度涨，`travel_job_total` **不动**   | Worker 全挂或卡住              | 先查 Worker 健康与日志，不要加副本 |

**加副本要加对的那个**。两个队列的处置完全不同，这也是 `queue` 标签存在的理由：

| `queue` 标签值           | 加哪个            |
| ------------------------ | ----------------- |
| `travel-plan-generation` | generation-worker |
| `travel-plan-export`     | render-worker     |

**积压不会无限增长，但那不是好事。** 排队超过 600 秒的任务会在消费的第一件事
就失败掉（`JOB_QUEUE_TIMEOUT`）—— 在花掉 LLM 调用**之前**。这是刻意的：等了
11 分钟的用户早已离开页面，而生成它要花一次模型调用的钱。但它的意义是
**系统在丢请求而不是在变慢** —— 看到深度在 8 到几十之间封顶时，很可能已经
在报废任务了。

> **扩容后必须同步抬阈值。** 8 这个数字按**两个** generation-worker 副本的
> 容量定的（concurrency 硬编码为 2，T1 预算 75 秒、处理约 20～30 秒，
> 因此单副本下深度过 4 就吃 T1）。加到五副本后，深度 8 是健康的，
> 不抬阈值它就只是噪声。阈值在 `deploy/prometheus/rules/travel-poster.rules.yml`。

**注意这条告警用 `max` 而不是 `sum`**：队列在 Redis 里只有一份，而每个 API 副本
都上报同一个全局值。改成 `sum` 会让阈值随 API 副本数缩水。

**采样本身也会失败**：日志里的 `QUEUE_DEPTH_SAMPLE_FAILED` 说明那一轮没采到
（Redis 抖了）。此时 gauge **保持上一次的值而不置 0** —— 置 0 会在积压期间
造成一个假的「已恢复」，而告警的 `for: 5m` 恰好会被那个假恢复重置掉。

### 背压准入（深度过高时直接拒新任务）

上面那句「系统在丢请求而不是在变慢」曾经是唯一的结局：任务先被收下
（占一格日配额、一笔 CR 预留、一行用户看得见的计划），然后在 600 秒后
`JOB_QUEUE_TIMEOUT`。现在入口会先拒：

| 环境变量                    | 缺省 | 作用                                                   |
| --------------------------- | ---- | ------------------------------------------------------ |
| `QUEUE_ADMISSION_MAX_DEPTH` | 40   | 深度超过它时生成／导出端点返 503 `SYS_QUEUE_SATURATED` |

阈值**不等于告警阈值 8**，且故意高得多：8 是「叫人扩容」的信号，
把准入也定在 8 会把告警有意容忍的五分钟瞬时突发全变成用户可见的 503。
40 是从 600 秒排队上限反推的：单副本约 4.5 任务/分钟 ⇒ 600 秒约 45 条，
超过它再接下来的任务**在开始之前就会先撞上 600 秒**。

```promql
# 已经开始拒请求了吗
sum by (queue) (rate(travel_queue_admission_rejected_total[5m]))
```

这条曲线非 0 是比积压告警**更硬**的扩容信号 —— 积压可以容忍一阵，
真实用户拿到 503 不能。

> **扩容后要同时抬两个数**：告警阈值（8）与准入阈值（40）。
> 五副本的吞吐下深度 40 远达不到 600 秒，不抬就是在白白丢请求。

**采样挂了时准入放行（fail open）。** 从未成功采样过时不做判定 ——
反过来的后果是一个观测组件的故障变成全站不可生成。因此
`QUEUE_DEPTH_SAMPLE_FAILED` 持续出现时，准入也是失效的。

## 请求被限流（429 SYS_RATE_LIMITED）

**没有告警** —— 它按设计就会在受攻时大量触发，告警只会成为噪声。
在日志里按 `error_code=SYS_RATE_LIMITED` 与源 IP 聚合。

| 环境变量               | 缺省  | 作用                                       |
| ---------------------- | ----- | ------------------------------------------ |
| `RATE_LIMIT_MAX`       | 300   | 每 IP 每窗口允许的请求数。**`0` 关闭限流** |
| `RATE_LIMIT_WINDOW_MS` | 60000 | 窗口长度                                   |

**它与 21.4 的业务配额不是一回事。** 业务配额（`AUTH_RATE_LIMITED`，
每分钟 1／3 次生成）在**身份解析之后**判定，而身份解析本身就要查
Redis 与数据库 —— 不带有效 Cookie 的洪水根本走不到那一层，却已经把依赖
打满了。这一层在那之前，不看身份。

**三个必须知道的边界**

1. **每副本计数，不是全局。** 用内存而不是 Redis：后者把一条 Redis 往返加进
   每一个请求（包括洪水里的），限流器自己就成了放大器。
   实际上限是 `RATE_LIMIT_MAX × API 副本数`。
2. **探针与 `/metrics` 豁免。** 不豁免的后果是存活探针被打成 429 → 实例被
   重启，Prometheus 被拦 → 监控在最需要它的时候断掉。
3. **未匹配的路径（404）不受限流。** Fastify 的 `onRequest` 钩子不跑 404 路径。
   对随机路径的洪水靠网关挡，不靠这一层 —— 但 404 本身不碰数据库，
   代价只是 TLS 与解析。

**真用户被误伤时**：先确认不是前端轮询太快（任务状态每 1～2 秒一次是正常的，
300/分钟 已为此留了余量）；确认后抬 `RATE_LIMIT_MAX`，而不是关掉它。

## 主模型胜出率下降

**告警**：`TravelAiFailoverRatioHigh` —— 超过 20% 的模型调用要靠备选候选才成功，
持续 15 分钟。

**这个告警存在的理由**：故障转移的作用就是**把主模型的故障掩盖成「慢一点」**。
主模型完全挂掉时，成功率、`travel_ai_image_total`、任务状态全都正常，
只有 P95 悄悄涨一截 —— 而那会被「本来就有波动」解释掉。
这条告警是唯一能把「主模型有问题」从「今天有点慢」里分出来的信号。

**先看清是哪一种**

```promql
sum by (kind, position, outcome) (increase(travel_ai_failover_total[30m]))
```

| 现象                   | 含义                               | 处置                                                |
| ---------------------- | ---------------------------------- | --------------------------------------------------- |
| `position="1"` 占多数  | 主模型超时或报错，候选 2 顶住了    | 查主模型在中转站侧的状态；确认候选顺序              |
| `position="none"` 有量 | 整条链都失败                       | 图像侧降级占位图（用户仍有产物）；文本侧任务 FAILED |
| 只有 `kind="IMAGE"`    | 图像端点的问题                     | 单独换图像池的主模型                                |
| `kind` 两者都有        | 中转站整体问题（凭据、限流、网络） | 先查凭据与账户余额                                  |

**确认当前候选顺序**

```bash
pnpm model:pool -- --list
```

输出里每一档都会显示**实际生效**的候选序列（第一个就是主模型）。

**换掉主模型**

```bash
# 把顺序调整成把还活着的那个放前面。列表顺序即尝试顺序
# 模型 ID 必须带 provider 前缀（ofox 的形式），否则那个候选恒失败
# --models 的值必须加引号 —— PowerShell 会把不加引号的 a,b 拆成数组再用空格拼回
pnpm model:pool -- --set-pool paid --kind IMAGE --models "openai/gpt-image-2,google/gemini-3-pro-image" --dry-run
pnpm model:pool -- --set-pool paid --kind IMAGE --models "openai/gpt-image-2,google/gemini-3-pro-image"
```

**改完最多 60 秒生效**（池的进程内缓存 TTL），不需要重启 Worker。

**两次命令都会把旧值与一条回退命令打出来**：

```text
已写入 IMAGE 池 paid = [openai/gpt-image-2, google/gemini-3-pro-image]
覆盖前：IMAGE 池 paid = [google/gemini-3-pro-image, openai/gpt-image-2]  # 这一档只放便宜模型
回退命令（池无版本历史，只有这一条退路）：
  pnpm model:pool -- --set-pool paid --kind IMAGE --models "google/gemini-3-pro-image,openai/gpt-image-2"
```

**把那一行存下来。** 池没有版本历史 —— `planner_config_*` 与 `credit_price_*`
都是草稿加发布、能发布回上一版，而池是直接覆盖写。下面那条 `--unmap`
**不是**回上一版，它是放弃整个池。因此应急时唤回旧配置的唯一路径就是
上面那行命令，而它只存在于你的终端输出里。

> **`--note` 不传就不动。** 只改 `--models` 不会抹掉备注（应急时没人会先抄备注）。
> 要改备注传 `--note "新内容"`，要清空传 `--note ""`。
> 这也是上面回退命令不带 `--note` 的原因 —— 备注会自己活下来。

**不要做的事**：不要把候选数一路加上去。图像侧每多一个候选就多占 40 秒的
素材窗口，而窗口一共只有 80 秒 —— 超出的部分会被静默截断，见下一节。

**紧急回滚：让某一档回落到 env 单模型**

池本身配错（模型名全写错、整池指向已下线的端点）时，最快的止血是把映射
删掉 —— 那一档立刻回落到 `LLM_MODEL` / `IMAGE_MODEL` 的单模型行为，也就是
配置池之前的样子。

```bash
pnpm model:pool -- --unmap --kind IMAGE --min-tier 10 --dry-run   # 先看要动什么
pnpm model:pool -- --unmap --kind IMAGE --min-tier 10
```

**同样最多 60 秒生效**，不需要重启 Worker。档位打错时命令会说「没有这条映射」
并给非 0 退出码 —— 不会静默成功。

池不再需要时再删池本身；仍被映射引用时命令会拒绝并列出还指着它的档位：

```bash
pnpm model:pool -- --drop-pool paid --kind IMAGE
```

## 候选池配置被截断

**告警**：`TravelAiPoolClamped` —— 有候选池的配置候选数被时延预算削过。
**没有 `for`**：这度量的不是波动而是配置状态。

**这个告警说的是**：某一档的 `max_candidates` 大于时延预算允许的值，
运行时只试了截断后的数量。**配置看起来生效了，实际没有。**

**为什么是截断而不是拒绝**：候选数存在数据库里，运营可以在系统运行时改。
拒绝服务会让一次配置失误变成用户拿不到计划；截断只是少试几个候选。
但截断必须可见 —— 这条告警就是那个「可见」。

**看削掉了多少**

```bash
pnpm model:pool -- --list
```

被削过的那一行会带 `← 被时延预算削过`，并同时显示配置值与实际值。

**两个方向的处置，选一个**

1. **下调 `max_candidates`**（推荐）：接受时延预算，把配置改成真实生效的值。

   ```bash
   pnpm model:pool -- --map --kind IMAGE --min-tier 10 --pool paid --max-candidates 2
   ```

2. **调高时延预算**：`IMAGE_JOB_AI_BUDGET_MS`。**必须同时**调
   `TravelJobT2SlaBreach` 的阈值与 21.2 的 T2 目标，否则 T2 会开始违约而
   告警照旧。超过 80 秒时启动日志会打 `IMAGE_SLA_BUDGET_EXCEEDED` 提醒这件事。

**判断上限**：这是**一条候选链**的上限，不是整个任务的。

| kind    | 公式                                               | 默认配置             |
| ------- | -------------------------------------------------- | -------------------- |
| `IMAGE` | `floor(IMAGE_JOB_AI_BUDGET_MS / IMAGE_TIMEOUT_MS)` | `80000 / 40000 = 2`  |
| `LLM`   | `floor(LLM_CHAIN_BUDGET_MS / LLM_TIMEOUT_MS)`      | `100000 / 30000 = 3` |

`LLM_CHAIN_BUDGET_MS` 不是 env，而是 16.3 的 300 秒任务上限的三分之一 ——
一个任务最多串行调三次模型（14 天分两段，加一次修复），每次都可能是一条
完整的链。要改它得改代码（`model-selection.ts`），因为它与 `JOB_TIMEOUT_MS`
是联动的。

**任务窗口是另一回事**：一条链装得进上限，不等于同一任务的多条链加起来
也装得进。图像侧由 `AiImageBudget` 在运行时把关（每次 `reserve` 都算
「现在放行的话它最晚什么时候结束」），超出窗口的槽位拿到
`JOB_AI_TIME_EXHAUSTED` 并降级为占位图 —— 那是**正常的保护**，不是故障。
若这类 warning 变多，说明候选数或单候选超时相对窗口配得太大。

## ofox 模型进池前的兼容性检查

**不是告警，是一份配池前要看一眼的清单。** 放在这里是因为配错的症状会让你
先撞上 `TravelAiFailoverRatioHigh`（上两节），而那条告警看不出根因是配置。

### 先记住一条事实：换模型不用换 URL

ofox 有三套协议，**URL 与鉴权头都不同**（key 相同）：

```text
OpenAI 兼容    https://api.ofox.ai/v1          Authorization: Bearer $KEY
Anthropic 原生  https://api.ofox.ai/anthropic   x-api-key: $KEY
Gemini 原生     https://api.ofox.ai/gemini      x-goog-api-key: $KEY
```

但**每一个模型都能走 OpenAI 兼容协议** —— 原生协议是额外选项，不是唯一途径。
因此池里可以混装跨厂商模型，而我们只靠一个 base URL + 一个 key：

```bash
pnpm model:pool -- --set-pool paid --kind LLM \
  --models "openai/gpt-5.5,anthropic/claude-opus-4.8,google/gemini-3.5-flash"
```

**切换发生在请求体的 `model` 字段上，URL 不变。** 因此不要把 `LLM_BASE_URL`
配成每个模型一个地址 —— 没有那个概念。

> `LLM_BASE_URL` / `IMAGE_BASE_URL` 填 **`https://api.ofox.ai`，不带 `/v1`**。
> 代码自己拼 `/v1/chat/completions` 与 `/v1/images/generations`；
> ofox 文档里那个带 `/v1` 的是给 SDK 用的（SDK 自己补后半段）。
> 填错会在启动时被拒（R-59），不会变成运行期的 404 重试风暴。

### 两类模型不能进池

我们的客户端只打两个端点：文本 `/v1/chat/completions`、图像 `/v1/images/generations`。
不在这两个端点上的模型配进池就是一个永远失败的候选：

| 类别               | 例子                                                                 | 它只在哪里可用  |
| ------------------ | -------------------------------------------------------------------- | --------------- |
| **responses-only** | `openai/gpt-5.2-codex`、`openai/gpt-5.3-codex`、`openai/gpt-5.4-pro` | `/v1/responses` |
| **视频**           | `alibaba/wan-2.7`、`alibaba/happyhorse-1.1` 一类                     | `/v1/videos`    |

判断方法：看模型目录的 **Endpoints 列**。含 `chat` 的能进文本池，
含 `images` 的能进图像池；只写 `responses` 或 `/v1/videos` 的不能。

```bash
curl -s https://api.ofox.ai/v1/models -H "Authorization: Bearer $OFOX_API_KEY"
```

（ofox 官方 cookbook 仓库的 `MODELS.md` 是这份目录的可读快照，含 Endpoints 列与单价。）

### 配错了会看到什么（这一条是本节存在的理由）

**不会报错。** 那个候选快速失败（4xx），failover 立即转下一个 ——
这正是故障转移该做的事。于是：

```text
用户拿到了计划（备选顶住了）
任务状态正常，错误率正常
travel_ai_failover_total{position="1"} 持续增长
→ 撞上 TravelAiFailoverRatioHigh，而那条告警说的是「主模型有问题」
```

于是你会去查中转站侧的模型状态，而那个模型在中转站上**完全正常** ——
它只是不在我们打的那个端点上。

**区分方法**：结构性不兼容是**恒定**的 —— `position="1"` 的占比几乎是 100%
且不随时间波动；上游抖动是间歇的。看一小时的曲线就能分开。

**为什么不在写入时拦住**：设计稿 3.7.10 刻意不做「写入时校验模型名存在」——
中转站没有可靠的模型列表接口，而一份会过期的白名单比没有白名单更糟：
它会把新上线的模型拒在外面。代价就是本节 —— 靠人在配之前看一眼。

### 一个已经处理好的坑，不要“修”它

**Gemini 图片模型（`google/*-image-*`）不接受 `n` 参数。** 它们是
`generateContent` 模型，只返回单图。代码已经**不发 `n`**（R-60），
因此这类模型**可以**进图像池。

如果你在某份示例里看到 `n: 1` 并想把它补回去 —— 不要。
那一个零收益的字段会换掉一整类模型。

## Hero 缓存命中率下降

**告警**：`TravelHeroCacheHitRatioLow` —— `HERO_BACKGROUND` 的缓存命中率低于
0.7，持续 30 分钟。

**为什么它比 T2 违约更早响**：命中率是「20 秒 AI 生成不进入首屏路径」这套设计

**判定**

```promql
sum by (strategy) (rate(travel_asset_resolution_total{role="HERO_BACKGROUND"}[30m]))
```

| `strategy` 占比升高        | 含义                              | 处置                                |
| -------------------------- | --------------------------------- | ----------------------------------- |
| `ai_generated`             | 缓存里没有当前热门目的地          | 预热（见下）                        |
| `placeholder` / `gradient` | AI 也没成 —— 额度耗尽或供应商故障 | 看[成本超支与熔断](#成本超支与熔断) |
| `local_library`            | 素材库在兜，但分数可能偏低        | 看 `travel_asset_match_score` 分布  |

**缓存预热**

```bash
# 先看键与规模，不花钱
pnpm assets:preheat -- --dry-run --manifest infrastructure/seed/preheat-destinations.jsonl

# 真的预热（需要 IMAGE_MODE=direct|gateway 与真实凭据）
pnpm assets:preheat -- --manifest infrastructure/seed/preheat-destinations.jsonl
```

清单里的 `place_id` **必须来自客户端用的同一个地理编码器**。自己编一套 ID 会让
预热键与真实请求的缓存键永远不同 —— 600 张图一次都不会命中，而命中率指标
看起来「就是上不去」。

`IMAGE_MODE=fake` 下预热产出的是渐变占位图，不可作为上线预热（CLI 会警告）。

## 占位图占比升高

**告警**：`TravelAssetPlaceholderRatioHigh` —— 超过 20% 的素材槽位降级为占位图，持续 15 分钟。

**这条告警存在的理由**：降级是静默的，而它是唯一能看到降级规模的信号。

五层降级链落到最后一层（渐变占位图）时，**所有其他信号都是绿的**：

```text
任务 COMPLETED
页面 ready
错误率正常
travel_render_degraded_total 不动
→ 用户拿到一份「完整」的产物，只是图都是色块
```

`TravelHeroCacheHitRatioLow` 盖不住这个：它只看 Hero，而且只看缓存那一层 ——
素材库、搜索、AI 三层都没接住时它不一定会响。

### 先定位是哪一层没接住

```promql
# 五层各命中多少（排除路线图）
sum by (strategy) (
  rate(travel_asset_resolution_total{role!="ROUTE_MAP",outcome!="skipped"}[30m])
)
```

| 哪一层占比反常             | 含义                      | 处置                                                 |
| -------------------------- | ------------------------- | ---------------------------------------------------- |
| `cache_hit` 低             | 预热没覆盖当前热门目的地  | 看「预热库构建方案」补目的地；先确认 `place_id` 口径 |
| `local_library_match` 低   | 素材库太空或评分卡在 0.65 | 查分数分布直方图；轨道 B 灌更多真实照片              |
| `licensed_source_match` 低 | 搜索层没开或在熔断        | 查 `IMAGE_SEARCH_MODE`、日预算、连续失败计数         |
| `ai_generation` 低         | 额度耗尽或供应商挂了      | 查 `travel_ai_failover_total` 与日预算熔断           |

### 两个容易误判的地方

**一、`static_default` 不等于「用户看到了占位图」。** 这个策略名被两种结局共用：

```text
outcome="fallback"  真的给了占位图，用户看得到
outcome="skipped"   槽位被跳过，模板不渲染那个位置
```

告警只算前者。手工查分布时如果不带 `outcome`，你会看到一个偏高的数字。

**二、匿名用户的冷组合必然落到占位图。** `QUOTA_ANON_AI_HERO` 是 0（设计如此），
因此候选链对匿名用户只有四层。匿名流量占比高的时段这条告警会偏高，
这不是故障 —— 先按 `user_type` 分一下再下结论（`travel_job_total` 带那个标签）。

> **阈值 0.2 是起始值。** 21.2 措施二期望预热覆盖 ≥ 80% 的 Hero 请求，
> 因此健康状态下占位图应当只是残余。但预热覆盖率从未在生产规模验证
> （门禁 #17 是 manual），现在取 5% 会成噪声。实测出真实命中率后应当收紧。

## 图标加载失败

**告警**：`TravelIconLoadFailure` —— `travel_icon_load_failure_total` 十分钟内有
增长。**没有 `for`：一次就是缺陷**（验收标准 5 要求恒为 0）。

**这不是网络问题。** 9.1 把 19 个图标内联进构建产物，运行期没有请求可失败。
计数大于 0 只有一种原因：ViewModel 里出现了 `@tps/icon-library` 清单外的图标

**处置**

1. 在渲染出的页面里找 `[data-icon-missing]` 属性，它的值就是那个未知的图标名。
2. 对照 `packages/icon-library/src/index.ts` 的三张映射表
   （`MODULE_ICON_BY_KEY` / `PERIOD_ICON_BY_ENUM` / `TRANSPORT_ICON_BY_ENUM`）。
3. 补映射并加图标，或者改 ViewModel 侧的取值。

**这一条不能靠重启或回滚缓解** —— 它是数据与清单不匹配，重启后还是同一份数据。

## 素材图片加载失败

**告警**：`TravelAssetImageLoadFailureRatioHigh` —— `travel_render_asset_image_failure_total`
占 `travel_render_asset_image_seen_total` 超过 50%，持续 15 分钟。

**这一条最危险的地方是它以前完全没有信号。** `RenderReadyProbe` 刻意让加载失败的
图片**不阻塞就绪**（十八章降级链：一张坏图不该让整份导出作废）。那个决定是对的，
但它的副作用是素材全部取不到时：页面照样 ready、`degraded` 仍是 false、
导出仍然 `COMPLETED`、健康检查全绿 —— 而用户拿到的长图里每个图片位置都是空白。

**用比例而不是计数判定**：「21 张里坏 1 张」是降级链在正常工作，
「21 张全坏」是配置错误。只看计数分不出这两者。

**处置**（按可能性排序，前两条是配置问题，第三条才是数据问题）

1. **`S3_PUBLIC_BASE_URL` 在渲染容器内能否解析。** 这个地址有两个网络视角不同的
   消费者：用户的浏览器与 render-worker 容器内的 Chromium。填了只有一侧能解析的
   地址（`localhost` / `minio:9000`）必有一侧取不到图。

   ```bash
   docker exec tps-render-worker node -e "fetch(process.env['S3_PUBLIC_BASE_URL']).then(r=>console.log(r.status)).catch(e=>console.log(e.name))"
   ```

2. **素材桶是否允许匿名读。** 素材 URL 是裸拼的普通 `<img src>`，没有签名 ——
   桶私有就一律 403。`minio-init` 会设置它，换成托管对象存储时要自己配。

   ```bash
   docker run --rm --network travel-poster-system_default --entrypoint sh \
     minio/mc:RELEASE.2025-04-16T18-13-26Z -c \
     "mc alias set local http://minio:9000 tps tps_local_dev_only >/dev/null && mc anonymous get local/tps-assets"
   # 期望 download；若是 private，用 mc anonymous set download local/tps-assets 修
   ```

3. **对象是否还在。** 素材 URL 会被写进 `plan_presentations.view_model` 并
   **永久保存**（19.3），而对象本身可能已被清理。素材桶按设计不挂生命周期规则，
   所以这一条只会在有人手工删过对象时出现。

**改了 `S3_PUBLIC_BASE_URL` 却没生效**：19.2 的素材缓存命中时直接复用 `assets`
表里已存的 URL（首次入库时按当时的前缀拼好的），因此改配置 + 重启对**已缓存的
素材无效** —— 新生成的计划里仍是旧地址。要么清素材缓存，要么批量改库。
实测过：改完重启后连续五次生成，`view_model` 里全是旧地址。

**日志**：render-worker 会记一行，全坏是 `error` 级、部分坏是 `warn` 级，
带 `broken` / `total` / `page_type` 三个字段。

## Chromium 反复重启

**没有告警，靠看指标**：`travel_render_browser_restart_total`。

一次重启不是事（自愈已经把它接住了），**反复重启才是**。

### 自愈做了什么（R-84）

21.2 的渲染模型是「1 browser + 3 page」。Chromium 崩溃后那个句柄从此是死的 ——
在自愈之前，后果是**后续每一个导出都失败**，直到有人重启进程。

现在：

```text
崩溃那一刻   3 个在途导出失败 → BullMQ 重试（这一次救不回来，page 已经没了）
下一个任务   取 browser 时发现断开 → 串行重启 → 正常跑
```

**重启是串行的**：concurrency 是 3，崩溃后三个任务同时来取，但只会启起一个
新的 Chromium。不串行的后果是三个各约 400MB 的实例同时存在 —— 把「崩一次」
变成「反复 OOM」。

### 看到重启后查什么

```promql
# 重启频率
increase(travel_render_browser_restart_total[1h])

# 同期的渲染失败（一次崩溃应当带倒不超过 3 个导出）
sum by (reason_code) (increase(travel_render_failure_total[1h]))
```

| 现象             | 含义                 | 处置                                          |
| ---------------- | -------------------- | --------------------------------------------- |
| 一小时 1～2 次   | 偶发（某个特大页面） | 不用动，自愈已经接住                          |
| 持续每几分钟一次 | 内存不够             | 先看 `/dev/shm`（下面），再考虑降 concurrency |
| 重启后立即又崩   | 启动就 OOM           | 提容器内存上限；当前上限存不下 3 个 page      |

**先看 `/dev/shm`。** 启动日志里有 `devShm` 一项（探测结果），重启时的 warn
日志也带 `dev_shm`。低于 256MB 时会自动加 `--disable-dev-shm-usage` 降级到磁盘，
而那会让渲染变慢 —— 容器里把 `/dev/shm` 调到 512MB 比降并发更划得来。

### 两个容易误判的地方

**一、重启计数不包含首次启动，也不包含关停。** `browser.close()` 同样会触发
`disconnected`，但关停时不计数 —— 否则这个指标每次部署都 +1，从此无法
判断真实稳定性。

**二、重启不会让已失败的导出变成成功。** 崩溃那一刻的三个导出仍然计入
`travel_render_failure_total` 并由 BullMQ 重试。自愈保证的是「重试能成功」，
不是「不曾失败」。

> **自愈的副作用是崩溃变得不可见。** 以前它以「导出全挂」的形式刺眼，
> 现在只是一次重试。这个指标是它唯一的信号 —— 不看它就不会知道
> 渲染进程正在反复 OOM。

## 修复轮次异常

**告警**：`TravelPlanRepairIterationsHigh` —— 程序化修复轮次 P95 达到 3，持续 1 小时。

**它指向的是我们的规则集，不是模型。** P95 贴到 3（3.2.2 的单次上限）意味着大量
正常输出被判成了违规，而代价是每个任务多花两次定向重生成的钱。

**判定**

```promql
topk(10, sum by (rule_id) (rate(travel_validation_violations_total[1h])))
```

按 `rule_id` 排序后看最常触发的那几条：

- 某条规则一枝独秀 → 大概率是那条规则本身过严，或它与另一条互相打架
  （V-12 的平移会撞 V-13 的收尾时间）。
- 多条均匀升高 → 更可能是模型或提示模板变了，查 `llm_prompt_version`
  与 `llm_model` 在 `travel_plan_versions` 里的分布。

**注意**：`travel_validation_violations_total` 含**修复后重跑**的轮次（有意如此，
见 plan-metrics.ts），因此它的绝对值不能读成「模型犯了多少错」，
只能读成「哪条规则最常触发」。

## 降级产物占比升高

**告警**：`TravelRenderDegradedRatioHigh` —— 降级产物占比超过 10%，持续 30 分钟。

**含义**：17.3 的四轮重渲染没兜住，产物交付了但排版拥挤
（`RENDER_OVERFLOW_UNRESOLVED`）。用户拿到的东西可用但不好看。

**判定**

```promql
histogram_quantile(0.95, sum by (le, template_id, page_type) (rate(travel_render_overflow_rounds_bucket[30m])))
```

- P95 贴到 4（最后一轮）→ 模板的默认版式对真实内容普遍偏紧。该改模板，
  而不是继续靠降级兜。
- 只有某个 `page_type` 恶化 → 那一类页面的内容量变了（比如 LLM 开始写更长的
  描述），查 12.3 的 `*_compact` 文案是否还够短。

**不要做的事**：不要放宽 `page-checks.ts` 的溢出容差。那会让「文字被裁掉」
变成「检测不到」—— 而验收标准 9 要防的正是文字遮挡。

## 中文字体故障

**告警**：`TravelCjkFontUnavailable` —— `travel_render_failure_total`
带 `reason_code="CJK_FONT_UNAVAILABLE"` 十分钟内有增长。**没有 `for`**。

**为什么这是 critical**：字形缺失会让页面变成豆腐块，而 17.5 明确
**不允许降级输出** —— 静默交付比失败更糟，用户会以为是自己浏览器的问题，
而我们的监控一片绿色。

**两个可能的位置**

1. **渲染容器内没有字体。**

   ```bash
   kubectl exec deploy/tps-travel-poster-render-worker -- fc-list | grep -ci noto
   ```

   为 0 → 镜像构建时的字体安装步骤失效（22.3.2 要求 `fc-cache -f -v` 之后
   校验 `fc-list | grep -ci noto` ≥ 1，构建期就该失败）。检查镜像标签是不是
   回滚到了一个旧版本。

2. **web 的 `/fonts/` 静态资源不可达。** 页面用 `@font-face` 加载子集，
   而 `RenderError.detail = 'BODY_FONT_NOT_SUBSET'` 说明 woff2 加载成功但
   CSS 变量没生效（`--tps-font-*` 被覆盖）；`CJK_FONT_UNAVAILABLE` 说明
   woff2 本身没加载上。

   ```bash
   kubectl exec deploy/tps-travel-poster-render-worker -- \
     curl -sI http://tps-travel-poster-web:3000/fonts/noto-sans-sc-subset.woff2
   ```

**立即止血**：关掉导出（`--set featureFlags.exportEnabled=false`）。
HTML 页面在用户自己的浏览器里渲染，用的是他的系统字体，不受影响；
而导出产物是在我们的容器里渲染的，那才是会出豆腐块的地方。

## 错误码排查

13.7 的错误码分四层处置。查一条失败任务时，先看 `error_code` 落在哪一层：

| 前缀                                 | 归属           | 典型处置                                                                                 |
| ------------------------------------ | -------------- | ---------------------------------------------------------------------------------------- |
| `REQ_*`                              | 用户输入       | 不需要运维介入。若某个码突然激增，看是不是前端改版发错了字段                             |
| `PLAN_LLM_*`                         | 模型或供应商   | 看 `travel_llm_duration_seconds{outcome}`；供应商故障时切 `LLM_MODE`（direct ⇄ gateway） |
| `PLAN_HARD_CONSTRAINT_UNSATISFIABLE` | 用户的约束互斥 | 不可重试（13.7 第四层），不占重试次数。激增说明某个约束组合被大量用户选中而规则集拒绝它  |
| `RENDER_*`                           | 渲染           | 见上面两节                                                                               |
| `JOB_TIMEOUT` / `JOB_QUEUE_TIMEOUT`  | 容量           | 前者查 `stage_timings` 找瓶颈；后者扩副本                                                |
| `SYS_INTERNAL_ERROR`                 | **我们的缺陷** | 门禁 #14 要求它占比 < 1%。超过就是有一类未分类的异常，查日志的 stack                     |

**死信队列**：重试耗尽的任务进 `dlq:travel-plan-generation`（13.7）。

```bash
redis-cli LRANGE dlq:travel-plan-generation 0 9
```

里面**只有标识符**（二十章：Redis 不放个人数据副本），拿 `jobId` 回数据库查详情。
重放需要人工确认原因已修复 —— 直接重放一批因同一缺陷失败的任务只会再失败一次。

## 成本超支与熔断

21.4 的三层成本约束，从紧到松：

| 层         | 触发                               | 表现                                                |
| ---------- | ---------------------------------- | --------------------------------------------------- |
| 单任务     | AI 图片 3 张 / LLM 1+2 次          | 后续槽位走占位图，记 `warnings`                     |
| 单任务失败 | 连续失败 2 次（R-38）              | 本任务停用 AI，不再等 20 秒超时                     |
| 全局熔断   | 日调用量达 `AI_IMAGE_DAILY_BUDGET` | 全局切「素材库 + 占位图」，`GENERATING_ASSETS` 跳过 |

**判定当前状态**

```promql
sum by (outcome) (rate(travel_ai_image_total[1h]))
```

`outcome="skipped"` 激增 = 熔断已打开或额度耗尽（这是**设计行为**，系统降级但可用）。
`outcome="failed"` 激增 = 供应商故障。两者分开是刻意的（见 asset-metrics.ts）。

**处置顺序**

1. 确认不是被刷：`travel_identity_total{event="anon_created"}` 与
   `travel_job_total{user_type="ANONYMOUS"}` 的比率异常升高说明有人在批量建号。
   21.4 的 IP 维度限速（`QUOTA_IP_PLANS_PER_DAY`）是唯一不依赖 Cookie 的兜底。
2. 真的是正常流量增长 → 提高 `AI_IMAGE_DAILY_BUDGET`，或者先扩预热库
   （命中缓存不花钱）。
3. 要立刻停止出血 → 关生成开关（TP-5-10）：

   ```bash
   helm upgrade tps deploy/helm/travel-poster --reuse-values \
     --set featureFlags.generationEnabled=false
   ```

   保留导出：它只花几秒 Chromium CPU，而用户至少还能把已有计划带走。

## 匿名清理异常

15.1 的保留期清理由 retention-worker 执行。它**必须单副本**
（Helm 的 `replicas: 1` + `Recreate`）—— 多副本会并发清理同一批到期用户。

**告警之外的健康信号**：`travel_knowledge_rows` 应当**单调增长**。长期不动意味着

- 清理任务没在跑（进程挂了、或者间隔配得过长），或者
- 到期用户的计划都没有向量（嵌入服务一直在失败，`plan_embedding IS NULL`
  的行不参与转存）。

**判定**

```sql
-- 还有多少到期未清理的匿名用户（含 30 天宽限期）
SELECT count(*) FROM users
 WHERE user_type = 'ANONYMOUS'
   AND status = 'ACTIVE'
   AND anon_expires_at < NOW() - INTERVAL '30 days';

-- 知识库累积量与最近一次转存
SELECT count(*), max(created_at) FROM plan_knowledge;
```

**清理任务报错时的处置**：单个用户失败不会中断整批（见 purge.ts），因此
`travel_anon_purge_total{outcome="failed"}` 有零星计数是可容忍的。持续失败
最常见的原因是外键顺序 —— `plan_asset_bindings` 是 `ON DELETE RESTRICT`
（15.3，素材是共享资源），因此删用户前必须先转存再删绑定。

**绝对不要做的事**：不要为了「清干净」而手工 `DELETE FROM users WHERE ...`。
知识转存与删除在**同一个事务**里（purge.ts）—— 手工删会跳过转存，
那部分行程知识永久丢失，而它对用户已经不可识别（合规上本来是允许保留的）。

## 归并失败重放

13.9.4 的匿名归并把匿名用户的业务行改挂到目标账号上，整个过程在一个事务里。

**判定**

```promql
sum by (outcome) (rate(travel_identity_total{event="merge"}[1h]))
```

```sql
-- 停在 MERGED 但业务行还挂在原 user_id 上的（不该存在）
SELECT u.id FROM users u
 WHERE u.status = 'MERGED'
   AND EXISTS (SELECT 1 FROM travel_plans p WHERE p.user_id = u.id);
```

**重放**：归并是幂等的（门禁 #24），因此重复执行安全。让用户重新登录一次即可 ——
登录流程会检测到当前匿名身份并再次触发归并。

**为什么不提供一个「手工归并」的运维脚本**：归并涉及 `idempotency_key`
的保持（门禁 #25：历史键不重算，否则会撞唯一约束）与四张表的改挂顺序。
一个绕过 `mergeAnonymousInto` 的脚本迟早会漏掉其中一步，而漏掉的表现是
「用户的部分历史消失了」—— 那是不可逆的。要修就修那个方法本身。

## 重新打开匿名入口（P7 的回切）

**症状/触发**：产品决定恢复「未注册用户也能直接生成」，或需要临时回切验证。

**背景**：P7 把匿名入口关成了默认行为，但匿名体系的代码、数据库结构与测试
全部保留（详细设计 16.7 / R-54）。因此回切**不需要迁移、不需要数据修复**。

**处置步骤**

1. 改一个开关：

   ```yaml
   # deploy/helm/travel-poster/values.yaml
   featureFlags:
     anonymousEnabled: true
   ```

   或在非 Helm 的部署里设 `FEATURE_ANONYMOUS_ENABLED=true`。

2. 只需重启 **api**：另外四个服务不读这个开关。

3. 验证（按顺序，任一失败就停下）：

   ```bash
   # 会话端点重新签发匿名令牌，而不是返回 401
   curl -i https://<host>/api/v1/auth/session | grep -E 'HTTP/|tp_anon'
   ```

   期望：`200` 且响应头里有 `tp_anon=`。

4. 看两个互斥的指标翻转：

   ```promql
   # 应当开始上涨
   sum(rate(travel_identity_total{event="anon_created"}[5m]))
   # 应当降到 0
   sum(rate(travel_identity_total{event="anonymous_rejected"}[5m]))
   ```

   两者互斥（见 16.7）。如果 `anonymous_rejected` 没有归零，说明有实例还没
   重启完，或者开关只改到了一部分副本。

**注意事项**

- **存量匿名数据可能已经被清理掉了。** 保留期是 30 天（15.1），因此关闭期间
  超过 30 天的匿名行连同其产物已被删除，知识已转存到 `plan_knowledge`。
  回切不会把它们找回来。
- 回切后 `RISK-11`（匿名被用于刷 AI 成本）重新生效，因此同时确认
  TP-1-39 的 IP 防刷配置仍在（`QUOTA_IP_ANON_CREATE_PER_HOUR` 等）。
- 前端不需要改：`SessionProvider` 的 `anonymous` 态在拿到 200 之后自然不再出现。

**反向操作（重新关闭）**：把开关改回 `false` 并重启 api。已经建出来的匿名号
不会被立刻删除，它们照常走 30 天保留期清理。

## 部署与回滚

以下是 Kubernetes（Helm）形态。单机内测形态（一台 Ubuntu 云主机 + Docker
Compose）的完整步骤见 [云服务器部署说明.md](云服务器部署说明.md)，那里的升级与
回滚顺序与这里一致，只是换成 `docker compose build && up -d`。

**顺序不能换**：先迁移，再升级。

```bash
DATABASE_URL=... pnpm db:migrate     # 先
helm upgrade tps deploy/helm/travel-poster --set global.imageTag=<新标签>
```

迁移不放进 Helm hook 是刻意的：一次失败的迁移会让 release 卡在
`pending-upgrade`，而那时既不能回滚也不能重试。

**回滚两条路径**

| 场景               | 命令                                         | 代价                 |
| ------------------ | -------------------------------------------- | -------------------- |
| 新版本有缺陷       | `helm rollback tps`                          | 拉旧镜像，约一分钟   |
| 只想止血、不动版本 | `--set featureFlags.generationEnabled=false` | 几秒（只改环境变量） |

**迁移的回滚**：0001～0006 都是加列/加表，向后兼容 —— 旧版本代码在新 schema 上
能跑。因此**回滚代码时不要回滚迁移**。反过来（先回滚迁移）会让还没换掉的
新版本 Pod 立刻开始报错。

## 坏账速率异常

告警：`TravelCreditWriteOffHigh`（坏账 > 5000 CR/小时 = 5 元/小时）。

「我们自己吃掉的钱」有两个来源，**处置完全不同**：

| 来源     | 含义                                   | 判据                                     |
| -------- | -------------------------------------- | ---------------------------------------- |
| 结算超支 | 真实用量超出预留，又超出用户余额       | `travel_job_total{status="FAILED"}` 平稳 |
| 任务失败 | 上游故障时每次失败都真的烧了供应商的钱 | `FAILED` 同步升高                        |

```promql
sum(rate(travel_credit_settled_cr_total{direction="write_off"}[1h])) * 3600
sum(rate(travel_job_total{status="FAILED"}[1h]))
```

**处置**

1. `FAILED` 同步升高 → 这是上游故障在烧钱，处置见「主模型胜出率下降」与
   「成本超支与熔断」。坏账会随故障恢复自然回落。
2. `FAILED` 平稳 → 是估算不准。两条路：
   - 短期：提高 `CREDIT_HOLD_BUFFER_PERCENT`（预留多冻一点，多退少补）；
   - 根治：重定价目表，或调 `CREDIT_EST_*` 的估算参数。
     `travel_credit_settled_cr_total{direction="charged"}` 与
     `refunded` 的比值能说明预留偏了多少 ——
     退回占比一直很高说明预留过量，坏账高说明预留不足。
3. 要立刻止血 → 关生成开关（同「成本超支与熔断」第 3 步）。

**不要做的事**：把 `plan.base_fee` 调高来「补回」坏账。那是向所有正常用户
收一笔本该我们承担的钱，而问题在估算，不在定价水平。

## 有SKU没配价

告警：`TravelCreditUnpriced`。

运营往模型池里加模型（`pnpm model:pool`）与登记价格（`clone_credit_prices`）
是两条独立的命令，忘一个不会报错：命中兜底价 `:*` 就按一个偏贵的价收，
连兜底都没有就**完全不收费**。

**先拿到完整 SKU**（指标只带域，模型名在日志里）：

```bash
# generation-worker 的日志
grep '"stage":"billing"' | grep sku
```

**再补上那一项**：

```sql
SELECT clone_credit_prices(<当前版本>, <新版本>, '补 llm.in:<model>');
INSERT INTO credit_price_items (version_id, sku, unit, price_cr)
SELECT v.id, 'llm.in:<model>', 'PER_MILLION_TOKENS', <价格>
FROM credit_price_versions v WHERE v.version = <新版本>;
SELECT publish_credit_prices(<新版本>);
```

**在途任务不受影响** —— `credit_holds.price_version` 锁定了结算用的版本
（见 [用户货币与计费](用户货币与计费.md) 第四节）。因此补价只对新任务生效，
已经按兜底价收过的那些不会追溯。

`domain=export.png|export.pdf|render.page` 等固定项漏配说明的是另一件事：
那些 SKU 由代码写死，漏配只可能是发布价目表时漏了几行。

## 余额不足占比升高

告警：`TravelCreditInsufficientRatioHigh`（> 20% 的计费请求被 402 拒）。

**这不是故障。** 每一次都返回了语义完全正确的 402，日志、错误率、SLA
全都正常。而用户不会来问「为什么我不能生成」—— 他会走。

```promql
sum by (event) (rate(travel_credit_gate_total{outcome="insufficient"}[30m]))
```

**判定是「定价问题」还是「用户真的花完了」**

```bash
# 对几个典型天数报一次价，与赠送额比
curl -s -X POST localhost:8080/api/v1/credits/quote \
  -H 'content-type: application/json' -b "$COOKIE" \
  -d '{"total_days":5}'
```

`hold_cr` 接近或超过 `CREDIT_SIGNUP_GRANT_CR` → **是定价问题**：
新注册用户一次都用不了。占位价下 14 天行程就是这种状态
（预留 10578 CR > 赠送 9900 CR）。

**处置**（都要产品决策，不要自己改）

1. 重定价目表 —— 优先看 `llm.out:*`，输出 token 占报价 60~75%；
2. 提高 `CREDIT_SIGNUP_GRANT_CR`（只影响新注册，存量用户要 `pnpm user:credit`）；
3. 接受「长行程需要充值」，那么支付入口必须先上线。

`event=export` 占多数是另一回事：导出单价（30~50 CR）远小于生成，
集中在导出说明用户余额已经接近 0 —— 根因仍在上面那三条。
