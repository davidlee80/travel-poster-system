# 前端接入契约

给**替换前端呈现层**的人看的唯一入口。任意 HTML、任意框架、任意样式，只要按本文
拼请求、按本文读响应，后端一行都不用改。

**自测**：拼好一份请求体存成 JSON，然后

```bash
pnpm validate:request path/to/your-request.json
```

退出码 0 即合法。它直接用后端那份 Zod schema 校验，不依赖后端在跑 ——
因此结论与线上一致，且不会因为文档过时而骗你。

两份可以照抄的夹具：

- [`packages/schemas/fixtures/travel-request.minimal.json`](../packages/schemas/fixtures/travel-request.minimal.json) —— 只有 11 个必填字段
- [`packages/schemas/fixtures/travel-request.full.json`](../packages/schemas/fixtures/travel-request.full.json) —— 覆盖三态、新字段、全部可选项

## 1 边界在哪

```text
你的前端                          后端（不需要改）
─────────                        ─────────────────
① 采集表单
                POST /api/v1/travel-plans/generate
                载荷 = travel_request_ui_v1          → 201 { plan_id, job_id, request_id }
② 轮询进度
                GET  /api/v1/generation-jobs/{job_id} → 200 { status, progress, message }
③ 读计划
                GET  /api/v1/travel-plans/{plan_id}  → 200 TravelPlan
④ 导出（可选）
                POST /api/v1/travel-plans/{id}/exports → 201 { export_id }
                GET  /api/v1/exports/{export_id}       → 200 { status, files[].url }
```

**唯一的契约是 `travel_request_ui_v1`**（`packages/schemas/src/travel-request.ts`）。
它是 Zod schema，也是运行期真正在校验的东西 —— 本文档若与它冲突，以它为准。

## 2 两条硬性的部署前提

**① 前端必须与 api 同域。** api 没有装 CORS 插件（有意为之），而身份完全依赖
HttpOnly + SameSite=Lax 的 Cookie。跨站请求既过不了 CORS 也带不上 Cookie。
把 api 挂在站点的 `/api/` 路径下（反代配置见 `docs/云服务器部署说明.md` 第 8 节）。

**② 每个 fetch 都要带 `credentials: 'include'`。** 不带的话每个请求都被当成新访客。

```js
await fetch('/api/v1/travel-plans/generate', {
  method: 'POST',
  credentials: 'include', // ← 少了它一切都不工作
  headers: { 'content-type': 'application/json' },
  body: JSON.stringify(request),
});
```

**身份**：P7 之后前端来的一切请求都必须是注册用户。未注册时
`GET /api/v1/auth/session` 返回 401 `AUTH_IDENTITY_REQUIRED` —— 把它当作
「未登录」而不是故障，引导注册即可。注册端点是 `POST /api/v1/auth/register`
（`{ email, password, display_name? }`，口令有强度要求）。

## 3 必填字段：只有 11 个

一份只带这 11 项的请求**必须**能生成出计划。这是替换前端的最低门槛。

| 字段                    | 类型                     | 说明                                                           |
| ----------------------- | ------------------------ | -------------------------------------------------------------- |
| `schema_version`        | `"travel_request_ui_v1"` | 字面量。别给它默认值 —— 见下方「为什么这四个不能省」           |
| `client_request_id`     | string ≤100              | 你生成的幂等键。**点「重新生成」必须换新值**，否则拿回上次结果 |
| `timezone`              | IANA 名 ≤64              | `Intl.DateTimeFormat().resolvedOptions().timeZone`             |
| `trip.origin.text`      | string ≤200              | 出发地                                                         |
| `trip.destination.text` | string ≤200              | 目的地                                                         |
| `trip.dates.start_date` | `YYYY-MM-DD`             | 出发日期                                                       |
| `trip.dates.end_date`   | `YYYY-MM-DD`             | 返回日期                                                       |
| `travelers.adults`      | int 0–20                 | 成人数                                                         |
| `budget.basis`          | 见枚举                   | **决定 min/max 的含义**                                        |
| `budget.min`            | number ≥0                | 预算下限                                                       |
| `budget.max`            | number ≥0                | 预算上限                                                       |

### 为什么这四个「看起来是常量」的字段不能省

它们不是用户填的，但也不能给默认值 —— 理由各不相同，且都属于「猜错了不会报错」
的那一类：

- **`schema_version`**：契约的版本判别式。给它默认值意味着一个 v2 客户端漏传时
  会被**静默当作 v1 解析**，而那正是版本号要防的事。
- **`client_request_id`**：13.8 的幂等键。服务端代生成等于每次请求都唯一，
  幂等保护消失 —— 用户双击提交会得到两份计划、扣两份配额。
- **`timezone`**：N-01 用它判断「今天」。默认成 `Asia/Shanghai` 而用户在别的时区，
  出发日期的合法性判断会**错一天**，且没有任何报错。
- **`budget.basis`**：决定 min/max 是「人均每天」还是「全程总额」。猜错让预算偏差约
  （人数 × 天数）≈ 20 倍，而 N-12 的「每人每天 ≥50 元」下限也是按它折算的。

## 4 附加字段：不传就走默认值

下表的「默认」列是**服务端会填的值**。你不需要为了「让类型通过」而显式传一遍它们
—— 那只会让你的前端与 schema 的默认值漂移，而漂移方向通常是「前端比 schema 旧」。

| 字段                                           | 默认                                                    |
| ---------------------------------------------- | ------------------------------------------------------- |
| `locale`                                       | `"zh-CN"`（只有这一个合法值）                           |
| `trip.destination.mode`                        | `"FIXED"`                                               |
| `trip.destination.place_id`                    | 无（缺省时按 19.1 归一化文本）                          |
| `trip.destination.allow_multiple_destinations` | `false`                                                 |
| `trip.dates.flexibility_days`                  | `0`                                                     |
| `trip.existing_bookings`                       | `[]`                                                    |
| `travelers.children`                           | `[]`                                                    |
| `travelers.seniors`                            | `[]`                                                    |
| `budget.currency`                              | `"CNY"`                                                 |
| `budget.tier`                                  | 无（不传就是「没选档位」，与「档位是经济」不同）        |
| `budget.included_items`                        | `["ACCOMMODATION","MEALS","LOCAL_TRANSPORT","TICKETS"]` |
| `pace`                                         | `{}`（各字段由标准化阶段按 `level` 补默认）             |
| `conditions`                                   | `[]`                                                    |
| `custom_requirements.raw_text`                 | `""`                                                    |
| `output_preferences.language`                  | `"zh-CN"`                                               |
| `output_preferences.template_id`               | `"travel_infographic_v1"`                               |
| `output_preferences.generate_png` / `_pdf`     | `true` / `true`                                         |

**一个例外**：`budget.included_items` 可以不传，但**不能显式传空数组** ——
`[]` 会让 min/max 失去意义，因此仍被 `.min(1)` 拒。

## 5 枚举取值

```ts
BudgetBasis         'PER_PERSON_PER_DAY' | 'TOTAL'
Currency            'CNY'
Locale              'zh-CN'
DestinationMode     'FIXED'
PaceLevel           'RELAXED' | 'BALANCED' | 'PACKED'
ConditionMode        'MUST' | 'SHOULD'
TemplateId          'travel_infographic_v1' | 'travel_full_plan_v1'
ExportFormat        'PNG' | 'PDF'

BudgetIncludedItem  'ACCOMMODATION' | 'MEALS' | 'LOCAL_TRANSPORT' | 'TICKETS'
                  | 'INTERCITY_TRANSPORT' | 'SHOPPING'

BudgetTier          'ECONOMY' | 'STANDARD' | 'QUALITY' | 'LUXURY' | 'CUSTOM'
ExistingBooking     'INTERCITY_TRANSPORT' | 'LODGING' | 'TICKETS'
```

`pace.intensity` 是 1–5 的整数，与 `level` 并存（`level` 只有三档，
5→3 会把「躺平」与「慢游」压成同一个 `RELAXED`）。数值与 `level` 冲突时**以数值为准**。

### 条件字典：46 个 code

`conditions` 里的 `code` 必须来自这个白名单 —— 不在其中会被
`REQ_CONDITION_CODE_UNKNOWN` 拒绝，**不做静默丢弃**（一个拼错的
`accessibility.wheelchar` 若被丢掉，轮椅需求凭空消失而计划看起来完全正常）。

中文文案的权威来源是 `packages/presentation/src/condition-labels.ts` 的
`CONDITION_LABEL`。

| 域              | code                                                                                                                                                                         |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `interest`      | `history_culture` `nature` `food` `shopping` `art_museum` `nightlife` `photography` `family_kids` `city_walk` `cafe` `hot_spring` `theme_park` `zoo_aquarium` `light_hiking` |
| `transport`     | `public_transit` `self_drive` `walking_first` `avoid_transfer` `cycling` `rail`                                                                                              |
| `accommodation` | `elevator` `near_transit` `private_bath` `family_room` `hotel` `homestay` `apartment` `resort` `hostel` `breakfast` `kitchen` `shared_dorm` `single_base`                    |
| `budget`        | `lodging_quality` `unique_experience` `transport_convenience`                                                                                                                |
| `accessibility` | `wheelchair` `stroller` `low_walking` `child_car_seat`                                                                                                                       |
| `diet`          | `vegetarian` `halal` `no_spicy` `allergy_seafood`                                                                                                                            |
| `schedule`      | `no_late_night` `daily_rest`                                                                                                                                                 |

`conditions` 数组最多 46 条（= 字典大小，一个 code 勾一次）。

## 6 三态：偏好 / 必须 / 不要

`mode` 与 `value` 两个字段组合出三种表达。**没有第四种**。

| 用户意图     | `mode`   | `value` | 后端行为                                      |
| ------------ | -------- | ------- | --------------------------------------------- |
| 偏好（尽量） | `SHOULD` | `true`  | 进软约束命中率统计，不满足不阻断              |
| 必须         | `MUST`   | `true`  | 硬约束，V-30 校验；不满足则计划被拒或触发修复 |
| **不要**     | `MUST`   | `false` | 同上，反向                                    |

**否定语义走 `value: false`，不进 code 名。** 「不要多人间」是
`{ code: 'accommodation.shared_dorm', mode: 'MUST', value: false }` ——
字典里没有 `no_shared_dorm`，因为那与「不要它」会组合成读不懂的双重否定。

**两个域即使用户只表达「偏好」也应发 `MUST`**：`accessibility` 与 `diet`。
轮椅通行与食物过敏不是偏好，发 `SHOULD` 会让 V-30 不再校验它们，
而生成的计划看起来完全正常。参考实现见
`apps/web/src/lib/travel-request-form.ts` 的 `conditionToContract`。

## 7 V1 不支持的三个输入

它们在契约里有字段（或干脆没有），但**一定会被拒或无处安放**。建议界面上保留控件、
置灰、标「V2」——用户填了才被拒的体验比看不到更差。

| 输入           | 结果                                                                                     |
| -------------- | ---------------------------------------------------------------------------------------- |
| 日期弹性 ≠ 0   | `REQ_DATE_FLEXIBILITY_UNSUPPORTED`（N-09）。只接受 `flexibility_days: 0`                 |
| 多目的地       | `REQ_MULTI_DESTINATION_UNSUPPORTED`（N-10）。`allow_multiple_destinations` 必须 `false`  |
| 目的地尚未确定 | 契约无此态（`DestinationMode` 只有 `FIXED`）。生成链路要求确定目的地才能检索素材与算路线 |

## 8 错误处理

失败响应体是统一形态（13.7）：

```json
{
  "error": {
    "code": "REQ_DATE_RANGE_INVALID",
    "message": "返回日期不能早于出发日期。",
    "retryable": false,
    "field": "trip.dates.end_date",
    "request_id": "...",
    "trace_id": "..."
  }
}
```

- **`field`** 是点分路径，**与 `pnpm validate:request` 打印的路径同源** ——
  直接拿它定位并高亮出错的表单项。
- **`retryable`** 为 `true` 时保留用户填的表单再让他重试；为 `false` 时清空重填毫无帮助。
- **`message`** 已经是面向用户的中文文案，直接展示。自己拼一句「请求失败」会盖掉
  「请放宽部分条件后重试」这种唯一有用的指引。
- **`REQ_SCHEMA_INVALID`** 意味着连字段都读不出来（类型错、枚举非法）。
  拿到它先跑一遍 `pnpm validate:request` —— 它会告诉你具体是哪个 path。

## 9 生成与轮询

`POST /api/v1/travel-plans/generate` 返回 201 后**任务还没开始跑**。轮询
`GET /api/v1/generation-jobs/{job_id}`：

- `status` 走状态机，`progress` 是 0–100 的整数，`message` 是可直接展示的中文
- 到达 `COMPLETED` 后 `GET /api/v1/travel-plans/{plan_id}` 可读
- `FAILED` 时 `message` 就是错误码对应的用户文案
- 建议 2 秒一次；整个任务上限 300 秒，客户端超时应略高于它（否则你会比服务端先放弃）

**导出**：`POST /api/v1/travel-plans/{plan_id}/exports`，载荷
`{ format, template_id, scope, day_numbers }`。`scope` 为 `ALL_DAYS` 时
`day_numbers` 必须为 `null`；`SINGLE_DAY` 时必须恰好一个天号。
轮询 `GET /api/v1/exports/{export_id}` 到 `SUCCEEDED`，`files[].url` 是**预签名 URL**
（有有效期，过期重新 GET 一次即可拿到新的）。

## 10 不要碰的一条路由

`/render/**` 是内部渲染路由（17.1），返回用户私有计划内容，由 HMAC 令牌 + 网络层
双重保护。它不是给前端用的接口 —— 反代应当直接 404 掉这个前缀。

**但它不能被整个封掉。** 那两条路由是**服务端渲染**的，也是 PNG / PDF 导出的
唯一输入：render-worker 用 Playwright 打开它们截图。所以要求是
「对公网 404、对容器网络可达」，而不是「这个前缀没用」。

由此有两件事对替换前端的人成立：

- **web 进程必须留着。** 把前端换成静态站发到 CDN 是可以的，但那只替换了
  `/`（需求采集）与 `/plans/{planId}`（用户可见的计划页）—— 这两条的输出对
  所有用户相同，内容都是浏览器里的 JS 调本文的 API 拿的。
  `/render/**` 与它引用的两套模板（`travel-full-plan-v1`、
  `travel-infographic-v1`）属于导出流水线，要原样留在 web 容器里。
- **漏掉这一点的表现很隐蔽。** 生成链路全绿、用户在网页上看得到完整计划，
  只有点「导出」才失败（每个任务 `EXPORT_PNG_FAILED`）。

## 附：字段的必填/附加是怎么定的

判定原则是「缺了它生成的计划一定是错的或无法生成」才进必填集，而不是
「有它计划会更好」。逐字段的判定过程、原型 70 个输入节点的对应关系，
见 [`docs/前端字段清单.md`](前端字段清单.md)。
