# 用户货币与计费（CR）

用户充值人民币换成 **CR**，每次生成、导出扣一部分。CR 把两类成本合成一个数：
大模型的 token 消耗，与后端其余生成服务（AI 配图、图源搜索、渲染、导出）的消耗。

本文是这套系统的设计与实施计划。分期进度见文末，**定价目前是占位值**，见「待定：真实定价」。

---

## 一、为什么需要它，以及它不替代什么

现有的 `QuotaGuard`（[quota-guard.ts](../packages/shared/src/identity/quota-guard.ts)）
是 Redis 计数的**次数**配额：每分钟 / 每日 / 每月 / 单 IP / 每计划导出次数。
它解决的是「防滥用」，不是「计费」—— 一个 5 天行程与一个 14 天行程各算「1 次」，
而两者的真实成本差 3.5 倍。

CR 系统解决计费。两者**并存**，理由有两条：

1. 次数配额是防滥用，秒/小时级恢复，用户看不到。删了它，一个充了钱的脚本
   能把供应商额度打满。
2. **价目表被配成 0 时货币闸门失效，次数闸门是最后一道防线。**

产品上用户只看到 CR，不看到次数：日/月计划次数对注册用户提到很高的兜底值
（env 可配），不再作为产品概念展示。

**匿名用户不进货币体系** —— `FEATURE_ANONYMOUS_ENABLED` 默认已是 `false`，
必须注册才能生成。注册时赠送 `CREDIT_SIGNUP_GRANT_CR` 个 CR。

## 二、单位与两层兑换

**CR 是整数，全程不用浮点。** 这是钱：`0.1 + 0.2 !== 0.3` 在余额上的表现是
「充 100 次 1 元，余额显示 99.99999999996」，而每一次「余额够不够」的比较
都可能在边界翻面。

两层兑换分开，各只有一个真相源：

| 层 | 谁定 | 在哪 |
| --- | --- | --- |
| 人民币 → CR | `CREDIT_CR_PER_CNY`（默认 1000，即 1 元 = 1000 CR） | env |
| 供应商用量 → CR | 价目表里每个 SKU 一个 CR 单价 | 数据库 `credit_price_items` |

1 元 = 1000 CR 的粒度是刻意的：要能表示单次模型调用的成本（几分钱量级）。
若 1 元 = 100 CR，一次 20K token 的调用是 2～3 CR，舍入误差占到 30%。

**改 `CREDIT_CR_PER_CNY` 会让存量余额的含义变化** —— 库里存的是 CR，
改比率等于给所有人的钱包重新标价。因此代码里刻意不提供任何「按新比率折算」
的辅助函数：没有那个函数，下一个人会先想清楚再动。

舍入方向永远朝「不亏」的一侧：
- 充值（元 → CR）**向下**取整 —— 非整数余额一旦落库，后续整数运算的前提就没了
- 计费（用量 → CR）**向上**取整 —— 向下会让一个 50 token 的调用恒为 0 CR，
  于是把一次生成拆成很多次短调用就能免费

## 三、价目表

需求里那个「大模型 token 与我们自己的货币的兑换关系」不是一个全局系数，
而是**每个计费项一个单价**：不同模型的输入/输出单价能差一个数量级，
而 AI 图与 token 根本不是同一量纲。

### SKU

`<域>.<项>[:<变体>]`，变体是模型名。

| SKU | 单位 | 说明 |
| --- | --- | --- |
| `plan.base_fee` | 每任务 | 每次生成的固定服务费，可为 0 |
| `llm.in:<model>` / `llm.out:<model>` | 每百万 token | 计划生成与修复重生成 |
| `embedding.in:<model>` | 每百万 token | 检索投影的向量化 |
| `image.ai_generate` | 每张 | AI 生成配图 |
| `image.search` | 每次 | 授权图源搜索 |
| `render.page` | 每页 | HTML → PNG |
| `export.png` / `export.pdf` | 每次 | 导出 |

token 按**每百万**计（与供应商口径一致），避免「单 token 价 < 1 CR 无法用整数表示」：

```text
cr = ceil(tokens × price_cr_per_million / 1_000_000)
```

### 兜底价 `:*` 是必须的

`model_pools`（迁移 0009）允许运营随时加模型 —— 那是那次迁移的整个用意。
而「加模型」与「配价格」在不同的表、由不同的命令完成，忘配一定会发生。此时：

| 做法 | 后果 |
| --- | --- |
| 没有兜底 → 结算抛错 | 任务卡在终态之前。**用户的计划已经生成好了，却永远看不到** |
| 兜底按 0 | 那个模型的调用完全免费，而没有任何人会发现 |
| 兜底按 `:*` 价 | 按一个偏贵的价收，同时打 `travel_credit_unpriced_total` 告警 |

只有第三条既不影响用户又能被发现。兜底价刻意定得比常见模型贵。

同理，**连兜底都没有时不收费但报出来**（`PricedUsage.unpriced`）——
少收一笔远好于弄丢一份已经生成好的产物。

### 毛利倍率不进代码

`price_cr` 是**售价**，运营定它时已经把供应商成本与毛利算进去了。
代码里再乘一个 `markup` 会造出第二个真相源，而两处不一致时
「我们到底按什么价卖」这个问题没有答案。

### 版本化发布

照 `planner_config_*`（迁移 0010～0012）的形态：`credit_price_versions` +
`credit_price_items`，`clone_credit_prices()` / `publish_credit_prices()`，
`status` 为 `DRAFT | PUBLISHED | ARCHIVED`，同时只有一个发布版，改价不重启。

价格比问卷选项更需要可回放：三个月后对账要能答出「那一单是按哪一版价格结算的」，
而 `credit_ledger.price_version` 指回具体版本才让这个问题有答案。

## 四、生成：预留 → 结算

```text
POST /travel-plans/generate
  ├─ 既有配额（分钟 / IP / 日月兜底）          不动
  ├─ 幂等命中 → 原样返回，不预留不扣费          复用既有的 findByIdempotencyKey
  ├─ 报价 estimateJobCost(天数, 模型, 价目表)
  ├─ 原子预留 = holdAmount(typical)
  │     0 行 → 402 AUTH_INSUFFICIENT_CREDITS（带 required / balance）
  └─ 入队（payload 带 hold_id）

generation-worker
  ├─ 四处打点累加真实用量（UsageMeter）
  └─ 任务终态时单事务结算
```

### 预留取典型值，不取最坏上界

这是设计中途改过的一处，起因是拿占位价实跑了一遍报价：

| 天数 | 典型（0 次重生成） | 上界（2 次重生成） | 倍数 |
| --- | --- | --- | --- |
| 3 | 2345 CR | 4671 CR | 2.0x |
| 5 | 2475 | 5041 | 2.0x |
| 7 | 3588 | 8360 | 2.3x |
| 8 | 6099 | 15883 | 2.6x |
| 14 | 8815 | 23971 | 2.7x |

拿上界当预留额的后果是 **9.9 元连一次 14 天行程都买不了**，而那一次的实际
花费约 8.8 元 —— 用户的余额必须覆盖一个几乎不会发生的最坏情况，
「充 9.9 元」这个价位直接失效。

因此：

- **预留** = 典型值（0 次重生成）× `CREDIT_HOLD_BUFFER_PERCENT`
- **结算**按真实用量。超出预留时从余额继续扣；余额不足则扣到 0，
  差额记 `WRITE_OFF` **由我们承担**
- **上界**仍然计算，用于报价展示（「预计 ~2.5 元，最多 5.0 元」）
  与「余额连上界都不够」的提前提示

让我们承担而不是让用户欠账或让任务失败：超出预留是**我们估算不准**，
另两种做法一个要向用户解释他看不懂的负余额、一个要丢掉已经生成好的计划。
恶意用户拿最低余额反复触发高成本任务这条路，由保留下来的次数配额挡住 ——
这正是那两层不删掉的价值。

### 估算的依据：成本本来是有界的

```text
AI 图      ≤ 3 张/任务      ai-budget.ts 的 MAX_AI_IMAGES_PER_JOB
图搜       ≤ 8 次/任务      search-budget.ts 的 MAX_IMAGE_SEARCHES_PER_JOB
LLM 分段   = ⌈天数 / 7⌉     prompt.ts 的 MAX_DAYS_PER_SEGMENT
重生成     ≤ 2 次           3.2.2，落库时有 CHECK 约束兜着
渲染页     = 1 + 天数       完整版 1 页 + 每日各 1 页
```

输出 token 有硬上限（`MAX_TOKENS_TIERS` 按天数分档），直接用它。
输入 token 没有硬上限（提示词长度取决于约束条数与检索到的参考数量），
用「每天多少 token」的经验值乘天数，`CREDIT_EST_INPUT_TOKENS_PER_DAY` 可调。

前两个常量在 `apps/generation-worker` 里，而包不能依赖 app，因此
`@tps/billing` 持有一份副本 `DEFAULT_JOB_LIMITS`。
[billing-limits.test.ts](../apps/generation-worker/src/assets/billing-limits.test.ts)
守住「billing 的估算参数不低于真实常量」—— 那是仓库里唯一能同时 import
到两边的地方。断言是 `>=` 而不是 `===`：允许 billing 保守，不允许它乐观。

### 失败全额退，成本记坏账

任务 FAILED 时预留全额释放，另写一条 `WRITE_OFF` 记我们实际烧掉的成本
（不扣用户，供成本分析与「上游故障正在烧钱」告警）。

理由：重试与故障转移都是我们的实现细节，不该让用户为一份没拿到的计划付费。

### 幂等

结算幂等键 `job:<job_id>`，由 `credit_ledger.idempotency_key` 的唯一约束保证。
**这是整套设计里最重要的一个约束**：生成任务会被重投（队列重试、worker 崩溃后
接管），结算逻辑因此会被执行多次。没有它，一次重投就是一次重复扣费 ——
而用户不会因为「少了 2000 CR」来提工单，他只会觉得这个产品贵。

## 五、导出：定价固定，直接扣、失败退

导出成本是几秒 Chromium CPU + 存储，量级比生成小三个数量级，
且**与内容无关**。因此不做预留/结算往返：请求时一次原子扣减
（幂等键复用既有的 `computeExportIdempotencyKey`），导出任务失败时退回。

## 六、报价用端点，不下发价目表

生成按钮旁要显示「预计消耗 ~N CR / 余额 M CR」，不够就禁用。
做成 `POST /api/v1/credits/quote`（服务端算，权威）而不是把价目表下发给浏览器：

- 价目表是运营数据
- 下发之后前端与服务端各算一份，会出现「按钮说够、提交被拒」

## 七、数据表

| 表 | 是什么 | 可变性 |
| --- | --- | --- |
| `credit_wallets` | 当前余额 `balance_cr` 与冻结额 `held_cr` | 可变 |
| `credit_ledger` | 流水 | **只追加** |
| `credit_holds` | 生成任务的预留 | 有状态机 |
| `credit_price_versions` / `credit_price_items` | 价目表 | 版本化 |
| `credit_prices_current` | 当前发布版视图 | 只读 |

### 为什么钱不放 Redis

现有配额用 Redis 是对的：丢了下个时间窗自动重置，损失是「某个用户多生成一次」。
钱不一样 —— Redis 没有持久化保证（AOF 也有窗口），一次重启丢掉的是用户充的钱。
因此钱包全在 Postgres，且余额变动与流水写入必须在同一个事务里。

### 为什么保留可变余额而不是纯事件溯源

余额本可以由流水求和得出，但那让「查余额」变成一次全表聚合，
而余额在每次生成请求的关键路径上。折中：保留一列可变余额，
由 `credit_ledger.balance_after_cr` 让流水能自校验
（任何一行的 after = 上一行 after + amount）。

### 流水的六种 kind

| kind | 方向 | 什么时候 |
| --- | --- | --- |
| `TOPUP` | + | 充值（本轮无支付网关，仅结构预留） |
| `GRANT` | + | 赠送（注册赠送、运营授予） |
| `SPEND` | −（或 0） | 消费（生成结算、导出扣费） |
| `REFUND` | + | 退还（预留多退、任务失败全退） |
| `WRITE_OFF` | **恒 0** | 坏账：我们实际烧掉但不扣用户的成本 |
| `ADJUST` | ± | 运营手工冲销 |

`WRITE_OFF` 恒为 0 是为了让「求和 = 余额」这条自校验仍然成立，
金额本身在 `metadata` 里。方向与 kind 的一致性由 CHECK 约束保证 ——
写错方向的表现是「退款把余额扣得更少」这种读起来完全正常、
对账时才发现的错。

### 六道约束（迁移 0013，已逐条实测）

```text
✓ 负余额被 CHECK 拒绝                    不透支的最后一道防线
✓ 负数的 REFUND 被拒绝                   方向与 kind 必须一致
✓ 非零的 WRITE_OFF 被拒绝                它不动用户余额
✓ 重复幂等键被唯一索引拒绝                任务重投不重复扣费
✓ ACTIVE 的预留不许带 settled_at         否则无法判断这笔结没结
✓ 同一 job_id 只能有一笔预留
```

## 八、运营操作

### 改价并发布

```sql
SELECT clone_credit_prices(1, 2, '按 2026Q3 供应商报价重定');

UPDATE credit_price_items i
SET price_cr = 45000
FROM credit_price_versions v
WHERE i.version_id = v.id AND v.version = 2 AND i.sku = 'llm.out:*';

SELECT publish_credit_prices(2);
```

发布是单事务：原发布版自动归档，目标草稿变为发布版。API 最多缓存 60 秒。

**已提交的任务不受影响** —— `credit_holds.price_version` 锁定了结算用的版本，
中途调价不会让用户按新价被扣。

### 回滚不是一句 publish

`publish_credit_prices` 只接受 `status = 'DRAFT'`，而刚被顶下来的版本已是
`ARCHIVED`，直接调会报 `draft credit price version N not found`。
归档时 `published_at` 已被置 NULL，因此改回 DRAFT 不会撞形态约束：

```sql
BEGIN;
UPDATE credit_price_versions SET status = 'DRAFT' WHERE version = 1;
SELECT publish_credit_prices(1);
COMMIT;
```

（同一个坑在 `planner_config` 那边踩过一次，见 [规划器配置中心](规划器配置中心.md)。）

### 钱包与流水不提供回滚

流水是只追加的账。冲销要写一条反向的 `ADJUST`，而不是删行或改行。

### 环境变量

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `CREDIT_CR_PER_CNY` | 1000 | 1 元兑多少 CR。**改它等于给所有存量余额重新标价** |
| `CREDIT_SIGNUP_GRANT_CR` | 9900 | 注册赠送。0 = 不赠送 |
| `CREDIT_HOLD_BUFFER_PERCENT` | 120 | 预留相对典型估算的放大。**必须 ≥ 100** |
| `CREDIT_EST_INPUT_TOKENS_PER_DAY` | 3000 | 输入 token 的每天经验值 |
| `CREDIT_EST_MAX_AI_IMAGES` | 3 | 估算用的 AI 图上限，须 ≥ worker 的真实常量 |
| `CREDIT_EST_MAX_IMAGE_SEARCHES` | 8 | 同上 |
| `CREDIT_EST_MAX_REGENERATIONS` | 2 | 同上 |

## 九、待定：真实定价

**迁移 0013 种下的价目表（版本 1）全是占位值**，是为了让系统在没有运营配置时
也能跑通，不是真实定价。`isSeedPriceBook()`（判据：版本号 == 1）让启动时能
打一条 warn —— 带着占位价上线的表现不是报错，是**收错钱**，
而收错钱要到对账时才发现。

调研市面上大模型价格之后需要重定。有一个数值优先级最高：

> **`llm.out:*` 占位价是 60000 CR/百万 token（= 60 元/百万），
> 而输出 token 占了报价的 60~75%** —— 它决定整个产品的价格带，
> 比其他八项加起来都重要。

定价要同时定下来的三件事：

1. 各模型的 `llm.in` / `llm.out` 单价（按供应商成本 + 毛利）
2. 兜底价 `:*` —— 应当**高于**所有已登记模型，因为它命中意味着配置漏了
3. 「9.9 元买几次 5 天行程」这个产品形态，与 `CREDIT_SIGNUP_GRANT_CR` 的联动

## 十一、验证

1. `pnpm typecheck && pnpm lint && pnpm test` 全绿。
2. **并发预留**：同一钱包两个并发请求、余额只够一次 → 恰好一个 201、一个 402，
   且 `balance_cr + held_cr` 守恒。
3. **重复结算**：同一 `job_id` 结算两次 → 流水只有一条，钱包只动一次。
4. **失败退款**：任务 FAILED → 余额回到扣前，流水有 `REFUND` 与 `WRITE_OFF`。
5. **兜底价**：发布一份缺某模型 `llm.in` 的价目表 → 命中 `*`，指标 +1，不崩。
6. **迁移**：在临时库跑（`docker exec psql --single-transaction`），
   核对版本 1 已发布后删库。`travel_poster` 的迁移单独确认后再执行。
7. **8080 端到端**：CLI 授予 9900 CR → 生成一次 → 余额下降、流水一条 `SPEND`、
   `held_cr` 归零；再把余额调到不足 → 生成返回 402 且前端按钮禁用。
8. `pnpm test:visual` 保持 0.0000%（本设计不碰 `/render/**`）。
