# 用户货币与计费（CR）

用户充值人民币换成 **CR**，每次生成、导出扣一部分。CR 把两类成本合成一个数：
大模型的 token 消耗，与后端其余生成服务（AI 配图、图源搜索、渲染、导出）的消耗。

本文是这套系统的设计与实施计划。分期进度见文末，**定价目前是占位值**，见「待定：真实定价」。

---

## 一、为什么需要它，以及它不替代什么

现有的 `QuotaGuard`（[quota-guard.ts](../packages/shared/src/identity/quota-guard.ts)）
是 Redis 计数的**次数**配额：每分钟 / 每日 / 每月 / 单 IP / 每计划导出次数。
它解决的是「防滥用」，不是「计费」—— 一个 5 天行程与一个 14 天行程各算「1 次」，
而两者的真实成本差 3.5 倍。

CR 系统解决计费。两者**并存**，理由有两条：

1. 次数配额是防滥用，秒/小时级恢复，用户看不到。删了它，一个充了钱的脚本
   能把供应商额度打满。
2. **价目表被配成 0 时货币闸门失效，次数闸门是最后一道防线。**

产品上用户只看到 CR，不看到次数：日/月计划次数对注册用户提到很高的兜底值
（env 可配），不再作为产品概念展示。

**匿名用户不进货币体系** —— `FEATURE_ANONYMOUS_ENABLED` 默认已是 `false`，
必须注册才能生成。注册时赠送 `CREDIT_SIGNUP_GRANT_CR` 个 CR（C-5）。

赠送的幂等键是 `signup:<user_id>`，因此一个用户只可能拿到一次 ——
匿名原地升级走的是同一个 `user_id`，「先匿名生成、再注册」不会比直接注册多拿。
发放在**构造会话响应之前**：反了的话新用户拿到的第一份会话余额是 0，
而前端据它禁用生成按钮，用户注册完看到的是「余额不足」。

发放失败**不影响注册**（吞掉 + error 级日志）：走到那一步时用户行已落库、
会话 Cookie 已写进响应头，抛错会让用户看到一个失败的注册而账号其实建好了 ——
他会再注册一次，然后拿到「该手机号已注册」。补救是
`pnpm user:credit --phone ... --grant N`，日志里有 `user_id`。

## 二、单位与两层兑换

**CR 是整数，全程不用浮点。** 这是钱：`0.1 + 0.2 !== 0.3` 在余额上的表现是
「充 100 次 1 元，余额显示 99.99999999996」，而每一次「余额够不够」的比较
都可能在边界翻面。

两层兑换分开，各只有一个真相源：

| 层              | 谁定                                                | 在哪                        |
| --------------- | --------------------------------------------------- | --------------------------- |
| 人民币 → CR     | `CREDIT_CR_PER_CNY`（默认 1000，即 1 元 = 1000 CR） | env                         |
| 供应商用量 → CR | 价目表里每个 SKU 一个 CR 单价                       | 数据库 `credit_price_items` |

1 元 = 1000 CR 的粒度是刻意的：要能表示单次模型调用的成本（几分钱量级）。
若 1 元 = 100 CR，一次 20K token 的调用是 2～3 CR，舍入误差占到 30%。

**改 `CREDIT_CR_PER_CNY` 会让存量余额的含义变化** —— 库里存的是 CR，
改比率等于给所有人的钱包重新标价。因此代码里刻意不提供任何「按新比率折算」
的辅助函数：没有那个函数，下一个人会先想清楚再动。

舍入方向永远朝「不亏」的一侧：

- 充值（元 → CR）**向下**取整 —— 非整数余额一旦落库，后续整数运算的前提就没了
- 计费（用量 → CR）**向上**取整 —— 向下会让一个 50 token 的调用恒为 0 CR，
  于是把一次生成拆成很多次短调用就能免费

## 三、价目表

需求里那个「大模型 token 与我们自己的货币的兑换关系」不是一个全局系数，
而是**每个计费项一个单价**：不同模型的输入/输出单价能差一个数量级，
而 AI 图与 token 根本不是同一量纲。

### SKU

`<域>.<项>[:<变体>]`，变体是模型名。

| SKU                                  | 单位         | 说明                         |
| ------------------------------------ | ------------ | ---------------------------- |
| `plan.base_fee`                      | 每任务       | 每次生成的固定服务费，可为 0 |
| `llm.in:<model>` / `llm.out:<model>` | 每百万 token | 计划生成与修复重生成         |
| `embedding.in:<model>`               | 每百万 token | 检索投影的向量化             |
| `image.ai_generate`                  | 每张         | AI 生成配图                  |
| `image.search`                       | 每次         | 授权图源搜索                 |
| `render.page`                        | 每页         | HTML → PNG                   |
| `export.png` / `export.pdf`          | 每次         | 导出                         |

token 按**每百万**计（与供应商口径一致），避免「单 token 价 < 1 CR 无法用整数表示」：

```text
cr = ceil(tokens × price_cr_per_million / 1_000_000)
```

### 兜底价 `:*` 是必须的

`model_pools`（迁移 0009）允许运营随时加模型 —— 那是那次迁移的整个用意。
而「加模型」与「配价格」在不同的表、由不同的命令完成，忘配一定会发生。此时：

| 做法                | 后果                                                         |
| ------------------- | ------------------------------------------------------------ |
| 没有兜底 → 结算抛错 | 任务卡在终态之前。**用户的计划已经生成好了，却永远看不到**   |
| 兜底按 0            | 那个模型的调用完全免费，而没有任何人会发现                   |
| 兜底按 `:*` 价      | 按一个偏贵的价收，同时打 `travel_credit_unpriced_total` 告警 |

只有第三条既不影响用户又能被发现。兜底价刻意定得比常见模型贵。

同理，**连兜底都没有时不收费但报出来**（`PricedUsage.unpriced`）——
少收一笔远好于弄丢一份已经生成好的产物。

### 毛利倍率不进代码

`price_cr` 是**售价**，运营定它时已经把供应商成本与毛利算进去了。
代码里再乘一个 `markup` 会造出第二个真相源，而两处不一致时
「我们到底按什么价卖」这个问题没有答案。

### 版本化发布

照 `planner_config_*`（迁移 0010～0012）的形态：`credit_price_versions` +
`credit_price_items`，`clone_credit_prices()` / `publish_credit_prices()`，
`status` 为 `DRAFT | PUBLISHED | ARCHIVED`，同时只有一个发布版，改价不重启。

价格比问卷选项更需要可回放：三个月后对账要能答出「那一单是按哪一版价格结算的」，
而 `credit_ledger.price_version` 指回具体版本才让这个问题有答案。

## 四、生成：预留 → 结算

```text
POST /travel-plans/generate
  ├─ 既有配额（分钟 / IP / 日月兜底）          不动
  ├─ 幂等命中 → 原样返回，不预留不扣费          复用既有的 findByIdempotencyKey
  ├─ 预检 checkJob(天数)                      余额 < 预留额 → 402，此时还没建任务行
  ├─ createGeneration                         建 travel_requests / plans / jobs
  ├─ 原子预留 = holdAmount(typical)            **真正的闸门**
  │     0 行 → 取消刚建的任务 + 402
  └─ 入队

generation-worker
  ├─ 四处打点累加真实用量（UsageMeter）
  └─ 任务终态时单事务结算
```

### 为什么是「预检 + 预留」两步

`job_id` 由数据库生成（`generation_jobs.id` 的默认值），因此预留只能发生在
建任务行**之后** —— 而 `credit_holds.job_id` 是那一行的 id。

只靠预留的后果：每次余额不足都留下一条 QUEUED 任务与一个被占用的幂等键，
而用户充值后拿同一份表单重试会命中那个幂等键，得到一个**永远不会跑的任务**。
因此加一次只读预检，把绝大多数「余额不够」挡在建行之前。

预检**不是**闸门：它与预留之间有窗口，并发请求可以在这个窗口里把余额抢走。
闸门始终是 `UPDATE ... WHERE balance_cr >= $n` 那一条语句。走到那里才失败时
把刚建的任务取消，再返回 402。

预留在**入队之前**：反过来的话 worker 可能在预留落库前就跑完并结算，
而结算找不到预留 = 那次生成免费。

### API 的报价按兜底模型算

真正会用哪个模型由 worker 侧的模型池 + `tier_level` 决定，API 不知道。
把模型选择逻辑复制到 API 只为了报价，会造出第二个真相源。因此估算统一走
兜底 SKU `:*` —— 它**刻意定得比常见模型贵**，因此是偏保守的一侧：
预留略多，结算时多退。

若兜底价被配得比某个真实模型便宜，预留会不足；那种情况由结算的
「超出预留从余额继续扣」兜住，最坏是一笔坏账，而不是任务卡住。

### 预留取典型值，不取最坏上界

这是设计中途改过的一处，起因是拿占位价实跑了一遍报价：

| 天数 | 典型（0 次重生成） | 上界（2 次重生成） | 倍数 |
| ---- | ------------------ | ------------------ | ---- |
| 3    | 2345 CR            | 4671 CR            | 2.0x |
| 5    | 2475               | 5041               | 2.0x |
| 7    | 3588               | 8360               | 2.3x |
| 8    | 6099               | 15883              | 2.6x |
| 14   | 8815               | 23971              | 2.7x |

拿上界当预留额的后果是 **9.9 元连一次 14 天行程都买不了**，而那一次的实际
花费约 8.8 元 —— 用户的余额必须覆盖一个几乎不会发生的最坏情况，
「充 9.9 元」这个价位直接失效。

因此：

- **预留** = 典型值（0 次重生成）× `CREDIT_HOLD_BUFFER_PERCENT`
- **结算**按真实用量。超出预留时从余额继续扣；余额不足则扣到 0，
  差额记 `WRITE_OFF` **由我们承担**
- **上界**仍然计算，用于报价展示（「预计 ~2.5 元，最多 5.0 元」）
  与「余额连上界都不够」的提前提示

让我们承担而不是让用户欠账或让任务失败：超出预留是**我们估算不准**，
另两种做法一个要向用户解释他看不懂的负余额、一个要丢掉已经生成好的计划。
恶意用户拿最低余额反复触发高成本任务这条路，由保留下来的次数配额挡住 ——
这正是那两层不删掉的价值。

### 估算的依据：成本本来是有界的

```text
AI 图      ≤ 3 张/任务      ai-budget.ts 的 MAX_AI_IMAGES_PER_JOB
图搜       ≤ 8 次/任务      search-budget.ts 的 MAX_IMAGE_SEARCHES_PER_JOB
LLM 分段   = ⌈天数 / 7⌉     prompt.ts 的 MAX_DAYS_PER_SEGMENT
重生成     ≤ 2 次           3.2.2，落库时有 CHECK 约束兜着
渲染页     = 1 + 天数       完整版 1 页 + 每日各 1 页
```

输出 token 有硬上限（`MAX_TOKENS_TIERS` 按天数分档），直接用它。
输入 token 没有硬上限（提示词长度取决于约束条数与检索到的参考数量），
用「每天多少 token」的经验值乘天数，`CREDIT_EST_INPUT_TOKENS_PER_DAY` 可调。

### 四处打点各在哪

```text
LLM token   callModel 里，紧挨着 recordLlmCall —— 用 result.model 而不是
            llm.model：故障转移下前者才是真正出活的候选（见下）
AI 图       AiImageBudget.used.images，编排结束后一次读回
图搜        ImageSearchBudget.used.searches，同上
渲染页数    buildAndSavePresentations 的 result.pages
```

后三处**读预算对象的 `used` 而不是在素材管线里再埋一层**。`AiImageBudget` 的
`images` 恰好就是「真的生成出来的张数」—— 失败与同键去重都调了 `refund`，
不计在内。这与那条施工注意（打点必须挂在图真的生成成功处，不能挂在 `reserve`）
说的是同一件事，而这样不动素材管线就已经满足。

两个预算实例因此要提到 try 之外：编排抛异常时那些 AI 图已经生成、钱已经花了，
catch 分支里读不到它们的话，「编排崩了」会变成「这次生成的图不要钱」。

**token 用 `result.model`。** `llm.model` 在故障转移下恒为主候选的名字
（见 `wrapLlmFailover`），而价目表按模型定价 —— 拿主候选的名字计费会让
「主候选挂了、由更贵的备选顶上」按主候选的价收。

**嵌入不计费。** `EmbeddingClient.embed()` 不返回 usage，没有可信的用量数据；
而那一项按占位价是 0.2 CR 量级。估算里仍然算了它（1000 token），
因此这是偏保守的一侧。`embedding.in:*` 这个 SKU 目前没有调用方。

**`fake` 模式下 token 恒为 0**（`FakeLlmClient` 报 0，假调用不花钱）。
因此本地与 CI 跑一次生成只会扣到服务费 + 图 + 页数 —— 8080 上看到的
`SPEND` 金额远小于真实定价下的金额，这是对的。

前两个常量在 `apps/generation-worker` 里，而包不能依赖 app，因此
`@tps/billing` 持有一份副本 `DEFAULT_JOB_LIMITS`。
[billing-limits.test.ts](../apps/generation-worker/src/assets/billing-limits.test.ts)
守住「billing 的估算参数不低于真实常量」—— 那是仓库里唯一能同时 import
到两边的地方。断言是 `>=` 而不是 `===`：允许 billing 保守，不允许它乐观。

### 失败全额退，成本记坏账

任务终态失败时预留全额释放，另写一条 `WRITE_OFF` 记我们实际烧掉的成本
（不扣用户，供成本分析与「上游故障正在烧钱」告警）。

理由：重试与故障转移都是我们的实现细节，不该让用户为一份没拿到的计划付费。

### 但「可重试的失败」不释放预留

C-4 落地时发现的一处：释放了的话，BullMQ 重试成功时 `settle` 找不到 ACTIVE
的预留，按 C-2 的设计它**不扣费**（凭空扣一笔用户看不懂的钱更严重）——
于是「失败一次然后成功」的任务全部免费。而 `PLAN_LLM_TIMEOUT` /
`PLAN_LLM_UNAVAILABLE` 导致的重试并不罕见，这会是一个持续漏钱且完全不可见的洞。

因此口径按**队列还会不会再消费一次**分：

| 情形                   | 预留                                                 |
| ---------------------- | ---------------------------------------------------- |
| 成功                   | 结算                                                 |
| `rejected`（计划被拒） | 释放 —— 队列不重试它（`main.ts` 只对 `failed` 抛错） |
| 不可重试的 `failed`    | 释放                                                 |
| 可重试的 `failed`      | **保留**，留给重试                                   |
| 用户取消               | 释放                                                 |
| 重试耗尽               | 由队列的 `failed` 事件（死信分支）释放               |
| 进程被 SIGKILL         | 由 `expires_at`（2 小时）兜住                        |

代价：可重试失败那一次烧掉的成本没有进 `WRITE_OFF` 流水（只进日志）。
那一笔的载体是 `writeoff:<job_id>`，而它必须与释放同一个事务 ——
否则重试成功后会出现「既结算又坏账」两条自相矛盾的记录。

### 结算按预留锁定的价目版本

`credit_holds.price_version` 是提交那一刻的版本，结算用它而不是当前发布版
（`pricesForVersion` 专为此存在，它**不看那一版是否仍是发布版**）。
用当前版结算会让用户按他提交时看不到的价格被扣，而他不会来提工单。

### 幂等

结算幂等键 `job:<job_id>`，由 `credit_ledger.idempotency_key` 的唯一约束保证。
**这是整套设计里最重要的一个约束**：生成任务会被重投（队列重试、worker 崩溃后
接管），结算逻辑因此会被执行多次。没有它，一次重投就是一次重复扣费 ——
而用户不会因为「少了 2000 CR」来提工单，他只会觉得这个产品贵。

## 五、导出：定价固定，直接扣、失败退

导出成本是几秒 Chromium CPU + 存储，量级比生成小三个数量级，
且**与内容无关**。因此不做预留/结算往返：请求时一次原子扣减
（幂等键复用既有的 `computeExportIdempotencyKey`），导出任务失败时退回。

### 失败时退回（C-4b）

render-worker 在 `captured.length === 0`（一页都没成功）之后退款：
按 `ref_type/ref_id` 回查当时那条 `SPEND`，退它的金额。

**退多少这件事只有一个正确答案：当时实际扣的那个数。**
`estimateExportCost(format, 当前价目)` 现算更省事，但调价窗口内会退错 ——
少退是我们赖账，多退是可以被反复触发的漏洞。`credit_ledger_ref_idx`
这个索引正是为这类回查建的。

**`PARTIAL` 不退。** 13.6 明确它是「部分成功 + 产物」而不是失败：
用户手里有文件，那一笔钱对应的服务确实交付了，`error` 字段已如实说明缺失。

**不必担心「退了钱重试又免费」**（生成侧那条陷阱）：`markRendering` 只从
`QUEUED` 转 `RENDERING`，因此已经落到 `FAILED` 的导出被重投时直接 `skipped`
—— 它不会再渲染一次。FAILED 就是终态。

一处已知的边：API 侧「建行失败就退回」用的是另一个幂等键（按导出幂等键），
而扣费的幂等键仍留在流水里 —— 因此那种情形之后，用户拿同一份参数重试
会得到一次不收费的导出（`charge` 走重放分支）。触发它要先撞上一次
非唯一约束的数据库错误，金额是一次导出（占位价 30～50 CR），
不值得为它把扣费键改成一次性的。

## 六、报价用端点，不下发价目表

生成按钮旁要显示「预计消耗 ~N CR / 余额 M CR」，不够就禁用。
做成 `POST /api/v1/credits/quote`（服务端算，权威）而不是把价目表下发给浏览器：

- 价目表是运营数据
- 下发之后前端与服务端各算一份，会出现「按钮说够、提交被拒」

因此「够不够」这个结论也由服务端给（响应里的 `sufficient`），
前端只负责禁用按钮，不做任何比较。

### 三个端点

```text
GET  /api/v1/credits/wallet    { balance_cr, held_cr, balance_cny }
POST /api/v1/credits/quote     { total_days } → 报价 + 余额 + sufficient
GET  /api/v1/credits/ledger    ?limit=&before=  倒序翻页
```

三个都**拒绝匿名身份**（403 `AUTH_ANONYMOUS_FORBIDDEN`）。返回「余额 0」是
另一种选择，而它更糟：前端会画出一个永远不够用的钱包，用户无从知道该去注册。

报价只收天数，不收整份 `TravelRequestUI`：用户还在填表时就想看到「大概多少钱」，
而那时表单必然不完整。权威金额在生成端点按**标准化后的**天数现算，
因此这里收一个客户端给的天数不构成绕过。

流水**不返回 `metadata`** —— 它装的是逐项 SKU 明细，含供应商模型名与我们的
单价，属于运营数据。用户要的「这一笔花了多少」已经在 `amount_cr` 里。

### 402 带上数值

`AUTH_INSUFFICIENT_CREDITS` 的响应体里有
`error.details = { required_cr, balance_cr }`（13.0 的错误信封新增了一个
只允许数字的 `details` 字段）。让前端拿到 402 后再请求一次报价是另一种做法，
而那是用户最需要一句「还差 N CR」的时刻，多一次往返多一次失败机会。

### 前端呈现（C-6）

```text
账号面板      剩余 CR ≈ N 元（替换原来的两个次数）+ 冻结额（非 0 时才占一格）
生成按钮旁    本次预计消耗 N CR（约 X 元） / 最多 M CR，当前余额 B CR
              余额不足时改成「还差 N CR」并**禁用按钮**
402 弹层      「还差 N CR。充值入口内测期尚未开放……已填写的内容不会丢」
/credits      消费明细，倒序翻页
```

四处刻意的选择：

- **判据是「会话里有没有 `wallet`」**，不是「余额是不是 0」。计费关着的部署里
  CR 这个概念对用户根本不存在，界面退回原来的两个次数。
- **「够不够」只认服务端的 `sufficient`。** 响应里同时有 `hold_cr` 与
  `balance_cr`，自己比一下更直接 —— 但那会造出第二套判断，
  分叉的表现是「按钮说够、提交被拒」。`shortfall` 只用于**措辞**。
- **不计费时什么都不显示**，而不是「本次免费」：那会被读成优惠活动，
  下次收费就成了背信。
- **不写「请去充值」。** 支付入口本轮不存在（见「明确不在范围」），
  指一个不存在的入口，用户会在界面上找它。
- **坏账行不展示。** `WRITE_OFF` 金额恒 0、真实数字在不下发的 `metadata` 里，
  留着它用户会看到几行「成本记账 0」。隐藏它不打断余额自校验那条链 ——
  恒 0 的行不改变任何余额，那正是 0013 把它约束成 0 的理由之一。

窄屏有一处专门处理：吸底动作条本来隐藏所有辅助文字（省高度），
但「余额不足」那一条留着 —— 它是**按钮为什么点不了**的唯一解释。

### 会话响应增加 `wallet`

`GET /auth/session` 的响应多一个 `wallet: { balance_cr, held_cr, balance_cny }`，
**只在装配了计费且身份是注册用户时出现**。既有的 `quota.*` 字段保留不动：
删它是破坏性契约变更，而 13.x 明确邀请第三方替换呈现层 —— 产品上它只是不再展示。

### 降级方向一律朝「不挡用户」

| 情形                           | 行为                                                                |
| ------------------------------ | ------------------------------------------------------------------- |
| 一版价目表都没发布             | 免费放行 + warn 日志。反过来是「运营还没配价格，全站不能生成」      |
| 报价算出 0 CR                  | 不预留（`credit_holds.amount_cr` 有 `> 0` 的 CHECK，预留 0 会 500） |
| 导出的那一项没价目             | 不收费。少收一笔好过让用户导不出已经生成好的计划                    |
| `CREDIT_BILLING_ENABLED=false` | 完全不碰钱包表 —— 库还没迁到 0013 的部署必须能跑                    |

这四条与「次数配额保留不删」是一套：货币闸门失效时次数闸门还在（见第一节）。

## 七、数据表

| 表                                             | 是什么                                   | 可变性     |
| ---------------------------------------------- | ---------------------------------------- | ---------- |
| `credit_wallets`                               | 当前余额 `balance_cr` 与冻结额 `held_cr` | 可变       |
| `credit_ledger`                                | 流水                                     | **只追加** |
| `credit_holds`                                 | 生成任务的预留                           | 有状态机   |
| `credit_price_versions` / `credit_price_items` | 价目表                                   | 版本化     |
| `credit_prices_current`                        | 当前发布版视图                           | 只读       |

### 为什么钱不放 Redis

现有配额用 Redis 是对的：丢了下个时间窗自动重置，损失是「某个用户多生成一次」。
钱不一样 —— Redis 没有持久化保证（AOF 也有窗口），一次重启丢掉的是用户充的钱。
因此钱包全在 Postgres，且余额变动与流水写入必须在同一个事务里。

### 为什么保留可变余额而不是纯事件溯源

余额本可以由流水求和得出，但那让「查余额」变成一次全表聚合，
而余额在每次生成请求的关键路径上。折中：保留一列可变余额，
由 `credit_ledger.balance_after_cr` 让流水能自校验
（任何一行的 after = 上一行 after + amount）。

### 流水的六种 kind

| kind        | 方向      | 什么时候                           |
| ----------- | --------- | ---------------------------------- |
| `TOPUP`     | +         | 充值（本轮无支付网关，仅结构预留） |
| `GRANT`     | +         | 赠送（注册赠送、运营授予）         |
| `SPEND`     | −（或 0） | 消费（生成结算、导出扣费）         |
| `REFUND`    | +         | 退还（预留多退、任务失败全退）     |
| `WRITE_OFF` | **恒 0**  | 坏账：我们实际烧掉但不扣用户的成本 |
| `ADJUST`    | ±         | 运营手工冲销                       |

`WRITE_OFF` 恒为 0 是为了让「求和 = 余额」这条自校验仍然成立，
金额本身在 `metadata` 里。方向与 kind 的一致性由 CHECK 约束保证 ——
写错方向的表现是「退款把余额扣得更少」这种读起来完全正常、
对账时才发现的错。

### 六道约束（迁移 0013，已逐条实测）

```text
✓ 负余额被 CHECK 拒绝                    不透支的最后一道防线
✓ 负数的 REFUND 被拒绝                   方向与 kind 必须一致
✓ 非零的 WRITE_OFF 被拒绝                它不动用户余额
✓ 重复幂等键被唯一索引拒绝                任务重投不重复扣费
✓ ACTIVE 的预留不许带 settled_at         否则无法判断这笔结没结
✓ 同一 job_id 只能有一笔预留
```

## 八、运营操作

### 改价并发布

```sql
SELECT clone_credit_prices(1, 2, '按 2026Q3 供应商报价重定');

UPDATE credit_price_items i
SET price_cr = 45000
FROM credit_price_versions v
WHERE i.version_id = v.id AND v.version = 2 AND i.sku = 'llm.out:*';

SELECT publish_credit_prices(2);
```

发布是单事务：原发布版自动归档，目标草稿变为发布版。API 最多缓存 60 秒。

**已提交的任务不受影响** —— `credit_holds.price_version` 锁定了结算用的版本，
中途调价不会让用户按新价被扣。

### 回滚不是一句 publish

`publish_credit_prices` 只接受 `status = 'DRAFT'`，而刚被顶下来的版本已是
`ARCHIVED`，直接调会报 `draft credit price version N not found`。
归档时 `published_at` 已被置 NULL，因此改回 DRAFT 不会撞形态约束：

```sql
BEGIN;
UPDATE credit_price_versions SET status = 'DRAFT' WHERE version = 1;
SELECT publish_credit_prices(1);
COMMIT;
```

（同一个坑在 `planner_config` 那边踩过一次，见 [规划器配置中心](规划器配置中心.md)。）

### 查余额与授予（`pnpm user:credit`）

```bash
pnpm user:credit -- --email a@b.com                  # 查余额、冻结额与最近 10 条流水
pnpm user:credit -- --phone 13800000000              # 同上，按手机号（会归一成 E.164）
pnpm user:credit -- --phone 13800000000 --grant 9900 --note "工单 123"
```

只需 `DATABASE_URL`，**与 `CREDIT_BILLING_ENABLED` 无关** —— 打开那个开关之前
正需要先用它给存量用户授一笔。

三处刻意的设计：

- **`--grant` 只收 CR，不收元。** 两个单位都收的话 `--grant 9.9` 与
  `--grant 9900` 长得同样合理，而两者差 1000 倍。元只出现在输出里。
- **默认拦住 1000 元以上的授予**（`--force` 放行）。多授出去的 CR
  没有撤销入口，而 `--grant 9900000` 与 `--grant 9900` 只差一个手滑。
- **支持 `--phone`。** P7 之后手机号是主要注册路径，而那些用户没有邮箱 ——
  只按邮箱查的话，对新注册用户全都报「这个用户不存在」。

幂等键是随机 UUID，因此**重跑会再授一次**。改成确定性键能防住重跑，
但会让「同一个用户补偿两次同样的金额」这种正常操作被静默吞掉，
而那比多授一次更难发现。命令末尾打印余额，人能当场看出授没授上。

### 钱包与流水不提供回滚

流水是只追加的账。冲销要写一条反向的 `ADJUST`，而不是删行或改行。
而 `credit()` 只接受正数，因此**目前没有冲销入口** —— 误授了大额只能改
数据库。这是有意的取舍：补一条带符号的 `ADJUST` 通道要连带处理
「扣到负数怎么办」，而 `--grant` 的上限已经把手滑挡在门外。

### 环境变量

| 变量                              | 默认      | 说明                                              |
| --------------------------------- | --------- | ------------------------------------------------- |
| `CREDIT_BILLING_ENABLED`          | **false** | 总开关。打开前必须先迁到 0013，见下               |
| `CREDIT_CR_PER_CNY`               | 1000      | 1 元兑多少 CR。**改它等于给所有存量余额重新标价** |
| `CREDIT_SIGNUP_GRANT_CR`          | 9900      | 注册赠送。0 = 不赠送                              |
| `CREDIT_HOLD_BUFFER_PERCENT`      | 120       | 预留相对典型估算的放大。**必须 ≥ 100**            |
| `CREDIT_EST_INPUT_TOKENS_PER_DAY` | 3000      | 输入 token 的每天经验值                           |
| `CREDIT_EST_MAX_AI_IMAGES`        | 3         | 估算用的 AI 图上限，须 ≥ worker 的真实常量        |
| `CREDIT_EST_MAX_IMAGE_SEARCHES`   | 8         | 同上                                              |
| `CREDIT_EST_MAX_REGENERATIONS`    | 2         | 同上                                              |

### 打开总开关的顺序

`CREDIT_BILLING_ENABLED` 默认 `false`，而这不是保守而已：钱包与价目表在
迁移 0013 才建立，**而应用与数据库的部署不是原子的**。装配了却没迁移的后果是
每个生成请求、每次会话查询都撞「relation credit_wallets does not exist」——
也就是全站不可用，而根因在一张不存在的表上。

```bash
pnpm db:migrate            # 到 0013
# 确认 credit_prices_current 有 9 行、版本 1 已发布
# 再把 CREDIT_BILLING_ENABLED=true 并重启 api
```

关闭时 `/credits/*` 三个端点不注册，生成与导出完全不计费，钱包表一次都不读。
启动日志里有 `credit_billing_enabled` 字段 —— 这一条必须能一眼看到。

**存量用户在开关打开的那一刻余额是 0**，因此 C-5（注册赠送 + `pnpm user:credit`）
应当先于「在生产上打开开关」落地，否则所有人立刻无法生成。

## 九、待定：真实定价

**迁移 0013 种下的价目表（版本 1）全是占位值**，是为了让系统在没有运营配置时
也能跑通，不是真实定价。`isSeedPriceBook()`（判据：版本号 == 1）让启动时能
打一条 warn —— 带着占位价上线的表现不是报错，是**收错钱**，
而收错钱要到对账时才发现。

调研市面上大模型价格之后需要重定。有一个数值优先级最高：

> **`llm.out:*` 占位价是 60000 CR/百万 token（= 60 元/百万），
> 而输出 token 占了报价的 60~75%** —— 它决定整个产品的价格带，
> 比其他八项加起来都重要。

### 三个阶段的价目表

| 版本 | 来源            | 行为             | 判定                     |
| ---- | --------------- | ---------------- | ------------------------ |
| 1    | 迁移 0013       | **不计费**       | `isSeedPriceBook`        |
| 2    | 迁移 0014       | 计费 + 启动 warn | `isProvisionalPriceBook` |
| ≥ 3  | 运营 clone 改价 | 计费，无 warn    | 两个判定都 false         |

**版本 1 不计费**，因为它与注册赠送额恰好不兼容：占位价下一次 14 天行程要冻
10578 CR，而赠送额是 9900 CR —— 刚注册的用户点 14 天直接拿到 402。
两个互不相干的占位数凑在一起必然出现这类矛盾。而按它收钱更糟：
**收错钱比不收钱严重**，错账要到对账时才发现。

**版本 2 是开发期定价**，存在的唯一理由是：占位版不计费会让**计费链路在
开发期一次都不被走到**，而一条没人跑的链路会烂掉。它的数字按「能跑通」
选而不是按成本选，判据只有一条：

> **连 14 天的最坏上界都要落在注册赠送额之内。**

```text
天数   典型 CR   上界 CR   预留 CR（× 120%）   9900 CR 能买几次
   5       767      1379                921                 10
   7      1047      2198               1257                  7
  14      2317      5938               2781                  3
```

上界 5938 < 9900：因此**任何天数、任何重生成次数**下，一个刚注册的用户都能
生成成功。只保证「典型值不超」不够 —— 那会让「重生成两次」这条路径变成
一个只在特定条件下出现的 402，而它恰恰最难复现。

这条判据由 [dev-prices.test.ts](../packages/billing/src/dev-prices.test.ts)
守住，而那个测试**直接解析迁移 SQL** —— 在测试里抄一份数字的话，
漂移方向恰好是最坏的：测试说能跑通，库里那一版跑不通。

**运营改价必须 clone 到新版本，不要原地改。** 版本号是判据：
在版本 2 上改价等于「改完了系统仍然认为这是开发期定价」，那条 warn 会一直响。

```sql
SELECT clone_credit_prices(2, 3, '按 2026Q3 供应商报价重定');
-- 改价（见第八节）
SELECT publish_credit_prices(3);
```

改完最多 60 秒生效（价目表缓存），不改代码、不重启。

### 占位价下的实测报价（C-3 用真实种子价目跑出来的）

| 天数 | 典型 CR | 上界 CR | 预留 CR   | 预留折合 | 9900 CR 能买几次 |
| ---- | ------- | ------- | --------- | -------- | ---------------- |
| 3    | 2345    | 4671    | 2814      | 2.81 元  | 3                |
| 5    | 2475    | 5041    | 2970      | 2.97 元  | 3                |
| 7    | 3588    | 8360    | 4306      | 4.31 元  | 2                |
| 8    | 6099    | 15883   | 7319      | 7.32 元  | 1                |
| 14   | 8815    | 23971   | **10578** | 10.58 元 | **0**            |

> **占位价下 14 天行程的预留额（10578 CR）超过注册赠送额（9900 CR）。**

这一行是「占位价不计费」那个决定的证据：两个占位数不兼容，而按占位价计费
就意味着刚注册的用户点 14 天必然被拒。**它现在卡不住流程**（版本 1 不计费），
但运营定真实价时必须同时定下赠送额 —— 否则同一个坑会在版本 2 上重现。

三条出路都要定价决策：调低 `llm.out:*`、提高 `CREDIT_SIGNUP_GRANT_CR`、
或接受「长行程需要充值」（那要求支付入口先上线）。

定价要同时定下来的三件事：

1. 各模型的 `llm.in` / `llm.out` 单价（按供应商成本 + 毛利）
2. 兜底价 `:*` —— 应当**高于**所有已登记模型，因为它命中意味着配置漏了
3. 「9.9 元买几次 5 天行程」这个产品形态，与 `CREDIT_SIGNUP_GRANT_CR` 的联动

### C-3 的两处与原计划的偏差

1. **队列载荷不带 `hold_id`。** 计划里写了「入队（payload 带 hold_id）」，
   但结算是按 `job_id` 查预留的（`credit_holds.job_id` 唯一），worker 用不到
   hold_id。加它要改 `@tps/queue` 的消息契约与 worker 两侧，换不来任何东西。
2. **多了一次只读预检**，理由见第四节「为什么是『预检 + 预留』两步」。

### C-4 的一处施工注意（已按它落地）

`AiImageBudget.reserve` 在 `70bf637` 之后把占位递增移到了 await 之前、
熔断拒绝路径补了 `refund`。因此**计费打点必须挂在图真的生成成功处，
不能挂在 reserve** —— 否则被 refund 掉的占位也会被计费。

落地方式是读 `budget.used.images`：那个计数在失败与同键去重时都被 `refund`
减回去了，因此它本身就是「真的生成出来的张数」。不动素材管线就已经满足。

### 三侧开关必须一起开

`CREDIT_BILLING_ENABLED` 在 api、generation-worker、render-worker 各读一次：

- 只开 api：每个任务都留下一笔永不结算的预留，钱冻到 2 小时后过期；
  渲染失败的导出也不退款 —— 用户为一份拿不到的 PDF 付了费；
- 只开 generation-worker：没有预留可结，`settle` 找不到 hold 就直接返回
  —— 一次都不收费；
- 只开 render-worker：没有扣费记录，什么都不退（无害，但也没用）。

三个进程的启动日志都打了 `credit_billing_enabled`，值不一致时能一眼看到。

### 明确不在范围

- 支付网关（回调验签、对账、退款、发票）—— 流水表留了 `payment_ref` 结构
- 存储字节计费（MinIO 没有计量点，量级远小于模型调用）
- 订阅制 / 有效期 / 分级折扣 —— `tier_level` 已能承载，但定价策略是产品决策
- 删除匿名子系统 —— `FEATURE_ANONYMOUS_ENABLED` 默认 `false` 已达到「必须注册」

2. **并发预留**：同一钱包两个并发请求、余额只够一次 → 恰好一个 201、一个 402，
   且 `balance_cr + held_cr` 守恒。
3. **重复结算**：同一 `job_id` 结算两次 → 流水只有一条，钱包只动一次。
4. **失败退款**：任务 FAILED → 余额回到扣前，流水有 `REFUND` 与 `WRITE_OFF`。
5. **兜底价**：发布一份缺某模型 `llm.in` 的价目表 → 命中 `*`，
   `travel_credit_unpriced_total{domain="llm.in"}` +1，不崩。
6. **迁移**：在临时库跑（`docker exec psql --single-transaction`），
   核对版本 1 已发布后删库。`travel_poster` 的迁移单独确认后再执行。
7. **8080 端到端**：CLI 授予 9900 CR → 生成一次 → 余额下降、流水一条 `SPEND`、
   `held_cr` 归零；再把余额调到不足 → 生成返回 402 且前端按钮禁用。
   （需要 C-4 与 C-5 都到位，且 `travel_poster` 迁到 0013。）
8. **开关关闭时零影响**：`CREDIT_BILLING_ENABLED=false` 下生成与导出照常，
   钱包表一次不读 —— 由 `travel-plans.test.ts` / `exports.test.ts` 里
   「未装配计费时不碰钱包」两条守住。
9. `pnpm test:visual` 保持 0.0000%（本设计不碰 `/render/**`）。

## 十二、可观测（C-7）

到 C-6 为止，坏账、兜底价命中、402 频次**全都只在日志里**。而这三件事的
共同点是：出问题时没有任何东西会失败。

```text
坏账     用户照样拿到计划，任务照样 COMPLETED，只是钱我们出了
兜底价   那个模型照一个偏贵的价收，用户不会来问，运营也不知道自己漏配了
402      语义完全正确，错误率与 SLA 全都正常 —— 而用户会走
```

日志能查，但**查的前提是先怀疑**。

### 三个指标

| 指标                             | 标签              | 进程              | 回答什么                               |
| -------------------------------- | ----------------- | ----------------- | -------------------------------------- |
| `travel_credit_settled_cr_total` | `direction`       | generation-worker | 收了多少 / 退了多少 / **我们吃掉多少** |
| `travel_credit_unpriced_total`   | `domain`          | generation-worker | 有没有漏配价格                         |
| `travel_credit_gate_total`       | `event` `outcome` | api               | 有多少人撞在余额上                     |

**单位是 CR 而不是次数。** 「发生了 10 次坏账」不说明任何事 ——
10 次 1 CR 与 10 次 10000 CR 是完全不同的两件事，而告警要判的是后者。

**`unpriced` 的标签是 SKU 的域而不是完整 SKU。** `llm.in:<model>` 里的
model 是供应商回给我们的，有些供应商返回带日期的版本名，那个集合会随时间
慢慢长 —— 而 21.3 的标签白名单只收「取值集合由代码封闭」的东西。
完整 SKU 在日志的 `sku` 字段里；告警要回答的是「有没有漏配」，
「漏配了哪一个」是随后一次 grep 的事。

**`gate_total` 的 `outcome=free` 必须可见。** 那条路径下所有生成都不收费
（没有价目表、或算出 0 CR），而除了这条曲线之外没有任何迹象。

### 三条告警

| 告警                                | 阈值                | 为什么是这个数                                                                                                                      |
| ----------------------------------- | ------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `TravelCreditWriteOffHigh`          | 坏账 > 5000 CR/小时 | = 5 元/小时。一次生成占位价约 1～3 元，因此它相当于「每小时有两三次生成的钱是我们出的」——偶发失败退款到不了，一次上游故障会瞬间越过 |
| `TravelCreditUnpriced`              | 15 分钟内 > 0       | 一次可能来自灰度中的新模型；漏配的表现是**持续**命中                                                                                |
| `TravelCreditInsufficientRatioHigh` | 被拒占比 > 20%      | 产品告警。分母只算真进了闸门的（`allowed + insufficient`），不含 `free`                                                             |

处置步骤在 [运维手册](运维手册.md) 的三节：坏账速率异常、有SKU没配价、
余额不足占比升高。告警注解里的 runbook 链接由
`packages/observability/src/runbook.test.ts` 守住 —— 改标题会让它变红。

### 有意没做的两个指标

- **导出退款次数**：`travel_export_total{outcome="failed"}` 与退款是 1:1
  （见 C-4b：只在 `captured.length === 0` 时退），再加一个指标只是同一条曲线换个名字。
- **每笔消费的分布直方图**：结算金额只取决于天数与重生成次数，
  而 `travel_job_duration_seconds` 已经按 `total_days_bucket` 分了档。
  真要按金额分析，流水表里有逐笔明细，那是对账的工作而不是监控的。
