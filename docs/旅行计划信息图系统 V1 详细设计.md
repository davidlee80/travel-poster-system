本设计以最终自动生成类似示例图片的旅行计划页面为目标。最终交付物包括：

- 可浏览的 HTML 旅行计划；
- 每日信息图页面；
- 可下载的 PNG 长图；
- 可保存或打印的 PDF；
- 注册用户空间中的历史版本。

全链路不需要人工介入：

```text
用户提交旅行诉求
→ 后端标准化
→ 大模型生成结构化旅行计划
→ 程序校验并自动修复
→ 展示编排器生成素材需求
→ 素材服务自动获取图片、图标和地图
→ 生成展示 ViewModel
→ React 模板渲染 HTML
→ Playwright 导出 PNG/PDF
→ 自动展示给用户
```

## 1.2 V1 不支持范围

暂不处理：

- 航班和酒店实时库存；
- 自动下单；
- 商家点评聚合；
- 多人实时协同；
- 用户自由设计页面布局；
- 模型动态生成 React 代码；
- 模型直接写数据库；
- 模型直接生成最终 HTML；
- 复杂地理导航；
- 大规模公共社区图库。

**R-12 补充：以下三项在 V1.0 中范围模糊，V1.1 明确不支持。**

| 项目         | V1 行为                                                                                                                                  | 说明                                                                |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 多目的地行程 | `trip.destination.mode` 只接受 `FIXED`；`allow_multiple_destinations` 只接受 `false`，传 `true` 返回 `REQ_MULTI_DESTINATION_UNSUPPORTED` | `TravelPlan.days[].city` 字段保留但 V1 内所有天必须同城，为 V2 预留 |
| 日期弹性     | `dates.flexibility_days` 只接受 `0`，非 0 返回 `REQ_DATE_FLEXIBILITY_UNSUPPORTED`                                                        | V1.0 定义了该字段但全文没有任何处理逻辑，属于契约悬空               |
| 目的地推荐   | 不支持 `mode: "SUGGESTED"`，用户必须指定目的地                                                                                           | 目的地推荐需要独立的候选集与排序模型，不在 V1                       |

以上三项均在请求标准化阶段（3.1）拒绝，不进入 LLM 生成，避免浪费模型成本。

# 三、核心服务拆分

## 3.1 Travel Request Service

职责：

- 接收前端提交的旅行诉求；
- 保存原始请求；
- 标准化标签；
- 计算人数、天数和预算；
- 检查输入冲突；
- 生成 `NormalizedTravelRequest`。

不调用图片服务，也不负责页面渲染。

### 3.1.1 标准化计算规则（R-03 补充）

| 派生字段            | 计算规则                                                                                                       |
| ------------------- | -------------------------------------------------------------------------------------------------------------- |
| `total_days`        | `end_date - start_date + 1`（含首尾）。超出 1～14 返回 `REQ_TRIP_DAYS_OUT_OF_RANGE`                            |
| `traveler_count`    | `adults + children.length + seniors.length`，必须 ≥ 1                                                          |
| `budget_total_max`  | `basis` 为 `PER_PERSON_PER_DAY` 时 `= budget.max × traveler_count × total_days`；`TOTAL` 时直接取 `budget.max` |
| `budget_total_min`  | 同上，取 `budget.min`                                                                                          |
| `has_child`         | `children.length > 0`，用于向 LLM 注入亲子约束                                                                 |
| `has_senior`        | `seniors.length > 0`，用于注入无障碍与体力约束                                                                 |
| `must_conditions`   | `conditions` 中 `mode === "MUST"` 的子集，硬约束                                                               |
| `should_conditions` | `conditions` 中 `mode === "SHOULD"` 的子集，软约束                                                             |

### 3.1.2 输入冲突检查（R-03 补充）

以下检查在标准化阶段同步执行，失败直接返回 4xx，不入队、不调用 LLM。

| 编号 | 检查                                                                                   | 错误码                              |
| ---- | -------------------------------------------------------------------------------------- | ----------------------------------- |
| N-01 | `start_date` 不早于今天（按 `timezone` 计算）                                          | `REQ_START_DATE_IN_PAST`            |
| N-02 | `end_date >= start_date`                                                               | `REQ_DATE_RANGE_INVALID`            |
| N-03 | `total_days` ∈ [1, 14]                                                                 | `REQ_TRIP_DAYS_OUT_OF_RANGE`        |
| N-04 | `budget.max >= budget.min > 0`                                                         | `REQ_BUDGET_RANGE_INVALID`          |
| N-05 | `pace.attractions_per_day_max >= pace.attractions_per_day_min >= 1`                    | `REQ_PACE_RANGE_INVALID`            |
| N-06 | `origin.place_id != destination.place_id`                                              | `REQ_ORIGIN_EQUALS_DESTINATION`     |
| N-07 | `traveler_count >= 1`                                                                  | `REQ_TRAVELER_COUNT_INVALID`        |
| N-08 | 所有 `conditions[].code` 存在于条件字典（见五章 5.1）                                  | `REQ_CONDITION_CODE_UNKNOWN`        |
| N-09 | `flexibility_days === 0`                                                               | `REQ_DATE_FLEXIBILITY_UNSUPPORTED`  |
| N-10 | `destination.mode === "FIXED"` 且 `allow_multiple_destinations === false`              | `REQ_MULTI_DESTINATION_UNSUPPORTED` |
| N-11 | `output_preferences.template_id` 在已注册模板列表中                                    | `REQ_TEMPLATE_UNKNOWN`              |
| N-12 | 预算下限对天数在物理上可行：`budget_total_min >= total_days × traveler_count × 50 CNY` | `REQ_BUDGET_INFEASIBLE`             |

## 3.2 Generation Orchestrator

这是整个流程的核心编排器。

职责：

1. 加载标准化旅行需求；
2. 检索历史计划；
3. 加载已验证的目的地资料；
4. 调用大模型生成 `TravelPlan`；
5. 执行 JSON Schema 校验；
6. 执行业务规则校验；
7. 自动修复违规项；
8. 保存有效计划版本；
9. 触发展示编排任务；
10. 触发渲染和导出任务。

### 3.2.1 业务规则校验规则表（R-03 新增）

V1.0 在第 6、7 步只写了「执行业务规则校验」「自动修复违规项」，但全文没有任何一条具体规则，而验收标准 3 完全依赖它。以下是 V1 的完整规则集。

**严重级定义**

| 级别         | 含义                     | 处理                                           |
| ------------ | ------------------------ | ---------------------------------------------- |
| `BLOCKING`   | 硬约束违规，计划不可用   | 修复；修复迭代耗尽后任务 `FAILED`              |
| `REPAIRABLE` | 软约束违规，可程序化修正 | 修复；修复失败降级为 `assumptions` 记录后放行  |
| `ADVISORY`   | 不影响可用性             | 只写入 `constraint_report.assumptions`，不修复 |

**结构与一致性规则**

| 编号 | 规则                                                                        | 级别         | 修复动作                                                               |
| ---- | --------------------------------------------------------------------------- | ------------ | ---------------------------------------------------------------------- |
| V-01 | `days.length === normalized.total_days`                                     | `BLOCKING`   | 缺天：对缺失 `day_number` 触发单日补生成；多天：截断尾部               |
| V-02 | `days[].day_number` 从 1 连续递增无重复                                     | `BLOCKING`   | 按 `date` 排序后重编号                                                 |
| V-03 | `days[].date` 等于 `start_date + (day_number - 1)` 天                       | `BLOCKING`   | 按 `day_number` 重算日期覆写                                           |
| V-04 | `days[].city` 与 `destination.text` 一致（V1 单目的地）                     | `REPAIRABLE` | 覆写为目的地名，记入 `assumptions`                                     |
| V-05 | 每日 `schedule.length >= 1`                                                 | `BLOCKING`   | 触发该日补生成                                                         |
| V-06 | `schedule[]` 按 `start_time` 升序且时间区间不重叠                           | `REPAIRABLE` | 按 `start_time` 排序；重叠则后项顺延至前项 `end_time`                  |
| V-07 | `end_time > start_time`，且 `duration_minutes` 与时间差一致（容差 ±5 分钟） | `REPAIRABLE` | 以 `start_time` + `duration_minutes` 重算 `end_time`                   |
| V-08 | 每条 `schedule[].location.latitude ∈ [-90, 90]`、`longitude ∈ [-180, 180]`  | `REPAIRABLE` | 坐标非法则置 `location.latitude/longitude` 为 `null`，该节点退出路线图 |

**节奏与体力规则**

| 编号 | 规则                                                                                        | 级别         | 修复动作                                                                                |
| ---- | ------------------------------------------------------------------------------------------- | ------------ | --------------------------------------------------------------------------------------- |
| V-10 | 每日 `schedule.length ∈ [pace.attractions_per_day_min, pace.attractions_per_day_max]`       | `REPAIRABLE` | 超上限：按 `estimated_cost` 降序删除末位低优先条目；低于下限：记入 `assumptions` 不强补 |
| V-11 | 每日 `sum(estimated_walking_km) <= pace.walking_limit_km`（容差 +20%）                      | `REPAIRABLE` | 删除步行距离最大的一条 `schedule`，重算                                                 |
| V-12 | 每日首条 `schedule[0].start_time >= pace.earliest_departure_time`                           | `REPAIRABLE` | 整日行程平移至满足该时间，保持各条 `duration_minutes`                                   |
| V-13 | 每日最晚 `end_time <= 22:00`（含 `custom_requirements` 中「不要太晚」类语义时收紧到 21:00） | `REPAIRABLE` | 删除末位条目或压缩时长                                                                  |
| V-14 | `has_senior === true` 时 `walking_limit_km` 实际取 `min(pace.walking_limit_km, 4)`          | `ADVISORY`   | 记入 `assumptions`                                                                      |

**预算规则**

| 编号 | 规则                                                                            | 级别         | 修复动作                                                           |
| ---- | ------------------------------------------------------------------------------- | ------------ | ------------------------------------------------------------------ |
| V-20 | `daily_budget` 四项之和 = `daily_budget.breakdown[]` 金额之和（见六章 R-04）    | `REPAIRABLE` | 以 `breakdown[]` 之和覆写四项分桶                                  |
| V-21 | `sum(所有 daily_budget 总额) × traveler_count <= budget_total_max`（容差 +10%） | `REPAIRABLE` | 按「门票 → 其他 → 餐饮」顺序下调金额并替换对应条目为更低价选项标注 |
| V-22 | 总额 `>= budget_total_min × 0.6`                                                | `ADVISORY`   | 低于预算不视为错误，记入 `assumptions`                             |
| V-23 | 所有 `currency` 与 `budget.currency` 一致                                       | `BLOCKING`   | 覆写为请求币种，不做汇率换算，记入 `assumptions`                   |
| V-24 | 所有金额 `>= 0` 且为整数或两位小数                                              | `REPAIRABLE` | 四舍五入到两位小数，负数置 0                                       |

**约束满足规则**

| 编号 | 规则                                                                 | 级别       | 修复动作                                    |
| ---- | -------------------------------------------------------------------- | ---------- | ------------------------------------------- |
| V-30 | 每个 `must_conditions` 都必须出现在 `constraint_report.satisfied` 中 | `BLOCKING` | 不可程序化修复，触发带违规清单的 LLM 重生成 |
| V-31 | `constraint_report.violated` 中不得包含 `mode === "MUST"` 的条目     | `BLOCKING` | 同 V-30                                     |
| V-32 | `should_conditions` 满足率 `>= 60%`                                  | `ADVISORY` | 记入 `assumptions`                          |
| V-33 | `has_child === true` 时每日至少一条 `schedule` 标注适合儿童          | `ADVISORY` | 记入 `assumptions`                          |

**内容质量规则**

| 编号 | 规则                                                                        | 级别         | 修复动作                                  |
| ---- | --------------------------------------------------------------------------- | ------------ | ----------------------------------------- |
| V-40 | `title` 长度 ≤ 30 字，`days[].theme` ≤ 18 字，`days[].subtitle` ≤ 32 字     | `REPAIRABLE` | 超长交由 3.2.3 文案压缩                   |
| V-41 | `food_recommendations` 每日 1～4 条，`meal` 值不重复                        | `REPAIRABLE` | 去重保留首条，超量截断                    |
| V-42 | `photo_spots[].entity_name` 必须能在同日 `schedule[].location.name` 中找到  | `REPAIRABLE` | 找不到则删除该 `photo_spot`               |
| V-43 | `route_recommendations[].nodes.length >= 2`                                 | `REPAIRABLE` | 不足 2 个节点则删除该条路线               |
| V-44 | 无空字符串、无 `null` 必填字段、无 `undefined` 字面量、无 Markdown 残留符号 | `REPAIRABLE` | 清洗字符串；必填缺失升级为 `BLOCKING`     |
| V-45 | 全文不含 URL、HTML 标签、`http://`、`<` `>`                                 | `REPAIRABLE` | 剥离；这是 1.2「模型不生成 HTML」的执行点 |

### 3.2.2 自动修复策略（R-03 新增）

V1.0 未说明自动修复是程序化改写还是二次调用 LLM，也未定义迭代上限。V1.1 明确采用**两级修复**：

```text
第一级：程序化修复（Deterministic Repair）
  → 处理 REPAIRABLE 与结构类 BLOCKING（V-01 部分、V-02、V-03、V-23）
  → 纯函数，无模型调用，耗时 < 200 毫秒
  → 修复后重跑全量规则

第二级：LLM 定向重生成（Targeted Regeneration）
  → 仅当第一级后仍存在 BLOCKING（主要是 V-05、V-30、V-31）
  → 不重生成整个计划，只重生成受影响的 day 或缺失约束
  → 输入 = 原始 NormalizedTravelRequest + 违规清单 + 上一版该日内容
  → 重生成结果再次进入第一级
```

**迭代上限与终止条件**

| 参数                   | 值                      | 说明                                                   |
| ---------------------- | ----------------------- | ------------------------------------------------------ |
| 程序化修复最大轮次     | 3                       | 每轮后重跑规则；规则集收敛性由「修复动作只删不增」保证 |
| LLM 定向重生成最大次数 | 2                       | 全任务累计，不是每天 2 次                              |
| 单次重生成超时         | 30 秒                   | 超时按失败计入次数                                     |
| 终止成功               | 无 `BLOCKING` 违规      | 进入 `SAVING_PLAN`                                     |
| 终止失败               | 迭代耗尽仍有 `BLOCKING` | 任务 `FAILED`，错误码见 13.7 `PLAN_REPAIR_EXHAUSTED`   |

**失败时的行为（对应验收标准 15）**

修复失败的计划**不保存为可展示版本**，只以 `status = "REJECTED"` 落库到 `travel_plan_versions` 供排查，`GET /api/v1/travel-plans/{plan_id}` 不返回它。用户看到的是明确错误码与「重试」入口，绝不展示未通过校验的草稿。

### 3.2.3 文案压缩规则（R-04 新增）

3.3 提到「哪些文字需要压缩」但没有算法。17.3 溢出重渲染也依赖压缩文案。V1.1 定义如下：

压缩产物在 `BUILDING_PRESENTATION` 阶段**一次性预生成并随 ViewModel 落库**，字段命名为 `*_compact`，渲染时溢出才启用，不在渲染循环里临时调用模型。

| 层级 | 手段                                                                                        | 是否调用模型                                 |
| ---- | ------------------------------------------------------------------------------------------- | -------------------------------------------- |
| L0   | 原文                                                                                        | 否                                           |
| L1   | 去除修饰性副词与括号补充，截断到限长并在词边界收尾（中文按标点）                            | 否                                           |
| L2   | 保留主谓宾骨架的规则化缩写（如「参观运河沿岸历史建筑与专题展览。」→「看运河建筑与专题展」） | 否                                           |
| L3   | LLM 摘要至限长                                                                              | 是，与计划生成合并为同一次调用的附加输出字段 |

V1 只实现 L0～L2；L3 作为 V1.1 之后的可选增强，接口预留但默认关闭。

### 3.2.4 历史资源检索的全局性与脱敏（R-13 新增）

3.2 第 2 步「检索历史计划」与第 3 步「加载已验证的目的地资料」的**检索范围是全局的，不按用户隔离，也不区分匿名与注册身份**。

```text
写入 / 读取自己的计划  → 按 user_id 强制隔离（13.0）
生成时检索历史参考     → 全局，跨用户、跨身份类型
```

理由：历史计划的价值在于「杭州运河主题这样安排是可行的」这类**可复用的行程知识**，把它锁在单个用户的空间里会让检索几乎永远命中不到东西 —— 对匿名用户尤其如此（首次访问即零历史）。

**隐私边界（必须实现，不是可选项）**

跨用户检索会把 A 用户的个人参数带进 B 用户的生成上下文。因此检索**只允许读取脱敏投影**，不允许读取 `plan_json` 全文：

| 字段                                                             | 进入检索结果 | 说明                                               |
| ---------------------------------------------------------------- | ------------ | -------------------------------------------------- |
| `destination.name` / `place_id`                                  | 是           | 行程知识                                           |
| `days[].theme` / `subtitle`                                      | 是           | —                                                  |
| `days[].schedule[].title` / `location.name` / `place_id`         | 是           | POI 序列是核心可复用知识                           |
| `days[].schedule[].period` / `duration_minutes`                  | 是           | 时间结构                                           |
| `days[].food_recommendations[].name` / `entity_type`             | 是           | —                                                  |
| `days[].route_recommendations[].nodes`                           | 是           | —                                                  |
| `total_days`                                                     | 是           | 用于筛选相近长度的行程                             |
| `days[].schedule[].description`                                  | 是           | 已由 V-45 清洗，不含用户输入                       |
| `start_date` / `end_date` / `days[].date`                        | **否**       | 具体日期是个人行程信息                             |
| 全部金额字段（`total_budget`、`daily_budget`、`estimated_cost`） | **否**       | 预算是敏感个人参数                                 |
| `traveler_count` 及人员构成（`children`、`seniors`）             | **否**       | —                                                  |
| `custom_requirements.raw_text`                                   | **否**       | 用户自由文本，可能含姓名、联系方式、健康信息       |
| `constraint_report`                                              | **否**       | 含用户的 `MUST` 条件（无障碍、饮食禁忌等敏感属性） |
| `user_id` / `plan_id` / `request_id`                             | **否**       | 不向 LLM 暴露任何标识符                            |

**实现方式**：`travel_plan_versions` 增加 `retrieval_projection JSONB` 列（写入时按上表裁剪），**向量检索与 LLM 参考资料都只读该列**，`plan_json` 在检索路径上完全不可达（见 15.2）。`plan_embedding` 也必须由 `retrieval_projection` 而非 `plan_json` 计算 —— 否则敏感字段会以向量形式残留。这样即使检索代码写错也无法泄漏敏感字段，安全性由数据布局保证而不是靠调用方自觉。

**检索约束**

| 约束         | 值                                                                                    |
| ------------ | ------------------------------------------------------------------------------------- |
| 候选数       | Top 5                                                                                 |
| 过滤条件     | 同 `destination.place_id`；`status IN ('READY', 'REPAIRED')`；`total_days` 在 ±3 天内 |
| 排除         | 本次请求自身产生的版本；`status = 'REJECTED'` 的版本                                  |
| 相似度下限   | 余弦 ≥ 0.75，低于此值视为无参考                                                       |
| 耗时上限     | 1.5 秒（见 21.2），超时按无参考继续                                                   |
| 无参考时行为 | 正常生成，`constraint_report.assumptions` 记录「无历史参考」                          |

**目的地资料**（3.2 第 3 步）与**素材库**（`assets`）本就是平台维护的公共资源，不带 `user_id`，全局读取无隐私问题（见十五章「表关系总览」）。

## 3.3 Presentation Planner

展示编排器负责把完整旅行计划转换为“适合模板展示的数据”。

它不负责查找图片，只负责回答：

- 当前页面需要哪些模块；
- 每个模块显示多少条内容；
- 哪些文字需要压缩；
- 哪些素材槽位需要被填充；
- 使用哪一种模板和版式。

例如：

```json
{
  "template_id": "travel_infographic_v1",
  "page_type": "DAILY_POSTER",
  "day_number": 3,
  "content_limits": {
    "title_max_chars": 18,
    "subtitle_max_chars": 32,
    "schedule_max_items": 3,
    "food_max_items": 3,
    "photo_spot_max_items": 3,
    "ticket_max_items": 4,
    "booking_tip_max_items": 4
  },
  "asset_requirements": []
}
```

### 3.3.1 产物与 page_type（R-07 补充）

V1.0 中 `asset_requirements` 是空数组，与第七章独立的 `AssetRequirement` 文档关系不明。V1.1 明确：

**Presentation Planner 对每个计划版本输出 N+1 个 `PresentationPlan`**（N = 天数，+1 为完整计划页），每个 `PresentationPlan` 的 `asset_requirements` 字段就是第七章 `requirements[]` 数组的内容 —— 第七章描述的是**批量解析请求的信封**（含 `plan_id` / `plan_version_id`），而 `PresentationPlan.asset_requirements` 是其中单页的槽位子集。素材解析时把 N+1 页的槽位合并去重后一次性提交给 14.1。

`page_type` 枚举：

| 值             | 说明                                                | `day_number`  | 模板                    |
| -------------- | --------------------------------------------------- | ------------- | ----------------------- |
| `DAILY_POSTER` | 每日信息图（PNG/PDF 导出对象）                      | 必填          | `travel_infographic_v1` |
| `FULL_PLAN`    | 响应式完整计划页（1.1 要求，V1.0 未定义 page_type） | 必须为 `null` | `travel_full_plan_v1`   |

`FULL_PLAN` 的 `content_limits` 全部为 `null`（完整页不裁剪内容），且它**只复用各日已解析的素材，不新增素材槽位**，因此不会因为增加完整页而增加 AI 生成成本。

## 3.6 Identity Service（R-13 新增）

V1.0 与 V1.1 都假定用户已登录，但产品要求**未注册用户也能直接生成计划**。本节定义双模式身份体系。

### 3.6.1 两种身份

| 身份     | `user_type`  | 识别方式                                 | 凭据                     | 数据保留            |
| -------- | ------------ | ---------------------------------------- | ------------------------ | ------------------- |
| 匿名用户 | `ANONYMOUS`  | 首次访问时服务端签发的不透明 Cookie 令牌 | 无邮箱、无口令           | 30 天后清理（15.1） |
| 注册用户 | `REGISTERED` | 邮箱 + 口令登录后的会话                  | 邮箱 + Argon2id 口令哈希 | 长期保留            |

### 3.6.2 关键设计：统一 `users` 表，不建独立匿名表

匿名用户是 `users` 表中 `user_type = 'ANONYMOUS'` 的行，与注册用户共用同一张表和同一个 `user_id`。

**这样做的收益**

| 收益           | 说明                                                                                                                                                                   |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 归属列唯一     | `travel_requests` / `travel_plans` / `generation_jobs` / `exports` 只需 `user_id NOT NULL`，不需要可空外键，也不需要「要么 `user_id` 要么 `anonymous_id`」的二选一约束 |
| 查询路径唯一   | 13.0 的 `WHERE user_id = :current_user_id` 对两类身份完全一致，不存在双查询分支                                                                                        |
| **升级零迁移** | 匿名用户注册时只填入 `email` / `password_hash` 并把 `user_type` 翻转为 `REGISTERED`，**`user_id` 不变，历史计划自动继承**，不需要搬运任何业务行                        |
| 配额机制统一   | 21.4 的配额逻辑对两类身份同构，只是阈值不同                                                                                                                            |

若改用独立匿名表，「匿名 → 注册」就要跨表迁移 `travel_requests` / `travel_plans` / `generation_jobs` / `exports` 四张表的归属列，且要处理迁移中途失败的部分继承状态。统一表把这个问题从设计里消除掉了。

**代价**：匿名行会累积，需要保留期清理（15.1）。这是可控的运维任务，比跨表迁移的正确性风险小得多。

### 3.6.3 生命周期

```text
首次访问（无 Cookie）
  → 服务端 INSERT users(user_type='ANONYMOUS')
  → 签发 Set-Cookie: tp_anon=<opaque>（HttpOnly, Secure, SameSite=Lax, 30 天）
  → 可直接提交生成请求

匿名用户注册
  → 携带 tp_anon 调用 POST /api/v1/auth/register
  → 同一事务内：UPDATE users SET email=?, password_hash=?, user_type='REGISTERED'
                WHERE id = <anon_user_id> AND user_type = 'ANONYMOUS'
  → 清除 tp_anon，签发 tp_session
  → 历史计划自动可见（user_id 未变）

已注册用户在新设备/清 Cookie 后登录
  → POST /api/v1/auth/login → 签发 tp_session
  → 若请求同时携带 tp_anon（该设备上先匿名用过）
      → 执行「匿名归并」：把匿名 user_id 下的业务行改挂到已登录 user_id，
        然后把匿名行标记 status='MERGED'（不删，保留审计链）
      → 归并是唯一需要搬运业务行的场景，见 13.9.4
```

**为什么登录时仍需归并**：用户可能先匿名生成了几个计划，才想起自己已有账号去登录。此时匿名行与注册行是两个不同的 `user_id`，必须搬运。这个场景无法用「统一表」消除，但它的发生率远低于「匿名后注册」，且失败时可安全重试（幂等：按 `travel_requests.id` 逐行改挂）。

### 3.6.4 匿名用户的能力边界

| 能力                   | 匿名                                             | 注册 |
| ---------------------- | ------------------------------------------------ | ---- |
| 提交生成请求           | ✅                                               | ✅   |
| 查看自己的计划与信息图 | ✅                                               | ✅   |
| 导出 PNG / PDF         | ✅                                               | ✅   |
| 历史计划列表           | ✅（后端与数据模型 V1 就位；**前端界面可延后**） | ✅   |
| 跨设备访问             | ❌（Cookie 绑定单浏览器）                        | ✅   |
| 数据长期保留           | ❌（30 天）                                      | ✅   |
| 每日 / 每月配额        | 更低（见 21.4）                                  | 标准 |

**「历史浏览可延后」的落地方式**：`GET /api/v1/travel-plans`（列表端点，13.9.5）在 P2 就实现并测试，前端只在计划详情页放一个入口占位。这样延后的是界面而不是数据模型 —— 数据模型若延后，`user_id` 归属与保留策略都要返工。

### 3.6.5 匿名令牌的安全约束

| 约束        | 说明                                                                     |
| ----------- | ------------------------------------------------------------------------ |
| 令牌形态    | 32 字节 CSPRNG 随机值，Base64URL 编码；服务端存哈希（SHA-256），不存原文 |
| 不可枚举    | 令牌不含 `user_id`，也不是自增或时间派生                                 |
| Cookie 属性 | `HttpOnly`、`Secure`、`SameSite=Lax`、`Path=/`、`Max-Age=2592000`        |
| 不用于跨源  | 内部渲染路由（17.1）不接受任何身份 Cookie，只认 `X-Render-Token`         |
| 令牌丢失    | 视为新匿名用户；旧数据在保留期内仍存在但不可达，到期清理                 |
| 滥用防护    | 匿名用户创建按 IP 限速（见 21.4）；否则可无限刷新令牌绕过配额            |

**匿名令牌等价于一个无口令账号**，因此不允许它执行任何账号级敏感操作（改邮箱、删账号、查看其他会话），这些端点只对 `REGISTERED` 开放。

## 5.1 枚举与条件字典（R-07 新增）

V1.0 使用了 `mode`、`basis`、`level`、`included_items`、`conditions[].code` 等取值但从未定义全集，而标准化服务（3.1）必须依赖它才能执行 N-08 校验。

**基础枚举**

| 字段                          | 全集                                                                          |
| ----------------------------- | ----------------------------------------------------------------------------- |
| `trip.destination.mode`       | `FIXED`（V1 仅此一项，`SUGGESTED` 保留给 V2）                                 |
| `budget.basis`                | `PER_PERSON_PER_DAY`、`TOTAL`                                                 |
| `budget.currency`             | `CNY`（V1 仅此一项）                                                          |
| `budget.included_items[]`     | `ACCOMMODATION`、`MEALS`、`LOCAL_TRANSPORT`、`TICKETS`、`INTERCITY_TRANSPORT` |
| `pace.level`                  | `RELAXED`、`BALANCED`、`PACKED`                                               |
| `conditions[].mode`           | `MUST`、`SHOULD`                                                              |
| `output_preferences.language` | `zh-CN`（V1 仅此一项）                                                        |

`pace.level` 与三个数值字段冲突时以**数值字段为准**，`level` 仅在数值字段缺省时提供默认值：

| `level`    | `attractions_per_day_min` | `attractions_per_day_max` | `walking_limit_km` | `earliest_departure_time` |
| ---------- | ------------------------- | ------------------------- | ------------------ | ------------------------- |
| `RELAXED`  | 2                         | 3                         | 5                  | `09:00`                   |
| `BALANCED` | 3                         | 4                         | 8                  | `08:30`                   |
| `PACKED`   | 4                         | 6                         | 12                 | `08:00`                   |

**条件字典（`conditions[].code` 全集）**

`code` 采用 `<域>.<项>` 两段式命名。`value` 类型随域固定。V1 冻结以下 24 项，新增 code 需要同时更新字典与 LLM Prompt 模板。

| 域              | code                                                                                                                                                                             | value 类型 |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- |
| `interest`      | `interest.history_culture`、`interest.nature`、`interest.food`、`interest.shopping`、`interest.art_museum`、`interest.nightlife`、`interest.photography`、`interest.family_kids` | `boolean`  |
| `transport`     | `transport.public_transit`、`transport.self_drive`、`transport.walking_first`、`transport.avoid_transfer`                                                                        | `boolean`  |
| `accommodation` | `accommodation.elevator`、`accommodation.near_transit`、`accommodation.private_bath`、`accommodation.family_room`                                                                | `boolean`  |
| `accessibility` | `accessibility.wheelchair`、`accessibility.stroller`、`accessibility.low_walking`                                                                                                | `boolean`  |
| `diet`          | `diet.vegetarian`、`diet.halal`、`diet.no_spicy`、`diet.allergy_seafood`                                                                                                         | `boolean`  |
| `schedule`      | `schedule.no_late_night`                                                                                                                                                         | `boolean`  |

`custom_requirements.raw_text` 上限 500 字，超长截断并记入 `assumptions`。它作为自由文本注入 Prompt，但**不能覆盖任何 `MUST` 条件**。

## 6.2 R-04：两处必须修正的字段级不一致

V1.0 的 `TravelPlan` 与十二章 `TravelPosterViewModel` 存在两处无法映射的断裂。修正方式是**在 TravelPlan 侧补源字段**，而不是让 ViewModel 层凭空编造数据。

**不一致 1：`budget.items[].label` 无数据源**

ViewModel 的 `budget.items` 需要 `{ label: "运河船票", amount_text: "约 ¥10" }` 这样的**语义化条目**，而 V1.0 的 `daily_budget` 只有 `ticket` / `transport` / `meal` / `other` 四个固定分桶，无法产出「运河船票」这个 label。

→ **修正**：`daily_budget` 新增 `breakdown[]`（语义化条目，含 `label` / `amount` / `bucket`），四个分桶字段保留并降级为**由 `breakdown[]` 汇总得出的派生值**（规则 V-20 保证一致）。ViewModel 的 `budget.items` 直接映射 `breakdown[]`。

**不一致 2：`daily_summary` 无源字段**

ViewModel 顶层有 `daily_summary`（例：「这一天更适合慢节奏，白天看展，傍晚逛运河。」），但 V1.0 的 `TravelPlan.days[]` 完全没有对应字段。

→ **修正**：`days[]` 新增 `daily_summary`（≤ 40 字），由 LLM 直接生成。**不采用**「从 `theme` + `subtitle` 拼接」的兜底方案 —— 那会产出与页面标题重复的冗余文案。

## 6.3 LLM 输出约束（R-05 补充）

- 输出必须为**单个 JSON 对象**，通过结构化输出（JSON Schema 约束模式）获取，不解析 Markdown 代码块；
- `plan_id` / `plan_version_id` / `request_id` 由**程序注入**，不接受模型生成值（对应 1.2「模型不直接写数据库」）；
- 模型输出中出现的任何 URL、HTML 标签一律剥离（规则 V-45）；
- 单次调用 `max_tokens` 按天数分档：≤ 5 天 16K，6～10 天 32K，11～14 天 48K；
- 超过 7 天的行程**分段生成**（每段 ≤ 7 天）后合并，避免长输出截断，合并后统一跑校验。

## 8.1 枚举定义（R-07 新增）

| 字段                        | 全集                                                                                                                          |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `status`                    | `RESOLVED`、`FALLBACK`、`SKIPPED`、`FAILED`                                                                                   |
| `asset.asset_type`          | `IMAGE`、`SVG`、`ICON`                                                                                                        |
| `asset.source_type`         | `PLATFORM_LIBRARY`、`LICENSED_SOURCE`、`AI_GENERATED`、`GENERATED_SVG`、`LOCAL_ICON`、`DEFAULT_PLACEHOLDER`                   |
| `asset.representation_type` | `PHOTOGRAPHIC`、`ILLUSTRATIVE`（`AI_GENERATED` 时必填为 `ILLUSTRATIVE`，见 9.4）                                              |
| `asset.license.type`        | `PLATFORM_OWNED`、`LICENSED`、`AI_GENERATED`、`CC0`                                                                           |
| `resolution.strategy`       | `LOCAL_LIBRARY_MATCH`、`LICENSED_SOURCE_MATCH`、`AI_GENERATION`、`SVG_RENDER`、`CACHE_HIT`、`STATIC_DEFAULT`、`TEXT_FALLBACK` |

**`status` 语义**

| 值         | 含义                                                   | 是否有 `asset`                 |
| ---------- | ------------------------------------------------------ | ------------------------------ |
| `RESOLVED` | 按首选或次选策略拿到合规素材                           | 有                             |
| `FALLBACK` | 走到了默认占位/文字降级                                | 有（占位素材也是正式素材记录） |
| `SKIPPED`  | `required: false` 且全部来源均未达阈值，模板隐藏该槽位 | 无                             |
| `FAILED`   | `required: true` 却无法解析                            | 无，任务按十六章判定是否阻断   |

# 十、素材匹配评分

从素材库检索图片时，可以使用综合评分：

```text
final_score =
    实体名称匹配 × 0.35
  + 目的地匹配 × 0.20
  + 语义相似度 × 0.20
  + 画面比例匹配 × 0.10
  + 分辨率评分 × 0.05
  + 素材质量评分 × 0.05
  + 使用许可评分 × 0.05
```

伪代码：

```python
def score_asset(requirement, asset) -> float:
    return (
        entity_match(requirement, asset) * 0.35
        + destination_match(requirement, asset) * 0.20
        + semantic_similarity(requirement, asset) * 0.20
        + aspect_ratio_score(requirement, asset) * 0.10
        + resolution_score(requirement, asset) * 0.05
        + quality_score(asset) * 0.05
        + license_score(asset) * 0.05
    )
```

低于最低阈值时不使用。

例如：

```text
score >= 0.80：直接使用
0.65～0.79：可用，但优先继续查找
< 0.65：不使用，进入下一层兜底
```

## 10.1 子函数定义（R-08 新增）

V1.0 给了权重却没给任何一个子函数的算法，公式无法实现。以下七个函数全部返回 `[0, 1]`。

**`entity_match`（权重 0.35）**

```text
requirement.subject.entity_name 与 asset.entity_name 归一化后比较
（归一化 = 去空格、去括号内容、繁转简、全角转半角）

完全相等                    → 1.00
一方是另一方的子串           → 0.85
分词后 Jaccard 相似度 >= 0.6 → 0.70
别名表命中（如「大运河博物馆」↔「中国大运河博物馆」） → 0.90
其余                        → 0.00
```

`entity_name` 缺省的需求（如 `HERO_BACKGROUND`）该项按 **0.5 中性值**计入，避免把权重最大的一项归零导致 Hero 永远走不到素材库。

**`destination_match`（权重 0.20）**

```text
place_id 相等              → 1.00
destination_name 归一化相等 → 0.95
同省/同都市圈（行政区划表）  → 0.50
其余                       → 0.00
```

**`semantic_similarity`（权重 0.20）**

```text
cosine(embed(query_text), asset.embedding) 线性映射到 [0, 1]：
  score = clamp((cosine + 1) / 2, 0, 1)

query_text = [entity_name, destination, role 中文名, style_tags 拼接].join(" ")
```

嵌入模型固定 `text-embedding-3-small`（1536 维），**模型或维度变更必须视为破坏性变更**，需全量重算 `assets.embedding` 后才能切换（见十五章索引定义）。

**`aspect_ratio_score`（权重 0.10）**

```text
r_req = 需求比例, r_asset = 素材比例
d = |log2(r_asset / r_req)|
score = max(0, 1 - d / 0.5)

即比例偏差在 1.41 倍（半个八度）以内线性得分，超出记 0。
```

用 `log2` 比值而不是差值，保证 16:9 与 9:16 的惩罚对称。

**`resolution_score`（权重 0.05）**

```text
w = asset.width, min_w = requirement.visual_constraints.min_width
w <  min_w         → 0.00（硬性不达标）
w ∈ [min_w, 2×min_w) → 0.6 + 0.4 × (w - min_w) / min_w
w >= 2×min_w       → 1.00
```

**`quality_score`（权重 0.05）**

直接取 `assets.quality_score` 列（入库时离线计算并写入，不在检索路径实时算）。构成：清晰度（拉普拉斯方差归一）0.4 + 曝光合理性 0.3 + 主体占比 0.3。缺失时取 0.5。

**`license_score`（权重 0.05）**

| `license_type`         | 分值 |
| ---------------------- | ---- |
| `PLATFORM_OWNED`       | 1.00 |
| `CC0`                  | 0.90 |
| `LICENSED`（无需署名） | 0.80 |
| `LICENSED`（需署名）   | 0.60 |
| `AI_GENERATED`         | 0.70 |

## 10.2 检索终止条件（R-08 新增）

V1.0 写了「0.65～0.79：可用，但优先继续查找」，但没定义「继续查找」查到什么时候停 —— 这会导致无界检索。

```text
1. 向量检索取 Top 30 候选（pgvector，带 entity/destination 预过滤）
2. 对候选逐一计算 final_score，按分降序
3. 终止规则（先满足者先生效）：
   a. 出现 score >= 0.80          → 立即采用，停止
   b. 30 个候选全部算完            → 取最高分
4. 取最高分后：
   最高分 >= 0.65 → 采用，status = RESOLVED，fallback_level = 0
   最高分 <  0.65 → 进入下一层来源（授权图源 / AI 生成 / 默认占位）
5. 单槽位素材检索总耗时上限 800 毫秒，超时按「未命中」处理进入下一层
```

「优先继续查找」的含义因此被明确为：**不提前退出，但候选集有界（30）且有时间上限（800 毫秒）**，不是无限扩大检索范围。

**时长文案（`duration_text`）**

```text
m = duration_minutes
m < 60            → `约 ${m} 分钟`
m 是 60 的整数倍   → `建议 ${m / 60} 小时`
其余              → `建议 ${floor(m / 60)}～${ceil(m / 60)} 小时`

示例：150 → 「建议 2～3 小时」（与 V1.0 示例一致）
      120 → 「建议 2 小时」
       45 → 「约 45 分钟」
```

**金额文案（`amount_text`）**

```text
a = amount, symbol = 币种符号（CNY → ¥）
a === 0                   → `${symbol}0`
a 是 10 的整数倍且 a > 0    → `约 ${symbol}${a}`
其余                      → `${symbol}${round(a)}`

金额一律四舍五入到整数展示，底层保留两位小数。
「约」字仅用于 10 的整数倍（估算值特征），精确值不加。
```

**总额文案（`total_text`）**

```text
total_text = `约 ${symbol}${round(daily_budget.total)} / 人`

daily_budget.total 必须等于 breakdown[] 金额之和（规则 V-20 保证）。
渲染前断言：sum(budget.items[].amount) === daily_budget.total，
不等则记 REPAIRABLE 违规而不是静默展示 —— 预算数字对不上是用户可见的严重错误。
```

## 12.2 `icons` 字段契约（R-04 新增）

`icons` 的键集合**必须与 9.1 的模块图标一一对应**（8 个），V1.0 只列了 6 个且包含清单中不存在的 `route`。V1.1 的键为：

```text
schedule | food | map | route | camera | ticket | budget | tips
```

时段图标与交通图标**不放在 `icons` 里**，而是由 `schedule[].period_icon` 和 `transport_tips[].icon` 按名引用 —— 它们是按条目变化的，放在顶层 `icons` 会导致重复。类型定义上用 `Record<ModuleIconKey, string>` 保证编译期穷尽。

## 12.3 压缩文案字段（R-04 新增）

对应 3.2.3，以下字段在 ViewModel 中成对存在，供 17.3 溢出重渲染切换：

# 十三、API 设计

## 13.0 通用约定（R-05 新增）

V1.0 的 API 章节没有任何认证、错误响应体或幂等约定，而验收标准 11、13、14 全部依赖它们。

**认证（R-13 已改为双模式）**

所有 `/api/v1/**` 业务端点接受**两种身份之一**（见 3.6）：

```http
Cookie: tp_session=<opaque>     # 注册用户会话
Cookie: tp_anon=<opaque>        # 匿名用户令牌
```

两者都是服务端不透明随机值（存哈希），不使用 JWT —— V1 无跨服务鉴权需求，不透明凭据可即时吊销。会话 30 天滑动过期，匿名令牌 30 天固定过期。

**身份解析顺序**

```text
1. 有 tp_session 且有效        → REGISTERED 身份，user_id 取自会话
2. 无有效 tp_session，有 tp_anon 且有效 → ANONYMOUS 身份，user_id 取自令牌
3. 两者都无 / 都无效
   a. 请求是 POST /api/v1/travel-plans/generate
        → 自动创建匿名用户，签发 tp_anon，继续处理（不返回 401）
   b. 其他端点 → 401 + AUTH_IDENTITY_REQUIRED
4. 两者同时存在且都有效        → 以 tp_session 为准；触发匿名归并（13.9.4）
```

第 3.a 条是产品要求「未注册用户也能直接生成」的落地点：**生成端点永不因为缺少身份而返回 401**，它会为访客现场建号。其余端点要求身份已存在，因为它们都在访问某个已有资源。

**`AUTH_IDENTITY_REQUIRED` 与 `AUTH_SESSION_INVALID` 的区别**：前者是「没带任何身份」，客户端应先访问首页取得匿名令牌；后者是「带了但已失效」，客户端应清除 Cookie 后重试。两者都是 `401`，但客户端处置不同。

**账号级端点的身份要求**

| 端点类别                             | 匿名                                  | 注册         |
| ------------------------------------ | ------------------------------------- | ------------ |
| 生成、查询计划、展示数据、导出       | ✅                                    | ✅           |
| 计划列表（13.9.5）                   | ✅                                    | ✅           |
| 注册、登录                           | ✅（注册即升级）                      | 已登录时拒绝 |
| 改邮箱、改口令、登出全部会话、删账号 | ❌ `403` + `AUTH_ANONYMOUS_FORBIDDEN` | ✅           |

**资源归属（对应验收标准 11）**

`travel_requests`、`travel_plans`、`travel_plan_versions`（经 `plan_id`）、`generation_jobs`、`exports` 全部带 `user_id NOT NULL`。所有查询在 SQL 层强制 `WHERE user_id = :current_user_id`，**不允许查出后在应用层过滤**。他人资源统一返回 `404` + `PLAN_NOT_FOUND`，不返回 `403` —— 避免通过状态码枚举出计划 ID 的存在性。

**归属规则对两类身份完全一致** —— 匿名用户也有 `user_id`（见 3.6.2），因此不存在「匿名数据无主」或「匿名数据互相可见」的情形。匿名用户 A 无法访问匿名用户 B 的计划，与注册用户之间的隔离强度相同。

**唯一的例外是生成时的历史检索**（3.2.4）：它跨用户、跨身份全局进行，但只读 `retrieval_projection` 脱敏投影，且结果只进入 LLM 上下文，绝不出现在任何 API 响应中。

**错误响应体**

所有非 2xx 响应使用同一结构：

```json
{
  "error": {
    "code": "REQ_TRIP_DAYS_OUT_OF_RANGE",
    "message": "行程天数需在 1 到 14 天之间。",
    "retryable": false,
    "field": "trip.dates.end_date",
    "request_id": "request_123",
    "trace_id": "0af7651916cd43dd8448eb211c80319c"
  }
}
```

| 字段                      | 必填 | 说明                                                      |
| ------------------------- | ---- | --------------------------------------------------------- |
| `code`                    | 是   | 见 13.7，稳定字符串，客户端可据此分支                     |
| `message`                 | 是   | 面向用户的中文提示，**不含内部细节、堆栈、SQL、模型原文** |
| `retryable`               | 是   | 客户端是否可原样重试                                      |
| `field`                   | 否   | 请求体字段路径，仅 4xx 校验类错误提供                     |

## 13.8 幂等与并发去重（R-05 新增）

对应验收标准 13「相同任务不会重复生成」。V1.0 定义了 `client_request_id` 却从未说明如何使用。

**幂等键**

```text
idempotency_key = sha256(
  user_id + "|" +
  client_request_id + "|" +
  canonical_json(NormalizedTravelRequest)
)
```

`canonical_json` = 键按字典序递归排序、去除空白、数值规范化。把标准化后的请求体一并纳入哈希，可以防止客户端复用同一 `client_request_id` 提交不同内容却拿到旧结果。

**流程**

```text
POST /api/v1/travel-plans/generate
  → 标准化 + 同步校验（3.1.2），失败直接 4xx，不占用幂等键
  → 计算 idempotency_key
  → SETNX lock:idem:{key}，TTL 300 秒
      获取失败 → 查 travel_requests
          已有已完成任务 → 200 返回既有 plan_id / job_id（幂等命中）
          有进行中任务   → 409 JOB_ALREADY_RUNNING + 既有 job_id
      获取成功 → INSERT travel_requests（idempotency_key 唯一索引兜底）
                → 入队
                → 201 返回新 job_id
```

Redis 锁是快路径，**`travel_requests.idempotency_key` 上的唯一索引是最终真相** —— Redis 丢失时唯一索引冲突仍能保证不重复生成，捕获冲突后转为返回既有任务。

**幂等结果有效期**：7 天。超过后同一幂等键视为新任务，避免用户想要「重新生成」时被永久锁死在旧结果上。用户显式点「重新生成」时客户端换新 `client_request_id`。

**Worker 侧并发保护**

- 每个 `job_id` 在消费时取 `lock:job:{job_id}`（TTL 600 秒，处理中定期续期），防止队列重复投递导致双执行；
- 素材解析对同一缓存键（十九章）取 `lock:asset:{cache_key}`，避免 N 天同主题 Hero 并发重复生成 —— 这一项对成本影响最大；
- `plan_asset_bindings` 的 `UNIQUE(plan_version_id, template_id, slot_id)` 为数据库层最终去重。

**幂等键包含 `user_id`**，因此两个不同用户（含两个匿名用户）提交完全相同的旅行需求会各自生成一份计划，互不干扰 —— 这是归属隔离的必然要求。跨用户的计算复用发生在**素材缓存**（十九章）与**历史检索**（3.2.4）两层，不在幂等层。

## 13.9 身份与账号 API（R-13 新增）

### 13.9.1 获取当前身份

```http
GET /api/v1/auth/session
```

响应：

```json
{
  "user_type": "ANONYMOUS",
  "user_id": "b3c1...",
  "email": null,
  "display_name": null,
  "quota": {
    "daily_remaining": 2,
    "monthly_remaining": 2,
    "reset_at": "2026-08-15T00:00:00+08:00"
  }
}
```

无任何身份 Cookie 时**自动创建匿名用户**并在响应中 `Set-Cookie: tp_anon=...`。前端在应用启动时调用一次即可，之后所有生成请求都带上了身份。

`user_id` 返回给前端仅用于问题反馈，不作为任何鉴权凭据 —— 鉴权只认 Cookie。

### 13.9.2 注册（含匿名升级）

```http
POST /api/v1/auth/register
```

请求：

```json
{
  "email": "user@example.com",
  "password": "<明文，仅 TLS 传输，不落日志>",
  "display_name": "小明"
}
```

**行为分两种，取决于请求是否携带有效 `tp_anon`**：

| 场景               | 行为                                                                                                                                                                                    |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 携带有效 `tp_anon` | **原地升级**：同一事务内 `UPDATE users SET email, password_hash, display_name, user_type='REGISTERED' WHERE id = <anon_id> AND user_type='ANONYMOUS'`；`user_id` 不变，历史计划自动继承 |
| 无 `tp_anon`       | 新建 `users` 行，`user_type='REGISTERED'`                                                                                                                                               |

两种场景都：清除 `tp_anon`、签发 `tp_session`、返回 13.9.1 结构。

响应 `201`。邮箱已被占用返回 `409` + `AUTH_EMAIL_ALREADY_REGISTERED`。

**口令要求**：≥ 10 字符，且不在弱口令字典中，否则 `400` + `AUTH_PASSWORD_TOO_WEAK`。哈希用 Argon2id（`m=19456, t=2, p=1`，OWASP 2024 建议基线）。

**并发保护**：升级语句带 `AND user_type='ANONYMOUS'` 条件，受影响行数为 0 时说明该匿名行已被并发升级，返回 `409` + `AUTH_ANONYMOUS_ALREADY_UPGRADED`，客户端重试即走登录流程。

### 13.9.3 登录 / 登出

```http
POST /api/v1/auth/login      # { email, password } → 签发 tp_session
POST /api/v1/auth/logout     # 吊销当前 tp_session
```

登录失败统一返回 `401` + `AUTH_CREDENTIALS_INVALID`，**不区分「邮箱不存在」与「口令错误」**，避免邮箱枚举。失败按邮箱与 IP 双维度限速（见 21.4）。

登出只吊销当前会话，**不重新签发 `tp_anon`** —— 登出后用户处于无身份状态，下次生成时会现场建新匿名用户。

### 13.9.4 匿名归并

无独立端点，作为 `POST /api/v1/auth/login` 的**副作用**执行：请求同时携带有效 `tp_anon` 与正确口令时，把匿名 `user_id` 名下的业务行改挂到登录用户。

```text
同一事务内，按固定顺序改挂：
  UPDATE travel_requests  SET user_id = :target WHERE user_id = :anon
  UPDATE travel_plans     SET user_id = :target WHERE user_id = :anon
  UPDATE generation_jobs  SET user_id = :target WHERE user_id = :anon
  UPDATE exports          SET user_id = :target WHERE user_id = :anon
  UPDATE users SET status = 'MERGED', merged_into = :target WHERE id = :anon
然后清除 tp_anon
```

| 约束       | 说明                                                                                                                                                                                                                             |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 幂等       | 全部为 `WHERE user_id = :anon` 的条件更新，重复执行无副作用                                                                                                                                                                      |
| 原子       | 单事务；失败则整体回滚，`tp_anon` 不清除，下次登录重试                                                                                                                                                                           |
| 不删匿名行 | 标记 `status='MERGED'` + `merged_into`，保留审计链；`MERGED` 行不可再作为身份使用                                                                                                                                                |
| 幂等键冲突 | 匿名期与注册期可能提交过完全相同的需求，导致改挂后 `travel_requests.idempotency_key` 冲突（键含 `user_id`，改挂后重算会撞）。**处理方式：不重算 `idempotency_key`**，它是历史事实的一部分，保持原值；仅新请求用新 `user_id` 计算 |
| 规模上限   | 匿名用户受配额限制（21.4），改挂行数量级为个位数，无需分批                                                                                                                                                                       |

**`idempotency_key` 不重算**是这里最容易出错的点：如果归并时重算键，会出现冲突且语义错误（幂等键描述的是「当时那次提交」，不是「现在的归属」）。

## users（R-13 已重写为双模式）

```sql
CREATE EXTENSION IF NOT EXISTS "citext";

CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    user_type VARCHAR(20) NOT NULL,

    -- 注册用户专属，匿名用户为 NULL
    email CITEXT,
    password_hash TEXT,
    display_name VARCHAR(100),

    -- 匿名用户专属：令牌哈希，不存原文（见 3.6.5）
    anon_token_hash CHAR(64),
    anon_expires_at TIMESTAMPTZ,
    created_ip INET,

    locale VARCHAR(20) NOT NULL DEFAULT 'zh-CN',
    timezone VARCHAR(50) NOT NULL DEFAULT 'Asia/Shanghai',

    status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE',
    merged_into UUID REFERENCES users(id),

    daily_plan_quota INTEGER NOT NULL,
    monthly_plan_quota INTEGER NOT NULL,

    upgraded_at TIMESTAMPTZ,
    last_seen_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    CONSTRAINT users_type_check
        CHECK (user_type IN ('ANONYMOUS', 'REGISTERED')),
    CONSTRAINT users_status_check
        CHECK (status IN ('ACTIVE', 'SUSPENDED', 'MERGED', 'DELETED')),

    -- 注册用户必须有邮箱与口令
    CONSTRAINT users_registered_shape CHECK (
        user_type <> 'REGISTERED'
        OR (email IS NOT NULL AND password_hash IS NOT NULL)
    ),
    -- 匿名用户不得有邮箱或口令，必须有令牌哈希与过期时间
    CONSTRAINT users_anonymous_shape CHECK (
        user_type <> 'ANONYMOUS'
        OR (email IS NULL AND password_hash IS NULL
            AND anon_token_hash IS NOT NULL AND anon_expires_at IS NOT NULL)
    ),
    -- MERGED 必须指向归并目标，其余状态不得指向
    CONSTRAINT users_merged_shape CHECK (
        (status = 'MERGED' AND merged_into IS NOT NULL)
        OR (status <> 'MERGED' AND merged_into IS NULL)
    ),
    CONSTRAINT users_merged_not_self CHECK (merged_into IS DISTINCT FROM id)
);

-- 邮箱唯一，但只约束注册用户（匿名行 email 为 NULL）
CREATE UNIQUE INDEX users_email_uk
    ON users (email) WHERE email IS NOT NULL;

-- 匿名令牌唯一查找
CREATE UNIQUE INDEX users_anon_token_uk
    ON users (anon_token_hash) WHERE anon_token_hash IS NOT NULL;

-- 保留期清理扫描（15.1）
CREATE INDEX users_anon_expiry_idx
    ON users (anon_expires_at)
    WHERE user_type = 'ANONYMOUS' AND status = 'ACTIVE';
```

**设计要点**

| 要点                     | 说明                                                                                                                |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| 三个 shape 约束          | 把 3.6.1 的身份形态规则下沉到数据库，「匿名行带口令」或「注册行无邮箱」这类脏数据在写入时就被拒绝，不依赖应用层自觉 |
| `email` 部分唯一索引     | 不能用列级 `UNIQUE` —— 大量匿名行的 `email` 为 `NULL`，虽然 PostgreSQL 允许多个 `NULL`，但部分索引更小更明确        |
| `anon_token_hash` 存哈希 | 数据库泄漏时无法据此冒充匿名用户（对应 3.6.5）                                                                      |
| `created_ip`             | 仅用于 21.4 的匿名创建限速与滥用排查，保留期与匿名行一致，到期随行删除                                              |
| `merged_into` 自引用     | 支撑 13.9.4 的审计链；`users_merged_not_self` 防止自环                                                              |
| 配额落列而非硬编码       | `daily_plan_quota` / `monthly_plan_quota` 按 `user_type` 在插入时取默认值（见 21.4），可对个别用户单独调整          |
| `last_seen_at`           | 匿名用户活跃则续期 `anon_expires_at`，避免正在使用中的匿名数据被清理                                                |
| 会话不落表               | `tp_session` 与 `tp_anon` 的活跃会话存 Redis；`anon_token_hash` 落表是因为它同时是**身份标识**而非纯会话            |

## 15.1 数据保留与清理（R-13 新增）

| 数据                                                        | 匿名用户                                         | 注册用户                                 |
| ----------------------------------------------------------- | ------------------------------------------------ | ---------------------------------------- |
| `users` 行                                                  | `anon_expires_at` 到期后 30 天宽限，然后物理删除 | 长期保留；`DELETED` 状态后 30 天物理删除 |
| `travel_requests` / `travel_plans` / `travel_plan_versions` | 随 `users` 行级联删除                            | 长期保留                                 |
| `generation_jobs`                                           | 90 天后删除（无论身份）                          | 90 天后删除                              |
| `exports` 行与对象存储文件                                  | 90 天生命周期规则（19.3）                        | 同                                       |
| `plan_presentations` / `plan_asset_bindings`                | 随 `travel_plan_versions` 级联删除               | 长期保留                                 |
| **`assets` / `asset_variants`**                             | **不删除**                                       | **不删除**                               |
| **`retrieval_projection`**                                  | **不随匿名行删除**，见下                         | 保留                                     |

**清理任务**：每日一次的定时 Worker，按 `users_anon_expiry_idx` 扫描到期匿名行，分批（每批 500）级联删除。删除前发出 `travel_anon_purge_total` 指标。

**关键决定：匿名用户的行程知识不随身份删除**

匿名行删除时，`travel_plan_versions` 会被级联删除，这会让 3.2.4 的全局历史检索**持续损失知识**（匿名请求占比可能很高）。因此：

```text
清理匿名 users 行之前：
  把其 travel_plan_versions 的 retrieval_projection + plan_embedding
  转存到 plan_knowledge 表（无 user_id，无任何标识符）
  然后再级联删除原行
```

```sql
CREATE TABLE plan_knowledge (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    destination_place_id VARCHAR(100) NOT NULL,
    total_days INTEGER NOT NULL,
    projection JSONB NOT NULL,
    embedding VECTOR(1536) NOT NULL,
    source_status VARCHAR(30) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX plan_knowledge_destination_idx
    ON plan_knowledge (destination_place_id, total_days);

CREATE INDEX plan_knowledge_embedding_idx
    ON plan_knowledge USING hnsw (embedding vector_cosine_ops);
```

`plan_knowledge` **不含 `user_id`、不含日期、不含金额、不含人员构成**（`projection` 就是 3.2.4 的脱敏投影），因此它不是个人数据，保留它不违反匿名数据的清理承诺 —— 被清理掉的是「谁在什么时候要去哪」，保留下来的是「杭州运河主题 5 天可以这样安排」。

3.2.4 的历史检索**同时查 `travel_plan_versions.retrieval_projection` 与 `plan_knowledge`**，两者合并后取 Top 5。

## 15.2 检索投影的隔离约束（R-13 新增）

3.2.4 要求全局历史检索只能读脱敏投影。为了让这一点由**数据布局**保证而不是靠调用方自觉：

| 约束                                                | 实现                                                                                                                                                                                                                 |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `plan_embedding` 必须由 `retrieval_projection` 计算 | 若由 `plan_json` 计算，金额、日期、人员构成会以向量形式残留，语义检索可反推                                                                                                                                          |
| 检索查询禁止 `SELECT plan_json`                     | 数据访问层为检索路径提供独立的仓储方法，其返回类型（TypeScript）中根本不含 `plan_json` 字段，误用是编译错误                                                                                                          |
| 数据库层加固                                        | 创建只读角色 `travel_retrieval_ro`，仅授予 `travel_plan_versions` 的 `(id, plan_id, status, total_days, retrieval_projection, plan_embedding)` 列级 `SELECT` 与 `plan_knowledge` 全表 `SELECT`；检索路径用该角色连接 |
| 写入时构造                                          | `retrieval_projection` 在 `SAVING_PLAN` 阶段由纯函数从 `plan_json` 裁剪生成，该函数有针对 3.2.4 表格逐行的单测                                                                                                       |

```sql
CREATE ROLE travel_retrieval_ro NOLOGIN;
GRANT SELECT (id, plan_id, status, retrieval_projection, plan_embedding)
    ON travel_plan_versions TO travel_retrieval_ro;
GRANT SELECT ON plan_knowledge TO travel_retrieval_ro;
```

列级 `GRANT` 是最后一道防线：即使应用代码写错，数据库也会拒绝返回 `plan_json`。

## 15.3 级联删除（R-13 新增）

15.1 的保留策略依赖级联。以下外键必须显式声明 `ON DELETE CASCADE`：

```sql
travel_requests.user_id            → users(id)                  ON DELETE CASCADE
travel_plans.user_id               → users(id)                  ON DELETE CASCADE
travel_plans.request_id            → travel_requests(id)         ON DELETE CASCADE
travel_plan_versions.plan_id       → travel_plans(id)            ON DELETE CASCADE
plan_presentations.plan_version_id → travel_plan_versions(id)    ON DELETE CASCADE
plan_asset_bindings.plan_version_id→ travel_plan_versions(id)    ON DELETE CASCADE
generation_jobs.user_id            → users(id)                  ON DELETE CASCADE
exports.user_id                    → users(id)                  ON DELETE CASCADE
exports.plan_version_id            → travel_plan_versions(id)    ON DELETE CASCADE
```

**不级联的两处**

| 外键                                        | 行为                 | 理由                                                                               |
| ------------------------------------------- | -------------------- | ---------------------------------------------------------------------------------- |
| `plan_asset_bindings.asset_id → assets(id)` | `ON DELETE RESTRICT` | 素材是共享资源，不能因为某个计划被删就删素材；反之素材被人工下架时不能悄悄删掉绑定 |
| `users.merged_into → users(id)`             | `ON DELETE SET NULL` | 归并目标被删时，`MERGED` 行降级为孤立审计记录而不是被连带删除                      |

`plan_asset_bindings` 因此需要**先删绑定再删素材**，或素材只标记下架不物理删除（后者是 V1 的做法，见 19.3）。

```sql
    ADD CONSTRAINT plan_presentations_day_number_check CHECK (
        (page_type = 'DAILY_POSTER' AND day_number IS NOT NULL)
        OR (page_type = 'FULL_PLAN' AND day_number IS NULL)
    ),
    ADD CONSTRAINT plan_presentations_validation_check
        CHECK (validation_status IN ('VALID', 'DEGRADED', 'INVALID'));

CREATE UNIQUE INDEX plan_presentations_uk
    ON plan_presentations (plan_version_id, template_id, page_type, COALESCE(day_number, -1));
```

`COALESCE(day_number, -1)` 让 `FULL_PLAN`（`day_number` 为 `NULL`）也能参与唯一约束 —— PostgreSQL 中 `NULL` 不参与唯一性比较，不处理会导致完整计划页可重复插入。

`validation_status` 语义：`VALID` = 全槽位解析成功；`DEGRADED` = 存在 `FALLBACK`/`SKIPPED` 槽位但可渲染；`INVALID` = 必需槽位缺失，不可渲染。

# 十六、任务状态机

```text
QUEUED
NORMALIZING
VALIDATING_REQUEST
RETRIEVING_REFERENCES
GENERATING_PLAN
VALIDATING_PLAN
REPAIRING_PLAN
SAVING_PLAN
BUILDING_PRESENTATION
RESOLVING_ASSETS
GENERATING_ASSETS
RENDERING_HTML
EXPORTING_PNG
EXPORTING_PDF
COMPLETED
FAILED
```

素材相关错误不一定导致整个计划失败。

例如：

```text
Hero 生成失败
→ 使用默认主题背景
→ 任务继续

景点图缺失
→ 使用默认景点卡片
→ 任务继续

路线 SVG 失败
→ 使用文字路线列表
→ 任务继续
```

只有以下错误应阻断任务：

- 完整旅行计划不符合 Schema；
- 硬约束无法满足；
- 页面核心结构无法生成；
- HTML 模板渲染失败；
- 数据库写入失败。

## 16.1 合法状态转移（R-05 新增）

V1.0 只列了 15 个状态名，没有转移边，也没有 `progress` 的算法（13.2 示例里 `progress: 76` 无从解释）。

```text
QUEUED
  → NORMALIZING
  → VALIDATING_REQUEST
  → RETRIEVING_REFERENCES
  → GENERATING_PLAN
  → VALIDATING_PLAN
      ├─ 无违规 ──────────────→ SAVING_PLAN
      └─ 有违规 → REPAIRING_PLAN
                    ├─ 修复成功 → VALIDATING_PLAN（回边，受 3.2.2 迭代上限约束）
                    └─ 迭代耗尽 → FAILED
  → SAVING_PLAN
  → BUILDING_PRESENTATION
  → RESOLVING_ASSETS
      └─ 需 AI 兜底 → GENERATING_ASSETS → RESOLVING_ASSETS（回边，最多 1 次）
  → RENDERING_HTML
  → EXPORTING_PNG      （generate_png 为 false 时跳过）
  → EXPORTING_PDF      （generate_pdf 为 false 时跳过）
  → COMPLETED

任意状态 → FAILED（仅阻断类错误）
任意非终态 → CANCELLED（用户主动取消）
```

**规则**

- 只有 `VALIDATING_PLAN ← REPAIRING_PLAN` 和 `RESOLVING_ASSETS ← GENERATING_ASSETS` 两条回边，其余严格前向，防止状态机成环；
- 终态为 `COMPLETED`、`FAILED`、`CANCELLED`，终态不可再转移；
- `EXPORTING_PNG` / `EXPORTING_PDF` 失败**不阻断** —— 按十八章重试一次后跳到下一状态，并把错误码写入 `warnings`，最终仍为 `COMPLETED`。这是「HTML、PNG、PDF 至少两种可用」（验收标准 10）的落地方式；
- 状态写入与 `progress` 更新在同一事务，且必须单调不减；
- `CANCELLED` 新增于 V1.1 —— V1.0 状态机没有取消态，但 20～60 秒的生成过程用户必然会想中断。

## 16.2 progress 与用户提示文案（R-05 新增）

# 十七、渲染流程

## 17.1 React 路由

```text
/render/plans/{plan_version_id}/days/{day_number}
```

该路由只供内部渲染服务访问。

完整计划页的内部渲染路由：

```text
/render/plans/{plan_version_id}/full
```

**R-05 补充：内部路由的访问控制**

V1.0 只写了「只供内部渲染服务访问」，没有任何机制。V1 采用**双重保护**：

1. **网络层**：`/render/**` 只监听内部网络，Ingress 显式拒绝该路径前缀（Helm 模板中作为断言，CI 校验）；
2. **签名令牌**：渲染 Worker 请求时携带短时效令牌

```http
GET /render/plans/{plan_version_id}/days/3
X-Render-Token: <hmac-sha256>
```

```text
payload = plan_version_id + "|" + page_key + "|" + expires_at
token   = base64url(payload) + "." + base64url(hmac_sha256(RENDER_SIGNING_KEY, payload))
有效期 120 秒，一次性（Redis 记录已用 jti）
```

只靠网络隔离不够 —— 该路由返回的是用户私有计划内容，任何内网服务被攻破即可遍历 `plan_version_id`。令牌校验失败返回 `404`（不是 `403`），避免探测版本 ID 存在性。渲染页面**不带用户会话**，因此不存在会话泄漏面。

## 17.3 页面检查（R-06 已修正）

**V1.0 的检测代码有实际缺陷，不能直接实现。** 原写法：

```javascript
// ❌ V1.0：对全部元素判断 scrollWidth > clientWidth
const overflowElements = [...document.querySelectorAll('*')].filter(
  (element) =>
    element.scrollWidth > element.clientWidth || element.scrollHeight > element.clientHeight,
);
```

三个问题：

1. **inline 元素必然误报** —— `<span>`、`<a>`、`<em>` 等非替换 inline 元素的 `clientWidth` 恒为 `0`，只要有内容就满足 `scrollWidth > 0`，一张信息图能报出成百上千个「溢出」；
2. **正常滚动容器必然误报** —— 任何 `overflow: auto/scroll` 的容器有内容溢出是设计意图，不是缺陷；
3. **正文说「核心元素溢出」，代码选的是 `*`** —— 没有任何「核心元素」判定，`overflowCount` 这个数字无法用于决策。

**V1.1 修正方案**：只检查显式标注的核心元素，用 `data-overflow-guard` 标记，并区分「裁切溢出」与「合法滚动」。

```javascript
const result = await page.evaluate(() => {
  const TOLERANCE = 1; // 抵消亚像素与四舍五入

  const guarded = [...document.querySelectorAll('[data-overflow-guard]')];

  const violations = guarded
    .map((el) => {
      const style = getComputedStyle(el);
      const scrollable =
        style.overflowX === 'auto' ||
        style.overflowX === 'scroll' ||
        style.overflowY === 'auto' ||
        style.overflowY === 'scroll';

      // 合法滚动容器不算溢出；导出场景下它们由模板保证不出现
      if (scrollable) return null;

      const overflowX = el.scrollWidth - el.clientWidth > TOLERANCE;
      const overflowY = el.scrollHeight - el.clientHeight > TOLERANCE;

      // 文本行数溢出：clamp 生效后 scrollHeight 不变，需单独判定
      const lineClamp = parseInt(style.webkitLineClamp, 10);
      const clamped = Number.isFinite(lineClamp) && el.scrollHeight - el.clientHeight > TOLERANCE;

      if (!overflowX && !overflowY && !clamped) return null;

      return {
        slot: el.dataset.overflowGuard,
        priority: Number(el.dataset.overflowPriority ?? '0'),
        overflowX,
        overflowY,
        clamped,
        overflowPx: Math.max(el.scrollWidth - el.clientWidth, el.scrollHeight - el.clientHeight),
      };
    })
    .filter(Boolean);

  const root = document.documentElement;
  return {
    violations,
    guardedCount: guarded.length,
    documentWidth: root.scrollWidth,
    documentHeight: root.scrollHeight,
    // 画布自身超界：信息图是定宽长图，宽度溢出一定是缺陷
    canvasOverflowX: root.scrollWidth - root.clientWidth > TOLERANCE,
  };
});
```

**核心元素标注约定**（模板侧责任）

| `data-overflow-guard` | `data-overflow-priority` | 溢出处理顺序           |
| --------------------- | ------------------------ | ---------------------- |
| `header.title`        | 100                      | 最高优先，必须完整显示 |
| `header.subtitle`     | 90                       | —                      |
| `schedule.item`       | 80                       | —                      |
| `budget.total`        | 80                       | 金额不可截断           |
| `food.card`           | 60                       | —                      |
| `photo_spot.card`     | 50                       | —                      |
| `booking_tip.item`    | 30                       | 最先被隐藏             |
| `transport_tip.item`  | 30                       | —                      |

`priority` 数值决定降级顺序：**从低优先级开始处理**。

**重渲染循环（V1.0 缺少上限）**

```text
第 1 轮：原始 ViewModel 渲染
  ↓ 有 violations
第 2 轮：对溢出元素启用 *_compact 文案（12.3）
  ↓ 仍有 violations
第 3 轮：按 priority 升序隐藏低优先级条目，直到消除溢出或触及 priority >= 80
  ↓ 仍有 violations
第 4 轮：切换宽松版式（travel_infographic_v1 的 relaxed 变体，行高与卡片高度放宽）
  ↓ 仍有 violations
终止：输出当前产物，
      记 RENDER_OVERFLOW_UNRESOLVED，
      plan_presentations.validation_status = 'DEGRADED'
```

**重渲染最多 4 轮（含首轮）**，单次渲染 ≤ 5 秒，总渲染预算 ≤ 20 秒。不设上限会让病态内容把 Worker 卡死。

`canvasOverflowX === true` 视为**阻断级**（`RENDER_TEMPLATE_FAILED`）—— 定宽长图的横向溢出必定是模板缺陷，不是内容问题，重渲染无用。

## 17.4 PNG / PDF 导出规格（R-06 新增）

V1.0 只写了「生成 PNG」「生成 PDF」，没有任何规格，两个实现者会产出完全不同尺寸的文件。

**Viewport 与截图**

| 参数                | 值                    | 说明                                     |
| ------------------- | --------------------- | ---------------------------------------- |
| `viewport.width`    | 1200                  | 信息图定宽                               |
| `viewport.height`   | 1600                  | 初始高度，实际按内容延展                 |
| `deviceScaleFactor` | 2                     | 2 倍图，输出 2400px 宽，满足打印与高分屏 |
| `fullPage`          | `true`                | 长图                                     |
| `type`              | `png`                 | 不用 JPEG，信息图有大面积纯色与文字      |
| `omitBackground`    | `false`               | 保留白底，避免 PDF 中透明区域变黑        |
| `animations`        | `disabled`            | 避免动画中间帧被截取                     |
| PNG 后处理          | `oxipng -o2` 无损压缩 | 典型体积下降 20～35%                     |

**PDF**

| 参数                | 值                                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------------------ |
| 页面尺寸            | A4 纵向（210 × 297 mm）                                                                                |
| `printBackground`   | `true`（否则背景色与渐变全部丢失）                                                                     |
| 页边距              | 上下 12mm，左右 10mm                                                                                   |
| `preferCSSPageSize` | `true`，模板用 `@page` 控制                                                                            |
| 分页控制            | 卡片级 `break-inside: avoid`，每日一页 `break-after: page`                                             |
| `scale`             | 1.0                                                                                                    |
| `ALL_DAYS` 合并     | 单次 Playwright 会话内依次导航 N 天并生成 N 个单页 PDF，用 `pdf-lib` 合并为一份，**不启动 N 个浏览器** |

**媒体类型**：导出前显式 `page.emulateMedia({ media: 'screen' })` —— 默认 `print` 媒体会触发不同的 CSS 规则，导致 PDF 与 HTML 页面外观不一致。分页由 `@page` 与 `break-*` 属性控制，不依赖 `print` 媒体查询。

## 17.5 中文字体方案（R-09 新增）

**V1.0 完全没有提到字体，这在 Playwright 容器中是必然故障** —— 官方 Playwright 镜像不含中文字体，中文全部渲染为豆腐块（□□□），PNG/PDF 直接不可用。而 17.2 的 `data-render-status="ready"` 只等字体**加载**完成，不检测字体是否**存在**，故障会静默通过。

**字体选型**

| 用途          | 字体                    | 授权                        |
| ------------- | ----------------------- | --------------------------- |
| 正文 / 无衬线 | Noto Sans SC            | SIL OFL 1.1，可商用可再分发 |
| 标题 / 衬线   | Noto Serif SC           | SIL OFL 1.1                 |
| 数字 / 金额   | Inter（`tabular-nums`） | SIL OFL 1.1                 |

选 Noto 系列的原因：OFL 许可允许自托管与嵌入 PDF，覆盖 GB 18030 全字符集，且有官方可变字重版本。**不使用**思源黑体以外的商业中文字体，也不引用任何第三方字体 CDN（外部依赖会让离线渲染失败，且违反二十章「不直接引用第三方地址」的同类理由）。

**交付方式**

1. 字体文件随仓库提供（`packages/fonts/`），子集化后 woff2 与 ttf 各一份 —— woff2 给浏览器页面，ttf 给 PDF 嵌入；
2. 子集范围：GB 2312 常用 6763 字 + 标点 + 拉丁 + 数字，字重 400/500/700 三档。全量 Noto Sans SC 单字重约 10MB，子集后约 1.8MB；
3. **字体安装进渲染镜像的系统字体目录**（`/usr/share/fonts/truetype/noto-sc/`）并 `fc-cache -f`，不只靠 `@font-face` —— 系统级安装可以让未被 CSS 覆盖的元素（如 `<input>`、SVG `<text>`、emoji 回退）也拿到中文字形；
4. CSS 侧同时用 `@font-face` 声明本地路径，`font-display: block`（不是 `swap`）—— 导出场景宁可等待也不能截到回退字体。

**字体就绪断言（补强 17.2）**

```javascript
await page.evaluate(async () => {
  await document.fonts.ready;

  // 仅 fonts.ready 不足以证明中文字形存在
  const probe = document.createElement('span');
  probe.style.cssText = 'position:absolute;visibility:hidden;font-size:100px;white-space:nowrap';
  probe.textContent = '运河博物馆';
  document.body.appendChild(probe);

  const withFont = probe.getBoundingClientRect().width;
  probe.style.fontFamily = 'monospace';
  const fallback = probe.getBoundingClientRect().width;
  probe.remove();

  // 目标字体与回退字体宽度一致 → 极可能未命中中文字体
  if (Math.abs(withFont - fallback) < 1) {
    throw new Error('CJK_FONT_UNAVAILABLE');
  }
});
```

该断言失败时任务 `FAILED` + `RENDER_TEMPLATE_FAILED`，**不允许降级输出** —— 豆腐块页面对用户毫无价值，静默交付比失败更糟。CI 中对渲染镜像跑一次基线截图，用图像比对确认中文正常渲染。

# 十九、缓存策略

## Hero 图缓存键

```text
destination
+ theme
+ visual_style
+ aspect_ratio
```

例如：

```text
hangzhou
+ canal_culture
+ chinese_editorial
+ 16x6
```

同类计划可以复用相同 Hero，不必每次实时生成。

## 景点图缓存键

```text
place_id + image_role + aspect_ratio
```

## 美食图缓存键

```text
dish_name + city + visual_style
```

## 地图缓存键

```text
route_node_hash + map_style
```

这样可以显著降低延迟和成本。

## 19.1 键归一化规则（R-10 新增）

V1.0 给了「`hangzhou` + `canal_culture` + `chinese_editorial` + `16x6`」这样的示例，但没说「杭州」怎么变成 `hangzhou`。归一化规则不明确会导致同一目的地产生多个键，缓存命中率趋近于 0。

```text
normalize(s) =
  1. 去首尾空白
  2. 全角转半角
  3. 繁体转简体
  4. 去除括号及其内容：「拱宸桥（运河段）」→「拱宸桥」
  5. 小写化（拉丁字符）
  6. 非字母数字字符替换为 "_"，连续 "_" 合并为一个，去首尾 "_"
```

| 维度              | 归一化来源                                                                 | 示例                                               |
| ----------------- | -------------------------------------------------------------------------- | -------------------------------------------------- |
| `destination`     | **优先 `place_id`**，缺失时才用 `normalize(destination_name)`              | `cn-hangzhou`；回退为 `hangzhou`                   |
| `theme`           | `normalize(theme)` 后取**主题语义桶**，不用原文                            | 「运河人文·古今交融」→ `canal_culture`             |
| `visual_style`    | 枚举值小写                                                                 | `chinese_editorial`                                |
| `aspect_ratio`    | `16:6` → `16x6`                                                            | —                                                  |
| `place_id`        | 原样，已是稳定标识                                                         | `hz-gongchen-bridge`                               |
| `dish_name`       | `normalize(name)`                                                          | 「葱包桧与小馄饨」→ `cong_bao_gui_yu_xiao_hun_tun` |
| `route_node_hash` | `sha256(nodes.map(n => `${n.name}:${round(lat,4)}:${round(lng,4)}`).join(" | ")).slice(0, 16)`                                  | 坐标保留 4 位小数（约 11 米精度），避免浮点抖动导致每次不同 |

**主题语义桶**是关键设计：Hero 图的 `theme` 是 LLM 自由生成的中文短语，直接归一化会得到几乎唯一的键，缓存永不命中。V1 预定义 12 个语义桶（`canal_culture`、`lake_scenery`、`old_town`、`museum_art`、`food_street`、`mountain_nature`、`temple_heritage`、`modern_city`、`night_view`、`garden_classic`、`coastal`、`family_park`），由主题文本关键词匹配 + 嵌入相似度归桶，无法归类时落 `general`。

**优先用 `place_id` 而非名称**：名称会因 LLM 措辞变化（「拱宸桥」/「拱宸桥历史街区」）产生不同键，`place_id` 稳定。

## 19.2 缓存键完整格式（R-10 新增）

```text
hero:      hero:v1:{destination}:{theme_bucket}:{visual_style}:{aspect_ratio}
place:     place:v1:{place_id}:{image_role}:{aspect_ratio}
food:      food:v1:{dish_name}:{city}:{visual_style}
map:       map:v1:{route_node_hash}:{map_style}
```

`v1` 是**键版本号**。任何影响产物外观的变更（AI 提示词模板改版、SVG 渲染器升级、比例定义变化）都必须递增它，而不是清空缓存 —— 递增可以保留旧产物用于回滚与对比。

## 19.3 TTL 与失效条件（R-10 新增）

V1.0 没有任何 TTL 或失效定义，缓存会无限增长且永不更新。

| 类型                     | 存储                                         | TTL               | 失效条件                                            |
| ------------------------ | -------------------------------------------- | ----------------- | --------------------------------------------------- |
| Hero 图（AI 生成）       | `assets.cache_key` 永久 + Redis 键映射 30 天 | 素材本体不过期    | 键版本递增；人工下架（`assets.status`）             |
| 景点图                   | 同上                                         | 素材本体不过期    | 授权到期（`license` 到期日）；人工下架              |
| 美食图                   | 同上                                         | 素材本体不过期    | 同景点图                                            |
| 路线 SVG                 | 对象存储 + `assets.cache_key`                | 90 天             | `route_node_hash` 变化自然失效（内容寻址）          |
| ViewModel                | `plan_presentations` 表                      | 永久              | 新计划版本产生时不删旧行，按 `plan_version_id` 隔离 |
| 导出文件                 | 对象存储                                     | 90 天生命周期规则 | 预签名 URL 7 天，过期重签不重渲染（13.6）           |
| 检索结果（评分后 Top N） | Redis                                        | 300 秒            | 只缓存**查询到候选 ID 列表**的映射，不缓存分数      |
| 嵌入向量                 | `assets.embedding` 列                        | 永久              | 嵌入模型变更需全量重算（见 10.1）                   |

**素材本体永不按时间过期**，只按业务事件失效。原因：AI Hero 生成成本最高，而「杭州 + 运河主题」的合适插画不会因为时间流逝而变得不合适。定期过期只会周期性地重新烧钱。

**Redis 侧只存 `cache_key → asset_id` 的轻量映射（30 天）**，作为跳过数据库查询的快路径；`assets.cache_key` 唯一索引是最终真相。Redis 冷启动只损失一次数据库查询，不会导致重复生成。

## 19.4 缓存命中后是否重算评分（R-10 新增）

**不重算。** `cache_key` 已经把决定匹配质量的全部维度（实体/目的地/角色/比例/风格）编码进去，命中即意味着这些维度完全一致，重算 `final_score` 只会得到同样的分数并浪费一次嵌入调用。

命中时直接产出：

```json
{
  "status": "RESOLVED",
  "resolution": { "strategy": "CACHE_HIT", "score": 1.0, "fallback_level": 0 }
}
```

`score: 1.0` 表示「精确键命中」，与 10.1 的相似度评分不是同一量纲，用 `strategy` 字段区分二者。

## 19.5 跨天与跨计划复用（R-01 关键优化）

这是让 14 天行程在 SLA 内完成的核心手段（见二十一章）。

| 复用范围       | 效果                                                                      |
| -------------- | ------------------------------------------------------------------------- |
| 同一计划内跨天 | 14 天若归入 3 个主题桶，Hero 只需生成 3 张而非 14 张                      |
| 跨用户跨计划   | 「杭州 + 运河主题 + 16:6」全平台只生成一次，后续所有用户命中缓存          |
| 同槽位并发     | 13.8 的 `lock:asset:{cache_key}` 保证同键并发只有一个生成者，其余等待结果 |

**预热策略**：对 Top 50 热门目的地 × 12 个主题桶 = 600 张 Hero 图**离线预生成**，上线前灌入素材库。这样绝大多数请求的 Hero 走缓存命中（毫秒级）而非实时 AI 生成（10～40 秒），是二十一章 SLA 能够成立的前提。

# 二十、安全和合规

## 图片来源必须记录

每个素材至少记录：

```text
source_type
license_type
original_url
attribution_text
generated_model
generated_at
```

**R-11 补充：`assets.generation_metadata` 结构**

十五章要求 `source_type = 'AI_GENERATED'` 时该列非空（验收标准 12 的判定依据）。结构固定为：

```json
{
  "generated_model": "image-model-name",
  "model_version": "2026-05-01",
  "generated_at": "2026-08-14T10:23:11+08:00",
  "prompt_template_version": "hero_v3",
  "visual_brief": { "task": "GENERATE_TRAVEL_HERO", "destination": "杭州" },
  "negative_requirements": ["no text", "no logo"],
  "seed": 918273,
  "cost_units": 1,
  "cache_key": "hero:v1:cn-hangzhou:canal_culture:chinese_editorial:16x6"
}
```

`visual_brief` 存 11.1 的完整 Brief（去除任何用户私有内容 —— 它只含目的地与主题，不含用户 ID、日期或预算）。`seed` 与 `prompt_template_version` 一起保证产物可复现，这是排查「为什么这张图不对」的唯一依据。`cost_units` 支撑 21.4 的成本核算。

## 用户侧展示

AI 生成的氛围图不必在页面显著标注，但后台必须可追踪。

AI 生成的具体景点代表图，建议在详细信息中显示：

```text
示意图
```

## 外部图片

外部图片应下载、审核并转存到自己的对象存储，不建议页面直接引用第三方地址。

原因包括：

- 防止图片失效；
- 防止防盗链；
- 确保 PDF 可导出；
- 控制图片格式和尺寸；
- 保存版权信息。

## 用户数据边界（R-13 新增）

双模式身份与全局历史检索共存，需要明确「什么数据可以跨用户流动」。

**三层数据分级**

| 级别            | 内容                                                                                                                                  | 跨用户可见性                                                  |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| L1 个人数据     | `raw_request`、`normalized_request`、`plan_json`、`constraint_report`、日期、金额、人员构成、`custom_requirements.raw_text`、邮箱、IP | **绝不跨用户**，仅本人可读（13.0）                            |
| L2 脱敏行程知识 | `retrieval_projection`、`plan_knowledge.projection`、`plan_embedding`                                                                 | 仅供生成时的 LLM 上下文（3.2.4），**不出现在任何 API 响应中** |
| L3 公共资源     | `assets`、`asset_variants`、目的地资料、图标、字体                                                                                    | 全局共享                                                      |

**L2 的关键约束**：脱敏投影可以进入 LLM 上下文，但**不能通过任何端点返回给用户**。否则用户可以借助生成接口把别人的行程内容读出来，等于绕过 L1 隔离。实现上，`retrieval_projection` 不出现在 13.3 / 13.4 / 13.9.5 任何响应结构中，且检索路径使用列级受限的只读角色（15.2）。

**匿名用户的额外声明义务**

匿名用户没有账号可以行使删除权，因此必须在首次生成前的界面上明确告知：

```text
未登录状态下生成的计划保存 30 天，仅当前浏览器可访问。
注册账号可长期保存并跨设备访问。
```

**匿名数据清理后的知识保留**（15.1）需要在隐私政策中显式说明：清理删除的是「谁、何时、去哪、花多少」，保留的是不含任何标识符与个人参数的行程结构知识。这一区分必须写进用户协议，不能只在代码里做。

**日志与遥测的身份字段**

| 字段                          | 可记录         | 说明                       |
| ----------------------------- | -------------- | -------------------------- |
| `user_id`                     | ✅             | UUID，非个人可识别信息     |
| `user_type`                   | ✅             | 用于分身份统计             |
| `email`                       | ❌             | 任何日志与指标标签中禁止   |
| `tp_session` / `tp_anon` 原文 | ❌             | 凭据禁止落日志             |
| `created_ip`                  | 仅安全审计日志 | 与业务日志分流，保留 90 天 |

指标标签**不得使用 `user_id`**（高基数会打爆 Prometheus），只用 `user_type` 作为维度。

# 二十一、性能目标

## 21.1 R-01：V1.0 性能目标不可能成立

V1.0 同时声明了三件互相矛盾的事：

- 1.1：支持 **1～14 天**，**每日一张信息图**；
- 二十一章：**AI Hero 生成 10～40 秒**；
- 二十一章：**完整流程 P95 < 120 秒**。

14 天行程的素材需求量级：

| 素材     | 数量        | 单项耗时                          |
| -------- | ----------- | --------------------------------- |
| Hero 图  | 14          | 10～40 秒（AI 实时生成）          |
| 路线 SVG | 14          | < 1 秒                            |
| 美食图   | 14 × 3 = 42 | 素材库 < 1 秒 / AI 兜底 10～30 秒 |
| 景点图   | 14 × 3 = 42 | 同上                              |

**串行**：仅 Hero 一项就是 140～560 秒，是 120 秒预算的 1.2～4.7 倍。
**即使 AI 生成 8 路并发**：14 张 Hero 仍需 2 批 × 40 秒 = 80 秒，加上计划生成 20～60 秒已经必然超 120 秒。

结论：**V1.0 的两个指标不可能同时满足。** V1.1 通过三项措施重建目标。

## 21.2 R-01 修正后的性能目标

**措施一：分段 SLA，不再用单一 P95 覆盖全链路**

用户的真实等待终点是「能看到 HTML 计划页」，而不是「PDF 落到对象存储」。V1.0 末尾已经提到「HTML 先完成，PNG/PDF 异步」，但性能表却仍用一个 P95 统摄全部，自相矛盾。

| 阶段            | 含义                                                | 目标                                                 | 用户感知               |
| --------------- | --------------------------------------------------- | ---------------------------------------------------- | ---------------------- |
| **T1 计划可读** | 提交 → `SAVING_PLAN` 完成，用户可看到文字版完整计划 | **P95 < 75 秒**                                      | 主要等待               |
| **T2 页面可看** | → `RENDERING_HTML` 完成，含图片的 HTML 计划页可访问 | **P95 < 110 秒**                                     | 次要等待，页面渐进出图 |
| **T3 产物就绪** | → PNG/PDF 全部导出完成                              | **P95 < 240 秒**（≤ 7 天）/ **< 420 秒**（8～14 天） | 后台完成，通知用户     |

T3 按天数分档，因为它与天数**线性相关**，用固定值必然对长行程失真。

**措施二：Hero 缓存优先，AI 实时生成不在主路径**

依赖 19.5 的预热与复用：

| 场景                          | Hero 获取方式 | 耗时       |
| ----------------------------- | ------------- | ---------- |
| 命中预热库（预期 ≥ 80% 请求） | 缓存命中      | < 50 毫秒  |
| 主题桶已有同城同风格素材      | 素材库匹配    | < 500 毫秒 |
| 全新组合                      | AI 实时生成   | 10～40 秒  |
| AI 失败 / 超时 20 秒          | 渐变背景      | < 10 毫秒  |

关键约束：**AI 实时生成的超时压到 20 秒**（V1.0 允许 40 秒），超时立刻降级渐变背景。同一计划内**最多允许 2 次实时 AI Hero 生成**，其余天数复用同主题桶产物或降级 —— 14 天不等于 14 次 AI 调用。

**措施三：显式并发模型**

| 层级                   | 并发度                                 | 说明                              |
| ---------------------- | -------------------------------------- | --------------------------------- |
| 计划生成（LLM）        | 1（> 7 天时分段串行 2 次）             | 分段间有上下文依赖，不能并行      |
| 天级素材解析           | 8                                      | 14 天分 2 批                      |
| 单天内槽位解析         | 6                                      | 1 Hero + 1 Map + 3 Food + 3 Photo |
| AI 图片生成            | 全任务 3，全局 20                      | 供应商速率限制是硬约束            |
| 页面渲染（Playwright） | 单 Worker 3 个 page，共用 1 个 browser | 启动浏览器是最贵的一步            |
| PNG/PDF 导出           | 4                                      | —                                 |

**修正后的分环节目标**

| 环节                                   | 目标                 | 与 V1.0 的差异                                   |
| -------------------------------------- | -------------------- | ------------------------------------------------ |
| 请求标准化                             | < 500 毫秒           | 从 1 秒收紧，纯计算无外部调用                    |
| 历史计划检索                           | < 1.5 秒             | HNSW 索引后可收紧                                |
| 旅行计划生成（≤ 7 天）                 | P50 25 秒，P95 55 秒 | 明确分位                                         |
| 旅行计划生成（8～14 天，分段 2 次）    | P50 45 秒，P95 90 秒 | V1.0 未区分天数                                  |
| 自动修复（程序化）                     | < 200 毫秒           | V1.0 的「10～30 秒」实际是 LLM 重生成            |
| 自动修复（LLM 定向重生成，单次）       | < 30 秒，最多 2 次   | 明确为可选路径而非常规环节                       |
| 单槽位素材检索                         | < 800 毫秒           | 与 10.2 终止条件一致                             |
| 全部素材解析（14 天，8 并发）          | P95 < 25 秒          | V1.0 的「素材检索 < 5 秒」未说明是单槽位还是全部 |
| AI Hero 生成（实时，含超时）           | ≤ 20 秒              | 从 40 秒收紧                                     |
| 单页渲染                               | < 5 秒               | 不变                                             |
| 全部页面渲染（14 天 + 完整页，3 并发） | < 30 秒              | V1.0 缺此项                                      |
| 单页 PNG 导出                          | < 8 秒               | —                                                |
| 单页 PDF 导出                          | < 10 秒              | —                                                |
| ALL_DAYS PDF 合并（14 页）             | < 15 秒              | V1.0 缺此项                                      |

**为了减少等待，链路分三段异步交付**（V1.0 的意图，V1.1 明确为契约）：

```text
T1 → 前端立即渲染文字版计划，进度条继续
T2 → 前端切换到完整信息图页面
T3 → 通知「长图与 PDF 已就绪」，不阻塞前两段
```

对应地，`generation_jobs` 在 T1、T2 各写一个里程碑时间戳，客户端据此提前展示，而不是等 `status === 'COMPLETED'`。

| `travel_knowledge_rows`              | Gauge     | —                                                             | `plan_knowledge` 行数，观察知识库累积  |
| `travel_retrieval_reference_total`   | Counter   | `outcome`(hit/miss/timeout), `source`(versions/knowledge)     | 3.2.4 全局检索命中率                   |

**R-13：`user_type` 作为通用维度。** `travel_job_total`、`travel_job_milestone_seconds`、`travel_ai_image_total`、`travel_export_total` 均额外带 `user_type` 标签，用于分身份观察 SLA、成本与转化。**禁止使用 `user_id` 作为指标标签** —— 高基数会打爆 Prometheus（见二十章）。

**结构化日志**：每条日志携带 `request_id`、`trace_id`、`job_id`、`user_id`、`plan_version_id`、`stage`。**禁止**记录 `raw_request` 全文、模型输出全文、素材二进制、会话 ID。

**Trace**：OpenTelemetry 覆盖 API → 队列 → Worker → LLM/图片供应商 → Playwright → 对象存储。队列跨进程时通过消息头透传 trace context，否则链路在入队处断开。

**告警（关联验收标准）**

| 告警     | 条件                                                                       |
| -------- | -------------------------------------------------------------------------- |
| SLA 违约 | `travel_job_milestone_seconds{milestone="t1"}` P95 > 75 秒，持续 15 分钟   |
| 缓存失效 | `travel_asset_cache_hit_ratio{role="HERO_BACKGROUND"}` < 0.7，持续 30 分钟 |
| 图标回归 | `travel_icon_load_failure_total` > 0（任意一次即告警）                     |
| 修复异常 | `travel_plan_repair_iterations` P95 ≥ 3，持续 1 小时（规则集可能过严）     |
| 降级异常 | `travel_render_degraded_total / travel_job_total` > 0.1                    |
| 字体故障 | 日志出现 `CJK_FONT_UNAVAILABLE`（任意一次即告警，见 17.5）                 |

## 21.4 成本控制与配额（R-11 新增）

V1.0 完全没有成本约束，而 LLM 与 AI 图片生成是这个系统最大的可变成本项，无配额的公开服务会被单个用户刷穿。

**单任务成本上限（硬约束，超出即降级而非继续付费）**

| 项目            | 上限                             | 超出行为                                   |
| --------------- | -------------------------------- | ------------------------------------------ |
| LLM 输出 token  | 48K（14 天档）                   | 截断并触发分段合并                         |
| LLM 调用次数    | 1 次主生成 + 最多 2 次定向重生成 | 拒绝再调，`PLAN_REPAIR_EXHAUSTED`          |
| AI 图片生成次数 | 3 张                             | 后续槽位直接走占位图                       |
| 单任务预估成本  | 折算上限写入配置                 | 超出记 `warnings` 并降级，不中断已完成部分 |

**用户配额**

**R-13：配额按身份分档。** 匿名用户是主要滥用面（换 Cookie 即换身份），因此额度必须显著低于注册用户 —— 这同时构成注册的正向激励。

**全部数值均为配置项**（环境变量，见 `env.example`），下表是 V1 的**初始默认值**而非硬编码常量。调整配额只改配置，不改代码、不改数据库结构。

| 维度                             | 环境变量                   | 匿名（`ANONYMOUS`）                          | 注册（`REGISTERED`） | 错误码                                     |
| -------------------------------- | -------------------------- | -------------------------------------------- | -------------------- | ------------------------------------------ |
| 每分钟提交                       | `QUOTA_*_PER_MINUTE`       | 1 次                                         | 3 次                 | `AUTH_RATE_LIMITED`（429 + `Retry-After`） |
| 每日生成（`daily_plan_quota`）   | `QUOTA_*_DAILY_PLANS`      | **5 个计划**                                 | 5 个计划             | `AUTH_QUOTA_EXCEEDED`                      |
| 每月生成（`monthly_plan_quota`） | `QUOTA_*_MONTHLY_PLANS`    | **10 个计划**                                | 20 个计划            | `AUTH_QUOTA_EXCEEDED`                      |
| 同时进行中任务                   | —                          | 1 个                                         | 1 个                 | `JOB_ALREADY_RUNNING`（409）               |
| 每计划导出次数                   | `QUOTA_*_EXPORTS_PER_PLAN` | 3 次                                         | 10 次                | `AUTH_QUOTA_EXCEEDED`                      |
| 实时 AI Hero 生成                | `QUOTA_*_AI_HERO`          | **0 次**（只用缓存与素材库，耗尽即渐变背景） | 2 次                 | 记入 `warnings`，不报错                    |

匿名日配额与注册持平（均为 5），差异体现在**月配额、导出次数、AI Hero 额度与数据保留期**上。这样匿名用户的单次体验不打折，注册的价值落在长期保留、跨设备访问与更高的月度总量上 —— 比"让匿名用户当天就撞墙"更合理，后者只会把人劝退而不是转化。

匿名 AI Hero 额度为 0 是有意的成本设计：AI 图片是最贵的一项，而匿名流量占比最高且无留存价值。依托 19.5 的 600 张预热库，匿名用户绝大多数情况下仍能拿到合适的 Hero。

**防刷：匿名身份创建限速（对应 3.6.5）**

不限制匿名用户的**创建**，上面的配额就毫无意义 —— 攻击者清一次 Cookie 就重置额度。

| 维度                                 | 环境变量                              | 限制         | 错误码                                   |
| ------------------------------------ | ------------------------------------- | ------------ | ---------------------------------------- |
| 单 IP 每小时创建匿名用户             | `QUOTA_IP_ANON_CREATE_PER_HOUR`       | 5 个         | `AUTH_ANON_CREATION_RATE_LIMITED`（429） |
| 单 IP 每日创建匿名用户               | `QUOTA_IP_ANON_CREATE_PER_DAY`        | 20 个        | 同上                                     |
| 单 IP 每日生成总量（跨全部匿名身份） | `QUOTA_IP_PLANS_PER_DAY`              | 10 个计划    | `AUTH_QUOTA_EXCEEDED`                    |
| 单 IP 登录失败                       | `QUOTA_IP_LOGIN_FAILURES_PER_HOUR`    | 10 次 / 小时 | `AUTH_RATE_LIMITED`                      |
| 单邮箱登录失败                       | `QUOTA_EMAIL_LOGIN_FAILURES_PER_HOUR` | 5 次 / 小时  | `AUTH_RATE_LIMITED`                      |

**「单 IP 每日生成总量」是真正的兜底** —— 它不依赖 Cookie，因此清 Cookie 无效。

该阈值必须**高于**单匿名用户的日配额，否则 IP 维度会先撞墙，账号维度配额就成了摆设。匿名日配额定为 5 后，IP 日上限相应定为 10（两倍），保证同一 IP 下至少两个正常用户能各自用满。IP 维度会误伤 NAT 后的多用户（如办公网），但注册用户不受 IP 维度生成限制、只受账号维度限制，因此受影响的用户有明确解决路径：注册。

**这两个数值存在耦合关系**：调整 `QUOTA_ANON_DAILY_PLANS` 时必须同步检查 `QUOTA_IP_PLANS_PER_DAY >= 2 × QUOTA_ANON_DAILY_PLANS`，否则防刷会退化成对正常用户的限制。启动时校验该不变式，不满足则拒绝启动（fail fast，避免带着错误配置上线）。

配额计数存 Redis（键含日期与身份/IP），过期自动重置；`users.daily_plan_quota` / `monthly_plan_quota` 是**可对个别用户覆盖**的上限值，插入时按 `user_type` 取上表配置的默认值。

**幂等命中不计入配额** —— 否则用户刷新页面重试就会被扣额度。

**全局熔断**：AI 图片供应商日调用量达到预算阈值时，全局切换到「仅使用素材库 + 占位图」模式，`GENERATING_ASSETS` 状态直接跳过。系统降级但仍可用，这比超支停服更可接受。

# 二十二、V1 技术栈与开发目录（R-12 已重写）

## 22.1 技术栈决定

V1.0 的目录建议混用了 Python（`local_library.py` 等）与 React 模板。V1.1 统一为**全 TypeScript**。

| 层            | 选型                                                                                                              |
| ------------- | ----------------------------------------------------------------------------------------------------------------- |
| 运行时        | **Node 24 LTS**（V1.1 曾定 22；实施时改为 24 —— 它是当前 active LTS，钉在 22 只会要求额外安装一个运行时而无收益） |
| 包管理 / 构建 | pnpm workspaces + Turborepo                                                                                       |
| 前端与模板    | Next.js（App Router）+ React + TypeScript                                                                         |
| API           | Fastify + TypeScript                                                                                              |
| 队列          | BullMQ（Redis）                                                                                                   |
| 数据库访问    | Drizzle ORM + `pg`，pgvector 走原生 SQL                                                                           |
| Schema 契约   | **Zod 单一真相源**，导出 TypeScript 类型与 JSON Schema                                                            |
| LLM           | Anthropic SDK（结构化输出用 JSON Schema 约束）                                                                    |
| 图片处理      | sharp（WebP 转换、缩略图、尺寸校验）                                                                              |
| 渲染          | Playwright（Chromium）                                                                                            |
| PDF 合并      | pdf-lib                                                                                                           |
| 测试          | Vitest（单元/集成）+ Playwright（视觉回归）                                                                       |

**为什么全 TypeScript**

1. 渲染链路（React 模板 + Playwright）必须是 Node，Python 方案等于强制双语言双工具链；
2. **最脆弱的契约是 `TravelPosterViewModel` ↔ React 模板** —— V1.0 已在此处出现三处字段级不一致（见 6.2、12.2）。单语言下 `packages/schemas` 被 API、Worker、模板共同引用，**同类不一致变成编译错误**；Python 方案必须双份维护 pydantic 与 TypeScript 定义，漂移是时间问题；
3. Python 的 LLM 生态优势已很薄：TS SDK 是一等公民、结构化输出走 JSON Schema 两语言同构、pgvector 有成熟 TS 客户端、`sharp` 在 WebP 与缩略图上优于 Pillow。

**若实施团队是既有 Python 团队**，则改为 FastAPI + Next.js，但必须以 JSON Schema 为中间层用 `datamodel-code-generator` 生成 pydantic 侧类型，**禁止手写两份 ViewModel 定义**。

## 22.3 Linux 运行时约束（R-14 新增）

**全部后端组件（`api`、`generation-worker`、`render-worker`）与 `web` 的服务端部分必须能在 Linux 上运行**，并以 Linux 容器为唯一生产部署形态。开发可以在 Windows / macOS，但**Linux 是唯一的正确性基准** —— 本地跑通不算通过，CI 在 Linux 上跑通才算。

### 22.3.1 容器基线

| 项           | 选择                                                          | 理由                                                                                         |
| ------------ | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 发行版       | **Debian 12 slim（glibc）**                                   | 不用 Alpine：Chromium 在 musl 上问题多，`sharp` 需额外构建，`tzdata` / `fontconfig` 缺省缺失 |
| 架构         | `linux/amd64`                                                 | 生产统一；Apple Silicon 开发机必须显式 `--platform=linux/amd64` 构建镜像验证                 |
| Node         | 24 LTS，官方 `node:24-bookworm-slim`                          | 当前 active LTS                                                                              |
| 渲染镜像基底 | `mcr.microsoft.com/playwright:v<版本>-jammy`（Ubuntu，glibc） | 已含 Chromium 全部系统依赖，自建容易漏库                                                     |
| 运行用户     | 数值型非 root UID/GID（如 `10001:10001`）                     | 用名字（`node`）在某些 K8s `runAsUser` 校验下不生效                                          |
| 时区         | 安装 `tzdata`，容器 `TZ=UTC`                                  | 应用按请求 `timezone` 转换；容器不设本地时区                                                 |
| 语言环境     | `LANG=C.UTF-8`                                                | 避免依赖宿主 locale                                                                          |
| 初始化进程   | `--init` 或 `tini`                                            | Chromium 会产生僵尸子进程，无 init 会累积                                                    |

### 22.3.2 逐组件的 Linux 依赖

| 组件                            | Linux 特有依赖与陷阱                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`render-worker`（Chromium）** | 1. **`/dev/shm` 默认 64MB，Chromium 会崩** → 部署时 `--shm-size=1g`，K8s 用 `emptyDir: { medium: Memory }` 挂载 `/dev/shm`，或退而使用 `--disable-dev-shm-usage`（更慢，作为兜底）<br>2. 容器内需 `--no-sandbox` 或提供 seccomp/`SYS_ADMIN`；**优先用 seccomp profile 保留沙箱**，`--no-sandbox` 仅在受信内网可接受<br>3. `--font-render-hinting=none` 保证与基线截图一致<br>4. 内存 ≥ 2Gi（21.2 单 browser + 3 page） |
| **中文字体（17.5）**            | 安装到 `/usr/share/fonts/truetype/noto-sc/` 后必须 `fc-cache -f -v`；镜像构建时校验 `fc-list \| grep -ci noto` ≥ 1，为 0 则构建失败。**不要依赖宿主字体挂载**                                                                                                                                                                                                                                                          |
| **`sharp`**                     | 需 `linux-x64` 预编译二进制。`pnpm` 默认可能只装宿主平台的可选依赖 → `.npmrc` 设 `supportedArchitectures`，或 `pnpm add --config.platform=linux --config.arch=x64`；CI 在 Linux 上安装可规避。**禁止把 `node_modules` 从 Windows 拷进镜像**                                                                                                                                                                            |
| **`oxipng`（17.4）**            | 使用 `linux-x64` 二进制；或改用 `sharp` 自带 PNG 压缩以减少一个原生依赖                                                                                                                                                                                                                                                                                                                                                |
| **PostgreSQL 扩展**             | `vector`（pgvector）、`pgcrypto`、`citext` 三个扩展必须在镜像中可用；用 `pgvector/pgvector:pg17` 而非官方 `postgres:17`                                                                                                                                                                                                                                                                                                |
| **Argon2id**                    | 用纯 JS 实现（`@node-rs/argon2` 提供 Linux 预编译，或 `hash-wasm`）；避免需要本机编译工具链的方案                                                                                                                                                                                                                                                                                                                      |
| **BullMQ / Redis**              | 无平台特异性                                                                                                                                                                                                                                                                                                                                                                                                           |

### 22.3.3 跨平台开发护栏（Windows 开发 → Linux 运行）

这些是 Windows 上开发、Linux 上部署时**最常见的四类静默故障**，必须由工具强制，不能靠自觉。

| 陷阱             | 后果                                                                                             | 护栏                                                                                              |
| ---------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| **文件名大小写** | Windows 不区分大小写，`import './TravelCard'` 引用 `travelCard.tsx` 本地能跑，Linux 构建直接失败 | TypeScript `forceConsistentCasingInFileNames: true`；CI 在 Linux 上执行 `tsc --noEmit` 与完整构建 |
| **路径分隔符**   | 硬编码 `\` 或字符串拼接路径在 Linux 上失效                                                       | ESLint 规则禁止字符串字面量含 `\\`；一律用 `node:path`；URL 与对象存储键一律用 `/`                |
| **换行符**       | `CRLF` 混入 shell 脚本导致 `bad interpreter`；混入快照文件导致视觉回归误报                       | `.gitattributes`：`* text=auto eol=lf`，`*.sh text eol=lf`；Prettier `endOfLine: "lf"`            |
| **可执行权限**   | Windows 无执行位，脚本提交后在 Linux 上 `Permission denied`                                      | 用 `git update-index --chmod=+x`；或不用 shell 脚本，全部走 `package.json` 的 `scripts`           |

**其他约束**

- **任务入口不使用 PowerShell**。`enterprise-ai-platform` 用 `.ps1` 作任务运行器；本项目一律用 `package.json` 的 `scripts` + 必要时 POSIX `sh`，保证 CI 与生产容器内可直接执行；
- **不使用 Windows 独有 API**，不依赖 `%APPDATA%`、盘符、`os.tmpdir()` 的具体形态；
- **区分大小写的对象存储键**：MinIO / S3 键区分大小写，键生成必须确定性（见 19.1 归一化）；
- **inotify 上限**：Next.js dev 在 Linux 上可能触发 `ENOSPC`，文档记录 `fs.inotify.max_user_watches` 调整方法（仅开发环境问题）；
- **进程信号**：容器内必须正确处理 `SIGTERM` 优雅停机 —— Worker 收到信号后停止取新任务、等当前任务完成或超时后退出，避免任务半途中断留下 `RENDERING_HTML` 悬挂状态。

# 二十四、V1 验收标准

满足以下条件即可进入内测：

1. 用户提交表单后无需人工处理；
2. 模型输出能够自动保存到数据库；
3. 计划必须经过 Schema 和业务规则校验；
4. 每日都能生成一个信息图 ViewModel；
5. 图标加载成功率为 100%；
6. 路线图失败时能自动降级；
7. Hero 图失败时仍能生成页面；
8. 景点和美食图片缺失时不阻断流程；
9. 页面不存在文字遮挡和明显溢出；
10. HTML、PNG、PDF 至少两种输出可用；
11. 用户只能访问自己的私有计划；
12. 所有素材均可追踪来源；
13. 相同任务不会重复生成；
14. 生成失败有明确错误码和重试机制；
15. 不向用户展示未通过校验的模型草稿。

# 二十五、V1 最终链路

```text
TravelRequestUI
    ↓
NormalizedTravelRequest
    ↓
历史计划与资料检索
    ↓
大模型生成 TravelPlan
    ↓
Schema 校验
    ↓
业务规则校验
    ↓
自动修复
    ↓
保存 TravelPlanVersion
    ↓
Presentation Planner
    ↓
AssetRequirement
    ↓
Asset Resolver
    ├── 本地图标
    ├── 路线 SVG
    ├── 素材图库
    ├── AI 图片生成
    └── 默认兜底
    ↓
TravelPosterViewModel
    ↓
React 模板
    ↓
HTML
    ↓
Playwright
    ├── PNG
    └── PDF
    ↓
对象存储
    ↓
前端展示结果
```

这版设计的核心边界是：

> **大模型决定“旅行内容是什么”，展示编排器决定“页面需要展示什么”，素材服务决定“图片和视觉素材从哪里来”，React 模板决定“最终页面长什么样”。**

四个部分相互独立，后续更换大模型、增加图库、增加模板或替换图片生成服务时，都不需要推翻整套系统。
