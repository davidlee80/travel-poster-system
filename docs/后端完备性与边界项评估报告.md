## 三、边界项深挖

四个边界项分属四种不同性质，不应被同等看待。

### 3.1 真实 LLM / 图片端点联调

**性质：物理未发生。** 代码 100% 就绪，只差真实凭据与一次真实网络往返。

- LLM 文本（`packages/llm/src/client.ts`）与图片（`image.ts`）的 `direct`/`gateway` 客户端**完整实现**，OpenAI 兼容协议，请求体一字不差。
- 关键约束已用「启动即失败」硬校验固化：base URL 禁 `/v1` 尾缀、`mode!==fake` 时凭据三项必填、图片 `timeout > jobAiBudget` 硬拒。
- 强约束 `response_format: json_schema + strict:true` → 候选池只能配支持 structured outputs 的模型（deepseek/bailian 多数不支持，配错会伪装成 `PLAN_LLM_UNAVAILABLE` 且白烧调用）。
- **实测证据**：`probe:llm --dry-run` 确认——原样 z.toJSONSchema 产物不合规（20 节点缺 additionalProperties、4 种禁用关键字），而生产实际发出的净化 schema 完全合规。**联调成功的前提（schema 合规）已在本地验证满足。**
- **联调 = 3 步**：`pnpm probe:llm`/`probe:image` 探测 → 改 `.env`（`LLM_MODE=direct` + 三个变量）→ 小流量灰度。**不改代码。**
- **回滚**：改 `LLM_MODE=fake` 重启，秒级、零风险。
- **授权图源例外**：`IMAGE_SEARCH_MODE=direct` **启动即失败**（供应商未选定），是三者中离生产最远的——详见 3.2。

### 3.2 授权图源适配器接入

**性质：有意的半成品。** `direct` 分支故意留空（启动即失败），因为供应商未选定。

- 接口极小：`LicensedSourceClient` 只有 3 个成员（`providers`、`search()`、`download()`）。
- 整条入库流水线（`apps/generation-worker/src/assets/search-ingest.ts`）**已实现并测试**：五道门禁（授权→MIME→下载→指纹去重→后处理/质量）、标签合并（R-47）、source_metadata 落库、预算闸三约束（单任务 8 次 / 连续失败 2 次停用 / 全局日预算 2000）全部走真实代码路径。
- **核心工作量**：写一个 `<Provider>LicensedSourceClient` 适配器（~150–250 行）+ 一处工厂分支 + license 词汇映射表 + 单测。**小时级到 1–2 天级。**
- **真正门槛在代码之外**：选定供应商、签授权合约、license 映射、真实命中率/下载稳定性验证——是产品/商务决策，不是工程缺口。
- **硬约束**：MIME 白名单仅 jpeg/png/webp（SVG 被排除，防脚本注入）；`licenseType` 映射不出必须返回 `null`（不许填默认值，那等于替图源做法务判断）；超时可下调不可上调（5 秒）；失败必须以 Promise reject 抛出；白名单只从配置读、无运行时添加 API。
- **回滚**：改 `IMAGE_SEARCH_MODE=fake` 重启。

### 3.3 CR 计费开启全链路

**性质：建好的开关，等产品决策来拉。** 代码 100% 就绪 + 已测，故意默认关闭。

- **六条跨章不变量（设计 21.5）全部落地，代码 + 数据库双重固化**：

  | # | 不变量 | 数据库固化 |
  | --- | --- | --- |
  | 一 | 结算幂等键 `job:<job_id>`（重投不重复扣费） | `credit_ledger_idem_uk UNIQUE` |
  | 二 | 预留必须在入队之前（建行→预留→入队） | `credit_holds_job_uk UNIQUE (job_id)` |
  | 三 | 可重试失败**不**释放预留 | 靠 `expires_at`（2h）兜底 |
  | 四 | 降级一律朝「不挡用户」（无价目→免费、超支→WRITE_OFF 我们承担） | — |
  | 五 | 三侧开关必须一起开（api/gen/render 各读一次，启动日志都打值） | — |
  | 六 | 匿名不进货币体系（`/credits/*` 拒匿名 403；注册赠送幂等键 `signup:<user_id>`） | — |

- 钱流三态：成功→`settle`（多退少补，不足我们吃）、不可重试失败→`release`（退预留+记 WRITE_OFF）、可重试失败→**什么都不做**（预留留给重试）。导出侧只在 `FAILED` 退款、`PARTIAL` 不退。
- **开启 = 有严格顺序的运维动作**：迁到 0013/0014 → **发布真实价目（替换 0014 开发价）** → `pnpm user:credit` 给存量用户授 CR → **三个进程同时**设 `CREDIT_BILLING_ENABLED=true` → 核对三侧启动日志一致。**不改代码。**
- **最大风险——收错钱**：迁移 0014 是「按能跑通选、不按成本选」的开发价，带它上线不报错、只静默收错钱。真实定价是尚未做的产品决策；无支付网关（`TOPUP` 只是数据结构）。
- **回滚**：三侧同时设 `false` 重启，分钟级；关闭后完全不碰钱包表。

### 3.4 前端历史列表 + regenerate 入口

**性质：两个就绪度天差地别的入口，wiki 并列登记但不该同等看待。**

**历史列表——后端 + 前端 API 客户端 + 游标 + 测试全部就绪，唯一缺一个 React 页面：**

| 层 | 状态 |
| --- | --- |
| API 端点 `GET /api/v1/travel-plans` | ✅ |
| 游标 repo 层（`(created_at, id)` 复合游标 Base64URL） | ✅ |
| 前端 API 客户端 `listPlans()`（`api-client.ts:459`，含 next_cursor/has_more 类型） | ✅ |
| route 测试（items/next_cursor/has_more + 翻页） | ✅ |
| React 列表页面（`app/plans/` 下只有 `[planId]` 详情，无列表页） | ❌ |

- **补齐**：新建 `app/plans/page.tsx`，调已有的 `listPlans()` 渲染卡片 + "加载更多"。**半天~一天，纯前端，风险极低。**

**regenerate——数据模型完整，公网入口故意不做（设计 R-36）：**

- 版本模型完整存在（`travel_plan_versions` 含 `version_number`、`regeneration_count(0..2)`、`repair_iterations(0..3)`、UNIQUE 约束、`current_version_id` 外键）；`?plan_version_id=`、`EXPORT_PLAN_VERSION_MISMATCH` 也实现了。**但无任何 regenerate 端点。**
- R-36 明确这是**有意的 V2 契约**：13.1 每次提交都建新 `travel_plans` 行（幂等键含 `client_request_id`），因此用户「想重新生成」= 换 client_request_id 生成一份全新计划（新 plan_id）；多版本机制（同 plan 追加 version）当前无路径触发。
- **补齐 = 新功能**，触及三处跨章语义，每处都需设计决策：
  1. **幂等语义**：13.8 幂等键含 NormalizedTravelRequest，直接复用会让 regenerate 命中旧结果变 no-op——需重定义幂等意图。
  2. **版本选择语义**：追加版本后 `current_version_id` 指向谁？新版 REJECTED 回退？`regeneration_count` 上限到了怎么办？
  3. **计费语义**：CR 开启时 regenerate 是新的可计费任务，job 挂既有 plan 下，`credit_holds.job_id` 语义要理清。
- **工作量**：数天 + 必须先做产品/设计决策（regenerate 语义三选一：替换当前版本 / 追加并切换 / 追加保留）。**不建议简单地「加个端点」。**

## 五、建议的推进顺序

综合 wiki 07 的「推荐近期技术顺序」与本次深挖：

1. **用 `probe:llm`/`probe:image` 验证真实端点**，再开一档 tier 灰度（最低成本解锁最核心阻塞）。
2. **补 `app/plans/page.tsx` 历史列表页**（半天、低风险、后端全就绪，性价比最高的一个前端补齐）。
3. 接真实授权图源或灌种子素材，随后做 Hero 预热。
4. 在完整 Docker 栈跑真实导出与 MinIO 生命周期验证。
5. 决定 CR 真实价目/赠送/充值，存量授予后再三侧开启计费。
6. regenerate 作为**独立 V2 功能**，先出设计再实现——不要在 V1 草率加端点。

## 六、判断「功能完成」的标准（引自 wiki 07）

对本仓库，至少同时满足以下才能称为完成：

- 契约有 Zod 真相源，并被 API/Worker/Web 共用；✅ 已满足
- 主路径和到底降级同时有测试；✅ 已满足
- 数据归属、幂等、保留期与错误码已定义；✅ 已满足
- 指标在 catalog 登记且实际注册，告警引用存在；✅ 已满足
- Linux/Chromium/字体/原生依赖在 CI 或容器验证；✅ 已满足（CI 护栏）
- **外部 Provider 功能已用真实凭据联调，不能只靠 fake**；⚠️ 待办（边界 3.1/3.2）
- **人工 SLA/命中率目标以真实样本报告，不用本机假模型数据代替**。⚠️ 待办

前五条已满足，后两条是当前的主要待办——它们**天然无法靠代码自证，只能靠真实联调与真实流量完成**。
