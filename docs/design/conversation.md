我已经把 `planner.html` 的现有信息架构和前面那套“私人专属旅行服务体系”逐项对了一遍。结论是：**第一版已经是一个不错的“行程偏好采集器”，但还没有达到“私人旅行顾问客户建档 + 可执行性判断”的层级。**

目前页面是 8 步：基本信息、同行人员、预算、节奏路线、交通住宿、饮食、兴趣、特殊需求；同时有“偏好 / 必须 / 不要”三态条件和右侧条件汇总。这些是值得保留的核心设计。

真正需要迭代的重点，不是简单地把完整版里的 196 个服务项全部塞进网页，而是要重新划分：**哪些问题应该问客户，哪些应该由系统推导，哪些应该由后台自动调研，哪些应该在行程确定后再补充。**

---

# 一、首先重新定义 planner 的角色

我建议把现在的定位：

> “结构化采集旅行诉求 → 生成一张行程信息图”

升级为：

> **“建立客户旅行画像 → 收集硬约束与偏好 → 判断旅行可行性 → 自动研究目的地 → 生成私人旅行方案 → 持续补齐行前与旅中服务资料”**

这两者区别非常大。

当前 planner 主要回答：

> “你喜欢怎么玩？”

未来应该同时回答四个问题：

| 层次   | 系统需要知道什么             | 数据从哪里来          |
| ---- | -------------------- | --------------- |
| 旅行画像 | 你是谁、为什么旅行、喜欢什么       | 客户填写            |
| 旅行约束 | 什么必须满足、什么不能接受        | 客户填写            |
| 可执行性 | 签证、交通、健康、安全是否允许      | 系统自动核验 + 少量客户信息 |
| 服务执行 | 什么时候订、什么时候提醒、出了问题怎么办 | 系统自动生成          |

这会直接决定 planner 的产品架构。

---

# 二、不要让客户填写“196 项”

这是这次迭代最重要的一条原则。

完整版里的 196 项不是 196 个客户问题。

应该拆成四种数据：

| 数据类型          | 举例                        | 应该怎么处理       |
| ------------- | ------------------------- | ------------ |
| **客户主动输入**    | 预算、兴趣、日期、同行人、饮食、节奏        | Planner 直接询问 |
| **条件触发输入**    | 自驾→驾照；儿童→年龄；潜水→资质；过敏→严重程度 | 动态展开问题       |
| **系统自动推导**    | 行程天数、是否跨国、是否跨时区、预算总额      | 不问客户         |
| **系统自动调研/核验** | 签证要求、天气、安全、交通票制、景点开放时间    | 后台查，不让客户填写   |

所以客户第一次填写 planner，理想状态仍然应该控制在：

**5～8 分钟完成主问卷。**

复杂客户可能通过条件分支增加到 10～15 分钟。

而不是做成一份旅行版“人口普查”。

---

# 三、现有 8 步建议升级为 9 步

我建议下一版的信息架构变成：

| 新步骤 | 名称           | 主要解决的问题             |
| --- | ------------ | ------------------- |
| 01  | **这次想怎么旅行**  | 目的地、日期、旅行目的、最重要的体验  |
| 02  | **谁一起旅行**    | 人员、年龄、关系、儿童/老人/特殊需求 |
| 03  | **准备花多少钱**   | 总预算、预算弹性、钱花在哪里      |
| 04  | **旅行节奏与边界**  | 作息、步行、排队、风险容忍、自由时间  |
| 05  | **怎么去、怎么移动** | 航班/铁路/自驾/公共交通偏好     |
| 06  | **想住什么样**    | 酒店、房型、地段、床型、设施      |
| 07  | **想吃什么、玩什么** | 餐饮、兴趣、必去、不要去        |
| 08  | **需要特别照顾什么** | 健康、无障碍、证件、特殊活动等条件分支 |
| 09  | **确认你的旅行画像** | 汇总、缺失项、风险项、服务方式、授权  |

其中当前的“交通住宿”强烈建议拆成两个步骤。

因为这两个领域实际需要收集的信息都很多，而且决策逻辑完全不同。

---

# 四、第一步「基本信息」需要明显升级

现在第一步采集：

出发地 → 目的地 → 日期 → 已有订单。

这个作为骨架没问题，但信息还不足。

建议改成：

### A. 旅行目的

增加：

**“这次旅行主要为了什么？”**

例如：

休闲度假 / 蜜月纪念 / 亲子 / 美食 / 摄影 / 购物 / 滑雪 / 看演出 / 体育赛事 / 商务+休闲 / 探亲 / 其他。

这个字段非常重要，因为它决定系统后面所有取舍。

---

### B. 本次旅行最重要的 3 件事

例如：

> 必须吃好
> 酒店一定要舒服
> 不想赶行程
> 想拍很多照片
> 小朋友开心最重要
> 尽量少折腾交通

这是目前 planner 最大的缺失之一。

因为“兴趣”不能完全代表“决策优先级”。

一个人可以喜欢博物馆、美食、购物，但真正愿意牺牲其他东西换来的可能只有“酒店”。

---

### C. 日期弹性必须从 V2 提前

目前日期弹性是 disabled，多个目的地组合也是 V2。

这两个其实应该尽早做。

日期建议：

**日期固定**

**前后 ±1 天**

**前后 ±3 天**

**整周都可以**

**月份确定但日期未定**

这会极大提高：

机票优化、酒店价格优化、天气规避、大型活动匹配。

---

### D. “目的地尚未确定”需要变成真正的分支

目前界面虽然出现了“目的地尚未确定”，但它不能只是一个 checkbox。

如果选择：

> 我还没决定去哪

系统就应该切换成：

**目的地发现模式。**

问：

想去国内还是国外？

飞多久可以接受？

预算多少？

喜欢冷还是暖？

海岛 / 城市 / 自然 / 历史？

签证麻烦能不能接受？

是否带儿童/老人？

然后推荐 3～5 个目的地。

这个功能后期会非常有产品价值。

---

# 五、「已有订单」不能只做三个 checkbox

当前只有：

已有往返交通
已有酒店
已有门票或演出。

这是不够的。

因为“已有订单”其实代表：

> **不可移动的行程锚点。**

一旦选择“已有航班”，应该展开：

航班号 / 车次
出发时间
抵达时间
机场/车站
是否可改签

已有酒店则：

酒店名称
入住日期
退房日期
地址
是否可取消

已有演出：

活动名称
日期
开始时间
地点

系统随后把这些变成：

**Locked Constraint（锁定条件）**

而不是普通偏好。

---

# 六、「同行人员」是下一版最需要改造的模块之一

目前用：

成人 18～64
儿童 0～17
老人

三个计数器。

对于粗略估算可以，但私人顾问服务不够。

例如：

2 岁儿童和 16 岁儿童，在机票、酒店、餐厅、景点、儿童座椅、行程节奏方面完全不同。

所以建议：

## 先问人数，再生成 Traveler Card

例如：

**旅行者 1**
成人 · 35岁 · 本人

**旅行者 2**
成人 · 34岁 · 配偶

**旅行者 3**
儿童 · 6岁

每位旅行者不需要一上来填写很多东西。

只收：

年龄/年龄段
同行关系
是否有特别旅行需求

如果触发特殊情况，再展开。

---

# 七、儿童和老人不要用年龄直接代表行动能力

例如：

70 岁但每天能走 15 km的人，与 55 岁但膝盖不方便的人，完全不能按年龄判断。

因此建议分离两个变量：

**年龄**

和

**行动能力 / 体力需求**

例如：

正常活动
希望减少步行
不能长时间站立
避免大量台阶
需要轮椅
需要婴儿车通行

这样规划模型会准确很多。

---

# 八、预算模块目前的逻辑需要重构

当前预算使用：

> ¥800～¥1,500 / 人 / 天

然后：

> 人均每日预算 × 人数 × 天数

计算总预算。

这个方法简单，但现实旅行中容易产生误导。

尤其：

机票不是按天发生的。

长途机票很贵的旅行会严重扭曲结果。

建议改为“双入口”。

### 用户可以选择：

**我知道总预算**

例如：

> 整个旅行控制在 ¥30,000

或者：

**我只知道旅行档次**

经济 / 舒适 / 品质 / 豪华。

然后系统再推算。

预算还应该增加：

| 字段      | 示例              |
| ------- | --------------- |
| 预算主体    | 总预算 / 人均预算      |
| 币种      | CNY / JPY / USD |
| 硬上限     | ¥30,000不能超过     |
| 舒适目标    | ¥25,000左右       |
| 是否含国际机票 | 是               |
| 是否含购物   | 否               |
| 已支付金额   | ¥8,000          |
| 备用预算    | ¥5,000          |

---

# 九、固定的“¥300～¥6000/人/天”不要做成绝对标准

目前几个档位的固定人民币区间，在曼谷、东京、巴黎、瑞士、马尔代夫代表的体验完全不同。

建议：

客户先选：

经济型 / 舒适型 / 品质型 / 奢华型

等目的地确定以后，再由系统提示：

> “按照东京当前住宿及交通水平，你选择的『舒适型』预计约为……”

也就是说：

**旅行档次是用户偏好。**

**金额应该目的地化。**

---

# 十、「节奏路线」中有一个很好的功能，也有一个需要弱化的功能

目前“旅行节奏 1～5”非常值得保留。

但建议增加：

最早几点出门
最晚几点结束
每天能走多少
连续走多久需要休息
能不能早起
能不能晚归
能不能排队
是否午休
每天希望留多少自由时间

---

## “中心辐射 / 双中心 / 多城市跳转”不建议作为普通用户核心问题

这是旅行规划师语言。

普通客户真正知道的是：

> 我不想频繁换酒店。

> 我愿意为了多玩几个城市搬行李。

> 我最多接受换两次住宿。

因此应该让客户回答：

**愿意换几次酒店？**

**喜欢慢慢住还是多城市？**

然后系统自己推导：

> 双中心 / 环线 / 单向线路。

现在这组选项可以保留在：

**高级设置**

而不是主流程。

---

# 十一、新增一个非常关键的「风险容忍度」

完整版里有这个概念，但当前 planner 基本没有。

建议在节奏后面增加：

> 哪些旅行方式你可以接受？

例如：

直飞优先
可以转机
最多一次转机
不坐红眼航班
可以坐红眼航班
不坐很小的飞机
不接受夜间长途巴士
可以自驾
不走偏远地区
不参加高风险活动

这是行程“推荐质量”非常重要的数据。

---

# 十二、「交通住宿」必须拆开

现在交通和住宿放在同一个步骤。

建议拆成：

## STEP 5 怎么去 / 怎么移动

增加：

直飞优先程度
最多接受几次转机
接受红眼吗
经济舱 / 超经 / 商务
铁路与飞机偏好
起飞时间偏好
机场偏好
航空公司偏好
是否有大件行李
是否自驾
是否需要儿童安全座椅

---

# 十三、住宿采集目前明显不够

现有：

酒店 / 民宿 / 公寓 / 度假村 / 青旅

以及：

电梯、独卫、靠近地铁、早餐、厨房、多人间。

下一版至少增加：

房间数量
大床 / 双床
连通房
酒店星级
酒店品牌偏好
住宿预算 / 晚
更重视位置还是酒店本身
安静程度
景观要求
浴缸
健身房
泳池
洗衣设施
办公桌/Wi-Fi
24小时前台
晚到入住

其中：

**床型和房间数不是偏好标签，而应该是结构化字段。**

---

# 十四、饮食模块是目前过于简单的地方之一

现在只有：

素食
清真
不吃辣
海鲜过敏。

至少建议增加四层。

### 饮食风格

当地特色
Fine Dining
街头美食
咖啡甜品
居酒屋/酒吧
市场
中餐
日料
西餐

### 用餐预算

普通
适中
愿意为特色餐厅花钱
预算不限

### 用餐习惯

愿意排队
不愿排队
可以预约
想吃早餐
习惯晚餐较早/较晚

### 饮食安全

这里尤其要改。

“海鲜过敏”不能再放在：

> 偏好 → 必须 → 不要

这种三态标签体系里。

**过敏不是偏好。**

应该问：

是否存在食物过敏？

→ 是

→ 哪种？

→ 严重程度？

→ 是否需要避免交叉污染？

这类字段进入：

**Safety Constraint**

# 十五、兴趣模块方向正确，但要加入“排序”

当前 14 个兴趣标签已经是不错的基础。

建议不是无限打标签，而是：

### 第一层：选择所有感兴趣

然后：

### 第二层：选出 Top 3

例如：

🥇 美食
🥈 摄影
🥉 历史

模型才能真正知道：

出现冲突时应该保谁。

---

# 十六、增加三个非常重要的兴趣字段

### 必去

> 有哪些地方不去会遗憾？

输入具体名称。

### 想去但可以放弃

Wish List。

### 明确不要

例如：

> 不去动物园
> 不逛奢侈品店
> 不看寺庙
> 不参加旅行团

这三个比泛兴趣标签对规划模型更有价值。

---

# 十七、现在的「特殊需求」必须拆掉重做

现在最后提供一个大文本框，让客户写：

> 健康状况、必去地点、其他特殊要求。

自由文本应该保留。

但它只能作为：

> “还有什么想告诉我们？”

不能承担安全相关信息。

尤其这些内容必须结构化：

健康限制
长期用药
孕期
行动不便
轮椅
视听障碍
食物过敏
高原活动
潜水
极限运动

否则模型可能漏读。

---

# 十八、健康信息建议采用“两层采集”

不要问客户：

> “请描述你的健康状况。”

而先问：

> 是否存在可能影响旅行安排的健康或行动需求？

有 / 没有 / 不确定。

如果“有”，再展开。

这样既保护隐私，也符合完整版里“最小化敏感信息采集”的原则。

---

# 十九、增加「国际旅行条件」动态模块

这部分是目前 planner 和完整私人旅行服务差距最大的地方之一。

但也不能每个人都显示。

如果：

> 出发国 ≠ 目的国

自动出现：

### 国际旅行准备

国籍
长期居留地
护照有效期
目前是否已有目的地签证
是否计划自驾
是否携带处方药
是否有未成年人非双亲同行

注意：

这里一般**没必要第一阶段收集护照号码**。

只需要拿到足够判断旅行规则的信息。

---

# 二十、旅行保险也应该成为条件字段

建议问：

> 是否已经购买覆盖本次旅行的旅行保险？

有
没有
还没决定

如果包含：

滑雪 / 潜水 / 登山 / 自驾 / 偏远地区

系统进一步提示：

> “需要确认该活动是否在保险承保范围内。”

这比简单推荐保险有价值得多。

---

# 二十一、支付和网络应该采集，但不要放在第一次问卷前半段

这两个在完整版里很重要：

支付方式
eSIM
手机网络
银行卡
备用支付

但它们通常不会决定“第一版行程怎么排”。

所以建议放在：

**旅行方案生成之后的「行前准备」阶段。**

例如：

> 你的手机支持 eSIM 吗？

> 主要使用 Visa / Mastercard / Apple Pay / 现金？

然后系统生成：

**目的地支付方案**

和：

**目的地通信方案**

这样不会增加第一次填写负担。

---

# 二十二、会员权益可以设计成一个高级选项

完整版中有：

航空会员
酒店会员
信用卡权益。

这些对高价值用户特别有用。

例如：

Marriott Titanium
Hilton Diamond
ANA Platinum
Star Alliance Gold

系统可以因此优先：

酒店品牌
早餐权益
行政酒廊
机场贵宾室
额外行李
延迟退房。

建议放：

> 「我有常旅客会员权益」

展开后填写。

---

# 二十三、右侧「我的旅行条件」需要升级

目前右侧主要是：

必须满足
优先满足
明确不要

以及人数、预算、天数、步行。

下一版建议变成五块：

| 区域        | 内容                         |
| --------- | -------------------------- |
| **旅行骨架**  | 东京 · 7天 · 2成人1儿童 · ¥30,000 |
| **必须满足**  | 双床 / 不坐红眼 / 清真             |
| **优先满足**  | 靠近地铁 / 美食 / 摄影             |
| **明确不要**  | 大量换酒店 / 夜间巴士               |
| **还需要确认** | 护照有效期 / 保险 / 儿童座椅          |

最后这个：

## 「还需要确认」

非常关键。

它使系统从：

> 偏好收集器

变成：

> **旅行顾问。**

---

# 二十四、完成度算法也应该改变

现在是：

> 编辑了几步 / 8步

来计算完成度。

不太合理。

因为用户随便点一下一个步骤，不代表资料完整。

建议以后分：

### 行程基本信息

✓ 完整

### 个性化程度

82%

### 旅行可执行性

⚠ 还有 3 项待确认

例如：

> ✓ 日期确认
> ✓ 人数确认
> ✓ 预算确认
> ⚠ 护照条件未确认
> ⚠ 儿童年龄未填写
> ⚠ 旅行保险未确认

这比“78%完成”有价值得多。

---

# 二十五、“偏好 / 必须 / 不要”的设计值得保留，但交互要优化

这个其实是第一版最有价值的设计之一。

但目前是：

> 连续点击一个标签，在不同状态间切换。

这对于第一次使用的客户不是特别直观。

建议点标签以后出现：

**♡ 喜欢**

**✓ 必须**

**× 不要**

或者右键/长按不是一个好方向，移动端会更复杂。

还要注意：

只有“主观偏好”适合三态。

以下不应该三态：

过敏
轮椅
儿童安全座椅
孕期
药物
签证
护照

这些属于：

**事实 / 硬约束。**

# 二十六、建议建立 5 类条件，而不只是现在的 3 类

最终数据层建议是：

| 类型             | 示例      |
| -------------- | ------- |
| **FACT 事实**    | 2成人+1儿童 |
| **HARD 必须**    | 必须双床    |
| **PREFER 偏好**  | 更喜欢精品酒店 |
| **EXCLUDE 排除** | 不坐红眼    |
| **VERIFY 待核验** | 需要确认签证  |

这个数据结构非常重要。

以后模型规划的时候：

**FACT + HARD 不能违反**

**PREFER 尽量满足**

**EXCLUDE 不能安排**

**VERIFY 需要调研后再决定**

这会比现在三态体系完整很多。

# 二十七、一个值得立即修复的小问题

当前 textarea 设置的是：

`maxLength="5000"`

但界面计数显示：

> `0 / 500 字`

两者不一致。

这是 P0 可以直接修掉的 UI/规则问题。

# 二十八、还有一个产品层面的矛盾需要解决

第一页写：

> “填完这三项就能生成方案。”

但是右侧：

> “生成旅行计划需要先注册或登录”。

建议以后区分：

### 生成「初步方案」

不需要登录。

让客户先看到价值。

### 保存 / 深度规划 / 实时旅行服务

需要登录。

这样用户转化路径通常会更自然。

# 二十九、我建议的最终 Planner 数据流程

整个产品不要设计成“一次填完”。

而应该是：

**第一次：客户旅行画像**

↓

**系统判断缺什么**

↓

**条件式追问**

↓

**自动目的地调研**

**生成旅行方案 V1**

↓

↓

↓

**旅中旅行管家**

↓

**返程与售后**

这才和我们前面那套完整的私人旅行服务体系真正接上。

## 最核心的产品判断

如果只是把完整版里的内容继续往现在 8 个页面里添加，最终很容易得到一个**非常复杂、客户不愿填的旅行问卷**。

更合适的方向是把 Planner 从：

> **“问客户所有问题”**

升级为：

> **“只问客户他才知道的信息，其余由系统自己查、自己推导、自己提醒。”**

因此，完整版 196 项最终可以对应到后台，而客户端真正需要设计好的，大概只是 **30～40 个核心问题 + 20～30 个条件触发问题**。

这会更接近一个真正的**数字化私人旅行顾问**，而不是高级版旅游问卷。

另外，我目前拿到的 `planner.html` 是 Next.js 构建后的页面 HTML，可以完整判断页面已有的信息架构和控件，但实际状态管理、校验、API 提交等逻辑位于引用的 `_next/static/chunks/...` 中，并没有包含对应源代码，因此上面关于流程和数据模型的部分是产品/UX迭代建议，而不是对现有前端实现细节的代码审计。

如果下一步准备真正进入第二版设计，我建议直接把上述内容进一步落成一张 **《Planner V2 产品字段表》**：逐个定义“页面 → 问题 → 控件类型 → 选项 → 是否必填 → 触发条件 → 数据类型 → HARD/PREFER/FACT/VERIFY → 后端用途 → 对应196项ID”。这张表做出来以后，产品、UI、前端、后端和AI规划模型基本就可以使用同一份规范开发。
