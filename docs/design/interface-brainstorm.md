最终落地建议采用：

> **移动端优先、卡片式任务界面为主、对话式AI为辅、地图与时间轴结合，并根据“规划前—出发前—旅行中—旅行后”自动切换首页。**

它不能只是一个聊天机器人，也不能只是传统OTA的功能列表。最合适的形态是：

> **结构化可操作界面负责执行，AI对话负责理解需求和处理复杂修改。**

# 一、整体产品形态

## 1. 建议的终端组合

### 第一阶段：微信小程序＋H5分享页

适合验证产品：

- 无需下载，获客门槛低；
- 方便分享给爸爸、老人和同行家庭；
- 家人无需完整注册即可查看、投票和认领任务；
- 适合寒暑假低频使用场景。

### 第二阶段：独立App

适合完善：

- 实时位置与天气提醒；
- 行中导航；
- 离线旅行包；
- 系统日历、相册和通知集成；
- 长期家庭档案；
- 更稳定的行中服务。

### 第三阶段：平板、车机和智能穿戴适配

- 平板适合家庭共同规划；
- 车机显示下一站、停车点和预计到达时间；
- 手表提供集合、出发、儿童走失等提醒。

# 二、产品总体信息架构

建议底部只保留四个一级入口：

| 一级入口 | 主要职责 |
|---|---|
| **旅程** | 当前旅行状态、下一步任务、行程与动态调整 |
| **地图** | 路线、景点、厕所、母婴室、餐厅、医院 |
| **家庭** | 家庭成员、投票、任务、位置与消息 |
| **我的** | 家庭档案、订单、预算、历史旅行、隐私设置 |

中间设置一个全局悬浮按钮：

> **问管家**

用户可以随时通过文字、语音、图片表达：

- “孩子累了，下午重新排一下。”
- “这个餐厅适合5岁孩子吗？”
- “把明天改得轻松一点。”
- “这张酒店订单帮我加进行程。”
- “老人不想爬坡，换一个景点。”

但“问管家”不能成为唯一交互入口。门票、时间、预算、任务等必须以结构化组件展示和编辑。

这是整个界面设计的核心。系统应根据旅行阶段自动改变首页内容，而不是全年展示同一套功能。

- 不展示大面积旅游广告；

- 首屏只有一个核心行动：“开始规划”；

# 四、核心页面一：对话式创建旅行

建议采用“聊天＋选择卡片”的混合交互，不使用长表单。

## 1. 页面布局

```text
┌──────────────────────────┐
│ 创建家庭旅行         保存退出│
├──────────────────────────┤
│ AI：这次想去哪里？          │
│                            │
│ 用户：北京，暑假去5天       │
│                            │
│ AI：这次有哪些家人同行？     │
│ [成人 － 2 ＋]              │
│ [儿童 － 1 ＋]              │
│ [老人 － 2 ＋]              │
│                            │
│ [继续]                      │
├──────────────────────────┤
│ [输入补充信息……]       🎙️   │
└──────────────────────────┘
```

## 2. 输入原则

第一轮只问：

1. 去哪里；
2. 什么时候；
3. 玩几天；
4. 从哪里出发；
5. 有哪些成员；
6. 预算多少。

完成后立即生成初版，不让用户填写十几页资料。

## 3. 渐进式追问

只有在真正影响规划时才追问：

> 孩子5岁，是否需要午睡？

- 每天都需要；
- 偶尔需要；
- 不需要；
- 暂时不确定。

> 老人的步行能力如何？

- 可正常步行；
- 不适合连续走1小时；
- 尽量少爬坡；
- 需要轮椅或无障碍路线。

用户选择后即时显示结果：

> 已将每天13:00—15:00设为低强度时段。

## 4. 支持多模态输入

用户可以：

- 语音描述家庭需求；
- 上传已经收藏的攻略截图；
- 上传酒店或门票订单截图；
- 粘贴内容平台链接；
- 转发家庭群中的意见。

系统解析后必须让用户确认：

> 从截图中识别到“北京环球影城”和“故宫”，是否都设为必去？

不能未经确认就修改正式行程。

# 六、核心页面三：行程时间轴

这是规划阶段的主工作区。

## 1. 页面结构

```text
┌──────────────────────────┐
│ 北京5日游      [地图] [分享]│
│ D1  D2  D3  D4  D5          │
├──────────────────────────┤
│ 7月19日 · 预计32℃ · 7200步  │
│ 强度：均衡  午休：已安排      │
├──────────────────────────┤
│ 08:35 出发                  │
│       ↓ 25分钟·打车          │
│ 09:30 故宫博物院  🔒必去      │
│       适合5岁｜约2.5小时      │
│       预约完成｜室外偏热      │
│       [查看] [替换] [调整]    │
│                            │
│ 12:10 午餐                  │
│       儿童座椅｜清淡菜       │
│                            │
│ 13:20 回酒店午休             │
│       预留2小时              │
│                            │
│ 16:00 胡同轻松散步           │
│       可随时取消·无损失       │
├──────────────────────────┤
│ [＋增加活动]   [让AI调整当天] │
└──────────────────────────┘
```

## 2. 卡片的信息优先级

每个行程卡片默认只显示：

- 时间；
- 地点；
- 适合年龄；
- 预计时长；
- 是否预约；
- 风险提示；
- 是否可取消；
- 交通衔接。

展开后再显示：

- 详细介绍；
- 厕所、母婴室；
- 入口信息；
- 身高限制；
- 用户实测；
- 儿童讲解；
- 附近医院和药店。

## 3. 操作方式

每张卡片支持：

- 点击：查看详情；
- 长按拖动：调整时间；
- 左滑：删除或移到备选；
- “锁定”：AI调整时不可删除；
- “替换”：打开同类型备选；
- “轻松一点”：寻找低强度替代方案。

所有手势操作都必须同时提供显式按钮，避免老人或不熟悉手势的用户无法使用。

## 4. 修改后的反馈

用户拖动行程后，系统即时提示：

> 将故宫调整到下午后，会增加高温暴露，并与午休冲突。

提供三个动作：

- 保持上午；
- 仍然调整；
- 查看其他日期。

不要每次修改都进入完整聊天页。简单修改使用底部弹层完成。

```text

├──────────────────────────┤
│ 调整范围                    │
│ ● 只调整今天                │
│ ○ 调整整个旅行              │
```

```text
景山公园               中国科技馆
```

- 查看原因；
- 查看影响；
- 撤销；
- 恢复上一版本。

# 八、核心页面五：地图

亲子游地图不能只是普通地图，应围绕家庭即时需求设计。

## 1. 地图顶部

```text
[搜索地点、厕所、餐厅……] 🎙️
```

快捷筛选：

- 厕所；
- 母婴室；
- 休息点；
- 儿童餐；
- 药店；
- 儿科；
- 室内活动；
- 无障碍设施。

## 2. 地图标记

不同标记需要结合图标与文字，不能只靠颜色：

- 蓝色路线：当前计划；
- 绿色圆点：亲子友好设施；
- 橙色：需要注意；
- 红色十字：医疗；
- 灰色：已闭馆或不可用。

## 3. 地点底部卡片

用户点击母婴室后显示：

```text
国家博物馆母婴室
距离320米 · 步行约5分钟
开放状态：今日已核验
设施：尿布台 / 热水 / 哺乳区
位置：地下一层东侧
婴儿车：可乘电梯到达

[步行导航] [查看现场照片]
```

信息应显示：

- 更新时间；
- 来源类型；
- 是否为官方信息或家庭实测；
- 信息可靠程度。

# 十、核心页面七：“计划有变”

```text
原定公园：可免费取消
晚餐预约：仍可保留
下午项目：建议移到第4日上午

影响：
· 今天少走约3200步
· 预算增加打车费约¥45
· 不影响已购门票

[按此调整]  [查看其他方案]
```

用户确认后出现状态反馈：

> 已调整下午行程，并通知爸爸、外公和外婆。

底部提供：

> 撤销本次调整

撤销入口至少保留一段时间，并可在版本记录中恢复。

- 大字号、高对比度；
- 支持离线查看关键资料；
- 明确区分紧急医疗、普通不适和行程调整。

# 十二、核心页面九：订单和预算

订单、预算与行程必须联动，不能作为独立账本存在。

## 1. 预算仪表盘

```text
总预算 ¥18,000
已支付 ¥8,620
待支付 ¥4,300
预计现场支出 ¥3,200
剩余缓冲 ¥1,880

交通      ¥4,200
住宿      ¥5,600
门票活动   ¥2,300
餐饮      ¥3,100
其他      ¥920
```

## 2. 用户真正需要的预算信息

不仅显示价格，还应展示：

- 是否可退；
- 最晚退改时间；
- 儿童票规则；
- 是否存在现场二次消费；
- 价格是否已经计入总预算；
- 调整行程会损失多少钱。

例如：

> 删除环球影城后可节省¥1,680，但当前门票不可退，实际只能减少约¥320现场支出。

## 3. 商业内容标识

推荐卡明确标识：

- 最适合你们家的推荐；
- 性价比推荐；
- 商业合作；
- 已包含返佣。

不能让商业排序伪装成AI客观判断。

# 十三、视觉设计系统

## 1. 风格关键词

建议采用：

- 温暖；
- 可靠；
- 清晰；
- 轻松；
- 不幼稚；
- 不像传统旅行社；
- 不像儿童早教产品。

家庭旅行产品的主要操作人是成年人，不能满屏卡通形象和高饱和色。

## 2. 色彩

### 主色

建议使用低饱和蓝绿色或湖蓝色：

- 传递可靠、安全、清爽；
- 适合旅行和家庭场景；
- 户外强光下识别性较好。

### 辅助色

- 绿色：已完成、安全、适合；
- 橙色：提醒、待处理；
- 红色：医疗、严重冲突；
- 蓝色：信息、导航、预约；
- 灰色：非核心、已取消。

颜色不能是唯一的信息表达手段，必须结合：

- 图标；
- 文字；
- 状态标签；
- 形状差异。

## 3. 字体

移动端建议：

- 页面标题：22—24px；
- 模块标题：18—20px；
- 正文：16px；
- 辅助信息：14px；
- 行中主要时间与按钮：18px以上；
- 老人模式支持放大至1.3—1.5倍。

正文不要大量使用浅灰色，以免室外无法阅读。

## 4. 圆角与卡片

- 卡片圆角建议12—16px；
- 主按钮高度不低于48px；
- 主要点击区域不小于44×44px；
- 阴影轻量化，主要依赖留白和背景层级；
- 磨砂玻璃效果仅用于底部浮层、导航等局部，不要大面积使用，以免影响性能和文字对比度。

## 5. 图标

统一采用线面结合图标，并为高频亲子场景设计专用图标：

- 午睡；
- 婴儿车；
- 母婴室；
- 儿童座椅；
- 老人友好；
- 步行强度；
- 排队；
- 室内；
- 预约；
- 可退款；
- 医疗。

# 十四、动效与状态反馈

动效目的不是展示技术，而是解释变化。

## 1. AI生成过程

不要只显示“正在生成”。使用阶段化反馈：

```text
✓ 已理解家庭成员
✓ 已匹配孩子作息
● 正在计算路线和步行量
○ 正在准备天气备选
```

如果时间较长，可以先逐步生成：

1. 行程框架；
2. 每日路线；
3. 餐厅与交通；
4. 备选方案。

用户可以先看已经生成的部分。

## 2. 修改行程

修改后用短动画显示：

- 卡片从原时段移动到新时段；
- 预算数字发生变化；
- 步数重新计算；
- 被影响的预约高亮。

同时显示：

> 已调整3处，预算增加¥120，步行减少2600步。

## 3. 成功反馈

使用轻量提示，不要频繁弹出庆祝动画：

- 家人已认领任务；
- 门票已加入行程；
- 行程已同步；
- 离线包已下载。

## 4. 错误状态

错误信息必须说明“发生了什么”和“下一步怎么办”。

错误示例：

> 暂时无法更新实时排队时间。你仍可以查看已下载的行程和地图。

按钮：

- 重试；
- 使用上次数据；
- 稍后提醒。

避免只显示“网络错误10023”。

# 十五、AI界面的具体设计原则

## 1. AI不应该占满所有页面

适合用AI的情况：

- 用户需求模糊；
- 需要综合调整；
- 需要解释推荐理由；
- 需要解析截图或自然语言；
- 发生复杂突发情况。

不适合用聊天完成的情况：

- 查看票券；
- 修改时间；
- 删除景点；
- 分配任务；
- 导航；
- 查看预算；
- 选择家庭成员。

这些应使用按钮、卡片和表单。

## 2. AI输出必须组件化

用户说：

> “明天下午下雨，换成室内，别增加太多预算。”

系统不应只回复一段文字，而应生成可操作的方案卡：

```text
原计划：奥林匹克森林公园
替换为：中国科技馆

预算：＋¥80
步行：－2100步
交通：＋15分钟
适合年龄：4—12岁
预约状态：尚有余量

[替换] [再换一个] [保留原计划]
```

## 3. AI推荐需要可解释

“为什么推荐”展开后只展示3—5条最相关原因：

- 适合5岁儿童；
- 室内，不受降雨影响；
- 距离晚餐地点仅12分钟；
- 老人可随时休息；
- 预算增加较少。

不要展示复杂算法分值。

---

# 十六、通知设计

通知应围绕“需要行动”，而不是提高打开频率。

## 必须通知

- 预约即将开放；
- 退改期限临近；
- 航班、高铁变动；
- 极端天气；
- 家庭投票即将截止；
- 关键任务未完成；
- 行程因外部条件无法执行。

## 不建议通知

- 泛目的地推荐；
- 高频促销；
- 与本次旅行无关的内容；
- 已经在App内完成的事项；
- 不提供解决方案的天气提醒。

### 通知文案示例

错误：

> 明日北京高温预警。

正确：

> 明日最高35℃，原定户外行程可能偏热。建议提前1小时出发，下午改为室内活动。  
> [查看调整]

# 十七、关键空状态与边界状态

最终设计稿不能只画理想流程，还要覆盖以下情况：

## 1. 不知道去哪

通过预算、天数、出发地、孩子年龄和兴趣推荐目的地，不要求先输入城市。

## 2. 预算不够

不能只说“预算不足”，应提供：

- 缩短一天；
- 更换酒店区域；
- 删除高价活动；
- 改为周边目的地；
- 保留体验但降低交通成本。

## 3. 家庭意见冲突

例如孩子想去乐园、老人想看文化景点，系统生成：

- 分时方案；
- 分组方案；
- 轮流满足方案；
- 全家共同项目＋自由时段。

## 4. 关键门票没预约到

立即提供：

- 同类景点；
- 日期交换；
- 候补提醒；
- 不增加太多交通时间的替代方案。

## 5. 无网络

仍可使用：

- 完整行程；
- 酒店地址；
- 票券二维码；
- 离线地图；
- 紧急电话；
- 医疗和过敏信息；
- 家庭集合点。

## 6. 数据不确定

明确标识：

> 母婴室开放状态最后核验于3天前，建议到达前再次确认。

不要把推测包装成确定事实。

# 十八、无障碍和家庭友好标准

落地时至少满足：

- 支持系统字体放大；
- 重要文字和背景具备足够对比度；
- 不仅依靠颜色表达状态；
- 图片支持替代文本；
- 触控区域不小于44×44px；
- 表单有明确标签；
- 支持屏幕阅读器；
- 支持减少动效；
- 支持单手操作；
- 老人模式可提高字号和简化导航；
- 儿童模式避免误购、误删和访问敏感资料；
- 儿童位置、照片、健康信息默认不公开。

可将WCAG 2.2作为无障碍验收基础。

# 二十、首版MVP界面范围

首版不要追求做成完整OTA，建议只落地五个核心交互闭环：

## 闭环一：快速输入家庭需求

用户在3分钟内完成目的地、人员、年龄、预算和节奏输入。

## 闭环二：得到结构化行程

输出可比较、可编辑的时间轴，而不是一篇AI长文。

## 闭环三：查看亲子适配度

每个地点至少呈现：

- 适合年龄；
- 游玩时长；
- 步行强度；
- 午休影响；
- 厕所/母婴设施；
- 预约要求。

## 闭环四：分享并分配任务

家人不下载App也能：

- 看日程；
- 投票；
- 认领任务；
- 接收变化。

## 闭环五：一键处理计划变化

至少支持：

- 孩子累了；
- 下雨了；
- 太热了；
- 迟到了；
- 排队太久。

---

# 二十一、最终界面设计的判断标准

每一张页面都可以用四个问题来验收：

## 1. 用户现在最想解决的问题是什么？

一张页面最好只突出一个核心任务。

## 2. 用户下一步应该做什么？

主按钮必须明确，不能让五个操作拥有相同视觉权重。

## 3. 系统为什么这样建议？

AI推荐要可解释，尤其涉及预算、健康、安全和行程删除时。

## 4. 用户后悔了怎么办？

修改、删除和自动调整都应该支持撤销或恢复。

---

最终，界面不应该让用户感觉自己在操作一套复杂的旅行管理软件，而应该让她始终看到三类信息：

> **现在最重要的是什么、系统建议我怎么做、我能否一键接受或修改。**

具体到不同阶段就是：

- 规划时：**帮我少做选择；**
- 出发前：**告诉我还缺什么；**
- 旅行中：**告诉我现在做什么；**
- 出现变化：**直接给我一个能执行的新方案；**
- 旅行结束：**替我留下回忆，并记住我们家的习惯。**

这才是这款亲子旅行产品最终落地时最核心的界面逻辑。
